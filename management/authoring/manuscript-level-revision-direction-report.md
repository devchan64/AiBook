# 원고별 수정 방향 수립 리포트

> 작성일: 2026-07-31
> 근거 문서: `management/authoring/manuscript-level-revision-proposals.md`
> 검토 범위: 제안서에 오른 Part 1-7 한국어 원고

## 검토 기준

이 리포트는 원고를 바로 고치는 문서가 아니라, 제안별 대상 페이지를 읽고 실제 수정 방향을 정리하는 문서다.

판단 기준은 다음과 같다.

1. 학습 개선: 사례, 예시, 연습, 예제가 현재 Section의 중심 질문을 닫는 데 실제로 기여하는가
2. 규칙 준수: Section 경계, 용어 병기, 출처 최신성, 메타데이터 형식, 다국어 동기화 기준을 지키는가
3. 제외 기준: 진행 메타 추가, 소제목 교체만을 위한 수정, 사례·예제의 후반부 일괄 이동, 과도한 압축은 수정 방향으로 잡지 않는다.
4. 폐기 기준: `사례 및 예시`, `연습 및 예제` 같은 공통 소제목 구조는 원칙으로 유지하지 않는다. 사례·예시·연습·예제는 소제목 형식이 아니라 현재 설명 안에서 맡는 학습 역할과 문단 배치로 판단한다.

## 전체 판단

Part 1은 추가 압축보다 유지 판단이 우선이다. 특히 P1-3.1은 길지만 규칙 기반 시스템의 강점과 한계를 사례·도식·연습으로 닫고 있어, 독자 기준에서는 더 줄이는 작업이 학습 손잡이를 약하게 만들 수 있다.

Part 2와 Part 4는 긴 예제형 Section이 많다. 방향은 예제 삭제가 아니라 `각 예제가 맡는 판단 역할`을 선별하는 것이다. 실제 중복은 줄일 수 있지만, 입력을 바꾸고 출력을 관찰하게 만드는 예제는 유지해야 한다. 이때 `사례 및 예시`, `연습 및 예제`라는 분류형 소제목을 유지하는 것은 목표가 아니다.

Part 6은 제품·API 문서와 로컬 모델 실행 예제가 들어간다. 구조는 학습에 기여하지만, 출처 최신성 점검과 실행 조건 설명은 배포 전 별도 확인 대상으로 둔다.

Part 7은 실습 산출물 구조가 잘 잡혀 있다. 다만 모든 한국어 Section의 메타데이터가 현재 blockquote 형식이 아니라 일반 문단 형식으로 되어 있어, 본문 수정 작업과 분리해 규칙 준수 작업으로 처리할 필요가 있다.

## 사례 문단 배치 추가 검토

사례가 여러 개인 Section은 사례 수 자체보다 배치 역할을 먼저 본다. 적절한 배치는 `개념 설명 -> 사례로 판단 차이 확인 -> 연습 또는 예제로 적용` 흐름이다. 부적절한 배치는 사례가 Section 끝에 한꺼번에 쌓여 앞의 개념 설명과 떨어지거나, 여러 사례가 같은 결론을 반복해 다음 연습으로 이어지지 않는 경우다.

| 대상 | 배치 판단 | 수정 방향 |
| --- | --- | --- |
| P1-1.1, P1-1.2, P1-1.3 | 사례가 개념 설명 뒤에 짧게 붙고 체크리스트 전에 회수된다. Part 1 초반의 범위·문제 유형·층위 구분을 독자가 다시 확인하게 하므로 배치가 적절하다. | 유지. 사례를 후반부로 더 밀거나 압축하지 않는다. |
| P5-6.1 | 이미지 분류, 문장 분류, 공통 루프 사례가 학습 루프 도식 뒤와 연습 전 사이에 놓인다. 서로 다른 입력 구조에서도 forward-loss-backward-step이 유지된다는 비교 역할이 분명하다. | 유지. 세 사례를 하나로 압축하지 말고, 공통 루프를 확인하는 비교 묶음으로 둔다. |
| P6-10.1 | 요약, 분류, 문서 기반 질의응답 사례가 프롬프트 요소 설명 뒤에 놓이고, 바로 뒤에서 입력 설계 기준으로 묶인다. 배치 자체는 적절하지만 각 사례가 길어 사례 안의 표가 반복되는 느낌은 생길 수 있다. | 유지 기반 점검. 사례 삭제보다 각 사례 마지막이 `무엇을 명시해야 흔들림이 줄어드는가`로 닫히는지 확인한다. |
| P6-13.1 | 계산기, 일정 조회, 파일 수정 사례가 도구 사용의 세 실행 유형을 분리한다. 사례 뒤에 실행 연결이 필요한 장면으로 회수되어 배치가 적절하다. | 유지. 같은 결론 반복 문장만 문장 단위로 점검한다. |
| P6-15.1, P6-15.2 | MCP와 하네스 사례가 각각 연결 형식, 실행 기록, 실패 원인 분리를 보여 준다. 특히 P6-15.2의 세 사례는 길지만 failure trace를 비교하는 역할이 서로 다르다. | 유지 기반 점검. 사례를 뒤로 옮기지 않고, 각 사례가 `어떤 기록이 없으면 무엇을 다시 설명하지 못하는가`로 닫히는지 확인한다. |
| P4-7.1, P4-7.2 | 사례 자체는 특징 선택·전처리 판단을 잘 받치지만, 같은 Section 안에서 분류형 사례 소제목이 두 번 반복된다. 이는 사례 위치 원칙보다 같은 역할의 문단이 형식상 나뉜 구조 문제다. | 우선 정리. `사례 및 예시` 같은 공통 소제목 구조는 폐기하고, 사례를 삭제하지 말고 첫 사례와 작은 예시가 한 흐름으로 이어지게 문단 배치를 정리한다. |

## 연습 문단 배치 추가 검토

연습이 여러 개인 Section은 연습 수보다 `독자가 어떤 행동을 하게 되는가`를 먼저 본다. 적절한 배치는 `기본 예제 실행 -> 값을 바꿔 보기 -> 출력 차이 해석 -> 기록 언어로 정리` 흐름이다. 부적절한 배치는 여러 연습이 같은 확인을 반복하거나, 해설 없이 질문만 쌓여 체크리스트로 넘어가는 경우다.

| 대상 | 배치 판단 | 수정 방향 |
| --- | --- | --- |
| P2-8.4 | 긴 반복 설명 뒤 `예시를 읽는 공통 질문` 하나로 묶음, 항목 처리·결과 묶음·누적 여부를 읽게 한다. 여러 연습을 늘리지 않고 공통 질문으로 회수하는 배치라 적절하다. | 유지. 추가 연습을 늘리기보다 기존 공통 질문이 앞선 여러 반복 예제를 회수하는지 확인한다. |
| P2-9.4 | 배열, 연결 리스트, 스택, 큐, 트리, 그래프, 해시 테이블 예제가 병렬로 길게 놓인다. 각 예제는 자료구조별 접근 감각을 분리하므로 역할은 분명하지만 독자에게 목록형으로 길게 보일 수 있다. | 유지 기반 점검. 예제를 삭제하지 말고, 각 미니 예제 앞의 `문제 상황/입력/출력/확인할 개념`이 실제로 다른 행동을 요구하는지 확인한다. |
| P4-7.1 | 다섯 기준 연습이 `작은 장면 -> 먼저 볼 질문 -> 1차 판단 -> 해설`로 반복된다. 길지만 특징 선택 기준을 하나씩 적용하게 하는 구조라 배치가 적절하다. | 유지. 다섯 기준을 합치지 않는다. 다만 각 기준의 해설이 바로 뒤에 붙어 자기 판단과 대조되는지 유지한다. |
| P4-7.2 | 결측치·스케일·인코딩 순차 예제 뒤에 거리 계산 예제가 이어진다. 전처리 전체 흐름과 스케일 민감성을 분리해 보여 주므로 배치가 적절하다. | 유지. 두 예제는 병합하지 않고, 첫 예제는 입력 행렬화, 둘째 예제는 거리 기준 변화로 역할을 분리한다. |
| P4-10.1, P4-10.2, P4-11.1, P4-14.1, P4-15.1 | 기본 Python 예제 뒤에 값 하나를 바꿔 보는 예제와 `무엇이 유지되고 무엇이 달라지는가` 해석이 이어진다. 알고리즘 장에서 반복되는 좋은 연습 배치 패턴이다. | 유지. 여러 연습을 줄이기보다 `기본 실행 -> 값 변경 -> 해석 회수` 패턴이 끊기지 않게 한다. |
| P5-15.3 | 고정 logits 예제로 sampling 규칙을 재현 가능하게 확인한 뒤, Ollama 선택 예제로 실제 출력 변화를 관찰한다. 재현 예제와 선택 실행 예제가 분리되어 배치가 적절하다. | 유지. 선택 예제를 설치 안내로 키우지 않고, 생성 설정이 출력 경험을 바꾸는 관찰로 닫는다. |
| P6-13.1, P6-15.1, P6-15.2 | 긴 Python 예제가 각각 도구 실행, 연결 형식, 실행 기록을 한 번에 보여 준다. 연습 수는 많지 않지만 코드가 길어 독자 행동이 흐려질 수 있다. | 유지 기반 점검. 코드 앞의 입력·출력·확인할 개념과 코드 뒤 해석이 충분히 가까운지 확인한다. |
| Part 7 전체 | 각 Section이 `입력 파일 -> 실행 기록 기준 -> Python 예제 -> 결과 해석 -> 프로젝트 기록 예시 -> 직접 바꿔 보기` 흐름을 반복한다. 실습 파트의 공통 문단 배치로 적절하다. | 유지. 형식 일괄 변경보다 실습 산출물과 조작 변수, 결과 해석의 연결을 우선 확인한다. |
