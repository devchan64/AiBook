## 전체 판단

Part 1-7 원고의 중심선은 대체로 유지되어 있다. 큰 결손보다 먼저 다룰 문제는 `사례·예제·연습이 절차 설명을 실제로 돕는지`, `긴 Section의 반복이 필요한 보강인지 단순 중복인지`, `다국어 동기화`, `변동 가능 출처 최신성`이다.

우선순위는 다음처럼 잡는 것이 좋다.

1. 사례와 예제를 뒤로 미루지 않고, 개념이 등장하는 위치에서 절차 설명을 돕는 장치로 유지한다.
2. Section 경계가 실제로 흐려지는 긴 구간만 선별하되, 설명 절차를 약하게 만드는 압축은 피한다.
3. 원고 구조 수정과 출처 최신성 점검을 같은 작업으로 섞지 않는다.
4. 한국어 원문 변경 뒤 영어·중국어 원고를 Section ID 기준으로 동기화한다.

## Part 1 제안

권장안은 P1-3.1을 추가 압축하지 않고, 사례가 규칙 기반 시스템의 강점과 한계를 설명하는 절차를 충분히 받치는지 확인하는 것이다. 독자 기준에서는 이미 많이 압축된 원고로 보일 수 있으므로, 소제목 정리보다 사례와 연결 문장의 역할 확인이 우선이다.

- 제안 작업:
  - Chapter 1-2의 기존 소제목은 필수 수정 대상으로 보지 않는다.
  - P1-3.3과 P1-5.2도 소제목만 바꾸는 작업을 별도 우선순위로 두지 않는다.
  - P1-3.1의 역사·계산 자원 전환 설명은 유지하고, P1-2.3/P1-9.1과의 연결 문장만 필요 시 조정한다.
  - 사례가 개념 설명 뒤로 밀리지 않고, 독자가 판단 절차를 따라가는 위치에 남아 있는지 확인한다.
- 대안:
  - 빠른 수정이 목표라면 본문은 건드리지 않고 검토 의견만 현재 기준으로 유지한다.
  - 배포 직전이라면 법률·정책·제품 문서 최신성 점검을 별도 작업으로 추가한다.
- 주의:
  - P1-3.1은 추가 압축을 기본 조치로 삼지 않는다.
  - 규칙 기반 시스템의 장점, 지식 획득 문제, 예외 증가, 현대 서비스에서의 규칙 역할은 현재처럼 유지한다.
  - 사례와 연습을 후반부에만 배치해야 한다는 원칙은 두지 않는다.

## Part 2 제안

권장안은 긴 Python·자료구조 Section의 예제가 절차 설명을 돕는지 표본 검토하는 것이다. 소제목 교체는 별도 관리 과제로 두지 않는다.

- 제안 작업:
  - P2-8.4와 P2-9.4를 표본으로 삼아 반복 예제가 실제로 다른 판단을 맡는지 확인한다.
- 대안:
  - 예제를 줄이면 초심자 손잡이가 약해질 경우, 압축 대신 도입·마무리 문장에 `다음 Part 연결`을 더 분명히 쓴다.
- 주의:
  - Python 장을 일반 프로그래밍 강의처럼 확장하지 않는다.
  - 수정은 `수식-코드-데이터 연결`을 더 잘 보이게 하는 방향이어야 한다.

## Part 3 제안

권장안은 현재 구조를 유지하고, Part 4 개정 시 P3-9.13만 함께 확인하는 것이다.

- 제안 작업:
  - P3-9.13의 time split, group split, data leakage, evaluation design 링크와 용어 표기를 Part 4와 맞춘다.
  - 외부 출처 확인 날짜는 Part 4 평가·분할 원고를 손볼 때 같이 갱신한다.
- 대안:
  - Part 3과 Part 4 사이 연결이 약하다는 피드백이 있으면 P3-9.13에 `Part 4에서 다시 다룰 것` 열을 추가한다.
- 주의:
  - Part 3의 유지 확인 항목을 새 수정 작업으로 바꾸지 않는다.
  - 짧은 Section 구조는 현재 장점이므로 불필요하게 합치지 않는다.

## Part 4 제안

권장안은 P4-7.1/P4-7.2의 절차 설명을 유지하면서 도구 이름 나열로 흐르는 부분만 정리하는 것이다. 알고리즘 장의 소제목 통일은 필수 작업으로 보지 않는다.

- 제안 작업:
  - P4-7.1/P4-7.2에서 특징 선택과 전처리 설명이 실제 판단 절차를 만드는지 확인한다.
  - scikit-learn 도구 이름 표는 짧은 보충으로 유지한다.
- 대안:
  - Part 4 전체 개정 시간이 확보되면 소제목보다 예제의 역할과 비교 흐름을 먼저 점검한다.
  - 시간이 제한되면 P4-7.1/P4-7.2만 먼저 처리한다.
- 주의:
  - 알고리즘 장을 공식 유도나 도구 사용법으로 확장하지 않는다.
  - 각 알고리즘은 `baseline 대비 언제 남고 언제 빠지는가`를 보여 주어야 한다.

## Part 5 제안

권장안은 최소 수정이다.

- 제안 작업:
  - P5-15.3은 샘플링 설정 관찰 예제로 유지한다.
- 대안:
  - P5-15.3이 확장될 경우 `설치·운영 안내가 아니라 샘플링 관찰 예제`라는 경계 문장을 추가한다.
- 주의:
  - P5-11.2처럼 긴 Section이라도 중심 질문이 하나로 닫히면 줄 수만 보고 압축하지 않는다.
  - Part 5는 현재 균형이 좋으므로 대규모 구조 변경은 피한다.

## Part 6 제안

권장안은 P6-13.1과 P6-15.2의 반복 역할을 먼저 표시한 뒤, 절차 설명에 필요한 사례와 실행 흐름은 유지하는 것이다.

- 제안 작업:
  - P6-13.1에서 RAG, tool use, 조회, 계산, 실행, 책임 경계 반복이 서로 다른 판단을 맡는지 확인한다.
  - P6-15.2에서 MCP와 하네스 차이 표, trace/log/eval/replay 절차 설명은 유지하고, 같은 결론만 반복하는 문장만 줄인다.
  - 제품·API 문서 최신성 점검은 배포 전 별도 작업으로 분리한다.
- 대안:
  - 반복이 초심자 이해에 도움이 된다고 판단되면 삭제 대신 각 반복의 역할을 명시한다.
- 주의:
  - P6-16 평가와 P6-17 운영 제약을 P6-15.2에서 앞당겨 강의하지 않는다.
  - 특정 API 사용법보다 모델 밖 실행 구조와 검토 가능한 기록을 중심에 둔다.

## Part 7 제안

권장안은 실습 산출물 기준과 메타데이터 표기를 확인하는 것이다. `판단 기준` 소제목 일괄 교체는 필수 관리 항목으로 두지 않는다.

- 제안 작업:
  - `Section ID`, `Version` 표기를 다른 Part와 같은 blockquote 형식으로 통일할지 결정하고 일괄 처리한다.
- 대안:
  - 빠른 표면 정리만 필요하면 제목은 그대로 두고 메타데이터 표기만 맞춘다.
  - Part 7 확장이 예정되어 있으면 체크리스트에 `입력 변경`, `출력 비교`, `실패 해석`, `다음 조치` 점검표를 추가한다.
- 주의:
  - Part 7은 이미 실습형 구조가 잡혀 있으므로 사례·연습의 위치를 뒤로 미루지 않는다.
