# P5-19 통합 미니 실습 구성 메모

## 작성 목적

- Part 5가 개념 설명으로만 끝난다는 구조 약점을 줄이기 위해, 요청 흐름 단위의 통합 미니 실습 장을 추가한 근거를 남긴다.

## 이번 장의 역할

- `토큰 -> Transformer -> next-token -> RAG -> tool use -> evaluation -> 운영`으로 이어진 Part 5의 개념을 하나의 요청 흐름으로 다시 묶는다.
- Part 6의 더 큰 프로젝트로 넘어가기 전에, `작은 기능도 어떤 구조로 구현하고 회고해야 하는가`를 먼저 보여 주는 중간 다리 역할을 한다.

## 배치 판단

- 통합 장은 Part 5 마무리 직전에 두는 편이 자연스럽다.
- 이유는 다음과 같다.
  - 앞선 장의 개념을 모두 한 번 회수할 수 있다.
  - summary와 Part 6 연결 문장이 더 구체적인 대상을 갖게 된다.
  - `완료 기준에는 구현이 있는데 본문은 개념 설명으로 끝난다`는 문제를 줄일 수 있다.

## 범위 제한

- 이번 장은 실제 상용 API 문법이나 배포 자동화까지 들어가지 않는다.
- 실제 API 호출, 더 현실적인 품질 비교, 프로젝트 산출물 문서화는 Part 6으로 넘긴다.
- 즉, 이 장은 `개념을 기능 흐름으로 묶는 최소 실습`까지를 담당한다.

## 사례 선택 이유

- `사내 문서 기반 휴가 정책 안내 도우미` 사례를 골랐다.
- 이유는 다음과 같다.
  - prompt만으로 충분한 작업과 retrieval이 필요한 작업을 비교하기 쉽다.
  - 상태 조회가 필요할 때 tool use로 자연스럽게 확장된다.
  - 근거 문서, 실패 기록, 사람 검토 전환을 함께 설명하기 쉽다.

## 남은 과제

- Chapter 3, 5의 배경 축을 더 압축하거나 보충학습화할지 결정해야 한다.
- 실제 Part 5 순서를 바꿀지, 현재 순서는 유지하되 index와 chapter title로 독서 경로를 보정할지 추가 판단이 필요하다.
- Part 6 첫 프로젝트와 P5-19 사이의 연결 문장을 더 촘촘하게 맞출 수 있다.
