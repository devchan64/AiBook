# 동작 단위에서 데이터셋까지: 문제 정의를 어떻게 바꿀 것인가

## 이 노트의 목적

이 노트는 동작 단위 원천데이터 사례를 책에서 사용할 때 `문제를 어떻게 정의할 것인가`에 집중한다.

이 노트에서는 특정 비즈니스 도메인 이름을 전면에 두지 않고, 기본적으로 `동작 단위 원시 로그`, `동작 단위 원천데이터`, `제어 파라미터 및 센서 시계열`이라는 일반화 문구를 사용한다.

원본 메모에서 쓰던 `shot`은 자동으로 실행되는 동작 1회를 뜻했지만, 이 노트에서는 일반 독자가 바로 이해할 수 있도록 기본적으로 `동작 1회`로 다시 쓴다.

여기서 `동작 1회`는 자동으로 실행되는 명령 1건이 시작되어 종료될 때까지의 한 사례를 뜻한다. 또 `동작 단위 원천데이터`에는 그 동작에서 사용한 제어 파라미터 시계열과, 동작 중 모니터링한 센서 데이터 시계열이 함께 들어 있다고 본다.

초심자에게 가장 중요한 출발점은 모델 이름이 아니라 문제 구조다.

같은 원시 로그라도 질문을 어떻게 세우느냐에 따라 전혀 다른 AI 문제가 된다.

## 가장 먼저 잡아야 할 문장

`동작 단위 원천데이터를 받았다고 해서 바로 모델을 고르는 것이 아니라, 먼저 무엇을 한 건의 샘플로 볼지, 무엇을 예측하거나 비교할지 정해야 한다.`

이 한 문장이 이 사례를 책에 넣는 이유다.

## 동작 단위 원천데이터 사례에서 가능한 문제 정의 층위

### 층위 1. 개별 측정값 읽기

질문:

- 지금 압력이 얼마인가
- 지금 유량이 얼마인가

이 층위는 AI 문제가 아니다.

여기서는 센서 읽기와 시각화가 중심이다.

책에서는 `원시 데이터가 곧바로 AI가 되는 것은 아니다`는 설명에 쓰기 좋다.

### 층위 2. 동작 1회를 요약하기

질문:

- 이번 동작은 어떤 구조를 가졌는가
- 초반, 중반, 후반 흐름이 어땠는가

이 층위부터 `표현(representation)` 문제가 생긴다.

샘플 단위를 동작 1회로 정하면, 행 하나가 동작 1회인 표를 만들 수 있다.

반대로 원시 로그 단계에서는 한 행이 동작 1회 전체가 아니라 `동작 중 한 시점 측정`일 수 있다. 따라서 원시 표를 바로 데이터셋으로 읽지 말고, 먼저 `지금 한 행이 무엇을 뜻하는가`와 `무엇을 샘플 1건으로 다시 묶을 것인가`를 분리해서 적는 편이 안전하다.

이때 가능한 열은 다음처럼 일반화할 수 있다.

- 총 동작 시간
- 중반 평균 유량
- 후반 하강률
- 압력 추종 오차
- 세그먼트별 방향 코드 또는 구간 표현

### 층위 3. 여러 동작을 비교하기

질문:

- 오늘 오전 동작들은 평소와 달랐는가
- 어떤 조건 그룹에서 변화가 반복됐는가

이 층위부터 집계(aggregation), 기준선(baseline), 표본 수(sample size)가 중요해진다.

### 층위 4. 경고 후보를 만들기

질문:

- 운영자가 우선 확인해야 할 변화는 무엇인가
- 단발성 튐과 반복 변화는 어떻게 구분할 것인가

이 층위부터 거짓 경보(false positive)와 놓침(false negative)의 비용을 말할 수 있다.

### 층위 5. 자동 진단을 시도하기

질문:

- 어떤 고장 유형에 가까운가
- 장비 이상인가 설정 변화인가

이 층위는 가장 매력적으로 보이지만, 책에서는 오히려 조심스럽게 다뤄야 한다.

왜냐하면 라벨 품질, 도메인 지식, 실제 원인 확인 절차가 복잡하기 때문이다.

## 책에서 추천하는 기본 문제 정의

공개 책에서는 다음 두 문제 정의가 가장 안전하고 교육적이다.

### 권장 문제 1. 동작 요약 문제

입력:

- 한 번의 동작에서 나온 제어 파라미터 시계열과 센서 시계열

출력:

- 사람이 읽을 수 있는 요약값과 구간별 특징

왜 좋은가:

- 전처리, 특징 추출, 요약, 시각화, 설명 가능성을 한 번에 보여 준다.
- 라벨이 없어도 된다.
- Part 2와 Part 3 초반에 쓰기 좋다.

### 권장 문제 2. 기준선 대비 변화 탐지 문제

입력:

- 일정 기간의 동작 요약들
- 최근 구간 동작 요약들

출력:

- 평소 대비 변화량
- 반복성 여부
- 운영 검토 후보

왜 좋은가:

- `정답 분류기`보다 현실적인 문제 정의를 보여 준다.
- 통계, 변화 추세, 변화 신호 탐지, 운영 평가를 연결한다.
- Part 3 후반, Part 6 프로젝트에 잘 맞는다.

## 왜 `원인 분류기`로 바로 가면 안 되는가

초심자는 현실 문제를 보면 종종 이렇게 생각한다.

`센서 로그가 있으면 AI가 바로 원인 종류를 맞히면 되지 않을까?`

하지만 이 도메인은 그 가정을 깨기에 좋다.

원인 분류기로 바로 가기 어려운 이유는 다음과 같다.

- 확정 라벨이 부족할 수 있다.
- 한 증상이 여러 원인에서 나올 수 있다.
- 조건과 설정 차이가 정상 변동을 크게 만든다.
- 센서 자체의 신뢰도 차이가 있다.
- 운영자는 확정 진단보다 `우선 확인할 변화 후보`를 먼저 원할 수 있다.

이 설명은 Part 1의 `문제 정의가 모델을 결정한다`와 매우 잘 맞는다.

## 동작 1회를 샘플로 본다는 것의 교육적 가치

동작 1회를 한 건의 샘플로 보면 다음 개념을 자연스럽게 설명할 수 있다.

- 샘플(sample)
- 특징(feature)
- 라벨(label)
- 집단(population)
- 구간(window)
- 기준선(baseline)

예를 들어 다음 표를 만들 수 있다.

| 샘플 단위 | 예시 |
| --- | --- |
| 센서 측정 한 점 | 12.4초 시점 유량 |
| 동작 1건 | 한 번의 동작 전체 |
| 30분 묶음 | 같은 조건의 여러 동작 요약 |
| 하루 기준선 | 직전 일정 기간의 대표 패턴 |

이 표 하나만으로도 데이터 과학의 여러 층위를 설명할 수 있다. 특히 `한 행이 곧 샘플 1건인가`, `여러 행을 묶어 샘플 1건으로 다시 만들 것인가`를 분리해 생각하는 감각을 초심자에게 주기 좋다.

## 데이터셋 설계로 바꾸면 생기는 질문

동작 단위 표를 만들겠다고 결정하면, 이제 데이터셋 질문이 생긴다.

### 어떤 열을 남길 것인가

- 절대 평균만 남길 것인가
- 구간별 값을 나눌 것인가
- 변화율을 넣을 것인가
- 변동성을 따로 넣을 것인가

### 어떤 키로 분리할 것인가

- 장비 범주별로 분리할 것인가
- 조건 그룹별로 분리할 것인가
- 설정이 다르면 같은 데이터셋으로 섞지 않을 것인가

### 어떤 라벨을 만들 수 있는가

- 정상/주의/검토 필요 같은 운영 라벨
- 품질 불만 여부
- 수리 이력과 연결된 후행 라벨

### 어떤 라벨은 만들기 어려운가

- 실제 내부 원인
- 분쇄도 문제, 압력 문제, 센서 문제를 확정 구분한 진단 라벨

이 질문들은 Part 3의 데이터셋 설계, 모델 평가, 데이터 누수 설명에 재사용할 수 있다.

## 책에 넣기 좋은 대비 문장

다음 대비는 반복해서 쓸 가치가 있다.

### 대비 1. 측정 vs 샘플

- 측정 한 점: 아주 작은 원시 기록
- 동작 1회: 분석 가능한 최소 단위

### 대비 2. 진단 vs 경고

- 진단: 원인을 확정하려는 판단
- 경고: 평소와 다른 변화를 먼저 알리는 판단

### 대비 3. 절대 임계값 vs 기준선 이탈

- 절대 임계값: 미리 정한 숫자를 넘는가
- 기준선 이탈: 평소와 비교해 달라졌는가

### 대비 4. 라벨 충분 vs 라벨 희소

- 라벨 충분: 지도학습으로 바로 가기 쉬움
- 라벨 희소: 변화 신호 탐지, 기준선 비교, 사람 검토 흐름이 더 현실적일 수 있음

## 이 노트의 현재 결론

이 사례를 책에 넣을 때 가장 먼저 해야 할 일은 `모델 선택`이 아니라 `문제 정의 재서술`이다.

공개 책에서는 `동작 요약`과 `기준선 대비 변화 탐지`를 중심 문제로 잡는 편이 가장 안전하고 교육적이다.

## 문제 정의를 잘못 잡으면 생기는 실패 유형

이 도메인은 문제 정의를 대충 잡았을 때 왜 곧바로 막히는지 보여 주기 좋다.

### 실패 유형 1. 너무 작은 단위만 본다

센서 한 점만 계속 보면 다음이 어려워진다.

- 동작 1회가 어떤 구조였는지 알기 어렵다
- 직전 흐름과 이후 흐름을 잃는다
- 운영자가 읽을 설명 문장이 잘 안 나온다

즉 원시 측정은 재료이지만, 곧바로 운영 질문의 단위는 아니다.

### 실패 유형 2. 너무 큰 단위만 본다

하루 평균만 보면 다음이 사라진다.

- 특정 메뉴만 달라진 변화
- 특정 시간대만 반복된 변화
- 개별 동작에서만 보이는 구조 변화

즉 집계는 필요하지만, 집계만으로는 원인을 추적하기 어렵다.

### 실패 유형 3. 입력과 출력의 수준이 어긋난다

예를 들어:

- 입력은 동작 단위인데 출력은 하루 전체 원인 확정 여부
- 입력은 개별 동작인데 라벨은 모호한 수리 완료 이력 하나

이 경우 학습 문제 자체가 흐려진다.

### 실패 유형 4. 운영 질문과 모델 출력이 어긋난다

운영자가 원하는 것이 `검토 우선순위`인데, 모델이 `고장 종류 5분류`만 내놓으면 실제 활용이 어렵다.

즉 문제 정의는 기술적으로 그럴듯한 출력보다 실제 사용자가 취할 다음 행동을 기준으로 다시 써야 한다.

이 목록은 매우 중요하다.

왜냐하면 독자가 `하나의 도메인 = 하나의 AI 문제`라고 오해하지 않게 해 주기 때문이다.

## 초심자가 특히 자주 혼동하는 문제 정의 쌍

### 혼동 1. 예측(prediction)과 비교(comparison)

이 사례에서 많은 질문은 미래를 맞히는 문제가 아니라, 지금 상태를 평소와 비교하는 문제다.

즉 `다음 동작이 몇 초일까`와 `최근 동작이 평소와 달라졌는가`는 전혀 다른 문제다.

### 혼동 2. 탐지(detection)와 진단(diagnosis)

탐지는 `무언가 달라졌다`를 찾는 일이다.

진단은 `왜 달라졌는가`를 특정 원인으로 연결하는 일이다.

이 사례는 전자는 비교적 가능하지만, 후자는 더 어려울 수 있다는 점을 잘 보여 준다.

### 혼동 3. 동작 결과 품질과 장비 상태

맛이 달라졌다고 해서 기계 이상만을 뜻하지는 않는다.

반대로 기계 상태가 달라져도 맛 관련 불만이 당장 기록되지 않을 수 있다.

즉 `품질 문제`와 `설비 상태 문제`는 겹치지만 동일하지 않다.

### 혼동 4. 라벨이 없는 것과 쓸모없는 것

라벨이 부족해도 할 수 있는 일은 많다.

- 기준선 비교
- 집계 요약
- 변화 신호 탐지
- 시각화
- 사람 검토 지원

이 점은 AI를 지도학습으로만 이해하는 독자에게 특히 중요하다.

## 문제 정의를 위한 질문 템플릿

책이나 노트에서 반복 재사용할 수 있는 질문 템플릿을 미리 만든다.

### 템플릿 1. 입력 정의

- 한 행(row)은 무엇을 뜻하는가
- 한 샘플(sample)은 무엇을 뜻하는가
- 입력 길이는 고정인가 가변인가
- 같은 입력끼리 비교 가능하다는 근거는 무엇인가

### 템플릿 2. 출력 정의

- 출력은 숫자인가 범주인가 순위인가 설명 문장인가
- 출력 하나가 실제로 어떤 행동(action)으로 이어지는가
- 출력이 틀렸을 때 비용은 무엇인가

### 템플릿 3. 비교 단위 정의

- 어떤 조건을 같은 집단으로 묶는가
- 메뉴가 다르면 분리하는가
- 머신이 다르면 분리하는가
- 시간대나 기간을 어떻게 나누는가

### 템플릿 4. 라벨 정의

- 라벨은 누가 남기는가
- 라벨 시점이 입력 시점보다 뒤인가
- 라벨이 실제 원인을 뜻하는가, 아니면 사람이 붙인 운영 상태인가
- 라벨 누락은 얼마나 흔한가

### 템플릿 5. 평가 정의

- 정확도보다 중요한 것은 무엇인가
- 거짓 경보와 놓침 중 어느 쪽 비용이 큰가
- 경고 우선순위가 필요한가

이 템플릿은 이 사례를 넘어서 Part 3 전체에 재사용 가능하다.

## 동작 단위 표를 설계할 때의 세부 판단

동작 단위 표는 단순히 열을 많이 만들수록 좋아지는 것이 아니다.

### 절대값 열

예:

- 총 추출 시간
- 전체 평균 압력
- 전체 평균 유량

장점:

- 이해가 쉽다
- 설명이 직관적이다

한계:

- 구조가 사라질 수 있다

### 구간값 열

예:

- 초반 유량 평균
- 중반 유량 평균
- 후반 유량 평균

장점:

- 구조를 일부 보존한다

한계:

- 구간 정의가 설계 문제다

### 변화율 열

예:

- 중반 상승률
- 후반 하강률

장점:

- 흐름을 요약할 수 있다

한계:

- 노이즈에 민감할 수 있다

### 안정성 열

예:

- 변동성
- 샘플 수
- 결측 비율

장점:

- 지표 자체의 신뢰도를 읽는 데 도움된다

### 패턴 열

예:

- 토큰 시퀀스
- 대표 shape

장점:

- 사람이 읽기 좋다
- 구조 비교에 유리하다

## 어떤 질문은 본편, 어떤 질문은 보충학습에 더 맞는가

### 본편에 넣기 좋은 질문

- 샘플 단위는 어떻게 정하는가
- 입력과 출력은 어떻게 정의하는가
- 왜 기준선 비교가 필요한가
- 라벨 부족 문제는 왜 생기는가

### 보충학습에 넣기 좋은 질문

- 시계열 데이터베이스 설계
- 스트리밍 파이프라인
- 온라인 학습
- 이상 탐지 알고리즘 세부 비교

즉 현재 노트는 본편 질문을 중심에 두고, 구현 세부는 보충학습 또는 범위 밖으로 둔다.

## 이 사례와 다른 도메인의 평행 비교

이 비교는 책을 풍부하게 만드는 데 도움된다.

| 도메인 | 샘플 단위 | 비교 단위 | 운영 질문 |
| --- | --- | --- | --- |
| 동작 단위 센서 | 동작 1회 | 최근 구간 vs 기준선 | 동작 상태가 평소와 달라졌는가 |
| 서버 모니터링 | 요청 1건 | 최근 5분 vs 평소 | 지연 시간이나 오류율이 달라졌는가 |
| 검색 품질 | 질의 1건 | 최근 세션 vs 기준선 | 클릭 패턴이 달라졌는가 |
| LLM 서비스 | 호출 1건 | 최근 배치 vs 기준선 | 비용, 지연 시간, 평가 점수가 흔들리는가 |

이 표는 이 사례를 특정 음료 이야기로만 묶어 두지 않고, 일반 AI 운영 문제로 확장하게 해 준다.

## 잘못된 문제 정의 예시를 일부러 만드는 연습

책에서 매우 유용한 훈련은 `나쁜 문제 정의를 써 보는 것`이다.

### 나쁜 예시 1

`센서 로그를 보고 원인 종류를 맞히는 AI 만들기`

왜 약한가:

- 입력과 라벨 연결 시점이 모호하다
- 실제 운영자가 원하는 출력이 아닐 수 있다

`최근 30분 동작 패턴이 직전 기준선에서 벗어났는지 요약하고, 사람이 우선 확인할 후보를 정리하기`

### 나쁜 예시 2

`평균 유량이 낮으면 무조건 문제`

왜 약한가:

### 더 나은 예시 2

`같은 조건 집단 안에서 중반 유량 평균과 후반 하강 구조를 함께 비교해 최근 변화 후보를 찾기`

## 문제 정의와 라벨 설계의 연결

라벨이 무엇인지에 따라 가능한 모델이 바뀐다.

### 라벨이 거의 없는 경우

- 기술통계
- 기준선 비교
- 변화 신호 탐지
- 군집화

### 운영 라벨이 있는 경우

- 검토 필요 여부 분류
- 재점검 우선순위 예측

### 품질 결과 라벨이 있는 경우

- 품질 저하 예측
- 상태와 품질의 관계 분석

### 수리 이력이 있는 경우

- 사건 전후 비교
- 후행 검증

즉 `라벨이 있는가`만이 아니라 `어떤 라벨인가`가 중요하다.

## 시간 축에서 생기는 누수(data leakage) 문제

이 사례는 데이터 누수를 설명하기도 좋다.

예를 들어:

- 미래 최근 구간 정보를 과거 예측에 섞으면 안 된다
- 수리 완료 후의 정보가 수리 전 판단에 들어가면 안 된다
- 최근 평균을 계산할 때 현재 구간 이후 데이터를 포함하면 안 된다

이런 설명은 Part 3의 훈련/검증 분할 설명에 매우 잘 맞는다.

## 문제 정의 점검 체크리스트

이 체크리스트는 실제 본문 작성 전마다 다시 볼 수 있다.

### 샘플 단위 체크

- 한 샘플이 하나의 완결 사건인가
- 샘플끼리 비교 가능한가
- 샘플 길이가 너무 제각각이면 어떤 정규화가 필요한가

### 출력 단위 체크

- 출력이 샘플 단위와 같은 층위인가
- 출력이 실제 행동으로 이어지는가
- 출력이 너무 야심차서 라벨이 부족한 상태는 아닌가

### 집단 정의 체크

- 어떤 조건끼리만 묶는가
- 묶으면 안 되는 이질 집단이 섞이지 않았는가
- 시간 흐름을 무시하는 집계는 아닌가

### 평가 체크

- 정확도만 보면 안 되는가
- false positive 비용은 무엇인가
- false negative 비용은 무엇인가
- 사람이 최종 검토하는 구조인가

## Part 3용 짧은 삽입 문단 초안

### 초안 C

이 사례에서는 처음부터 `고장 종류 분류기`를 만드는 것보다, 동작 요약 표와 기준선 비교 표를 먼저 만드는 편이 더 현실적입니다. 라벨이 희소하고 원인이 복합적일 수 있기 때문입니다. 이런 상황에서는 문제 정의를 더 작게 다시 써서 설명 가능한 기준 모델을 먼저 세우는 편이 안전합니다.

### 초안 D

같은 사건 요약 표라도 목표가 달라지면 모델링이 달라집니다. `review_needed`를 예측하면 지도학습이 될 수 있고, 최근 윈도우를 기준선과 비교하면 변화 추세 탐지가 되며, 라벨 없이 유사한 패턴을 묶으면 군집화가 됩니다. 데이터셋은 고정되어 있어도 문제 정의는 고정되지 않습니다.

## 자주 나오는 반론과 응답

### 반론 1

`그래도 결국은 더 큰 모델이 해결하지 않나?`

응답:

더 큰 모델이 더 많은 패턴을 잡을 수는 있다. 하지만 문제 정의가 흐리면 큰 모델은 더 비싼 모호함을 만들 뿐이다. 우선은 입력, 출력, 라벨, 행동 연결이 분명한 작은 문제부터 만드는 편이 낫다.

### 반론 2

`라벨이 적어도 사람 경험으로 찍어서 만들면 되지 않나?`

응답:

가능은 하지만 그 라벨이 무엇을 뜻하는지 먼저 분명히 해야 한다. 사람의 즉석 판단, 수리 결과, 고객 불만, 품질 검사 결과는 서로 다른 라벨이다. 이들을 같은 라벨처럼 섞으면 모델이 무엇을 배우는지 불분명해진다.

### 반론 3

`달라 보이면 다 같은 원인 아닌가?`

응답:

아니다. 레시피 변화, 원료 차이, 환경 변화, 센서 오차, 일시적 튐도 모두 이상처럼 보일 수 있다. 그래서 경고와 진단을 분리해야 한다.

## 문제 정의를 너무 넓게 잡을 때의 위험

초심자는 현실 문제가 흥미로우면 질문을 한 번에 너무 크게 잡기 쉽다.

예:

- 기계 이상 전부 자동 진단하기
- 품질 문제 원인까지 한 번에 맞히기
- 모든 메뉴를 하나의 모델로 동시에 다루기

이런 질문은 매력적이지만, 입문 교재에서는 오히려 안 좋은 출발점일 수 있다.

왜냐하면:

- 라벨 정의가 흐려지고
- 입력 집단이 섞이며
- 평가 기준이 모호해지고
- 실패 원인을 읽기 어려워지기 때문이다

그래서 이 노트는 `작게 다시 쓰는 능력`을 강조해야 한다.

## 문제 정의를 작게 다시 쓰는 네 가지 방법

### 1. 출력 좁히기

- 고장 원인 분류 -> 검토 필요 여부

### 2. 집단 좁히기

- 전체 메뉴 -> 특정 음료 유형

### 3. 시간 범위 좁히기

- 전체 월간 상태 -> 최근 구간 vs 기준선

### 4. 목적 바꾸기

- 자동 진단 -> 설명 가능한 비교 리포트

이 네 가지는 Part 1과 Part 3에서 반복해서 쓸 수 있다.

## 도메인 질문을 데이터 질문으로 번역하는 표

| 도메인 질문 | 데이터 질문 |
| --- | --- |
| 추출이 평소와 달라졌는가 | 최근 요약값과 기준선 차이가 있는가 |
| 어느 메뉴에서 반복되는가 | 메뉴별 최근 구간 차이가 누적되는가 |
| 한 번의 우연인가 | 동작 수와 반복성이 충분한가 |
| 사람이 확인할 가치가 있는가 | review priority를 높일 근거가 있는가 |

이 표는 `문제를 모델로 바꾸는 과정`을 가장 쉽게 보여 준다.

## 샘플 단위를 바꾸면 데이터셋이 어떻게 달라지는가

### 센서 점 단위 데이터셋

장점:

- 원시 정보가 많다

한계:

- 동작 전체 구조를 잃기 쉽다
- 행 수는 많아도 해석은 어려워질 수 있다

### 동작 단위 데이터셋

장점:

- 완결 사건으로 읽기 쉽다
- 특징 표로 바꾸기 좋다

### 최근 구간 단위 데이터셋

장점:

- 운영 상태를 읽기 좋다

한계:

- 개별 동작 구조는 일부 사라진다

즉 단위를 고를 때는 정보량만이 아니라 `질문과의 정합성`을 봐야 한다.

## 라벨이 없을 때도 데이터셋은 설계된다

이 점을 분명히 적어 두는 것이 좋다.

데이터셋이라는 말을 들으면 독자는 종종 `입력 + 정답 라벨`을 먼저 떠올린다.

하지만 이 사례에서는 라벨이 없어도 데이터셋 설계가 가능하다.

- 동작 요약 테이블
- 최근 구간 집계 테이블
- 기준선 비교 테이블
- 패턴 분포 테이블

즉 라벨은 데이터셋의 한 형태일 뿐 전체가 아니다.

## 문제 정의와 실험 순서의 연결

좋은 문제 정의는 곧 좋은 실험 순서를 만든다.

예를 들어:

1. 동작 요약표를 만든다
2. 메뉴별로 분리한다
3. 기준선 비교를 만든다
4. review priority 규칙을 만든다
5. 필요하면 ML 실험을 붙인다

이 순서는 그냥 구현 순서가 아니라 문제 정의를 점점 선명하게 만드는 순서다.

## 평가 없이도 먼저 확인할 수 있는 것

초심자는 모델 평가 지표가 없으면 아무것도 못 한다고 느낄 수 있다.

하지만 이 도메인에서는 먼저 확인 가능한 것이 많다.

- 동작 요약표가 사람이 읽히는가
- 메뉴별 분리가 자연스러운가
- 기준선 차이가 도메인 직관과 맞는가
- 경고 문장이 과장되지 않는가

즉 `모델 성능` 이전에 `문제 구조가 읽히는가`를 먼저 확인할 수 있다.

## 본문용 미니 문장 후보

- 같은 센서 로그도 질문을 어떻게 자르느냐에 따라 전혀 다른 데이터셋이 됩니다.
- 좋은 문제 정의는 거대한 질문을 작은 비교 가능한 질문으로 다시 쓰는 데서 시작합니다.
- 라벨이 없다고 해서 데이터셋 설계가 멈추는 것은 아닙니다.

## 문제 정의를 넓히는 방향과 좁히는 방향을 함께 보기

입문 독자는 문제를 작게 쪼개는 연습은 해도, 다시 어떤 방향으로 확장할 수 있는지는 놓치기 쉽다.

이 사례에서는 둘 다 적어 두는 편이 좋다.

### 좁히는 방향

- 전체 기계 상태 -> 특정 음료 유형 상태
- 모든 이상 -> 후반 하강 구조 변화
- 자동 진단 -> 검토 우선순위

### 넓히는 방향

- 동작 요약 -> 최근 구간 비교
- 경고 후보 -> 품질 리스크와의 연결
- 센서 비교 -> 운영 리포트 전체 설계

즉 문제 정의는 한 번 정하고 끝나는 문장이 아니라, 학습하면서 조정되는 지도라고 볼 수 있다.

## 출력 설계를 더 구체적으로 적어 두기

- `mid_flow_gap = -0.14`

장점:

한계:

### 출력 후보 B. 분류

- `normal`
- `review`

장점:

- 단순하다

한계:

- 애매한 경우가 잘 안 보일 수 있다

### 출력 후보 C. 우선순위

- `watch`
- `review`
- `urgent_review`

장점:

- 운영 행동과 더 잘 연결된다

### 출력 후보 D. 설명 문장

- `최근 후반 하강 구조가 반복되어 검토가 필요합니다.`

장점:

- 사람이 읽기 쉽다

한계:

- 근거가 함께 남아야 한다

## 추가 FAQ

### Q9. 출력은 숫자가 좋을까요, 문장이 좋을까요?

A. 둘 중 하나만 고를 필요는 없다. 숫자는 비교와 계산에 좋고, 문장은 사람 해석에 좋다. 실제로는 숫자와 설명 문장을 함께 남기는 구조가 자주 더 유용하다.

### Q10. 동작 요약표를 만들면 이미 머신러닝을 하는 건가요?

A. 꼭 그렇지는 않다. 하지만 그것은 이후의 머신러닝이나 비교 분석을 가능하게 만드는 중요한 표현 설계 단계다.

### Q11. 문제 정의가 여러 개면 혼란스럽지 않나요?

A. 오히려 현실 문제에서는 같은 데이터에서 여러 문제 정의가 나오는 것이 자연스럽다. 중요한 것은 그것들을 섞지 않고, 각 문제의 입력과 출력, 평가 기준을 분명히 나누는 일이다.
