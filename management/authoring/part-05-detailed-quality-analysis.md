# Part 5 상세 품질 분석

## 목적

이 문서는 `management/authoring/part-quality-analysis.md`에서 Part 5를 최우선 보강 대상으로 판정한 뒤, 실제 편집 단위로 이어 가기 위한 상세 작업 문서입니다.

## 현재 상태 업데이트

- Chapter 14~17의 반복 handoff 문장은 최근 커밋들에서 상당 부분 압축했습니다.
- 특히 `평가 -> 운영 -> 통합 미니 실습`과 `MCP -> 하네스 -> 평가` 경계는 이전보다 짧고 직접적으로 고정되었습니다.
- 추가로 `P5-15.1`, `P5-15.2`, `P5-16.1`, `P5-16.2`, `P5-17.1`, `P5-17.2`의 도입·마무리 메타 문장을 더 직접적인 전환 문장으로 정리했습니다.
- 이어서 `P5-9.1`, `P5-10.1`, `P5-10.2`, `P5-11.1`, `P5-11.2`, `P5-12.1`, `P5-12.2`, `P5-13.1`, `P5-14.1`, `P5-14.2`의 도입·마무리 안내형 문장도 같은 기준으로 대부분 정리했습니다.
- 따라서 Chapter 15~17은 이제 `같은 패턴의 반복 압축`보다 `정말 설명을 흔드는 문장만 남았는지 확인하는 유지 점검` 단계에 가깝습니다.
- 현재 본편 `section-01/02` 기준으로는 같은 패턴의 안내형 문장이 거의 소진되었고, 남은 확인 대상은 보충학습 절(`P5-9.3`)과 Part 6 연결 직접성 쪽에 더 가깝습니다.
- 따라서 다음 라운드부터는 같은 유형의 미세 문장 압축을 계속 늘리기보다, 실제로 독서 흐름을 다시 흔드는 문장만 선택적으로 만지는 편이 맞습니다.
- 남은 우선순위는 `추가 압축 그 자체`보다 `Chapter 9~14 전환 표의 통일감`, `배경 축 예고 과밀 여부`, `Part 6 연결 문장의 직접성`을 다시 점검하는 쪽에 더 가깝습니다.

Part 5는 현재 원고 전체에서 가장 구조가 복잡한 Part입니다. 이유는 단순히 주제가 어렵기 때문만이 아니라, 다음 세 층이 한 Part 안에서 강하게 이어지기 때문입니다.

- 모델 내부 구조: 토큰, 임베딩, Transformer, GPT, next-token prediction
- 서비스 연결 구조: 프롬프트, RAG, tool use, agent, MCP, 하네스
- 품질과 운영 구조: 평가, 운영 제약, 실패 대응, 통합 미니 실습

최근 작업으로 `본류 1~17, 배경 축 18~19` 구분은 많이 선명해졌습니다. 이제 남은 과제는 `현재 순서를 유지한 채 독자가 실제로 덜 흔들리게 읽히는가`를 더 세밀하게 점검하는 일입니다.

## 현재 독서 경로 진단

### 현재 구조 판단

현재 Part 5는 `대규모 재배치 필요` 상태는 아닙니다. 오히려 최근 보강 이후에는 `현재 순서를 유지하되, 독서 경로를 더 강하게 유도해야 하는 상태`에 가깝습니다.

지금 가장 안정적인 읽기 순서는 다음과 같습니다.

| 읽기 묶음 | 해당 Chapter | 현재 판단 |
| --- | --- | --- |
| 입력과 표현 | Chapter 1-2 | 안정적 |
| 생성 구조 | Chapter 3-5 | 안정적 |
| 학습과 조정 | Chapter 6-8 | 안정적 |
| 서비스 연결 | Chapter 9-14 | 전환 문장 정리는 많이 진행됨. 이제는 표 통일감과 Part 6 연결 직접성 점검이 더 중요함 |
| 평가와 운영 | Chapter 15-17 | 본류 닫힘 구조는 많이 안정됨. 이제는 유지 점검 단계에 가까움 |
| 배경 축 | Chapter 18-19 | 현재 위치 유지가 맞음 |

핵심은 `Chapter 9-17`입니다. 이 구간은 개념이 틀린 것은 아니지만, 독자가 다음처럼 읽기 쉬운 구간입니다.

- 프롬프트, RAG, tool use, agent가 모두 비슷한 `외부 연결`처럼 뭉개져 보임
- MCP, 하네스, 평가, 운영이 같은 종류의 운영 용어처럼 한꺼번에 밀려옴
- Part 5 후반이 `새 개념 추가`인지 `앞에서 만든 흐름의 운영 회수`인지 경계가 흐려질 수 있음

즉, Part 5의 현재 리스크는 `순서 자체의 오류`보다 `전환 구간에서 중심 질문이 충분히 압축되지 않아 체감 난도가 올라가는 점`입니다.

### 본류와 배경 축 판단

`docs/parts/part-05/index.md`와 `docs/parts/part-05/summary.md` 기준으로 보면 다음 판단은 유지하는 편이 맞습니다.

- Chapter 1~17은 본류다.
- Chapter 18~19는 배경 축이다.
- Chapter 18~19를 앞쪽으로 당기지 않는다.
- Chapter 18~19는 새 본편이 아니라 `본류 복습 뒤의 역사/비교 축`으로만 읽게 해야 한다.

이 판단은 현재 맞습니다. `P5-18.1`, `P5-19.1`도 이미 같은 방향으로 고쳐져 있으므로, 구조를 다시 뒤집기보다 `앞쪽 본류에서 배경 축을 왜 지금 읽지 않아도 되는가`를 더 자주 눌러 주는 편이 낫습니다.

## 리스크 장면 목록

### 1. Chapter 9-14가 모두 `외부 연결 기술`처럼 한 덩어리로 보일 수 있다

- 관련 Section: `P5-9.1`, `P5-10.1`, `P5-12.1`, `P5-13.1`, `P5-14.1`, `P5-14.2`
- 왜 피로를 만드는가:
  - 프롬프트는 입력 설계
  - RAG는 근거 연결
  - tool use는 실행 연결
  - agent는 목표 흐름
  - MCP는 연결 인터페이스
  - 하네스는 실행 관리
  이 차이가 문서 전체에서는 존재하지만, 연속 독서에서는 여전히 `다 비슷한 후반 기술 이름`처럼 읽힐 수 있습니다.
- 해결 방향:
  - 순서를 바꾸기보다, 각 장 끝이나 다음 장 도입에서 `바로 앞 장과 지금 장의 차이`를 더 짧게 다시 눌러야 합니다.
- 우선 판단:
  - 문단 보강으로 해결 가능

### 2. Chapter 15-17이 `평가 부록`처럼 밀려날 위험은 많이 줄었지만 완전히 사라진 것은 아니다

- 관련 Section: `P5-15.2`, `P5-16.1`, `P5-16.2`, `P5-17.1`, `P5-17.2`
- 왜 피로를 만들 수 있는가:
  - 앞쪽에서 구조를 많이 읽은 뒤라, 독자가 평가와 운영을 `마지막 덧붙임`으로 오해할 가능성은 여전히 남아 있습니다.
  - 다만 최근 압축으로 `좋은 답 판단 -> 운영 한도/복구 -> 기록 가능한 요청 흐름` 본류는 이전보다 훨씬 직접적으로 보입니다.
- 해결 방향:
  - 평가 -> 운영 -> 통합 미니 실습이 `부록`이 아니라 `서비스로 닫는 본류 마지막 단계`임을 더 자주 명시해야 합니다.
- 우선 판단:
  - 대규모 보강보다 유지 점검으로 관리 가능

### 3. Chapter 14의 MCP/하네스가 도구 이름 목록처럼 보일 위험이 있다

- 관련 Section: `P5-14.1`, `P5-14.2`
- 왜 피로를 만드는가:
  - MCP와 하네스는 초심자에게 가장 낯선 이름 축입니다.
  - 현재 설명은 비교적 안정적이지만, 바로 앞의 tool use/agent와 뒤의 평가/운영 사이에서 `왜 지금 필요한가`가 흐려지면 단어만 남을 수 있습니다.
- 해결 방향:
  - `MCP는 연결 인터페이스`, `하네스는 실행 관리와 기록 환경`이라는 최소 구분을 더 반복적으로 회수합니다.
- 우선 판단:
  - 문단 보강으로 해결 가능

### 4. Chapter 18-19는 현재 위치가 맞지만, 본류에서 너무 자주 예고되면 다시 과밀해질 수 있다

## 현재 결론

Part 5의 다음 단계는 `목차를 다시 섞는 작업`이 아니라 `후반 전환 장면을 더 압축해 독서 경로를 안정화하는 작업`입니다.

따라서 편집 우선순위는 다음처럼 잡는 편이 맞습니다.

1. Chapter 9-14의 손잡이 차이를 더 짧고 반복적으로 고정한다.
2. Chapter 15-17을 부록이 아니라 본류 마지막 단계로 더 또렷하게 닫는다.
