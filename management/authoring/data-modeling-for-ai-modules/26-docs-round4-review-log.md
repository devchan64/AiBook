# 실제 본문 편집 4차 반영 검토 메모

## 목적

이 문서는 `data-modeling-for-ai-modules`의 관점을 실제 `docs/` 본문에 4차로 반영하면서, 왜 이번 라운드에서 `평가/튜닝`과 `텍스트·검색 프로젝트`에 비교 기록 구조를 더 직접적으로 넣었는지 기록한다.

이번 라운드 대상은 다음 네 파일이다.

- `docs/parts/part-03/chapter-09/section-02.md`
- `docs/parts/part-03/chapter-10/section-02.md`
- `docs/parts/part-06/chapter-04/section-02.md`
- `docs/parts/part-06/chapter-05/section-02.md`

## 이번 반영의 핵심 판단

### 1. 튜닝은 점수 놀이가 아니라 비교 기록이 남는 반복 실험이어야 한다

`part-03/chapter-09/section-02.md`는 원래 검증 절차와 비용을 다루는 절이다. 이번 라운드에서는 여기에 `튜닝 전에 남겨 둘 메모`와 `검증 비용을 반복 실험 기록 비용으로도 읽는 관점`을 추가했다.

핵심은 다음과 같다.

- 샘플 단위와 입력 표현
- baseline과 현재 후보 점수
- 대표 오류 사례 또는 큰 오차 구간
- 다음 검토 메모

이 보강이 없으면 튜닝은 여전히 `값을 많이 바꾸는 일`처럼 읽히기 쉽다.

### 2. 회귀 절도 분류 절과 같은 비교 구조를 가져야 한다

`part-03/chapter-10/section-02.md`는 이미 baseline 오차와 큰 실패 구간을 다루고 있었다. 이번 라운드에서는 여기에 `기준 모델`과 `비교 기준선`을 회귀 문맥으로 연결하고, 검토 우선순위와 해석 경계 문장을 더 직접적으로 넣었다.

이 보강으로 회귀 평가도 다음 구조로 읽히게 된다.

- 평균 예측보다 나아졌는가
- 어떤 구간에서 큰 오차가 남는가
- 원인을 아직 확정할 수 없는가
- 다음에 무엇을 더 봐야 하는가

### 3. 텍스트와 검색 프로젝트도 같은 기록 원리를 따라야 한다

`part-06/chapter-04/section-02.md`와 `part-06/chapter-05/section-02.md`에서는 각각 토큰화 평가와 RAG 검증을 다루고 있다. 이번 라운드에서는 두 절 모두 `비교 가능한 기록 묶음`을 더 직접적으로 적었다.

- 텍스트 프로젝트: tokenizer 규칙, coverage, OOV, review 대상 문장
- RAG 프로젝트: retrieval 기준선, 질문별 상태, needs_revision 목록, 멈춘 이유

이 보강은 Part 6의 후속 프로젝트들이 모두 `점수 + 검토 기록` 구조로 이어지게 만든다.

## 파일별 반영 이유

### `part-03/chapter-09/section-02.md`

반영한 내용:

- 튜닝 전에 남겨 둘 메모 표
- 검증 비용을 기록 비용까지 포함해 읽는 문단
- 튜닝 후 실험 메모 예시 표

반영 이유:

- `part-03/chapter-08`에서 보강한 baseline 비교 구조를 `part-03/chapter-09`의 튜닝 절로 실제로 넘겨 주는 연결 고리가 필요했다.

### `part-03/chapter-10/section-02.md`

반영한 내용:

- 회귀 평가 전에 같이 남길 것 표
- 해석 경계 문장 세트
- 회고 메모 예시 표

반영 이유:

- 분류 절에서 정리한 비교 기준선과 검토 우선순위 구조가 회귀 절에도 동일하게 작동한다는 점을 보여 줄 필요가 있었다.

### `part-06/chapter-04/section-02.md`

반영한 내용:

- coverage 외에 같이 남길 평가 메모 표
- tokenizer 자체를 현재 기준선으로 읽는 연결 문장
- 비교 가능한 기록 묶음 표

반영 이유:

- 토큰화와 평가는 점수 해석보다 입력 표현 해석이 먼저라는 점을 더 분명하게 만들 필요가 있었다.

### `part-06/chapter-05/section-02.md`

반영한 내용:

- retrieval 기준선, review 질문, 멈춘 이유를 남기는 표
- RAG baseline을 현재 검색 규칙 전체로 읽는 연결 문장
- 비교 가능한 기록 묶음 표

반영 이유:

- 검색 실패와 답변 실패를 분리하는 것만으로는 부족하고, 다음 반복에서 무엇을 바꿔야 하는지 다시 읽을 수 있는 기록 구조가 필요했다.

## 이번 라운드에서 의도적으로 하지 않은 것

- 새 코드 예제는 만들지 않았다.
- 새로운 도메인 사례를 별도로 도입하지 않았다.
- 현재 비커밋 상태의 `docs/` 본문을 커밋하지 않았다.

## 현재 결론

이번 4차 반영은 데이터 모델링 모듈의 핵심을 `샘플 -> 기준선 -> 비교 -> 검토 기록 -> 다음 질문` 구조로 굳히고, 그 구조가 튜닝, 회귀, 텍스트, RAG 프로젝트까지 같은 방식으로 이어지게 만드는 작업이었다.
