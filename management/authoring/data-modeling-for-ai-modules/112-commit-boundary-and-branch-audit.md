# 커밋 경계와 브랜치 감사

## 목적

이 문서는 현재 스레드에서 `무엇을 커밋할 수 있고 무엇을 커밋하면 안 되는가`를 최근 사용자 지시와 현재 워크트리 기준으로 고정하기 위해 만든다.

이미 `docs/` 비커밋 원칙은 여러 상태 문서에 흩어져 있지만, 최근에는 `예외적으로 커밋해야 하는 파일`과 `수정해도 커밋하면 안 되는 파일`이 함께 존재하게 되었다. 이 문서는 그 경계를 한 번에 확인하는 운영 기준이다.

## 현재 브랜치 기준

- 현재 작업 브랜치: `dev`
- `main` 반영 지시는 현재 없다.
- 따라서 일반 원고 편집, 관리 문서 작성, 상태 감사는 모두 `dev` 기준으로만 진행한다.

## 현재 커밋 경계

### 1. 커밋 예외로 인정된 파일

다음 파일의 수정은 사용자 지시에 따라 커밋 대상으로 본다.

- `management/authoring/brewing-shot-ai-notes/02-problem-framing-from-shot-to-dataset.md`

현재 근거:

- `48-note-02-problem-framing-commit-log.md`
- 최근 사용자 지시: `02-problem-framing-from-shot-to-dataset.md`의 수정은 커밋해야 한다

운영 해석:

- `brewing-shot-ai-notes` 전체를 수정 대상으로 다시 여는 것이 아니라, 위 한 파일만 예외적 커밋 대상으로 인정한다.
- 이 예외는 이미 남겨 둔 커밋 근거 문서와 함께 관리한다.

### 2. 커밋하면 안 되는 파일 묶음

다음 묶음은 수정되더라도 현재 스레드 목표 안에서는 커밋하지 않는다.

- `docs/` 아래 책원고 본문 전체

현재 근거:

- 저장소 규칙의 `dev` 작성 브랜치 원칙
- 최근 사용자 지시: `/home/cbsim/ws/AiBook/docs 수정은 커밋하지 않는다`
- 현재 워크트리의 `git status --short`에서 Part 2, Part 3, Part 6 본문이 수정 상태로 남아 있음

운영 해석:

- 본문은 순차 검토와 보정의 결과가 남아 있어도, 완료 본문으로 간주해 커밋하지 않는다.
- 이후 새 검토 라운드가 열리더라도 같은 정책을 유지한다.

### 3. 현재 관리 문서 묶음

다음 묶음은 상태 관리와 계획 근거를 위해 계속 수정할 수 있다.

- `management/authoring/data-modeling-for-ai-modules/`

운영 해석:

- 이 디렉터리의 문서는 현재 목표의 `계획 근거를 문서로 작성하며 관리한다` 요구사항을 직접 담당한다.
- 다만 실제 커밋 여부는 사용자가 별도로 지시할 때만 판단한다.
- 즉 `수정 가능`과 `즉시 커밋 대상`은 같은 뜻이 아니다.

## 현재 워크트리 해석

현재 워크트리는 다음 세 층으로 나눠 읽는 편이 안전하다.

1. 예외 커밋 파일
2. 비커밋 원고 파일
3. 상태 관리용 관리 문서 파일

이 구분이 없으면 `원고 보정`과 `관리 근거 축적`이 같은 커밋 범위로 섞이기 쉽다.

## 이후 점검 규칙

- 커밋 전에는 항상 `git status --short`로 `docs/` 포함 여부를 먼저 확인한다.
- `brewing-shot-ai-notes`는 예외 파일 `02`를 제외하면 참조본으로만 읽는다.
- 새 커밋 예외가 생기면 이 문서와 관련 로그 문서를 함께 갱신한다.
- 새 본문 검토 라운드가 열려도 `docs/` 비커밋 정책은 유지한다.

## 현재 결론

현재 스레드의 커밋 경계는 `dev 브랜치 유지`, `노트 02만 예외적 커밋 대상`, `docs/ 본문은 비커밋 유지`, `관리 문서는 근거 문서로 계속 갱신 가능`으로 정리된다.
