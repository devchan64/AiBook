# 실제 본문 편집 5차 반영 검토 메모

## 목적

이 문서는 `data-modeling-for-ai-modules`의 관점을 실제 `docs/` 본문에 5차로 반영하면서, 왜 이번 라운드에서 `로지스틱 회귀`, `결정 경계`, `권한·로그`, `실패 회고` 절을 공통된 검토 기록 구조로 더 직접 연결했는지 기록한다.

이번 라운드 대상은 다음 네 파일이다.

- `docs/parts/part-03/chapter-11/section-01.md`
- `docs/parts/part-03/chapter-11/section-02.md`
- `docs/parts/part-06/chapter-06/section-02.md`
- `docs/parts/part-06/chapter-07/section-02.md`

## 이번 반영의 핵심 판단

### 1. 로지스틱 회귀는 점수 출력보다 review 정책과 함께 읽혀야 한다

`part-03/chapter-11/section-01.md`는 원래 점수, sigmoid, threshold를 설명하는 절이다. 이번 라운드에서는 여기에 다음 기록 구조를 붙였다.

- baseline과 로지스틱 회귀 비교
- threshold별 행동 변화 사례
- review 대상 점수 구간
- 다음 조정 질문

이 보강으로 로지스틱 회귀는 `확률처럼 보이는 점수를 만드는 모델`에 그치지 않고, `운영 행동과 검토 대상을 함께 정리하는 첫 비교 모델`로 읽히게 된다.

### 2. 결정 경계는 그림 설명이 아니라 검토 대상 사례를 남기는 프레임이다

`part-03/chapter-11/section-02.md`는 경계의 기하와 threshold 이동을 다룬다. 이번 라운드에서는 여기에 경계 근처 사례 ID, threshold 변경 시 이동한 사례, 다음 검토 질문을 남기는 표를 추가했다.

이 보강의 목적은 결정 경계를 `애매한 점이 모이는 위치`이자 `사람이 다시 볼 사례를 뽑는 위치`로 읽게 만드는 데 있다.

### 3. agent 운영 절도 비교 가능한 기록 묶음으로 읽혀야 한다

`part-06/chapter-06/section-02.md`는 권한과 로그를 다룬다. 이번 라운드에서는 success/blocked 여부를 넘어서 다음 구조를 같이 남기게 만들었다.

- permission과 scope
- approved / blocked 상태
- observation과 next_action
- review 대상 단계

이렇게 해야 agent 실행 기록이 단순 실행 로그가 아니라 정책과 도구 설계를 다시 보는 근거가 된다.

### 4. 실패 회고는 앞 절들의 review 기록을 다시 모아 우선순위를 붙이는 단계여야 한다

`part-06/chapter-07/section-02.md`는 배포 이후 실패 기록을 다룬다. 이번 라운드에서는 여기서 `review_summary`, `evaluation_records`, `needs_revision`, `blocked` 같은 앞 절들의 상태를 회수할 수 있도록 연결 문장을 보강했다.

또한 `원인 확정`을 서두르지 않고 `다음 검토 질문`을 먼저 남기는 태도를 경계 문장으로 다시 넣었다.

## 파일별 반영 이유

### `part-03/chapter-11/section-01.md`

반영한 내용:

- threshold와 review 구간을 함께 남기는 표
- 점수, threshold, review 여부를 한 줄에 적는 기록 예시

반영 이유:

- 로지스틱 회귀는 뒤 절의 결정 경계와 앞 절의 baseline 비교 사이를 잇는 절이므로, 점수와 행동 기준을 분리하면서도 같은 기록으로 묶을 필요가 있었다.

### `part-03/chapter-11/section-02.md`

반영한 내용:

- 경계 근처 사례를 review 대상으로 남기는 표
- threshold 이동과 검토 우선순위를 잇는 문장 세트

반영 이유:

- 결정 경계 절이 단순 시각화 설명으로 끝나지 않고, 운영적으로 어떤 사례를 다시 볼 것인지까지 이어지게 만들 필요가 있었다.

### `part-06/chapter-06/section-02.md`

반영한 내용:

- permission, blocked, review 단계가 묶인 기록 표
- `review_needed` 열을 추가할 수 있다는 제안

반영 이유:

- agent 절은 tool 호출과 운영 정책이 만나는 곳이므로, 성공/실패만으로는 부족하고 다음 반복의 검토 단계까지 드러나야 했다.

### `part-06/chapter-07/section-02.md`

반영한 내용:

- Part 6 전체의 review 상태를 마지막 회고 문서에서 회수하는 표
- 원인 확정 대신 다음 검토 질문을 남기는 경계 문장

반영 이유:

- Part 6의 여러 프로젝트가 각자 끝나지 않고 하나의 공통 실패 기록 구조로 묶이게 만들 필요가 있었다.

## 이번 라운드에서 의도적으로 하지 않은 것

- 새 코드 예제를 추가하지 않았다.
- 새 도메인 사례를 별도로 만들지 않았다.
- 현재 비커밋 상태의 `docs/` 본문을 커밋하지 않았다.
