## 목적

이 문서는 `data-modeling-for-ai-modules`의 관점을 실제 `docs/` 본문에 6차로 반영하면서, 왜 이번 라운드에서 `k-NN`, `거리와 스케일`, `agent 목표`, `배포와 모니터링 목표` 절을 앞단의 review 기록 구조와 더 직접 연결했는지 기록한다.

이번 라운드 대상은 다음 네 파일이다.

- `docs/parts/part-03/chapter-12/section-01.md`
- `docs/parts/part-03/chapter-12/section-02.md`

## 이번 반영의 핵심 판단

### 1. k-NN 소개는 이웃 목록과 review query를 같이 남기는 구조여야 한다

`part-03/chapter-12/section-01.md`는 원래 k-NN의 직관을 설명하는 절이다. 이번 라운드에서는 여기에 다음 기록 구조를 추가했다.

- baseline과 k-NN 비교
- 이웃 목록
- review 대상 query
- 다음 질문

이 보강으로 k-NN은 `가까운 사례를 보는 모델`에 그치지 않고, `어떤 사례를 근거로 판단했는지 다시 읽을 수 있는 비교 후보`로 정리된다.

### 2. 거리와 스케일은 전처리 설명보다 사례 이동 기록으로 먼저 읽혀야 한다

`part-03/chapter-12/section-02.md`는 거리 함수와 스케일 왜곡을 설명한다. 이번 라운드에서는 여기에 다음 기록 구조를 붙였다.

- 스케일 조정 전 이웃 목록
- 스케일 조정 후 이웃 목록
- 이동한 query 사례
- 다음 검토 질문

이 보강의 목적은 스케일 조정을 `점수 개선 기술`보다 `같은 사례가 왜 다른 이웃을 갖게 되었는지 기록하는 절`로 읽게 만드는 데 있다.

### 3. agent 프로젝트 입구에서도 review 상태가 보여야 한다

`part-06/chapter-06/section-01.md`는 agent 목표와 실행 루프를 소개한다. 이번 라운드에서는 목표, 도구, 관찰, review 상태를 입구에서부터 같이 남기는 표를 넣었다.

이 보강으로 권한과 로그 절에서만 review 구조가 갑자기 나타나는 것이 아니라, agent 프로젝트 시작 순간부터 `관찰 후 무엇을 다시 볼 것인가`가 문서에 드러난다.

### 4. 배포 시작 절은 뒤의 실패 회고 입력 자료를 만드는 절이어야 한다

`part-06/chapter-07/section-01.md`는 build, publish, 공개 확인의 최소 흐름을 다룬다. 이번 라운드에서는 여기에 review 대상 항목, 다음 점검 시점, `review_needed` 또는 `recheck_required` 같은 상태를 앞단에서부터 남기게 만드는 문장을 추가했다.

이 보강으로 운영 시작 절은 단순 준비 설명이 아니라, 뒤 절의 실패 기록으로 넘어갈 입력 자료를 모으는 절이 된다.

## 파일별 반영 이유

### `part-03/chapter-12/section-01.md`

반영한 내용:

- baseline, 이웃 목록, review query를 같이 남기는 표
- query별 기록 예시 표

반영 이유:

- k-NN 절이 단순 알고리즘 설명으로 끝나지 않고, `비교 후보 -> review 사례 -> 다음 실험` 구조를 갖추게 만들 필요가 있었다.

### `part-03/chapter-12/section-02.md`

반영한 내용:

- 스케일 조정 전후 이웃 목록과 query 이동을 비교하는 표
- 사례 이동 기록을 먼저 읽게 하는 문단

반영 이유:

- 거리와 스케일 절이 전처리 소개만이 아니라, 표현 변경이 실제 판단을 어떻게 흔드는지 기록하는 절이라는 점을 더 분명히 할 필요가 있었다.

### `part-06/chapter-06/section-01.md`

반영한 내용:

- 목표, 도구, 관찰, review 상태를 입구에서 같이 남기는 표
- 관찰 후 상태와 다음 행동을 잇는 간단한 기록 표

반영 이유:

- agent 프로젝트의 입구에서부터 `질문 -> 도구 -> 관찰 -> review 상태` 구조가 보여야 뒤의 권한과 로그 절도 더 자연스럽게 읽힌다.

### `part-06/chapter-07/section-01.md`

반영한 내용:

- 운영 시작 절에서 같이 남길 review 대상 항목 표
- `review_needed` 또는 `recheck_required` 상태를 앞단에서 두는 제안

반영 이유:

- 실패 회고는 갑자기 생기는 문서가 아니라, 배포 직후부터 쌓아 둔 확인 기록을 다시 읽는 문서라는 점을 분명히 할 필요가 있었다.
