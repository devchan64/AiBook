# Part 6 체크포인트 노트

이 문서는 Part 6을 목차 순서대로 읽을 때 각 Section이 담아야 할 중심 주제를 개괄식으로 정리한 체크포인트 노트입니다.

## 사용 원칙

- 이 노트는 `docs/book/table-of-contents.md`를 기준으로 Part 6의 시작/마무리 페이지, Chapter, Section을 같은 순서로 훑기 위한 개요 문서입니다.
- 순차 점검 기록, 품질 상태 메모, 안정성 판정 로그는 이 문서에서 운영하지 않습니다.
- 체크포인트는 `입력 단위 -> LLM 구조 -> 학습과 조정 -> 근거 연결 -> 실행 구조 -> 평가와 운영 -> 배경 축` 흐름을 Section 단위로 정리하는 데 목적을 둡니다.
- `학습 관점 누락 점검`은 Part 원고가 잃기 쉬운 설명 흐름을 점검하고, `목차 기준 체크포인트`는 Part 원고가 유지해야 할 구조 흐름을 관리합니다.

## 학습 관점 누락 점검

- 각 Chapter를 볼 때 `모델이 혼자 못 하는 일`을 무엇으로 보강하는 장인지 분명히 드러나는지 확인합니다.
- 각 Section를 볼 때 `모델 내부 구조`, `조정 방법`, `근거 연결`, `도구 실행`, `운영 판단` 가운데 어느 층위를 설명하는지 섞이지 않는지 확인합니다.
- 프롬프트, RAG, 파인튜닝, 도구 사용 비교에서는 `언제 무엇을 고를까`라는 선택 기준이 실제 실패 원인과 연결되는지 확인합니다.
- 실행 구조 장에서는 도구 이름 나열보다 `입력 -> 호출 -> 결과 -> 상태 판단` 흐름이 드러나는지 확인합니다.
- 평가와 운영 장에서는 `좋은 답`과 `운영 가능한 답`을 같은 것으로 취급하지 않는지 확인합니다.
- Part 6에서는 특히 `모델 성능과 시스템 구조 혼동`, `근거 부족과 생성 실패 혼동`, `배경 축이 본류를 덮는 문제`가 빠지지 않는지 다시 봅니다.
- 토큰, GPT-3.5/ChatGPT, Codex 축에서는 `표식 단위 -> 표현 계산 -> 대화형 조정 경험 -> 도구 실행 워크플로우`가 서로 다른 층위로 유지되는지 확인합니다.

## 재배치·추가 판단 기준

- 새 Section을 검토할 때는 먼저 `본선의 중심 질문`과 `초심자가 처음 붙잡는 법`이 같은지 다른지 확인합니다.
- 초심자 진입 장치가 본선 질문과 분리될 만큼 독립적이면, 보충 Section 추가를 검토할 수 있습니다.
- 이미 있는 절 안에서 `왜 여기서 등장하는가`, `어떤 문제 장면에서 먼저 떠올려야 하는가`를 보강하면 충분한 경우에는 새 Section보다 절 내부 보강을 우선합니다.
- 본류 흐름을 끊는 앞삽입형 Section보다, 선택 지도 뒤 보충 절이나 본선 뒤 회수 절이 더 자연스러운지 먼저 판단합니다.
- 재배치는 `내용이 사라지지 않았는가`보다 `현재 위치가 전후 Module의 질문 흐름에 더 잘 맞는가`를 기준으로 판단합니다.

## 목차 기준 체크포인트

- `index.md`: Part 6이 LLM 키워드 소개가 아니라 입력, 생성, 조정, 근거, 실행, 운영을 한 흐름으로 읽는 Part라는 점을 분명히 해야 합니다.
- Part 구조: Module 1부터 Module 3까지는 `LLM이 무엇을 입력으로 읽고 어떤 구조로 생성하며 어떻게 조정되는가`를 이해시키는 전반부로 읽혀야 합니다.
- Part 구조: Module 4부터 Module 6까지는 `이해한 LLM을 현재 서비스에서 어떤 연결 구조, 실행 구조, 운영 판단으로 써야 하는가`를 설명하는 후반부로 읽혀야 합니다.
- 전반부 흐름: `토큰 -> 임베딩 -> Transformer/GPT/next-token prediction -> 사전학습/파인튜닝/정렬`이 하나의 내부 계산 축으로 이어져야 합니다.
- 후반부 흐름: `프롬프트로 닫히는 문제 구분 -> 외부 근거 연결 -> 조회·계산·실행 연결 -> 평가·운영 판단`이 하나의 서비스 활용 축으로 이어져야 합니다.
- `summary.md`: 재진입 기준이 되는 대표 Section를 함께 남겨야 합니다.

### Module 1. 입력 단위와 표현

- 의도: 이 Module은 LLM을 기능 이름이 아니라 `입력을 어떤 계산 단위와 표현으로 읽는가`에서부터 붙잡게 하는 출발점이어야 합니다.

#### Chapter 1. 토큰과 토큰화 `LLM 핵심`

- 중심축: LLM이 문자열을 어떤 계산 단위로 읽고, 그 단위가 토큰 순서열과 토큰화 절차로 어떻게 이어지는지 다룹니다.
- `P6-1.1`: 왜 LLM이 문자나 단어 대신 토큰 단위를 쓰는지 설명하고, 토큰을 단어 자체나 의미 단위로 단정하지 않게 해야 합니다.
- `P6-1.2`: 토큰이 모델 계산에서 어떤 최소 단위인지, symbolic AI의 symbol과는 어떻게 느슨하게 이어지되 다른지 분명히 해야 합니다.
- `P6-1.3`: 토큰이 낱개 이름이 아니라 모델 입력의 순서열로 쓰인다는 점을 보여 주어야 합니다.
- `P6-1.4`: 토큰화가 문자열을 계산 가능한 조각으로 바꾸는 절차라는 점을 잡아야 합니다.
- `P6-1.5`: 토큰화가 같은 문장을 다른 계산 길이와 표현으로 바꾼다는 점을 보여 주어야 합니다.
- `P6-1.6`: 대표 토크나이저 계열이 무엇을 기준으로 나뉘는지 정리해야 합니다.
- `P6-1.7`: 토큰화 차이가 언제 실제 품질, 비용, 분절 문제로 드러나는지 설명해야 합니다.
- `P6-1.8`: 토큰 관점이 프롬프트, 문맥 창, 비용, 평가에 어디서 활용되는지 연결해야 합니다.

#### Chapter 2. 임베딩 `LLM 핵심`

- 중심축: 토큰 ID를 의미 공간의 벡터 표현으로 바꾸는 관점과 검색 연결의 입구를 세웁니다.
- `P6-2.1`: 임베딩을 토큰 번호와 다른 의미 표현으로 이해시키는 역할을 해야 합니다.
- `P6-2.2`: 의미와 거리를 임베딩 공간 비교 문제로 설명해야 합니다.
- `P6-2.3`: 임베딩 학습을 `무엇을 가깝게, 무엇을 멀게 둘 것인가` 기준으로 보충해야 합니다.
- `P6-2.4`: ANN 검색을 `가까운 후보를 충분히 빠르게 좁히는 구조` 기준으로 보충해야 합니다.

### Module 2. LLM 핵심 구조

- 의도: 이 Module은 입력 표현이 실제 생성 계산으로 이어지는 방식을 설명하며, LLM 본체를 이해하는 핵심 구조 축을 닫아야 합니다.

#### Chapter 3. Transformer 구조 복습 `딥러닝 구조`

- 중심축: LLM 계산의 핵심인 attention 기반 Transformer 구조를 다시 읽고 long-context 문제와 연결합니다.
- `P6-3.1`: Transformer를 LLM 관점에서 다시 읽으며 입력 토큰에서 다음 토큰 점수로 가는 구조를 잡아야 합니다.
- `P6-3.2`: attention과 context window가 문맥을 읽는 범위를 어떻게 제한하고 확장하는지 설명해야 합니다.
- `P6-3.3`: 위치 표현과 multi-head attention을 처음 읽는 최소 기준을 보충해야 합니다.
- `P6-3.4`: KV cache가 왜 추론 속도와 연결되는지 보충해야 합니다.
- `P6-3.5`: sparse attention과 long-context를 같은 말처럼 섞지 않고 `연결 수 조절`과 `장문맥 설계`의 다른 층위로 구분하게 해야 합니다.

#### Chapter 4. GPT 계열 `LLM 핵심`

- 중심축: GPT 계열이 생성형 LLM 본류에서 어떤 위치를 차지하는지와 대화형 전환을 함께 설명합니다.
- `P6-4.1`: GPT 계열이 LLM 계보에서 어떤 위치를 차지하는지 설명해야 합니다.
- `P6-4.2`: 대화형 LLM으로의 전환이 Transformer 구조 자체의 변화라기보다 instruction following, RLHF, dialogue format, API 제품화가 결합된 조정층과 사용 경험 문제라는 점을 보여 주어야 합니다.

#### Chapter 5. 다음 토큰 예측과 생성 `LLM 핵심`

- 중심축: 다음 토큰 예측 학습 목표와 실제 생성 반복이 어떻게 이어지는지 이해시킵니다.
- `P6-5.1`: next-token prediction이 무엇을 학습 목표로 삼는지 분명히 해야 합니다.
- `P6-5.2`: 생성 과정이 후보 분포 계산과 출력 선택의 반복이라는 점을 직관적으로 보여 주어야 합니다.

### Module 3. 학습과 조정

- 의도: 이 Module은 같은 LLM 구조가 왜 다른 응답 성격과 사용 경험으로 보이는지, 그리고 어디까지가 모델 조정 문제인지를 이해시키는 전반부의 마무리여야 합니다.

#### Chapter 6. 사전학습 `학습 원리`

- 중심축: 넓은 데이터로 기반 표현을 만드는 사전학습과 스케일 문제를 함께 다룹니다.
- `P6-6.1`: 사전학습이 넓은 데이터로 기반 표현을 만드는 과정이라는 점을 설명해야 합니다.
- `P6-6.2`: 데이터와 스케일이 성능 향상과 비용 증가를 함께 만든다는 점을 정리해야 합니다.

#### Chapter 7. 파인튜닝 `학습 원리`

- 중심축: 기반 모델을 목적에 맞게 조정하는 방식과 비용 절감형 조정 구조를 정리합니다.
- `P6-7.1`: 파인튜닝이 기반 모델을 목적에 맞게 조정하는 과정이라는 점을 잡아야 합니다.
- `P6-7.2`: LoRA 같은 효율적 조정이 왜 필요한지 설명해야 합니다.

#### Chapter 8. 지시 튜닝과 정렬 `LLM 핵심`

- 중심축: 대화형 응답 습관을 어떻게 조정하고 무엇을 안전성 문제로 볼지 기준을 세웁니다.
- `P6-8.1`: 지시 튜닝이 응답 습관을 바꾸는 조정층이라는 점을 설명해야 합니다.
- `P6-8.2`: 정렬 문제를 `잘 따름`과 `허용 가능함`의 차이로 이해시키는 역할을 해야 합니다.
- `P6-8.3`: 프롬프트, 파인튜닝, RAG, 도구 사용을 언제 고를지 실패 원인 기준으로 정리해야 합니다.
- `P6-8.4`: adapter, LoRA, QLoRA를 제약 장면 기준으로 구분하는 보충학습이 필요합니다.
- 검토 메모: `P6-8.3`은 Module 3의 마지막 설명을 넘어서, 뒤의 Module 4~6을 `기술 목록`이 아니라 `무엇을 어디서 먼저 손볼까`라는 선택 지도의 세부 장으로 읽게 만드는 전환점이어야 합니다.
- 검토 메모: `P6-8.4`는 본류를 새로 여는 절이 아니라, `파인튜닝 축을 먼저 고른 뒤` 그 안의 효율적 조정 이름을 다시 구분하는 옆가지 보충 절로 유지하는 편이 현재 흐름에 맞습니다.

### Module 4. 프롬프트와 근거 연결

- 의도: 이 Module은 `LLM 자체를 이해하는 일`에서 `LLM을 실제 답변 구조로 어떻게 보강할 것인가`로 넘어가는 후반부의 첫 관문이어야 합니다.
- 경계: `입력을 어떻게 설계할까`, `프롬프트만으로는 왜 부족한가`, `언제 외부 문서를 근거로 붙여야 하는가`를 다룹니다.
- 바깥 경계: 아직 실제 계산·조회·실행 호출 단계로는 넘어가지 않습니다. 그 전환은 Module 5에서 다룹니다.

#### Chapter 9. 프롬프트 엔지니어링 `LLM 핵심`

- 중심축: 입력 문장을 어떻게 설계해야 하는지와 프롬프트만으로 해결되지 않는 한계를 함께 읽게 합니다.
- `P6-9.1`: 프롬프트 엔지니어링을 입력 설계 문제로 설명해야 합니다.
- `P6-9.2`: 프롬프트의 한계가 모델 지식, 근거 부족, 실행 한계와 연결된다는 점을 보여 주어야 합니다.
- `P6-9.3`: Chain-of-thought, self-consistency, automatic prompt optimization이 프롬프트 층에서 무엇을 더 조정하려는지 구분하는 기준을 보충해야 합니다.

#### Chapter 10. RAG `서비스 구조`

- 중심축: 모델 밖의 문서를 검색해 근거를 붙이는 구조가 왜 필요한지와 실패 지점을 구분합니다.
- `P6-10.1`: RAG가 왜 필요한지와 어떤 부족함을 메우는지 설명해야 합니다.
- `P6-10.2`: 검색 결과와 생성을 결합할 때 검색 실패와 생성 실패를 구분해야 한다는 점을 보여 주어야 합니다.

#### Chapter 11. 벡터 데이터베이스 `서비스 구조`

- 중심축: 임베딩 검색을 실제 서비스 구조로 받쳐 주는 저장·인덱스 계층을 설명합니다.
- `P6-11.1`: 벡터 데이터베이스를 검색 가능한 임베딩 저장 구조로 이해시키는 역할을 해야 합니다.
- `P6-11.2`: 인덱스와 검색 품질이 어떻게 연결되는지 정리해야 합니다.

### Module 5. 실행 구조

- 의도: 이 Module은 `문서를 읽고 답을 만드는 단계`를 넘어, 현재 서비스에서 실제로 조회·계산·실행을 연결하는 구조를 이해시키는 구간이어야 합니다.
- 경계: `문서를 읽고 답하는 것`을 넘어 `외부 기능을 조회·계산·실행하는 구조`를 다룹니다.
- 바깥 경계: 여기서의 핵심은 실행 연결과 다단계 흐름이지, 품질 평가와 운영 종료 판단 자체는 아닙니다. 그 판단은 Module 6에서 본격적으로 다룹니다.

#### Chapter 12. 도구 사용(tool use) `서비스 구조`

- 중심축: 답변 전에 조회, 계산, 실행을 외부 도구에 맡기는 구조와 인터페이스를 다룹니다.
- `P6-12.1`: 도구 사용이 답변 전에 조회, 계산, 실행을 붙이는 구조라는 점을 설명해야 합니다.
- `P6-12.2`: 함수 호출이 모델과 외부 함수 사이의 명시적 인터페이스라는 점을 보여 주어야 합니다.

#### Chapter 13. 에이전트(agent) `서비스 구조`

- 중심축: 한 번의 응답이 아니라 목표를 여러 단계로 나눠 처리하는 실행 루프를 설명합니다.
- `P6-13.1`: 에이전트를 목표를 여러 단계로 나눠 처리하는 실행 흐름으로 설명하고, OS 대체재가 아니라 OS, IDE, 브라우저, CLI 위에서 동작하는 작업 인터페이스 층으로 보수적으로 다뤄야 합니다.
- `P6-13.2`: 계획, 행동, 관찰 루프가 왜 필요한지와 어디서 실패하는지 보여 주어야 합니다.

#### Chapter 14. MCP(Model Context Protocol)와 하네스(harness) `서비스 구조`

- 검토 메모: MCP와 하네스는 본선 앞 진입 Section을 새로 끼우기보다, 각 절 안에서 `왜 여기서 등장하는가`, `어떤 문제 장면에서 먼저 떠올려야 하는가`를 더 또렷하게 보강하는 편이 현재 흐름에 더 잘 맞습니다.
- `P6-14.1`: MCP가 모델과 도구를 공통 형식으로 연결하는 층이라는 점을 설명해야 합니다.
- `P6-14.2`: 하네스가 실행 추적, 재현 실행 정보, 승인 기록을 관리하는 환경이라는 점을 보여 주어야 합니다.

### Module 6. 평가, 운영, 통합 실습

- 의도: 이 Module은 `답을 생성하고 실행했다`에서 끝나지 않고, 그 결과를 어떻게 평가하고 어떤 상태로 기록하며 어떤 운영 판단으로 닫을 것인가를 이해시키는 후반부의 종결 구간이어야 합니다.
- 경계: `무엇이 좋은 답인가`를 평가하는 문제와 `그 답을 실제 서비스 흐름으로 감당할 수 있는가`를 판단하는 문제를 함께 다룹니다.
- 바깥 경계: 여기서는 모델 내부 원리나 개별 도구 연결 자체를 새로 설명하지 않고, 이미 붙인 구조를 어떻게 점검하고 기록으로 남길지에 집중합니다.

#### Chapter 15. LLM 평가 `LLM 핵심`

- 중심축: 답변 품질과 시스템 동작을 함께 평가하는 기준을 자동 평가와 사람 평가로 나눠 정리합니다.
- `P6-15.1`: LLM 평가를 답변 품질과 시스템 동작을 함께 보는 문제로 정리해야 합니다.
- `P6-15.2`: 자동 평가와 사람 평가가 어떤 답을 걸러 내고 어떤 답은 남기는지 구분해야 합니다.
- 검토 메모: `P6-15.2`는 `무엇을 평가할까`의 반복이 아니라, `누가 어떤 평가를 맡을까`를 정리한 뒤 그 판단을 바로 다음 운영 제약과 실패 대응 경로로 넘기는 전환점이어야 합니다.

#### Chapter 16. AI 서비스가 현실에서 만나는 제약 `서비스 구조`

- 중심축: 성능이 좋아도 운영에서 막히는 지연 시간, 비용, 용량, 실패 대응 문제를 다룹니다.
- `P6-16.1`: 지연 시간, 비용, 용량 같은 현실 제약이 평가 통과와 별개라는 점을 설명해야 합니다.
- `P6-16.2`: 운영 중 실패 대응이 어떤 신호와 어떤 조치로 이어지는지 정리해야 합니다.
- 검토 메모: `P6-16.1`은 평가를 통과한 답이 실제 운영 후보로 남을 수 있는가를 다시 가르는 절이어야 하고, `P6-16.2`는 그 후보가 실패했을 때 retry, fallback, stop, approval 중 어디로 갈지 정한 뒤 요청 흐름 기록으로 넘기는 절이어야 합니다.

#### Chapter 17. 작은 생성형 AI 기능을 한 흐름으로 묶기 `프로젝트 실습`

- 중심축: 질문, 근거, 답변, 상태 판단, 기록을 한 요청 흐름으로 묶는 통합 예시를 만듭니다.

- `P6-17.2`: 최소 구현과 회고 포인트가 답변 결과뿐 아니라 상태 기록과 운영 판단까지 포함해야 한다는 점을 정리해야 합니다.
- 검토 메모: `P6-17.1`은 앞 장의 평가·실패 대응 판단을 한 요청 구조 안으로 다시 묶는 절이어야 하고, `P6-17.2`는 그 구조가 실제 요청 실행 기록과 다음 패치 우선순위로 어떻게 남는지 보여 주는 마무리 절이어야 합니다.
