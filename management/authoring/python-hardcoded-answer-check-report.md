## 확정 해당 사례

### 1. P6-16.1 LLM 평가는 왜 자연스러운 답과 품질 기준을 나눠 보는가

- 파일: `docs/parts/part-06/chapter-16/section-01.md`
- 코드 위치: `answers = [`가 시작되는 Python 예제
- Section 중심축: LLM 평가를 자연스러운 답 고르기가 아니라 정확성, 근거성, 형식, 유용성 같은 여러 축으로 나눠 판정하는 일로 설명한다.
- 예제 역할: 환불 정책 질문에 대한 네 답변 후보를 여러 평가 축으로 점검하고 `best_candidate`, `next_fix`를 출력한다.
- 문제 판정: 하드코딩된 답변 후보와 정답 조건이 코드 안에 함께 들어 있다. `source_text`, `required_phrase`, `"14일"`, `"30일"`, `"개봉 제품"`, `"최신 정책 기준"`, `"접수"` 같은 문자열 포함 여부로 correctness, groundedness, format, helpfulness를 판정한다. 독자는 평가 기준이 데이터에서 어떻게 흔들리는지 실험하기보다, 이미 설계된 정답 후보 `answer_a`가 통과하는 과정을 확인하게 된다.
- 왜 학습 효과가 약한가: Section 중심축은 `평가 축을 나누는 기준`인데, 코드는 평가 축의 개념을 탐색하기보다 사람이 심은 문자열 규칙으로 후보 답안을 채점한다. 답이 왜 좋은지 토론하기보다 `어느 문자열이 들어 있으면 맞다`는 확인으로 읽힐 위험이 크다.
- 개선 방향: 여러 답변 후보와 근거 문장을 CSV로 분리하고, 자동 판정 가능한 표면 조건과 사람이 판단해야 할 항목을 나눈다. Python은 축별 통과율, false positive 후보, 근거 문장 불일치 사례처럼 평가 기준이 실패하는 조건을 드러내는 쪽으로 재설계한다.

### 2. P6-16.2 자동 평가와 사람 평가는 어떻게 반복 검사와 맥락 판단을 나누는가

- 파일: `docs/parts/part-06/chapter-16/section-02.md`
- 코드 위치: `outputs = [`가 시작되는 Python 예제
- Section 중심축: 자동 평가는 반복 가능한 검사에 강하고, 사람 평가는 맥락 판단에 필요하므로 둘의 역할을 나눠야 한다는 점을 설명한다.
- 예제 역할: 고객 응답 후보를 자동 평가 gate와 사람 검토 질문으로 나눠 승인, 수정, 탈락 경로를 출력한다.
- 문제 판정: 네 개의 답변 후보와 통과 조건이 모두 코드에 하드코딩되어 있다. 자동 평가는 `"공지"` 포함, 마침표, 길이를 보고, 사람 검토 질문도 `"주문번호"`, `"직접 찾아보세요"`, `"가능"`, `"조건"` 같은 문자열 포함 여부로 정한다. 결과적으로 `answer_d`가 승인 후보가 되도록 설계된 정답 확인형 라우팅에 가깝다.
- 왜 학습 효과가 약한가: Section 중심축은 `자동 검사와 사람 판단의 분업`인데, 코드는 사람 판단이 필요한 맥락을 실제로 남기기보다 사람이 만든 문구 규칙으로 사람 검토 질문까지 자동 생성한다. 자동 평가의 한계가 아니라 자동 규칙표의 통과 여부가 중심으로 보일 수 있다.
- 개선 방향: 자동 평가가 잘 잡는 항목과 놓치는 항목을 대비시키는 입력 묶음을 늘리고, 같은 자동 통과 후보라도 사람 평가에서 갈리는 사례를 별도 해설로 닫는다. Python은 `자동 통과지만 사람 검토 필요`, `자동 탈락이지만 실제로는 수정 가능`, `자동 기준이 놓친 위험` 같은 경계 사례 수를 집계하도록 바꾼다.

## 경계 사례

### 1. P6-12.1 벡터 데이터베이스는 왜 원문과 메타데이터까지 함께 저장하는가

- 파일: `docs/parts/part-06/chapter-12/section-01.md`
- 코드 위치: `query_vectors = [` 안의 `expected_category`, `top1_category_ok`
- Section 중심축: 벡터 데이터베이스를 임베딩, 원문, 메타데이터를 함께 저장하고 질문별 근거 조각을 반환하는 구조로 설명한다.
- 판정: `expected_category`와 `top1_category_ok`는 사람이 넣은 기대 범주와 검색 결과 범주를 대조하므로 정답 확인형 냄새가 있다. 다만 코드가 top-k 후보, 유사도, 원문, 메타데이터, payload를 함께 출력하고, 독자가 query vector와 records를 바꿔 순위와 payload 변화를 볼 수 있으므로 확정 해당으로 보지는 않는다.
- 개선 방향: `expected_category`를 중심 출력에서 낮추고, `top_matches`, `retrieval_payload`, `metadata` 보존 여부와 query vector 변화에 따른 순위 이동을 더 앞세운다. 범주 일치 확인은 보조 inspection으로 남기거나, 여러 애매한 query를 추가해 일치 실패 사례가 실제로 드러나게 한다.

### 2. P6-11.1 RAG는 왜 답변 전에 외부 근거를 붙이는가

- 파일: `docs/parts/part-06/chapter-11/section-01.md`
- 코드 위치: `inspect_question()`의 `memory_mentions_current_signal`, `rag_mentions_current_signal`, `top_doc_is_current`
- Section 중심축: RAG를 답변 전에 외부 근거 문서를 붙여 모델 기억 의존을 줄이는 구조로 설명한다.
- 판정: 질문 CSV의 `current_signal`과 문서 CSV의 `version_status == "current"`를 정답 신호처럼 사용해 memory 답과 RAG 답을 검사한다. 하지만 코드는 실제 TF-IDF 검색, 문서 순위, 유사도, 근거 문서 제목, RAG 답변 변화를 함께 보여 주며, 중심은 `검색 전후 근거 연결 차이`에 있다. 따라서 확정 해당이 아니라 경계 사례로 둔다.
- 개선 방향: `current_signal` 포함 여부를 유일한 성공 기준처럼 보이지 않게 하고, 검색된 문서의 버전·출처·유사도와 답변 근거 연결을 함께 해석하도록 출력 이름과 해설을 조정한다. 가능하면 최신 신호가 없는 질문이나 잘못된 근거가 top-1으로 올라오는 실패 사례를 추가한다.

## 검토 후 제외한 대표 유형

다음 유형은 하드코딩된 값이나 label이 있어도 이번 리포트의 확정 해당 사례로 보지 않았다.

- Part 2의 `label_map`, `label_to_id`, 샘플 딕셔너리 예제: 정답 확인이 아니라 딕셔너리 조회, 리스트 변환, 객체 속성 접근 같은 문법 설명이 중심이다.
- Part 3의 라벨 품질 점검 예제: label이 들어 있지만 샘플 단위, 중복 라벨, 검토 편향, 집계 단위 변화가 중심이다.
- Part 4의 분류·회귀·군집·트리·SVM 예제: 지도학습 label과 metric 계산에 쓰이며, 임계값, 모델 설정, 거리, margin, residual 변화가 관찰 대상이다.
- Part 5의 손실·gradient·optimizer·표현 변화 예제: 정답값이나 목표값이 있어도 계산 경로와 파라미터 변화가 중심이다.
- P6-9.1 지시 튜닝 예제: `base_ok`, `tuned_ok`를 계산하지만 CSV의 형식 신호와 요청 유형별 충족률 차이를 집계하는 구조이며, 정답 하나를 맞히는 코드가 아니다.
- P6-11.2 RAG 실패 분해 예제: 과장 표현과 무관 문서 누출을 문자열 규칙으로 잡지만, 검색 실패와 생성 실패를 분리하는 실패 유형 실험으로 설계되어 있다.
- P6-13.1 도구 사용 예제: 고정된 tool result가 있지만 핵심은 도구 호출 필요 여부와 결과 반영 여부를 구분하는 흐름이다.
- P6-20.2 이해 중심 NLP 태스크 예제: keyword label 규칙이 있지만 CSV 입력, `relation_threshold`, 분류·문장쌍·랭킹 출력 차이가 중심이다.
