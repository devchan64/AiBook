# Part 6 원고 대조 리포트

> 작성일: 2026-07-30
> 범위: `management/authoring/part-06-open-checklist.md`와 Part 6 한국어 원고

## 요약 판단

Part 6은 생성형 AI 산출물에서 시작해 LLM 대표 경로, 입력 표현, 다음 후보 생성, 학습과 조정, RAG, 도구 실행, 평가와 운영, 배경 비교로 이어지는 체크리스트 중심선을 대체로 잘 유지한다. 토큰, token ID, 임베딩, Transformer, GPT, next-token prediction을 같은 층위로 섞지 않으려는 장치도 확인된다.

수정 후보는 구조 결손보다 긴 서비스 구조 Section의 반복 역할 확인과 제품·API 문서 최신성 점검이다. 특히 P6-13.1, P6-15.2는 길지만 중심 질문은 유지된다. 사례와 실행 절차를 압축하면 RAG, tool use, agent, MCP, harness의 차이를 따라가기 어려워질 수 있으므로 실제 중복만 구분한다.

## 수정 필요 항목

### 1. P6-13.1의 도구 사용 설명 반복 역할 확인

- 대상: `docs/parts/part-06/chapter-13/section-01.md:12`, `:30`, `:683`
- 확인된 원고 근거: 도입부, 구분 표, 마무리에서 RAG와 tool use의 차이, 조회·계산·실행의 구분, 책임 경계를 여러 번 반복한다.
- 수정 필요 이유: 체크리스트는 P6-13을 제품 기능 소개가 아니라 모델 밖 실행을 판단하는 구조로 유지하라고 한다. 현재 방향은 맞지만 710줄 규모라 같은 구분이 반복되면 후속 P6-13.2, P6-14와 경계가 흐려질 수 있다.
- 수정 방향: `문서 근거`, `조회값`, `계산 결과`, `외부 세계 변경`의 차이를 보여 주는 표와 예제는 유지한다. 함수 이름·인자 구조는 P6-13.2로 넘긴다는 경계를 더 분명히 하고, 같은 결론만 반복하는 문장만 제한적으로 줄인다.

### 2. P6-15.2의 하네스 설명 중복 역할 확인

- 대상: `docs/parts/part-06/chapter-15/section-02.md:10`, `:29`, `:41`
- 확인된 원고 근거: 하네스를 실행 추적, 로그, 평가 입력, 재현 실행 정보, 승인 기록으로 설명하는 표와 문단이 반복된다.
- 수정 필요 이유: 체크리스트는 MCP와 하네스를 연결 형식과 재현 가능한 실행 기록 문제로 나누라고 한다. 현재 구분은 좋지만, 반복 설명이 길어지면 P6-16 평가와 P6-17 운영 제약을 앞당겨 설명하는 느낌이 생길 수 있다.
- 수정 방향: MCP와 하네스의 차이 표, trace/log/eval/replay 절차 설명은 유지한다. 평가 기준 자체는 P6-16, 운영 통제는 P6-17로 넘긴다는 경계를 확인하고, 같은 문장 기능만 반복되는 부분만 줄인다.

### 3. 제품·API 문서 출처 최신성 점검

- 대상 예:
  - `docs/parts/part-06/chapter-13/section-01.md:708`부터 `:710`
  - P6-10, P6-13, P6-15 이후의 프롬프트, tool use, function calling, MCP, 평가·운영 관련 제품 문서 사용 구간
- 확인된 원고 근거: OpenAI API Docs 등 제품 문서를 출처로 사용한다.
- 수정 필요 이유: 제품 기능, API 문서, 도구 사용 방식은 변동 가능성이 높다. 원고는 특정 API 사용법보다 구조 판단을 설명하지만, 배포 전 확인 날짜와 문서 상태를 갱신해야 한다.
- 수정 방향: 본문 구조 수정과 별도로, 배포 전 제품 문서 출처를 최신성 중심으로 재확인한다. 특정 API 세부가 바뀌어도 본문은 `모델 밖 실행 구조`, `검토 가능한 기록`, `운영 제약` 중심으로 유지한다.

## 유지 확인 항목

- P6-1부터 P6-3은 생성형 AI를 LLM 전체와 동일시하지 않고 LLM을 대표 경로로 둔다.
- P6-4부터 P6-6은 Part 5의 Transformer 구조를 반복하기보다 LLM 안에서 다음 후보 점수로 이어지는 흐름을 잡는다.
- P6-10은 프롬프트로 풀 문제와 RAG·도구 사용으로 넘길 문제를 분리한다.
- P6-11과 P6-12는 RAG와 벡터 데이터베이스를 합치지 않는다.
- P6-19와 P6-20은 발전사와 BERT 계열을 본류 뒤의 배경 지도와 비교 축으로 둔다.

## 검토 의견과 대안

### A안. P6-13.1과 P6-15.2의 반복 역할을 표시

- 의견: 두 Section 모두 방향은 맞지만 길고 반복이 있다. 먼저 반복 문단이 도입, 구분, 예제, 회수 중 어떤 역할을 맡는지 표시한다.
- 장점: 서비스 구조 구간의 독해 부담을 줄이면서도 사례와 절차 설명을 보존할 수 있다.
- 단점: 실제 원고 길이는 크게 줄지 않을 수 있다.
- 채택 기준: 독자용 흐름 개선과 초심자 보강을 함께 유지하려면 선택한다.

### B안. 실제 중복만 제한적으로 정리

- 의견: 반복처럼 보이는 문단이 실제로는 도입, 구분, 마무리 회수 역할을 나누고 있을 수 있다. 역할 표시 뒤 같은 결론만 반복하는 문장만 줄인다.
- 장점: 초심자 보강을 유지한다.
- 단점: 길이 문제는 그대로 남는다.
- 채택 기준: 역할이 없는 중복이 실제로 확인될 때만 선택한다.

### C안. 제품·API 출처 점검을 별도 배포 전 작업으로 분리

- 의견: OpenAI API Docs 같은 제품 문서는 최신성 확인이 필요하지만, 원고 구조 수정과는 성격이 다르다. 같은 작업에 묶으면 사례·절차 설명 점검이 늦어진다.
- 장점: 작업 범위가 명확해진다.
- 단점: 출처 최신성 문제가 당장 해결되지는 않는다.
- 채택 기준: 배포 전 점검 체크리스트에서 별도 항목으로 관리한다.

### 권장안

A안을 우선하되, 삭제 전 각 반복 문단이 맡는 역할을 표시해 보고 실제 중복만 줄인다. C안은 별도 배포 전 출처 점검으로 분리한다. 사례와 실행 절차를 뒤로 미루거나 과도하게 압축하지 않는다.

## 다음 작업 순서 제안

1. P6-13.1과 P6-15.2의 반복 문단이 맡는 역할을 먼저 표시한다.
2. 제품·API 출처는 배포 직전에 확인 날짜와 문서 상태를 갱신한다.
3. 구조나 제목이 바뀌면 다국어 원고를 Section ID 기준으로 동기화한다.
