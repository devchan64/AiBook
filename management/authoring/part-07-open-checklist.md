# Part 7 체크포인트 노트

이 문서는 Part 7을 목차 순서대로 읽을 때 각 Section이 담아야 할 중심 주제를 개괄식으로 정리한 체크포인트 노트입니다.

## 사용 원칙

- 이 노트는 `docs/table-of-contents.md`를 기준으로 Part 7의 시작/마무리 페이지, Chapter, Section을 같은 순서로 훑기 위한 개요 문서입니다.
- 이 노트는 작업 상태표가 아니라 Part 7 원고가 유지해야 할 중심선 문서입니다.
- 순차 점검 기록, 품질 상태 메모, 구조 재배치 로그는 이 문서에서 운영하지 않습니다.
- 체크포인트는 `실행 -> 비교 -> 실패 해석 -> 운영 회고` 흐름을 실제 실습 단위로 붙잡는 데 목적을 둡니다.
- `학습 관점 누락 점검`은 Part 원고가 잃기 쉬운 설명 흐름을 점검하고, `목차 기준 체크포인트`는 Part 원고가 유지해야 할 구조 흐름을 관리합니다.
- Section ID 기반 자동 대조는 문서 전체가 아니라 `목차 기준 체크포인트` 이후 구간을 기준으로 삼습니다.
- 체크포인트 문장은 집필 기준이며, 본문에는 `오픈체크리스트`, `중심축` 같은 관리 표현으로 노출하지 않습니다. 본문 보강은 문제 장면, 개념 대비, 독자용 판단 문장으로 풀어 씁니다.

## 학습 관점 누락 점검

- 각 Chapter를 볼 때 템플릿이나 결과물 목록보다 `무엇을 실제로 실행하고 무엇을 비교하는가`가 먼저 보이는지 확인합니다.
- 각 Section를 볼 때 `설명 -> 코드 실행 -> 출력 비교 -> 해석 -> 짧은 회고` 리듬이 실제로 보이는지 확인합니다.
- 각 Section를 볼 때 `기준선`, `중간 산출물`, `최종 출력`, `실패 사례`, `다음 수정` 가운데 빠진 축이 없는지 확인합니다.
- 각 Section를 볼 때 코드 블록이 단순 예시가 아니라, 입력을 바꾸면 출력과 해석이 함께 달라지는 실습으로 기능하는지 확인합니다.
- 실습 예제는 너무 작은 장난감 입력에 머물지 않고, 실제로 해석 차이가 드러나는 비교 장면을 포함하는지 확인합니다.
- 각 Chapter에는 가능하면 최소 1개의 도식, 그래프, 또는 비교표가 있어 `입력 -> 처리 -> 출력 -> 검토` 흐름을 눈으로 다시 읽을 수 있어야 합니다.
- 회고 문장은 감상문이 아니라 `무엇을 바꾸면 다음 결과가 달라질까`로 이어지는지 확인합니다.
- 운영 실습 장에서는 `동작 확인`, `장애 재현`, `우선순위 분류`, `재발 방지`가 함께 보이는지 확인합니다.
- Part 7에서는 특히 `실행 없는 요약`, `비교 없는 결과 나열`, `실패 해석 없는 회고`가 빠지지 않는지 다시 봅니다.
- 동작 단위 센서 사례처럼 반복 사용 가능한 공개형 합성 데이터는 Part 7의 연습 Section 후보로 볼 수 있습니다. 다만 도메인 설명을 새로 길게 열기보다 `입력 단위`, `baseline`, `비교 조건`, `실패 해석`, `운영 회고`를 바꾸는 실습 재료로만 사용합니다.

## Section 경계 정리

- Part 7 전체 경계는 새 이론을 추가하는 Part가 아니라, Part 1~6에서 배운 개념을 현재 널리 쓰이는 모델 실습으로 다시 회수하는 데 둡니다. 독자는 Stable Diffusion, 로컬 LLM, 비전 모델, 음성 모델, RAG, agent 같은 실제 모델군을 직접 실행하면서 `질문 -> 입력 -> baseline -> 비교 -> 실패 해석 -> 근거/실행 기록 -> 운영 회고 -> 재현 패키지`를 남겨야 합니다.
- Part 7의 중심은 `유행 모델 소개`가 아니라 `유행 모델을 실습 재료로 삼아 앞 Part의 개념을 다시 확인하는 것`입니다. 모델명과 저장소 목록은 목적이 아니라 실습 입구이며, 각 실습은 Part 1~6의 어떤 개념을 다시 확인하는지 분명히 연결해야 합니다.
- 각 Section은 설명 문서가 아니라 실습 단위여야 합니다. 최소한 입력 또는 조건을 바꾸고, 출력 차이를 비교하며, 그 차이를 다음 수정이나 회고 문장으로 연결해야 합니다.
- P7-1.1~P7-1.3은 프로젝트 질문, 샘플 단위, 기준선 구간을 여는 구간입니다. 데이터셋 소개나 문제 배경 설명으로 길어지지 않고, 무엇을 한 건으로 볼지와 무엇을 baseline으로 둘지가 실험 결론을 어떻게 바꾸는지에 집중합니다.
- P7-2.1~P7-2.3은 전통 머신러닝 비교 실험을 닫습니다. 점수, 오류 사례, 전처리 효과, 데이터 경계 부족을 한 평가 셋에서 비교하게 하고, 알고리즘 설명이나 Part 4 이론 반복으로 돌아가지 않습니다.
- P7-3.1~P7-3.3은 입력 구조가 프로젝트를 어떻게 바꾸는지 확인하는 구간입니다. 표, 이미지, 시퀀스, attention 계열 비교는 모델 이름 나열이 아니라 준비 코드, 샘플 확인, 실패 신호, 표현 축소의 손실을 비교하는 실습으로 유지합니다.
- P7-4.1~P7-4.4는 학습 결과와 표현 문제를 다시 읽는 구간입니다. loss, metric, 오류 샘플, coverage, OOV, 표현 정규화, shape token을 통해 구조 문제, 데이터 문제, baseline 문제를 분리하고, 딥러닝 이론이나 토큰화 일반론으로 확장하지 않습니다.
- P7-4.5~P7-4.7은 현 목차에서는 Stable Diffusion과 LoRA 조합을 생성형 이미지 프로젝트의 비교 실습으로 다룹니다. 다만 Part 7 재구성 시에는 이 묶음을 Chapter 4 안에 계속 두기보다 신규 Chapter `생성형 이미지 모델 실습`으로 분리하는 후보로 봅니다. diffusers 코드 실습, ComfyUI workflow 실습, kohya_ss 직접 LoRA 학습 확장을 각각 독립 Section으로 나누되, base model, LoRA adapter, adapter weight, prompt, seed, output review를 분리해 기록하게 하고 이미지 제작 팁 모음으로 확장하지 않습니다. 외부 자료는 스타와 포크가 많은 대표 저장소를 먼저 검토하되, 최종 실습 구성은 초심자가 기록 가능한 산출물을 남길 수 있는지로 판단합니다.
- P7-5.1~P7-5.3은 RAG의 검색 후보, 선택 근거, 최종 답변, 검색 실패, 근거 부족, 답변 과장 위험을 한 흐름으로 기록하게 합니다. RAG 개념 설명은 Part 6에서 닫았으므로, Part 7에서는 문서 집합과 질문을 바꾸었을 때 상태가 어떻게 갈리는지 실습에 집중합니다.
- P7-5.4와 P7-5.5는 검색 품질을 더 정밀하게 확인하는 실습입니다. ANN 인덱스 설정, 후보 수, 지연 시간, top-k 포함률, 버전 필터, 검색 평가셋을 다루되, 벡터 DB 제품 사용법이나 대규모 검색 시스템 설계로 확장하지 않습니다.
- P7-6.1~P7-6.3은 agent 실행을 계획, 도구 호출, 승인 경계, blocked 상태, 권한, 로그, 다음 행동으로 나누어 기록하는 구간입니다. agent를 자동화 만능 도구로 소개하지 않고, 어디서 멈춰야 하는지와 왜 사람 승인으로 넘겨야 하는지를 실습 결과로 남깁니다.
- P7-7.1~P7-7.5는 운영과 반복 개선을 닫는 구간입니다. 배포 확인, 상태 점검, 장애 기록, 운영 신호 분류, 경고 등급, 재현 가능한 프로젝트 패키지를 다루되, 장기 운영 체계 전체나 조직 프로세스 매뉴얼로 확장하지 않습니다.
- P7-7.5는 Part 7 전체의 마감 실습입니다. 질문, 입력, 코드, 환경, 실행 명령, 결과, 한계, 다음 조치를 묶어 다른 사람이 같은 실행을 다시 확인할 수 있는지 점검하는 데 집중하고, 배포 자동화나 협업 플랫폼 사용법으로 넓히지 않습니다.
- Part 7의 합성 데이터와 예제 코드는 도메인 설명을 위한 장치가 아니라 비교 조건을 바꾸기 위한 실습 재료입니다. 새 데이터셋을 추가할 때도 개인정보 없는 공개형 또는 자체 합성 데이터로 유지하고, 데이터 자체의 서사를 본문보다 크게 만들지 않습니다.
- Part 7의 회고 문장은 감상문이 아니라 `사실 -> 해석 -> 다음 질문` 또는 `실패 범주 -> 다음 조치` 형식으로 남아야 합니다. 실패를 숨기거나 성공 결과만 남기는 Section은 경계 밖으로 본다.
- Part 7은 Part 4~6의 재진입 색인 역할도 맡습니다. 비교 실험이 막히면 P7-2.3, 입력 표현 선택이 막히면 P7-3.3, 표현 정보 손실이 막히면 P7-4.4, RAG 검색 품질 점검이 막히면 P7-5.5, 운영 등급 판단이 막히면 P7-7.4, 실행 인수인계가 막히면 P7-7.5로 돌아갈 수 있게 연결을 유지합니다.
- 다국어 확장 시에도 Section ID를 기준 단위로 유지합니다. baseline, metric, loss, coverage, RAG, ANN, agent, blocked, deployment, incident review, reproducibility는 언어별 표현이 프로젝트 기록의 같은 축을 가리키도록 맞춥니다.

## Part 7 재구성 검토 기준

- Part 7 재구성은 기존 원고를 폐기하는 작업이 아니라, 기존 Chapter의 `기록 방법`, `비교 방법`, `실패 해석 방법`을 현재 널리 쓰이는 모델 실습 흐름에 맞게 다시 배열하는 작업입니다.
- 기존 Chapter 1과 Chapter 2는 유지 후보입니다. 프로젝트 질문, 입력 단위, baseline, 전통 머신러닝 비교는 뒤쪽 유행 모델 실습을 읽기 위한 기본 기록 형식이기 때문입니다.
- 기존 Chapter 3과 Chapter 4의 앞부분은 `입력 구조와 학습 결과 해석`의 공통 기반으로 유지하되, Stable Diffusion/LoRA 묶음은 신규 생성형 이미지 Chapter로 분리하는 방향을 우선 검토합니다.
- 기존 Chapter 5는 RAG 실습 Chapter로 유지하되, RAGAS, DeepEval 같은 평가 도구를 넣을 경우 `RAG 구축`과 `RAG 평가`를 한 Chapter 안에 둘지 별도 Chapter로 분리할지 다시 판단합니다.
- 기존 Chapter 6과 Chapter 7은 agent 실행, 승인 정책, 운영 관측, 재현 패키지로 이어지는 후반부 흐름으로 묶어 정리합니다. Langfuse, OpenLLMetry 같은 관측성 도구는 Chapter 7 보강 후보로 두되, 도구 사용법 문서로 확장하지 않습니다.
- 신규 Chapter는 모델군 하나를 소개하는 목적으로 만들지 않습니다. 각 신규 Chapter는 `직접 실행할 모델군`, `바꿀 조건`, `비교할 출력`, `Part 1~6에서 회수할 개념`, `실패를 다음 질문으로 넘기는 기록 양식`을 함께 가져야 합니다.

## 목차 기준 체크포인트

- `P7-index`: Part 7이 기록 문서 작성 Part가 아니라 Part 1~6의 개념을 현재 널리 쓰이는 모델 실습으로 다시 확인하는 프로젝트 Part라는 점을 분명히 해야 합니다.
- `P7-index`: `질문과 입력 정의 -> baseline 비교 -> 로컬 LLM/비전/이미지/음성 모델 실행 -> RAG와 agent 실행 기록 -> 운영 회고 -> 재현 패키지` 흐름이 시작 페이지에서 바로 보여야 합니다.
- `P7-index`: `Part 1~6을 어떤 모델 실습에서 다시 확인하는가`, `실습 기록의 최소 절차`처럼 독자가 현재 막힌 위치를 다시 연결할 기준이 남아 있어야 합니다.
- Part 흐름: Module 1부터 Module 4까지는 `질문과 입력 정의`, `비교 기준`, `실행`, `실패 해석`, `다음 수정`이 같은 실습 리듬으로 유지되어야 합니다.
- Part 흐름: Module 1과 Module 2 사이는 `점수 비교 중심 회고`에서 `구조와 입력 차이 해석`으로 중심이 바뀌는 전환이 분명해야 합니다.
- Part 흐름: Module 3과 Module 4는 `RAG 실패`, `agent 승인 경계`, `운영 로그 판단`, `배포 이후 조치`를 한 운영 기록 흐름으로 묶어야 합니다.
- `P7-summary`: Part 4, Part 5, Part 6의 재진입 경로를 바로 찾게 해야 합니다.

### Module 1. Part 4 실습: 질문, baseline, 비교 실험

#### Chapter 1. 분석 시작과 기준선 설계

- 중심축: 프로젝트 질문을 샘플 단위와 기준선 구간으로 다시 정의해 비교 실험의 출발점을 만듭니다.
- `P7-1.1`: 프로젝트 질문을 데이터 한 행, 샘플 한 건, 기준선 구간 관점으로 다시 정의하게 해야 합니다.
- `P7-1.2`: baseline이 어떤 비교 기준을 만들고 개선 판단을 어떻게 가르는지 보여 주어야 합니다.
- `P7-1.3`: cutoff와 샘플 단위를 바꾸면 회고 우선순위가 달라진다는 점을 직접 비교하게 해야 합니다.
- 동작 단위 사례 후보: `P7-1.3`에서 기준선 경계일, 최근 구간 크기, 동작 단위 묶음을 바꾸며 결론 문장이 어떻게 달라지는지 비교할 수 있습니다.

#### Chapter 2. 전통 머신러닝 비교와 개선

- 중심축: 점수, 오류 사례, 다음 수정 행동을 한 회고 흐름으로 연결합니다.
- `P7-2.1`: 점수와 오류 사례를 함께 읽어야 결과 해석이 닫힌다는 점을 보여 주어야 합니다.
- `P7-2.2`: 회고가 문장 작성으로 끝나는 것이 아니라 다음 실행 수정으로 이어져야 한다는 점을 설명해야 합니다.
- `P7-2.3`: 전처리로 해결되는 실패와 데이터 경계가 비어 있어 남는 실패를 구분하게 해야 합니다.
- 동작 단위 사례 후보: `P7-2.3`에서 원시 값 비교, 구간 평균, 정규화, 기준선 비교를 같은 평가 셋에 놓고 어떤 실패가 줄어드는지 읽게 할 수 있습니다.

### Module 2. Part 5 실습: 입력 구조, 학습 곡선, 오류 해석

#### Chapter 3. 입력 구조와 모델 구조 선택

- 중심축: 입력 구조 차이가 모델 선택, 준비 코드, 실패 신호를 어떻게 바꾸는지 비교합니다.
- `P7-3.1`: 입력 구조 차이가 준비 코드, 해석 방식, 실패 신호를 어떻게 바꾸는지 보여 주어야 합니다.
- `P7-3.2`: CNN, 순차 모델, attention 계열을 이름이 아니라 `언제 무엇이 깨지는가` 기준으로 비교하게 해야 합니다.
- `P7-3.3`: 같은 입력을 실제 분류기에 넣고 표현 축소가 정확도, 확신, 추가 검토 샘플을 어떻게 바꾸는지 비교하게 해야 합니다.

#### Chapter 4. 학습 결과와 표현 점검

- 중심축: 학습 곡선과 실패 사례를 읽어 구조 문제, 데이터 문제, baseline 문제를 구분하게 합니다.
- `P7-4.1`: loss와 metric을 실제 학습 곡선과 함께 읽게 해야 합니다.
- `P7-4.2`: 실패를 구조 문제, 데이터 문제, baseline 문제로 나누는 판단 절차를 설명해야 합니다.
- `P7-4.3`: 표현 정규화나 토큰화 규칙 변경이 coverage, 예측, 회고 우선순위를 어떻게 바꾸는지 직접 비교하게 해야 합니다.
- `P7-4.4`: 같은 평균을 가진 동작도 shape token을 붙이면 다른 패턴으로 갈라진다는 점을 직접 비교하게 해야 합니다.
- `P7-4.5`: diffusers로 Stable Diffusion base 모델에 LoRA adapter를 얹고 adapter weight를 바꾸며, 생성 결과 차이를 재현 가능한 코드형 비교 기록으로 남기게 해야 합니다.
- `P7-4.6`: ComfyUI workflow에서 LoRA, ControlNet, IP-Adapter의 역할을 분리해 보고, 여러 모델의 제어 신호가 충돌하는 지점을 기록하게 해야 합니다. Web UI, ControlNet 원 저장소, Web UI ControlNet 확장은 인기와 생태계 규모를 보는 비교 후보로 두되, 중심 실습은 workflow 기록이 가능한 ComfyUI로 유지합니다.
- `P7-4.7`: kohya_ss로 직접 LoRA 학습을 확장하되, 이미지셋, caption 규칙, 반복 횟수, sample prompt, 실패 신호를 다음 데이터셋 수정으로 연결하게 해야 합니다.
- 동작 단위 사례 후보: `P7-4.4`에서 평균, shape token, 정보 손실을 비교하는 독립 연습을 구성할 수 있습니다.

### Module 3. Part 6 실습: RAG, agent, 실행 기록

#### Chapter 5. RAG 근거 검증

- 중심축: 검색 후보, 선택 근거, 답변 결과를 한 흐름으로 읽으며 RAG 실패 지점을 구분합니다.
- `P7-5.1`: 검색 후보, 선택 근거, 최종 답변이 어떻게 연결되는지 실제 문서 집합으로 보여 주어야 합니다.
- `P7-5.2`: 검색 실패와 답변 실패를 서로 다른 실패 사례로 구분하게 해야 합니다.
- `P7-5.3`: 질문 문구와 문서 범위를 바꿨을 때 `근거 기반 답변`, `근거 부족`, `답변 과장 위험` 상태가 어떻게 갈리는지 직접 비교하게 해야 합니다.
- `P7-5.4`: ANN 인덱스 설정, 후보 수, 지연 시간, top-k 포함률, 버전 필터가 RAG 근거 품질을 어떻게 바꾸는지 기록하게 해야 합니다.
- `P7-5.5`: 검색 평가셋으로 검색 점수와 답변 가능 상태를 분리하고, mismatch를 다음 검색 보강 질문으로 바꾸게 해야 합니다.

#### Chapter 6. agent 실행과 승인 정책

- 중심축: 도구 호출, 승인 경계, blocked 상태, 로그 해석을 운영 판단 관점에서 읽게 합니다.
- `P7-6.1`: 도구 호출 흐름에서 승인 필요 지점과 blocked 상태가 어디서 생기는지 보여 주어야 합니다.
- `P7-6.2`: 권한, 로그, 다음 행동이 왜 운영 판단 기준이 되는지 실패 로그와 함께 설명해야 합니다.
- `P7-6.3`: 같은 실행 계획을 자동 진행 가능 단계와 즉시 보류 단계로 나누고, 더 안전한 다음 행동 순서를 직접 써 보게 해야 합니다.

### Module 4. 통합 운영 실습: 배포, 점검, 회고

#### Chapter 7. 배포와 운영 회고

- 중심축: 공개 상태 점검과 운영 신호 분류를 통해 배포 이후 회고 구조를 실제로 묶습니다.
- `P7-7.1`: 빌드 성공만이 아니라 공개 상태, 핵심 동작, 점검 루틴까지 함께 확인하게 해야 합니다.
- `P7-7.2`: 운영 회고가 장애 기록 나열이 아니라 우선순위와 재발 방지 판단으로 이어져야 한다는 점을 설명해야 합니다.
- `P7-7.3`: 운영 신호를 `즉시 수정`, `재현 확인`, `다음 반복 개선`으로 분류하게 해야 합니다.
- `P7-7.4`: 표본 수, 반복성, 최근성을 함께 읽어 `watch`, `review`, `action` 경고 등급을 설계하게 해야 합니다.
- `P7-7.5`: 질문, 입력, 코드, 환경, 실행 명령, 결과, 한계, 다음 조치를 묶어 재현 가능한 프로젝트 패키지로 닫아야 합니다.
- 동작 단위 사례 후보: `P7-7.4`에서 false alarm, 반복성 부족, 기준선 drift 신호를 경고 등급 설계 연습으로 구성할 수 있습니다.

- `P7-summary`: Part 7이 작은 산출물 나열이 아니라 실행, 비교, 실패 해석, 운영 회고를 묶는 마무리라는 점을 다시 정리해야 합니다.
- `P7-summary`: `다음 실행으로 이어지는 최소 절차`와 대표 Section 연결이 남아 있어, 독자가 실제 프로젝트를 다시 시작할 때 어떤 절을 재진입 기준으로 써야 하는지 바로 찾을 수 있어야 합니다.
