# 초심자 설명·예시 보강 기준

이 문서는 각 Part를 검토할 때 초심자용 설명과 예시를 어떻게 보강할지 판단하는 기준을 정리합니다. 목표는 모든 Section을 길게 만드는 것이 아니라, `현재 Section 안에서 보강할지`, `보충학습으로 분리할지`를 일관되게 판단하는 것입니다.

## 초심자 기준

이 저장소에서 초심자는 다음 조건을 우선 가정합니다.

- 대학 학사 교육을 받지 않았을 수 있습니다.
- 대학 수준의 미적분, 선형대수, 확률통계, 자료구조, 운영체제, 네트워크를 배우지 않았을 수 있습니다.
- Python, 터미널, 패키지 설치, Git, 노트북 환경에 익숙하지 않을 수 있습니다.
- AI 도구 사용 경험은 있을 수 있지만, 그 경험이 표준 용어와 연결되어 있지 않을 수 있습니다.

따라서 초심자용 보강은 `수준을 낮추는 일`이 아니라, 다음 공백을 메우는 일로 봅니다.

- 선행 개념 공백
- 용어 공백
- 실행 환경 공백
- 예시 해석 공백
- 왜 필요한지에 대한 맥락 공백

## 판단 원칙

초심자 보강은 다음 두 방법 중 하나로만 선택합니다.

1. 현재 Section에 설명·예시를 추가한다.
2. 별도 `보충학습` Section으로 분리한다.

새 Module이나 새 Chapter를 임의로 늘리는 것이 기본 선택지는 아닙니다.

## 현재 Section에 추가하는 경우

다음 조건이면 현재 Section 안에서 보강합니다.

- 그 설명이 현재 Section의 중심 질문에 직접 답합니다.
- 그 예시가 지금 배우는 개념을 이해하는 데 바로 필요합니다.
- 1~3개의 짧은 예시, 작은 표, 간단한 도식으로 충분합니다.
- 뒤 Section에서 다시 길게 다루지 않을 보조 설명입니다.
- 초심자가 지금 멈추는 이유가 `개념의 핵심을 못 알아듣는 것`이지, 선행 과목 전체를 모르는 것은 아닙니다.

예시:

- Part 3의 분류기 Section에서 `입력`, `라벨`, `예측`을 4행짜리 표로 한 번 더 보여 주기
- Part 4의 역전파 Section에서 `손실이 줄어드는 방향`을 한 문단과 작은 도식으로 다시 설명하기
- Part 5의 프롬프트 Section에서 `지시`, `맥락`, `예시`를 한 요청 사례로 다시 묶어 주기

## 보충학습으로 분리하는 경우

다음 조건이면 보충학습 Section으로 분리합니다.

- 현재 Section의 중심 질문에서 벗어나지만, 초심자에게 반복적으로 막히는 선행 개념입니다.
- 설명을 붙이기 시작하면 대학 기초 과목 한 단원을 다시 써야 합니다.
- 운영체제별 절차, 설치, 문법, 수학 표기, 자료구조처럼 재사용 범위가 넓습니다.
- 여러 Chapter에서 반복 참조될 가능성이 큽니다.
- 본문 흐름을 유지하려면 지금은 짧게 연결만 하고, 별도 문서에서 자세히 다루는 편이 낫습니다.

예시:

- Part 2의 터미널 사용법, Python 설치, 클래스와 객체
- Part 2의 그래디언트, 편미분, 경사하강법 보강
- 알고리즘 본문이나 모델 설명 본문에서 직접 다루기 어려운 수학적 전개나 라이브러리 세팅 절차

## 분리 판단 체크리스트

초심자 보강이 필요하다고 느껴질 때는 다음 순서로 판단합니다.

1. 지금 독자가 막히는 이유가 현재 개념의 핵심 때문인가, 선행 지식 부재 때문인가?
2. 이 설명이 현재 Section의 범위를 흐리지 않고 들어갈 수 있는가?
3. 작은 예시 하나로 해결되는가, 아니면 별도 학습 흐름이 필요한가?
4. 뒤 Chapter에서도 다시 같은 보강이 필요할 가능성이 높은가?
5. 지금 본문에 넣으면 핵심 설명보다 보조 설명이 더 길어지는가?

판단 결과는 다음처럼 정리합니다.

- `핵심 이해에 직접 필요`하면 현재 Section에 추가
- `선행 지식 복구가 목적`이면 보충학습으로 분리

## Part별 기본 기준

### Part 1. AI 개론과 지형도

- 기본 선택: 현재 Section 보강
- 이유: Part 1도 초심자 기준을 유지해야 하므로, 큰 지도를 잡는 설명 안에서도 용어 정의와 흐름 설명에 바로 읽히는 예시가 필요합니다.
- 추가 방식: 짧은 역사 맥락, 용어 해설, 생활/업무 예시, 비교 표, 간단한 도식
- 보충학습 분리 조건: 수학·법률·설치 절차처럼 개론 흐름을 크게 벗어나는 경우

### Part 2. 기초 복구

- 기본 선택: 현재 Section 보강 + 필요시 보충학습 적극 분리
- 이유: Part 2도 초심자 기준을 유지하되, 선행 지식 복구가 목적이므로 초심자가 실제로 막히는 기초를 따로 묶어 두는 가치가 큽니다.
- 추가 방식: 표기 해설, 작은 수식 예시, Python 실행 결과, OS/도구 차이 설명
- 보충학습 분리 조건: 운영체제별 절차, 설치, 클래스/객체, 미분·그래디언트처럼 재사용 범위가 넓은 경우

### Part 3. 머신러닝

- 기본 선택: 현재 Section 보강
- 이유: 머신러닝은 새 용어와 절차가 많으므로, 알고리즘 Section 내부에 바로 읽히는 예시와 해석을 두는 것이 우선입니다.
- 추가 방식: 입력-라벨-예측 표, 작은 장난감 데이터, 출력 결과 해석, 업무 예시, 오해 방지 문단
- 보충학습 분리 조건: 현재 알고리즘의 중심 질문을 벗어나는 수학 전개, 공통 전처리 환경, 라이브러리 설치/세팅

### Part 4. 딥러닝

- 기본 선택: 현재 Section 보강
- 이유: 딥러닝은 용어와 계산 흐름 자체가 추상적이므로, 각 Section 안에서 `왜 필요한가`와 `무엇이 흐르는가`를 바로 보강해야 합니다.
- 추가 방식: 층별 입력/출력 흐름, 작은 텐서 예시, 손실-역전파-업데이트 연결 도식
- 보충학습 분리 조건: 다변수 미분, 선형대수 전개, GPU/병렬 처리의 세부 구현처럼 현재 구조 설명을 넘어서는 경우

### Part 5. LLM과 생성형 AI

- 기본 선택: 현재 Section 보강
- 이유: 초심자는 LLM을 제품 경험으로 먼저 접하므로, 서비스 경험과 내부 개념을 같은 Section 안에서 이어 주는 것이 중요합니다.
- 추가 방식: 입력 예시, 토큰/임베딩/RAG/에이전트의 서비스 장면 예시, 비교 표
- 보충학습 분리 조건: 특정 프레임워크 설정, API 인증 절차, 배포 환경 세팅처럼 제품별 절차가 길어지는 경우

### Part 6. 프로젝트

- 기본 선택: 현재 Section 보강
- 이유: 프로젝트 Part는 실행 순서와 산출물 읽기가 중요하므로, 본문 안에서 바로 예시와 실패 기록을 보여 주는 편이 낫습니다.
- 추가 방식: 실행 명령, 출력 예시, 실패 기록, 회고 문장, 다음 개선 계획
- 보충학습 분리 조건: 공통 템플릿, 반복되는 운영 체크리스트, 특정 배포 도구의 장기 참고 절차

## 예시 보강 최소 단위

초심자 보강은 가능한 한 다음 단위부터 검토합니다.

1. 한 문장 직관 추가
2. 2~5행짜리 작은 표 추가
3. 1개의 장난감 데이터 예시 추가
4. 1개의 작은 도식 추가
5. 코드 + 실행 결과 추가
6. 위 다섯 가지로 해결되지 않을 때만 보충학습 Section 검토

즉, 처음부터 보충학습을 늘리기보다 `현재 Section 안에서 가장 작은 이해 손잡이`를 먼저 추가합니다.

## 사례 작성 기준

입문 독자에게 사례는 `개념 이름을 다른 말로 다시 쓰는 문장`이 아니라, 실제로 머릿속에서 장면이 떠오르는 설명이어야 합니다.

다음과 같은 사례는 약한 사례로 봅니다.

- 추상 용어만 바꿔 적고 끝나는 경우
- `모델이 더 잘 구분한다`, `표현을 학습한다`처럼 결론만 말하는 경우
- 입력이 무엇인지, 무엇을 구분하는지, 사람이 어디서 막히는지 보이지 않는 경우
- 독자가 `그래서 실제로 무엇이 달라졌는가`를 확인할 수 없는 경우

예를 들어 다음 문장은 사례로는 약합니다.

`공장 이미지 검사에서 사람이 금 간 선의 길이, 어두운 점의 개수만 세려 하면 놓치는 패턴이 생길 수 있다. 표현 학습 관점에서는 모델이 미세한 질감 차이와 부분 구조 조합을 내부 표현으로 형성해 정상과 불량을 더 잘 가를 수 있다.`

이 문장은 방향은 맞지만, 입문 독자가 다음을 알기 어렵습니다.

- 실제 입력이 무엇인가
- 사람이 무엇을 보고 판단하는가
- 어떤 경우에 사람이 놓치는가
- 모델은 무엇을 추가로 보는가
- 결과가 어떻게 달라지는가

따라서 사례는 가능하면 다음 순서로 씁니다.

1. 문제 장면을 먼저 쓴다.
2. 사람이 하던 단순 기준을 쓴다.
3. 그 기준이 어디서 실패하는지 쓴다.
4. 모델이 무엇을 한꺼번에 보게 되는지 쓴다.
5. 최종적으로 무엇이 더 잘 구분되는지 쓴다.

즉, 사례의 기본 뼈대는 다음과 같습니다.

| 순서 | 사례에 들어갈 내용 |
| --- | --- |
| 1 | 누가 어떤 입력을 본다 |
| 2 | 예전에는 무엇을 기준으로 판단했다 |
| 3 | 그 기준으로 놓치는 경우가 있었다 |
| 4 | 모델은 어떤 패턴을 함께 본다 |
| 5 | 그래서 어떤 출력 차이가 생긴다 |

### 사례를 더 강하게 만드는 질문

사례 문단을 쓴 뒤에는 다음을 점검합니다.

- 독자가 입력 장면을 바로 상상할 수 있는가?
- `정상`, `불량`, `관련`, `유사`, `위험` 같은 말이 무엇을 뜻하는지 문맥 안에서 드러나는가?
- 사람이 쓰는 규칙이나 기준이 최소 한 번은 보이는가?
- 모델이 바꾸는 것이 `마법 같은 성능 향상`이 아니라 `더 많은 패턴을 함께 보는 일`로 읽히는가?
- 결과를 숫자, 라벨, 분류, 검색 순위, 응답 차이 중 하나로 확인할 수 있는가?

### 권장 사례 길이

입문용 사례는 가능하면 2~5문장 안에서 닫습니다.

- 1문장: 문제 장면
- 1문장: 사람이 하던 기준과 한계
- 1~2문장: 모델이 바꾸는 점
- 1문장: 결과 차이

길어지더라도 `역사 설명`, `기술 자랑`, `산업 동향`으로 새지 않게 주의합니다.

### 권장 사례 형태

다음 형태가 입문 독자에게 특히 유리합니다.

- 같은 입력을 두 방식으로 비교하는 사례
- 사람이 직접 규칙을 세는 방식과 학습 기반 방식을 대비하는 사례
- 입력, 출력, 오답 가능성을 함께 보여 주는 사례
- 작은 표나 항목 3개 이내로 정리되는 사례

반대로 다음 형태는 가능한 한 피합니다.

- 산업 현장 이름만 있고 구체 입력이 없는 사례
- `복잡한 패턴`, `잠재 표현`, `고차원 특징`처럼 추상어가 중심인 사례
- 결과 차이가 보이지 않는 사례
- 실제로는 여러 장의 설명이 필요한데 한 문장으로 압축한 사례

### 약한 사례와 더 나은 사례 비교

약한 사례:

`공장 이미지 검사에서 사람이 금 간 선의 길이, 어두운 점의 개수만 세려 하면 놓치는 패턴이 생길 수 있다. 표현 학습 관점에서는 모델이 미세한 질감 차이와 부분 구조 조합을 내부 표현으로 형성해 정상과 불량을 더 잘 가를 수 있다.`

더 나은 사례:

`휴대폰 화면 검사에서 사람은 보통 금의 길이가 일정 기준을 넘는지, 검은 점이 몇 개인지를 먼저 셀 수 있습니다. 하지만 금이 짧아도 여러 방향으로 갈라져 있거나, 점은 적어도 한쪽 모서리에 몰려 있으면 실제 사용 중 더 쉽게 깨질 수 있습니다. 학습 기반 모델은 길이 하나, 점 개수 하나만 따로 보지 않고 화면 전체의 금 방향, 점 위치, 주변 밝기 변화를 함께 읽습니다. 그래서 사람이 만든 단순 기준표에서는 정상으로 넘어가던 화면을 불량으로 다시 잡아낼 수 있습니다.`

핵심은 문장을 더 어렵게 쓰는 것이 아니라, `독자가 판단 과정을 따라가게 만드는 것`입니다.

### 사례와 예제의 역할 구분

사례는 장면을 이해시키는 데 쓰고, 예제는 그 장면을 더 작게 확인하는 데 씁니다.

- 사례: 왜 이 개념이 필요한가를 보여 준다
- 예제: 입력과 출력이 어떻게 생기는지 더 작게 확인한다

따라서 사례만으로 부족하다고 느껴지는 절은 다음 두 보강 중 하나를 검토합니다.

- 사례 바로 아래에 2~5행 표 추가
- 사례를 장난감 데이터 예제로 이어서 확인

`사례를 읽고도 머릿속에 입력과 출력이 안 잡히면, 사례 문장만 늘리지 말고 작은 표나 예제를 붙인다`를 기본 원칙으로 둡니다.

## 보충학습 Section 작성 조건

보충학습을 새로 만들 때는 다음 조건을 함께 확인합니다.

- 현재 Section에서 왜 그 문서를 참조해야 하는지 한 문장으로 연결합니다.
- 보충학습 제목은 `보충학습:` 형식을 유지합니다.
- 해당 보충학습이 여러 Chapter에서 재사용될지 확인합니다.
- `mkdocs.yml`의 `nav` 반영 여부를 확인합니다.
- 근거 검토 메모가 필요하면 `management/authoring/section-...-evidence-analysis.md`에 남깁니다.

## 문장 기준

초심자 보강 문장은 다음을 우선합니다.

- 정의보다 질문
- 추상어보다 입력과 출력
- 수식보다 작은 값 예시
- 알고리즘 이름보다 어떤 장면에서 쓰는지
- 기능 설명보다 왜 필요한지

## 전체 Part 공통 규칙

다음 규칙은 특정 Part에만 적용하지 않고 전체 Part에 공통으로 적용합니다.

- 이전 Part에서 다룬 용어라도 현재 Section의 핵심 개념이면 짧게 다시 소개합니다.
- 알고리즘 이름, 라이브러리 API, 수식 표기를 먼저 앞세우지 않고 문제 상황, 입력과 출력, 데이터 예시, 모델이 하려는 일을 먼저 설명합니다.
- 예시는 가능한 한 작은 표, 짧은 업무 상황, 간단한 도식으로 시작합니다.
- Python 예제를 넣을 때는 코드 앞에서 문제 상황, 입력, 기대 출력, 코드가 확인하려는 개념을 먼저 짧게 설명합니다.
- Python 예제에는 가능하면 `print` 같은 출력 코드를 넣고, 코드 블록 아래에 실행 결과 예시도 함께 둡니다.
- Python 예제의 출력은 샘플 수, `shape`, 라벨 분포, 분리 결과, 예측값과 실제값 비교처럼 현재 Section의 중심 질문과 직접 연결된 기본 점검 지표를 우선합니다.
- 현재 Section에서 아직 설명하지 않은 고급 지표나 구현 세부는 무리하게 넣지 않고, 뒤 Chapter나 보충학습으로 넘깁니다.

초심자 보강 문장이 길어질수록 다음을 점검합니다.

- 이 문단이 현재 Section의 중심 질문에 답하고 있는가?
- 아니면 선행 지식을 따로 복구하는 문단이 되었는가?

두 번째에 가까우면 보충학습 분리를 다시 검토합니다.
