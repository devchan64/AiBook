작성일: `2026-07-18`

## 제안 요약

Part 7은 기존 초안을 유지·보수하는 방식보다, 현재 Part 1~6까지 다듬어진 중심축을 기준으로 사실상 다시 설계하는 편이 더 적절합니다.

다만 이 재설계는 `문서화 중심 프로젝트 파트`가 아니라, `코드와 도식이 본문 중심이 되는 철저한 실습 파트`라는 전제를 분명히 가져야 합니다. 기록과 회고는 필요하지만, 그것은 실습 결과를 정리하는 보조 층위여야지 본문 전면을 차지해서는 안 됩니다.

현재 책의 본류는 이미 다음 흐름으로 정리되어 있습니다.

- Part 3: 문제를 데이터와 기준선으로 어떻게 모델링하는가
- Part 4: 전통 머신러닝에서 데이터 분리, 평가, 일반화, 비교를 어떻게 읽는가
- Part 5: 딥러닝 구조를 `입력 구조와 계산 구조의 선택`으로 어떻게 읽는가
- Part 6: LLM, RAG, 에이전트, 평가, 서비스 제약을 어떻게 연결하는가

따라서 Part 7의 역할은 `프로젝트 유형을 하나씩 늘어놓는 파트`가 아니라, 위 주제들을 실제 프로젝트 판단 흐름으로 다시 묶고, 독자가 충분한 규모의 코드 실행과 도식 해석, 로그 검토를 통해 직접 확인하는 파트가 되어야 합니다.

한 문장으로 줄이면 다음과 같습니다.

`Part 7은 새로운 개념 파트가 아니라, 문제 정의 -> 기준선 -> 구조 선택 -> 실행 -> 평가 -> 운영 회고를 코드와 도식 중심 실습으로 닫는 파트여야 합니다.`

## 현재 Part 7 초안의 구조적 한계

현재 초안은 다음 장점이 있습니다.

- 프로젝트 단위로 실습을 구성해 앞 Part의 개념을 실제 실행 장면으로 다시 묶으려는 의도가 분명합니다.
- baseline, 회고, RAG, agent, 배포/실패 기록 같은 실전 요소를 이미 포함하고 있습니다.

하지만 현재 전체 원고 기준으로는 다음 한계가 더 크게 보입니다.

1. 프로젝트가 `주제 카탈로그`처럼 읽힙니다.  
   데이터 분석, 전통 ML, 이미지 분류, 텍스트 분류, RAG, agent, 배포가 나열되어 있지만, 왜 이 순서로 프로젝트가 이어지는지가 구조 선택 관점에서 충분히 닫히지 않습니다.

2. Part 3~6의 핵심 판단 축이 프로젝트 안에서 다시 회수되지 않습니다.  
   현재 초안은 `프로젝트 문서를 남긴다`는 목적은 분명하지만, `문제 구조 때문에 왜 CNN/RNN/attention/Transformer/RAG/agent를 선택하거나 배제하는가`가 전면에 나오지 않습니다.

3. 프로젝트보다 기록 템플릿이 먼저 보입니다.  
   현재 index와 여러 Section은 문서화 감각을 잘 주지만, 프로젝트의 중심 질문보다 `무슨 기록을 남길 것인가`가 더 먼저 보이는 구간이 많습니다.

5. 실습 파트인데도 코드와 도식이 본문 전개의 중심이 아닙니다.  
   현재 초안은 프로젝트 문서 구조와 기록 항목 설명이 길고, 독자가 실제로 `입력 -> 코드 실행 -> 출력 비교 -> 도식 해석`을 따라가며 배우는 흐름은 상대적으로 약합니다.

4. 이미지 분류와 텍스트 분류가 별도 프로젝트로 갈라져 있지만, 책 전체 흐름상 더 중요한 축은 `도메인 종류`보다 `입력 구조와 참조 구조`입니다.  
   즉 Part 5에서 정리한 핵심은 `이미지 프로젝트 하나`, `텍스트 프로젝트 하나`가 아니라 `문제 구조에 따라 어떤 계산 구조가 자연스러운가`였습니다.

## Part 7의 새 중심축

Part 7은 다음 중심축으로 다시 세우는 편이 맞습니다.

- 문제를 프로젝트 질문으로 어떻게 닫는가
- 입력과 출력 단위를 어떻게 정하는가
- baseline은 무엇으로 두는가
- 구조 선택은 어떤 이유로 정당화되는가
- 어떤 코드를 최소 단위로 직접 실행해 볼 것인가
- 어떤 도식과 그래프로 판단 흐름을 눈으로 확인하게 할 것인가
- 결과와 실패를 어떻게 읽는가
- 서비스/운영으로 가면 무엇을 추가로 기록해야 하는가

즉, Part 7은 `무슨 모델을 만들까`보다 `무슨 질문을 어떤 구조와 코드로 풀고, 그 결과를 어떤 도식과 출력으로 검증할까`를 묻는 파트여야 합니다.

## 실습 파트 원칙

Part 7은 철저하게 실습 중심으로 다시 짜야 합니다. 이 말은 단순히 코드 블록이 있다는 뜻이 아닙니다.

1. 각 Section에는 반드시 실행 가능한 코드가 본문 중심에 있어야 합니다.
2. 각 실습은 코드 실행 전 예상 질문과 실행 후 해석을 함께 가져야 합니다.
3. 각 장에는 최소 1개의 도식 또는 그래프가 있어야 합니다.
4. 도식은 이론 설명이 아니라 `입력 -> 처리 -> 출력 -> 검토` 흐름을 눈으로 다시 읽게 해야 합니다.
5. 회고와 기록 템플릿은 장 말미의 산출물 예시로 낮추고, 본문 전개는 코드 실습과 출력 해석이 끌고 가야 합니다.

즉, Part 7의 학습 단위는 `설명 -> 템플릿`이 아니라 `문제 장면 -> 코드 실행 -> 출력 비교 -> 도식 해석 -> 짧은 회고`가 되어야 합니다.

## 재구성 원칙

1. 프로젝트는 `모델 종류`보다 `판단 단계` 순서로 배치합니다.
2. 각 장은 반드시 앞선 Part의 특정 축을 다시 회수해야 합니다.
3. 같은 개념을 새로 설명하지 말고, 프로젝트 안에서 `언제 그 개념이 의사결정 기준으로 다시 나타나는가`를 보여 줍니다.
4. 각 Section은 반드시 `실행 코드 + 출력 해석 + 도식 또는 그래프`를 함께 가져야 합니다.
5. 기록 템플릿은 본문을 대신하지 않고, 각 장 말미의 산출물 예시로 내려보냅니다.
6. 프로젝트는 `데이터 분석 -> 예측 -> 구조 선택 -> LLM 서비스 -> 운영 회고`처럼 점진적으로 커져야 합니다.

## 제안 구성안

기존 `7개 프로젝트 x 2개 Section` 초안은 폐기 가능하다고 보고, 아래처럼 다시 묶는 안을 제안합니다.

이 장의 역할:

### Module 2. 구조 선택이 드러나는 모델 프로젝트

이 장의 역할:
- Part 5의 핵심을 `모델 설명`이 아니라 `구조 선택 기준`으로 회수합니다.
- 현재 이미지 분류/텍스트 분류 프로젝트를 별도 장으로 두기보다, 구조 비교 프로젝트 안 사례로 다시 배치하는 편이 더 적절합니다.
- 이 장의 실습은 같은 문제를 표 입력, 이미지 입력, 시퀀스 입력으로 바꿔 보며 어떤 구조를 선택하는지 비교 코드와 구조 흐름도를 함께 두는 방식이 적합합니다.

- `P7-4.1` loss, metric, 오류 사례를 함께 읽는 프로젝트 검토

이 장의 역할:
- Part 4와 Part 5의 학습·평가·안정화 축을 실제 프로젝트 검토 장면으로 회수합니다.
- 지금 초안의 `토큰화와 평가`, `오류 사례 분석` 일부를 더 일반화해 포함할 수 있습니다.
- 이 장의 실습은 학습 곡선, 오류 샘플, 실패 유형 비교 그래프를 중심으로 두고, 문장 설명은 출력 해석을 받치는 정도로만 두는 편이 좋습니다.

이 장의 역할:

- 이 장의 실습은 plan -> tool call -> approval -> result -> blocked 상태를 보여 주는 실행 로그 예제와 도식이 본문 중심이 되어야 합니다.

## Section별 실습 초안

아래 초안은 `각 Section이 실제로 무엇을 실행하고 무엇을 눈으로 확인하게 할 것인가`를 더 구체적으로 적은 작업안입니다.

### P7-1.1 프로젝트 질문, 입력, 출력, 제약 조건을 한 문장으로 닫기

- 실습 중심 질문:
  - 같은 원시 표를 두고 `무슨 질문이 프로젝트를 여는가`
  - 입력 단위와 출력 단위를 바꾸면 프로젝트 정의가 어떻게 달라지는가
- 코드 중심 내용:
  - 작은 CSV 또는 DataFrame 생성
  - 질문별로 다른 target column, unit, slice를 잡는 코드
- 출력 중심 내용:
  - 질문 A와 질문 B가 서로 다른 요약표를 만드는 비교 출력
- 도식 중심 내용:
  - `질문 -> 입력 선택 -> 출력 정의` 흐름도 1개
- 이 Section의 목적:
  - Part 3의 문제 정의가 실제 프로젝트 첫 코드 셀에서 어떻게 다시 등장하는지 확인하게 한다

### P7-1.2 baseline과 비교 기준을 먼저 세우기

- 실습 중심 질문:
  - 왜 모델 전에 baseline을 먼저 실행해야 하는가
  - baseline이 바뀌면 `개선` 판단이 어떻게 바뀌는가
- 코드 중심 내용:
  - 평균 예측, 이전값 유지, 단순 규칙 같은 baseline 2~3개 비교 코드
- 출력 중심 내용:
  - baseline별 score 표
  - baseline 실패 사례 몇 개
- 도식 중심 내용:
  - `입력 -> baseline A/B/C -> 비교표` 흐름도
  - baseline score bar chart
- 이 Section의 목적:
  - Part 4의 baseline 관점을 실습 첫 비교 구조로 고정한다

### P7-2.1 비교표, 오류 사례, 관찰 메모를 어떻게 남기는가

- 실습 중심 질문:
  - 점수 하나만 보고는 왜 프로젝트 검토가 닫히지 않는가
- 코드 중심 내용:
  - 예측 결과와 정답을 merge한 비교표 생성
  - 오류 샘플만 필터링하는 코드
- 출력 중심 내용:
  - comparison rows
  - top error cases
- 도식 중심 내용:
  - confusion matrix 또는 error category bar chart
- 이 Section의 목적:
  - Part 4의 평가 지표와 오류 사례 읽기를 프로젝트 검토 표로 회수한다

### P7-2.2 회고 문서를 사실 / 해석 / 다음 질문으로 닫기

- 실습 중심 질문:
  - 결과 요약과 회고는 어떻게 다른가
- 코드 중심 내용:
  - 비교표와 오류표에서 회고용 필드를 자동 추출하는 간단한 코드
- 출력 중심 내용:
  - `fact / interpretation / next question` 회고 초안
- 도식 중심 내용:
  - `출력 -> 관찰 -> 보류 판단 -> 다음 질문` 흐름도
- 이 Section의 목적:
  - 회고는 실습 뒤의 부록이 아니라, 출력 해석을 다음 반복으로 넘기는 구조임을 보여 준다

### P7-3.1 표 데이터, 이미지, 시퀀스 입력은 프로젝트를 어떻게 다르게 바꾸는가

- 실습 중심 질문:
  - 같은 분류 문제라도 입력 구조가 바뀌면 왜 프로젝트 코드가 달라지는가
- 코드 중심 내용:
  - 표 입력, 이미지 배열, 시퀀스 토큰/시계열 예시를 동일한 목표 아래 비교하는 준비 코드
- 출력 중심 내용:
  - 각 입력 구조의 sample shape / sample view / target alignment 출력
- 도식 중심 내용:
  - `표 -> MLP`, `이미지 -> CNN`, `시퀀스 -> 순차/attention` 비교 흐름도
- 이 Section의 목적:
  - Part 5의 구조 선택을 실습 입구에서 다시 판단하게 만든다

### P7-3.2 CNN, 순차 모델, attention 계열을 프로젝트 선택 기준으로 비교하기

- 실습 중심 질문:
  - 왜 어떤 프로젝트는 CNN이 맞고, 어떤 프로젝트는 attention 계열이 맞는가
- 코드 중심 내용:
  - 완성 모델 학습보다 `입력 구조 -> 후보 모델 -> 선택 이유`를 출력하는 비교 코드
  - 가능하면 아주 작은 toy inference 예시 포함
- 출력 중심 내용:
  - 선택 기준 표
  - 구조별 장단점 비교 출력
- 도식 중심 내용:
  - 구조 선택 decision flow
  - 입력 구조별 계산 구조 비교 다이어그램
- 이 Section의 목적:
  - Part 5가 모델 소개가 아니라 선택 기준이었음을 프로젝트 단계에서 확인하게 한다

### P7-4.1 loss, metric, 오류 사례를 함께 읽는 프로젝트 검토

- 실습 중심 질문:
  - loss가 좋아도 프로젝트가 실패할 수 있는가
- 코드 중심 내용:
  - epoch별 loss/metric 로그 읽기
  - 오류 사례 샘플 연결
- 출력 중심 내용:
  - 학습 곡선
  - metric 대비 오류 사례 표
- 도식 중심 내용:
  - loss curve
  - metric vs failure-case summary chart
- 이 Section의 목적:
  - Part 5의 학습 루프와 Part 4의 평가 읽기를 한 화면에서 다시 묶는다

### P7-4.2 실패한 학습 결과를 구조 문제, 데이터 문제, 기준선 문제로 나누기

- 실습 중심 질문:
  - 실패를 `모델이 안 좋다`로만 적으면 왜 부족한가
- 코드 중심 내용:
  - 실패 사례를 category tag로 나누는 간단한 분류 코드
- 출력 중심 내용:
  - failure buckets
  - next action priority list
- 도식 중심 내용:
  - `loss 문제 / data 문제 / baseline 문제` 분기 흐름도
- 이 Section의 목적:
  - 실패를 다음 실험 질문으로 바꾸는 훈련을 시킨다

### P7-5.1 검색, 근거 선택, 답변 생성은 각각 무엇을 실패할 수 있는가

- 실습 중심 질문:
  - RAG는 왜 한 단계 실패가 아니라 여러 단계 실패로 읽어야 하는가
- 코드 중심 내용:
  - query -> retrieve -> rerank/choose -> answer 초간단 파이프라인
- 출력 중심 내용:
  - 검색 후보 목록
  - 선택 근거
  - 답변 초안
- 도식 중심 내용:
  - retrieval-to-answer pipeline flow
- 이 Section의 목적:
  - Part 6의 RAG를 구현 예시보다 failure surface 기준으로 다시 읽게 한다

### P7-5.2 검색 실패, 근거 누락, 답변 상태를 어떻게 기록하는가

- 실습 중심 질문:

- 코드 중심 내용:
  - answer state tagging

- 출력 중심 내용:

- 도식 중심 내용:
  - answer validation flow

- 이 Section의 목적:

### P7-6.1 계획, 도구 호출, 승인, 실패 상태를 어떻게 읽는가

- 도식 중심 내용:

- 이 Section의 목적:

### P7-6.2 권한, 로그, blocked 상태를 운영 기록으로 남기기

### Part 7 소개 문안 초안

`Part 7은 앞에서 배운 데이터 모델링, 머신러닝, 딥러닝, LLM 구조를 작은 프로젝트로 다시 실행해 보는 구간입니다. 여기서는 새로운 이론을 길게 늘리기보다, 같은 문제를 어떤 입력 단위로 정의하고 어떤 baseline을 두며 어떤 구조를 선택해야 하는지를 코드와 도식으로 직접 확인합니다.`

### Module 1. 프로젝트 문제 정의와 기준선

#### Chapter 1. 프로젝트 질문과 baseline `프로젝트 실습`

- **P7-1.1 프로젝트 질문과 입력 정의**: 같은 데이터도 질문과 입력 단위를 어떻게 잡느냐에 따라 전혀 다른 프로젝트가 된다는 점을 코드로 확인합니다.
- **P7-1.2 baseline과 첫 비교**: 가장 단순한 기준선을 먼저 실행하고, 개선 판단이 왜 비교 구조에서 시작되는지 확인합니다.

#### Chapter 2. 결과 해석과 회고 `프로젝트 실습`

- **P7-2.1 비교표와 오류 사례 읽기**: 점수 하나가 아니라 비교표와 오류 사례를 함께 읽어 프로젝트 결과를 해석합니다.
- **P7-2.2 회고와 다음 질문 만들기**: 실행 결과를 사실, 해석, 다음 질문으로 나누어 다음 반복으로 넘기는 연습을 합니다.

- **P7-4.2 실패한 결과를 다시 분해하기**: 구조 문제, 데이터 문제, 기준선 문제를 나누어 다음 실험 방향을 정합니다.

## 권장 결론

권장안은 다음과 같습니다.

1. 현재 Part 7은 `초안`으로 간주합니다.
2. 현재 목차의 `프로젝트 유형 나열` 구조는 폐기 가능합니다.
3. 새 Part 7은 `프로젝트 판단 흐름` 중심으로 다시 설계합니다.
4. 특히 Part 5와 Part 6에서 다듬은 주제를 `프로젝트에서 구조를 선택하고 실패를 읽는 단계`로 회수하는 것이 핵심입니다.
5. 단, 그 회수 방식은 `문서 템플릿 설명`이 아니라 `코드 실행 + 출력 비교 + 도식 해석`이어야 합니다.

가장 짧게 줄이면 새 Part 7은 다음 질문에 답해야 합니다.

`이 문제를 왜 이런 입력 단위로 정의했고, 왜 이런 구조를 선택했고, 어떤 코드를 실행해 무엇을 확인했고, 그 결과를 무엇으로 평가하며, 실패를 어떻게 다음 반복으로 넘길 것인가?`

이 질문이 Part 7 전체를 관통하면, 현재 책의 마지막 Part는 `프로젝트 예시 모음`이 아니라 `앞선 모든 Part를 실제 판단과 문서로 묶는 마무리 Part`가 될 수 있습니다.
