# Part별 세부 개선 계획

작성일: 2026-07-31

## 목적

이 문서는 `manuscript-learning-effect-improvement-report.md`의 우선순위를 실제 원고 편집 단위로 바꾸기 위한 관리 계획이다. 목표는 Part별로 어떤 문단을 추가하고, 어떤 설명 순서를 바꾸며, 어떤 용어 층위를 개념사전으로 관리할지 미리 정리하는 것이다.

이번 계획은 공개 본문을 바로 수정하지 않는다. 이후 Part별 원고 작업을 시작할 때 이 문서를 작업 큐로 사용한다.

## 공통 작업 기준

1. 본문 문단은 체크리스트 역할을 대신하지 않는다. 예시 뒤에 문단을 추가할 때는 요약 확인이 아니라 실제 표 설계, 코드 읽기, 출력 해석, 다음 설명 연결에 쓰이는 해설로 둔다.
2. 다른 Part로 넘기는 안내는 현재 Section에서 바로 설명하면 중심 질문이 흐려질 때만 짧게 쓴다. 반복적인 말미 안내로 고정하지 않는다.
3. Python 예제는 실행 가능한 기준 소스를 유지한다. 학습 초점을 나눌 때는 소스를 쪼개지 않고, 코드 앞·뒤·중간 해설을 나누어 같은 소스를 다시 읽게 한다.
4. `모델`, `추론`, `생성`, `파라미터`, `agent`, `층위`처럼 여러 의미가 겹치는 용어는 개념사전의 대표 표제어와 영어 기준 용어를 먼저 확인한다.
5. Part별 수정 후에는 Section ID, Version, 릴리즈노트 연결, 내부 링크, 개념사전 등장 Section을 함께 점검한다. 개념사전 항목 자체는 전용 가이드에 따라 릴리즈노트 대상에서 제외한다.
6. 관리 문서만 수정한 단계에서는 MkDocs 빌드를 실행하지 않는다. 공개 원고나 `mkdocs.yml`을 수정한 뒤 필요한 검증 시점에만 빌드한다.

## Part 1 세부 계획: AI 전체 지도와 용어 층위

### 목표

AI를 처음 다시 배우는 독자가 `규칙`, `모델`, `학습`, `추론`, `생성`, `agent`를 한 덩어리로 받아들이지 않게 한다. Part 1은 자세한 기술 설명보다 이후 Part에서 같은 단어가 다른 층위로 다시 등장한다는 길잡이 역할을 맡는다.

### 우선 작업

1. Part 1의 용어 지도 구간에서 단독 영어 일반어가 개념처럼 고정된 곳이 있는지 확인한다.
2. `agent` 계열 표현은 `AI 에이전트`, `LLM 에이전트`, `강화학습 에이전트`, `소프트웨어 에이전트`처럼 문맥을 좁혀 쓴다.
3. `추론`은 `inference`, `reasoning`, `prediction`, `generation`이 섞이지 않게 현재 문맥의 뜻을 짧게 붙인다.
4. Part 5·6의 상세 설명을 앞당겨 쓰지 않는다. 지금은 용어 지도를 만들고, 세부 계산과 서비스 판단은 해당 Part에서 처리한다.
5. Part 시작 페이지는 운영 메타보다 독자가 겪는 문제 장면을 먼저 보여 주고, 목표·범위·점검은 뒤쪽으로 옮긴다.

### 완료 증거

- Part 1에서 새로 고정한 핵심 용어가 개념사전 대표 표제어 또는 후보로 정리되어 있다.
- 같은 Section 안에서 개념사전 링크가 강조 목적으로 반복되지 않는다.
- 후속 Part 안내가 필요한 곳에만 짧게 남아 있다.

## Part 2 세부 계획: 수학·데이터·Python 읽기 기반

### 목표

초심자가 긴 설명과 긴 Python 예제를 보고도 `무엇을 관찰해야 하는가`를 놓치지 않게 한다. Part 2는 이후 Part의 실습을 위한 언어와 표 읽기 기반을 만든다.

### 우선 작업

1. `P2-8.2`~`P2-8.6`의 Python 예제를 확인해 실행 가능한 기준 소스가 유지되는지 점검한다.
2. 긴 기준 소스 앞에는 실행 전에 예상할 관찰값을 둔다.
3. 코드 뒤에는 출력에서 먼저 볼 행, 열, 값 변화, 반복 결과를 짚는 문단을 둔다.
4. 중간 해설이 필요하면 코드 조각을 다시 쓰지 않고 기준 소스의 줄이나 블록을 다시 보게 안내한다.
5. PEP, generator, 엄밀한 iterator 설명처럼 초심자 본문 흐름을 늦추는 내용은 필요한 경우 `보충학습`으로 분리한다.
6. `P2-9.4`, `P2-12`처럼 표·함수·입출력과 연결되는 구간은 예제 결과가 Part 3의 데이터 표현으로 어떻게 넘어가는지 한 문단으로 이어 준다.

### 완료 증거

- Python 예제가 학습 편의를 이유로 여러 실행 단위로 쪼개지지 않았다.
- 각 긴 예제마다 `실행 전 예상`, `출력에서 볼 것`, `다시 볼 코드 위치` 중 필요한 안내가 있다.
- 보충학습으로 보낸 내용이 `mkdocs.yml`과 Section 메타데이터 기준에 맞게 연결되어 있다.

## Part 3 세부 계획: 데이터 표현과 문제 승격

### 목표

Part 3은 가장 먼저 처리한다. 샘플 단위, 원시 로그, 요약 표, 특징, 라벨, 예측 문제 승격이 흔들리면 Part 4의 머신러닝 설명과 Part 7의 프로젝트 기록이 함께 흔들린다.

### 우선 작업

1. `P3-4.1`~`P3-4.5`에서 샘플 단위 예시 뒤에 실제 표 설계로 이어지는 해설 문단을 추가한다.
2. `P3-5.1`~`P3-5.7`에서 원시 로그를 요약 표로 바꾸는 기준을 예시 직후에 붙인다.
3. `P3-9.7`~`P3-9.13`에서 분석 질문이 예측 문제로 바뀌는 조건을 `입력`, `정답`, `평가 가능성`, `누수 위험` 순서로 다시 정렬한다.
4. time split, group split, data leakage처럼 자세한 절차가 필요한 항목은 현재 Section에서 이름과 위험만 확인하고, 평가 설계 구간에서 다루는 이유를 짧게 안내한다.
5. `샘플`, `feature`, `label`, `baseline`, `leakage`의 한국어 표현과 영어 병기가 개념사전과 맞는지 확인한다.

### 완료 증거

- 예시 뒤 문단이 표 설계나 문제 정의 행동으로 직접 이어진다.
- Part 4로 넘어가기 전에 독자가 최소한의 입력·출력·평가 단위를 설명할 수 있다.
- 개념사전에서 같은 표면형이 서로 다른 층위로 묶이지 않는다.

## Part 4 세부 계획: 머신러닝 실험 루프

### 목표

알고리즘 이름보다 실험 루프를 먼저 읽히게 한다. Part 4는 특징 선택, 전처리, baseline, 평가, 튜닝을 통해 `모델을 고르는 일`보다 `비교 가능한 실험을 만드는 일`을 앞세운다.

### 우선 작업

1. `P4-7.1`과 `P4-7.2`는 첫 예시를 앞으로 당기고, 정의·분류표·학술적 설명은 예시 뒤로 재배치한다.
2. `P4-8.1`~`P4-8.3`은 train/test split, validation, cross-validation이 서로 다른 이름 목록이 아니라 비교 절차의 위치로 보이게 정리한다.
3. `P4-9.1`~`P4-9.3`은 accuracy, precision, recall, F1, ROC-AUC를 문제 비용과 연결하는 문단을 보강한다.
4. 알고리즘별 Section은 수식이나 역사보다 `어떤 데이터 모양에서 어떤 실패가 생기는가`를 먼저 보여 준다.
5. `모델`은 학습 알고리즘, 학습된 예측기, 배포 API 모델이 섞이지 않게 현재 문맥의 범위를 좁혀 쓴다.

### 완료 증거

- 긴 실험 준비 Section의 앞부분에서 실제 사례가 먼저 보인다.
- baseline과 metric이 체크 항목이 아니라 실험 판단 기준으로 설명되어 있다.
- Part 7 프로젝트 기록에서 재사용할 수 있는 비교 언어가 정리되어 있다.

## Part 5 세부 계획: 딥러닝 계산 구조

### 목표

딥러닝을 층 이름 목록으로 읽지 않고, 입력 표현이 여러 계산 단계를 지나 출력 분포로 바뀌는 과정으로 읽게 한다. Part 6으로 넘어가기 전에 attention, Transformer, 파라미터, 샘플링의 역할을 사용 경험과 연결한다.

### 우선 작업

1. `P5-6` 계열에서 신경망의 층은 `층(layer)` 또는 `계층(layer)`으로 쓰고, 개념 구분 수준은 `층위(level)`로 구분한다.
2. `P5-14` 계열의 Transformer 설명은 구조 이름보다 토큰 표현이 어떻게 갱신되는지에 초점을 둔다.
3. `P5-15`와 `P5-summary`에는 Part 6의 프롬프트, 토큰, 생성 설정, RAG가 Part 5의 계산 구조와 어떻게 연결되는지 짧은 전환 문단을 둔다.
4. 파라미터는 모델 파라미터, 하이퍼파라미터, LLM 생성 설정값을 분리해 쓴다.
5. 수식이나 계산 그래프 설명이 길어지는 곳에는 입력값, 중간 표현, 출력 후보를 비교하는 표나 도식을 검토한다.

### 완료 증거

- `층위(level)`와 `층(layer)`의 용례가 섞이지 않는다.
- Transformer 설명이 Part 6의 사용 판단으로 이어지는 문단을 갖는다.
- `generation`, `generative AI`, `sampling`이 같은 말처럼 처리되지 않는다.

## Part 6 세부 계획: LLM·생성형 AI·도구 사용

### 목표

LLM과 생성형 AI를 제품 기능 목록이 아니라 실행 흐름으로 이해하게 한다. 모델이 직접 답하는 일, 외부 도구로 넘기는 일, 기록으로 검토하는 일을 구분해 서비스 판단 능력을 만든다.

### 우선 작업

1. `P6-1`~`P6-6`은 Part 5의 계산 구조가 토큰, 프롬프트, 생성 결과로 어떻게 보이는지 연결한다.
2. `P6-10`~`P6-12`는 프롬프트, RAG, 검색 결과, 출처 검토를 하나의 답변 생산 흐름으로 정리한다.
3. `P6-13`~`P6-18`의 도구 사용, AI 에이전트, MCP, 하네스, 평가, 운영 제약은 `직접 답변`, `도구 호출`, `기록 검토`의 축으로 재배치한다.
4. `agent`는 단독 표기가 아니라 AI 에이전트, LLM 에이전트, 소프트웨어 에이전트 등 현재 설명 범위에 맞춰 쓴다.
5. `모델`, `앱`, `도구`, `하네스`, `로그`, `서비스`가 같은 층위로 섞이지 않게 문단 첫 설명에서 역할을 분리한다.

### 완료 증거

- 도구·에이전트 구간의 Chapter 도입부가 실행 흐름을 먼저 보여 준다.
- 제품명이나 기능명이 개념사전 표제어처럼 늘어나지 않는다.
- 운영 로그의 필드명과 일반 개념이 구분되어 있다.

## Part 7 세부 계획: 프로젝트 실행과 회고

### 목표

Part 7은 앞 Part의 개념을 실제 프로젝트 판단으로 다시 묶는다. 독자가 예제를 따라 실행하는 데서 끝나지 않고, 입력을 바꾸고, 출력을 비교하고, 실패 원인을 기록하게 한다.

### 우선 작업

1. 각 Section 도입 뒤에 이번 실습에서 바꿀 입력, 비교할 출력, 회고로 남길 문장을 짧게 둔다.
2. 코드 예제가 있는 곳은 기준 소스를 유지하고, 설명을 `설정값`, `입력 데이터`, `출력 해석`, `실패 기록`으로 나누어 읽게 한다.
3. `P7-5`와 `P7-6`은 RAG, 평가, 로그, 운영 제약을 Part 6의 실행 흐름과 연결한다.
4. `P7-7`은 프로젝트 결과물을 단순 완료물이 아니라 비교 가능한 기록 묶음으로 정리한다.
5. 산출물 이름, 로그 필드명, 파일명은 개념사전 표제 관리 제외 대상으로 볼 수 있는지 먼저 점검한다.

### 완료 증거

- 각 프로젝트 Section에서 독자가 무엇을 바꿔 보는지 앞부분에서 알 수 있다.
- 출력 비교와 실패 기록이 예제 끝에 남는다.
- 운영 산출물명이 일반 개념처럼 개념사전에 늘어나지 않는다.

## Part 시작·마무리 페이지 세부 계획

### 목표

Part 시작 페이지는 독자가 겪을 문제 장면으로 열고, Part 마무리 페이지는 다음 학습에서 다시 사용할 판단 기준을 남긴다. 목표·범위·완료 기준 같은 운영 메타는 필요하지만 첫인상이 되지 않게 배치한다.

### 우선 작업

1. 각 Part 시작 페이지 첫 문단이 독자의 실제 혼란이나 문제 장면을 보여 주는지 확인한다.
2. Part 목표와 범위는 도입 뒤에서 정리한다.
3. Part 마무리 페이지는 새 개념을 더 넣기보다 다음 Part에서 재사용할 판단 기준을 압축한다.
4. Part 5와 Part 7의 시작 페이지는 각각 `딥러닝 구조 이름이 많아지는 문제`, `실습 후 무엇을 비교해야 하는지 모호한 문제`를 더 분명히 보여 준다.
5. Part 경계에서 후속 Part를 과도하게 예고하지 않는다. 필요한 경우 왜 지금은 이름만 알고 넘어가도 되는지 짧게 안내한다.

### 완료 증거

- Part 시작 페이지가 운영 메타보다 문제 장면으로 먼저 읽힌다.
- Part 마무리 페이지가 다음 Part의 상세 설명을 미리 쓰지 않는다.
- Part 경계 안내가 반복 문구처럼 붙어 있지 않다.

## 후속 관리 체크

Part별 원고 수정 작업을 시작하면 다음 순서로 관리한다.

1. 수정 전 해당 Part의 open checklist와 관련 가이드라인을 확인한다.
2. Section ID와 현재 Version을 확인한다.
3. 본문 문단, 예시, 코드, 표, 개념사전 링크를 함께 수정한다.
4. 공개 본문을 수정했다면 릴리즈노트 연결을 확인한다.
5. 개념사전 항목을 수정했다면 중심 Section, 등장 Section, 한국어·영어·중국어 색인 include를 확인한다.
6. 전체 작업 묶음이 끝난 뒤 필요한 시점에 MkDocs 빌드를 실행한다.
