### v2026.07.08

- 변경 이유: 모델 metric과 운영 metric을 구분하는 챗봇 사례에 예시 분기 도식이 없어 해석 흐름이 즉시 보이지 않았다.
- 본문 반영: 챗봇 사례 아래에 offline quality 상승 이후 latency/timeout 점검과 answer quality 점검으로 갈라지는 Mermaid 도식을 추가하고 Section 버전을 갱신했다.
- 변경 이유: SRE의 네 가지 기본 신호 도식이 네 항목의 병렬 나열에 가까워, traffic, saturation, latency, errors가 운영 신뢰성 안에서 어떻게 이어지는지 즉시 읽기 어려웠다.
- 본문 반영: 네 가지 기본 신호 도식을 `user requests -> traffic -> saturation -> latency/errors -> user-facing reliability` 흐름으로 다시 구성하고, 도식 아래 설명도 관계 중심 문장으로 보강했다.
- 변경 이유: 수정 후 도식도 여전히 신호 소개형에 머물러, 운영자가 `어떤 순서로 네 신호를 읽는가`와 `정상 경로/위험 경로`가 충분히 드러나지 않았다.
- 본문 반영: 네 가지 기본 신호 도식을 `traffic 확인 -> capacity 판단 -> saturation 상승 시 latency/errors 악화 -> reliability 저하`와 `capacity 여유 시 latency 안정`의 두 경로가 보이도록 다시 구성하고 설명도 운영 판단 순서 중심으로 고쳤다.
- 변경 이유: 모델 metric과 운영 metric 비교 Python 예제가 숫자 나열에 머물러, `어떤 경우에 모델 문제를 먼저 보고 어떤 경우에 운영 문제를 먼저 보는가`라는 의도가 약했다.
- 본문 반영: 사례별 임계값 비교와 해석 문장을 추가해 `model is strong, but service reliability is weak`와 `service is stable, but model quality is weak`가 바로 드러나도록 예제와 설명을 고쳤다.
- 번역 동기화 메모: 향후 번역본에서도 서비스 문제와 모델 문제를 가르는 사례 분기 구조를 유지해야 한다.
- 번역 반영 상태: 향후 반영 필요
- 관련 자산: 없음
- 원문 기준 버전: `v2026.07.08`
