- 두 모델 3쌍 재생성: 새 seed `5414`·`5415`·`5416`에서 두 모델을 순차 실행했다. Animagine 세 출력은 수직 다리·지지발·팔의 후방 가림 계약을 모두 만족하지 못해 PNG·guide를 삭제했다. FLUX 세 출력은 짧은 단발, 수직 든 다리, 협곡과 열린 바닥을 함께 보여 사람 검수 후보로 기록했지만 승인하지 않았으므로, 사용자 지시에 따라 모든 후보 PNG·guide를 삭제했다. 이 세트는 승인 스토리보드를 자동 교체하지 않는다.
- Animagine step 단일 비교: 같은 짧은 단발·팔 가림 prompt와 seed `5416`에서 `28`과 `40` step을 한 번씩 비교했다. 28 step은 수직 다리·지지발 계약에 미통과였고, 40 step은 옆차기·긴 뒷머리·팔과 다리의 관계가 더 흔들려 개선되지 않았다. 기본값 28 step을 유지하고, 두 출력과 파생 guide는 모두 삭제했다. 이 실패 유형은 step만 높여 재실행하지 않는다.
- 승인 갱신: 텍스트 전용 Animagine XL 4.0 스토리보드(`832×1216`, 28 step, CFG 5.0, seed `5413`)와 그 파생 guide를 장면 기준으로 승인했다. 이어 Apache-2.0 FLUX.2 Klein 4B에 이 스토리보드·P7-5.3 얼굴·전신 복장 기준을 세 이미지 입력으로 주고, `512×768`·50 step·seed `5413`·sequential CPU offload에서 생성한 캐릭터 컷을 최종 승인했다(285.8초, peak 3.36 GiB). 협곡·열린 바닥·수직 든 다리·지지발·두 팔, 턱선 길이 청록 단발, 흰 재킷·청록 넓은 바지·흰 운동화·남색 가방이 함께 읽힌다. 8-step 승인본과 비교해 선화·얼굴·단발·가방·넓은 바지 형태가 더 안정적이어서 교체했으며, 든 다리의 드러난 발목은 넓은 바지의 자연스러운 동작 연출로 수용했다. 승인 PNG와 실행 JSON만 공개 자산으로 남기고, 4-step·8-step 비교와 미승인 ControlNet·Posecode·SCAIL·참조 후보 자산은 제거했다. 그 실패·보류 판단은 아래 항목의 기록으로만 유지한다.
- SCAIL 로컬 실행 기록: SCAIL-Preview Q2 GGUF와 CPU offload를 8 GB GPU에서 `352×512`·5 frame·4 step으로 실제 실행했다. model patch·text encode·sampling·VAE decode가 38.78초, peak allocated 6.09 GiB·reserved 6.31 GiB로 완료되어 실행 가능성만 확인했다. 다만 전신 기준 이미지와 정지 골격 한 장(공식 pose 영상 아님)의 축약 입력에서는 협곡·수직 든 다리·수평 양팔이 재현되지 않아 미통과였다. PNG 다섯 장은 삭제하고 입력 기록만 남겼다. 공식 `512p`·긴 pose 영상 조건과 다르므로 모델 일반 실패로 단정하지 않되, 현 8 GB 축약 계약은 승인하지 않고 재실행하지 않는다. 후속은 리그·skin·헤어·의상 mesh를 갖춘 3D 자산처럼 입력 계약이 달라질 때만 검토한다.
- 경로 경고 정리: 본문이 현재 추적 자산에 없는 `p7-5-3-guide-adherence-benchmark/` 폴더를 상대 링크로 가리키던 문장을 제거하고, 공개 자산에는 승인 스토리보드·파생 guide PNG만 유지한다는 설명으로 바꿨다.
- 반복 재실험 경고: 본문 체크리스트에 미통과 `backbone + guide 종류/출처 + 해상도 계약`을 seed·step·강도만 바꿔 반복하지 않도록 명시했다. 재개에는 실패 원인을 바꿀 새 가설과 입력 계약 변화, 그리고 실행 기록의 차이 설명이 필요하다.
- text-to-pose 인체 수용도 검수: image-to-pose 경로를 제외하고, 자연어 지시를 `지지발=오른발`·`왼다리 수직 들기`·`양팔 수평` pose ticket으로 제한한 뒤 운동학적 제약 22관절→OpenPose·관절 depth로 렌더했다. 지도 자체는 지지발·무릎·발목·양팔 연결을 통과했다. SDXL OpenPose+관절 depth(`512×768`, 24 step, 23.3초, peak 1.50 GiB)는 든 다리를 머리 뒤 부속지로 해석했다. 관절 depth를 원본 협곡 depth로 바꾼 23.2초·peak 1.50 GiB 재실행도 양팔이 사라지고 든 다리·몸통이 합쳐져 미통과였다. 두 PNG·JSON은 삭제했다. 즉 text-to-pose 관절 컴파일은 통과했지만 현 ControlNet의 인체 수용도는 미통과다.
- Animagine XL OpenPose 재판정: 동일 text pose ticket과 원본 협곡 depth를 512×768·24 step으로 실행했다(23.0초·peak 972 MiB). 인체가 정면 대칭 장식물처럼 변형돼 수직 다리·양팔·협곡을 모두 잃었다. PNG·JSON을 삭제했으며 Animagine XL OpenPose도 text-to-pose 후보에서 제외한다.
- text-to-pose 전용 후보 탐색: PoseDiffusion/GUNet은 텍스트에서 17채널 관절 heatmap을 생성해 OpenPose로 변환하는 Apache-2.0 가중치 후보라 image-to-pose와 구분해 실제 검증했다. 공식 256×256·27 step 계약도 현 PyTorch에서는 내부 관절 행렬 자료형·CFG batch=2 가정의 임시 보정이 필요했고, sequential CPU offload·CFG 단일 배치까지 적용해도 중간 블록에서 8 GB VRAM 부족으로 완주하지 못했다. 검수할 PNG가 없으므로 임시 소스·5.2 GB 가중치·부분 산출물을 삭제하고 8 GB 단일 GPU 후보에서 제외했다. HumanSD는 사람 골격 특화 코드가 Apache-2.0이지만 공식 저장소가 추론 코드·사전학습 가중치 공개를 TODO로 두고 가중치 사용권도 명시하지 않아 채택하지 않는다.
- 다음 대안 실행 검수: Posecode는 텍스트를 관절 DSL로 컴파일하고 `ground-lock: foot_right`·관절 각·IK를 검사한다. 가동범위는 배제 사유가 아닌 입력 일관성 제약으로 수용했다. `hip_left: flex 135`·`knee_left: extend 0`·`shoulders: abduct 90`·오른발 접지 DSL을 두 번 변환한 22관절 JSON의 SHA-256이 동일했고, 오른발 접지는 y=0.01 m로 유지됐다. 이 결정론적 좌표에서 OpenPose·관절 depth·surface Canny·surface depth 네 지도를 만들어 사람 검수 후보로 보존했다. 든 다리가 몸통보다 앞이라는 z-order는 고정하지만, 기본 가동범위가 원본의 극단 수직 다리를 완전히 재현하지 않고 생성 컷 품질도 아직 검증하지 않았으므로 승인하지 않는다. HY-Motion 1.0은 24–26 GB 최소 VRAM, UniPose는 LLaVA Mistral 7B 의존성으로 8 GB 단일 GPU 후보에서 제외한다.
- Posecode 사람·캐릭터 동시 수용 검수: 정확한 Posecode surface guide와 P7-5.3 전신·얼굴 기준 두 장을 Animagine XL Plus IP-Adapter에 넣는 명시적 저해상도 검증 경로를 추가했다. 512×768·24 step·sequential CPU offload에서 Canny+surface-depth는 24.235초·peak 974.6 MiB로 끝났지만 사람 대신 회색 고체 실루엣을 만들었다. Canny를 빼고 surface depth만 준 별도 계약은 17.7초·peak 970.1 MiB에서 얼굴은 만들었지만 든 다리와 팔이 원통형으로 붕괴했다. 두 PNG·JSON은 삭제했다. 따라서 다중 구조 조건과 IP-Adapter의 API 조합은 가능해도, 현재 8 GB·단일 생성에서 교차 순서·해부학·캐릭터 특징을 동시에 통과했다는 근거는 없다. 동일 조합의 seed·강도 재실행은 금지하고, 다음 대안은 통과한 인체 초안의 국소 mask/inpaint 또는 인체 표면 전용 조건 모델처럼 입력 계약을 바꿀 때만 검증한다.
- 3D 리그 대안 검수: Posecode 관절을 직접 연결하고 검정 타이즈, 얼굴 reference texture, 지지발 그림자를 둔 절차적 3D 리그 프록시를 렌더했다. 든 다리의 전면 z-order·두 팔·두 다리·접지 순서는 결정론적으로 유지됐지만, 프록시는 캐릭터의 몸·팔·의상 mesh를 만들지 못했다. 즉 3D 관절과 2D reference만으로 캐릭터 3D 표면이 생기지는 않는다. 검수할 작화 품질이 아니므로 PNG·JSON·임시 렌더러를 삭제했다. 다음 3D 경로는 사용 허가된 리깅·skin·헤어·의상 mesh를 가진 캐릭터 자산을 별도로 확보할 때만 진행한다.
- pose-transfer 후보 조사: MimicMotion은 DWPose와 기준 이미지를 직접 받으며 16-frame U-Net은 8 GB, VAE decoder는 CPU 실행 가능하다고 안내하지만, 공개 가중치는 연구·교육 전용 및 Stable Video Diffusion 사용 조건을 따르므로 개방 라이선스 기준에서 제외했다. MusePose도 기준 이미지+pose sequence 경로이지만 가중치가 비상업 연구 전용이고 512×512×48에서 16 GB를 안내해 제외했다. MagicAnimate는 기준 appearance와 DensePose surface를 분리하는 BSD-3-Clause 코드·가중치 후보로 남겼다. 다만 지금의 Posecode 관절은 DensePose UV surface가 아니므로, 사용 허가된 사람 surface mesh에서 IUV 지도를 만드는 입력 계약을 확인하기 전에는 다운로드·실행하지 않는다.
- MagicAnimate 입력·실행 탐침: 공식 예제의 16-frame DensePose RGB part 영상 규약에 맞춰 Posecode 3D 관절에서 surface-part 영상을 근사 렌더했다. 이는 실제 mesh UV가 없어 정식 IUV가 아니므로 결과 품질 판정 입력으로 쓰지 않았다. 공식 코드를 `.tmp`에서 import한 결과, 현 Python 3.12·Torch 2.11·Diffusers 0.37 환경은 오래된 `diffusers.pipeline_utils` API 제거로 즉시 중단했다. 공식 의존성은 Torch 2.0·Diffusers 0.21·Xformers 0.0.22이며, 실행 경로는 16-frame latent와 appearance encoder·ControlNet을 GPU에 올린다. 따라서 새 가중치를 내려받지 않았고, MagicAnimate는 이 환경의 8 GB 실험 후보에서 제외했다. 임시 입력 영상·소스는 삭제한다.
- 외부 근거 비교: ControlNet 원논문, xinsir SDXL OpenPose 모델 카드, NeurIPS 2024 Stable-Pose를 대조했다. ControlNet은 공간 조건 추가 구조이며 가림·표면·정체성의 완전 제약은 아니다. 현 모델 카드는 기본 관절선 렌더링 불안정과 1024 bucket 권장을 명시하고 HumanArt 생성 평가 mAP 0.357을 제시한다. Stable-Pose도 기존 pose-guided T2I가 복잡한 측면·후면 자세에서 제한됨을 보고한다. 따라서 이 절에서는 SD 계열 OpenPose를 단순 비가림 포즈 보조 조건으로 한정하고, 현 8 GB·단일 생성·극단 교차 자세의 인체 수용도에는 불충분하다고 판정했다.
- 표준 OpenPose 입력 계약 재판정: 모델 카드의 두꺼운 선·18관절 순서·1024 bucket 권장에 맞춰 text pose ticket을 다시 렌더하고 `768×1152`·30 step, `768×1024`·24 step을 실행했다. 전자는 추가 다리, 후자는 얼굴 완전 가림으로 미통과였고 고해상도 실행 뒤 GPU 드라이버 단절도 반복됐다. PNG·JSON·임시 입력을 삭제했다. 굵은 표준 OpenPose는 부분 수용은 개선했지만 현 컷의 채택 해법은 아니다.
- 단순 포즈 가설의 승인 보류: 복잡한 교차 자세의 실패는 단순·비가림 포즈에서도 같은 결과를 뜻하지 않는다. 단순 포즈에서 더 높은 인체 수용도가 나올 가능성은 원고에 `검증 필요` 가설로만 남기며, 별도 통제 실험으로 얼굴·양팔·두 다리·접지를 모두 확인하기 전까지 승인·기본 경로 채택을 하지 않는다.
- DWPose 대안 재판정: OpenPose가 빈 map을 낸 승인 스토리보드에 Apache-2.0 DWPose ONNX 사람 검출·whole-body pose를 적용해 사람 1명, 134 keypoint 중 129개를 검출했다. `--extract-dwpose-from`·`--dwpose-output`을 추가했지만, 사람이 map을 검수한 결과 들어 올린 다리의 무릎·발목 관절 연결이 실제 자세와 달랐다. DWPose+상대 depth·sequential CPU offload의 512×768(23.12초·peak 972 MiB)과 768×1152(35.876초·peak 2.17 GiB)도 장면 또는 수직 다리 관계를 유지하지 못해 PNG·JSON을 삭제했다. keypoint 수·신뢰도는 통과 기준이 아니며, DWPose도 이 장면의 관절 추출 대안으로 미통과다.
- 가려짐 대안 실행 검수: Apache-2.0 T2M-GPT를 `.tmp`에 내려받아 동작 prompt에서 HumanML3D 22관절 168 frame을 실제 생성했다(peak 1.30 GiB). `--render-3d-joints`로 한 frame을 OpenPose와 관절·뼈대 z-order depth PNG로 렌더하고, `--use-rendered-skeleton-depth`와 `--sequential-cpu-offload`를 추가했다. 일반 CPU offload의 SDXL ControlNet 두 개는 768×1152와 512×768 모두 8 GB OOM이었다. 순차 CPU offload는 512×768·24 step·24.9초·peak 972 MiB로 실행됐으나 얼굴·한쪽 다리·팔 연결이 사라져 PNG·JSON을 삭제했다. T2M-GPT도 수직 다리라는 세부 동작을 맞추지 못했다. 따라서 OpenPose+뼈대 depth는 채택하지 않으며, 인체 표면 가림에는 mesh/DensePose 또는 사람 검수 3D blockout의 normal·depth·mask를 별도 검증해야 한다.
- surface blockout 실행 검수: SMPL 원본 body model의 별도 배포 조건을 피하기 위해, 같은 22관절을 capsule 표면으로 z-buffer 렌더한 `--use-rendered-surface-guides`를 추가했다. silhouette Canny+surface-depth는 교차한 팔다리의 앞뒤 순서를 유지했지만, T2M-GPT의 부정확한 동작과 거친 surface proxy 때문에 512×768·19.6초·peak 972 MiB 생성에서 얼굴·사지 세부가 뭉개졌다. PNG·JSON을 삭제했으며, 자동 capsule surface도 채택하지 않는다.
- 캐릭터 일관성 재판정: 얼굴 turnaround Plus-Face, 흰 마스크 얼굴 Inpaint, 그리고 P7-5.3 최신 얼굴·전신 기준 11장으로 학습한 Animagine XL UNet LoRA(rank 8, 384×512, BF16, 300 step)를 다시 비교했다. LoRA 학습 peak는 6.56 GiB였다. 두 Canny 컷 모두 가방·바지·두 다리 또는 기준 얼굴의 눈·얼굴형·머리 형태가 무너져 삭제했다. Inpaint/Plus-Face도 기준 얼굴을 재현하지 못했다. 따라서 기본 실행에서 자동 얼굴 참조를 제거하고, IP-Adapter·Inpaint·LoRA 모두 캐릭터 통과 근거가 아닌 실험 옵션으로 격하했다.
