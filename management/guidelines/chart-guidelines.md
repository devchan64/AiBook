# 차트와 다이어그램 작성 기준

이 문서는 책 본문에 들어가는 차트와 다이어그램의 작성 기준을 정리합니다. 특히 수학 개념, 모델 계산, 벡터·행렬, 변화율처럼 시각적 설명이 필요한 도식을 만들 때 참고합니다.

## 이 문서가 추가로 다루는 질문

- 지금 필요한 것이 `표`인가, `플로우차트`인가, `차트`인가, `다이어그램`인가?
- 같은 내용을 다른 형식으로 반복해 독해를 무겁게 만들고 있지는 않은가?
- 표가 비교를 돕는지, 오히려 절차 설명을 끊고 있지는 않은가?
- 플로우차트가 유리한 구간인데도 비교 표로 눌러 담아 읽기 순서를 흐리고 있지는 않은가?

## 기본 원칙

- 차트와 다이어그램은 장식보다 설명 목적을 우선합니다.
- 차트는 본문에서 설명하는 하나의 중심 개념을 시각적으로 보강해야 합니다.
- 한 차트에 너무 많은 개념을 넣지 않습니다. 두 개 이상의 중심 개념이 섞이면 차트를 나눕니다.
- 외부 차트를 그대로 복사하지 않습니다. 필요한 경우 공개 라이선스와 인용 가능성을 확인하고, 가능하면 자체 도식으로 다시 작성합니다.
- 외부 자료의 도식이나 차트를 참고해 재작성한 경우에도 근거 메모에 출처와 재작성 여부를 남깁니다.
- 형식을 먼저 정하지 않고 내용을 억지로 밀어 넣지 않습니다. `비교`, `절차`, `좌표`, `구조`, `판단 흐름` 중 무엇이 중심인지 먼저 정한 뒤 형식을 고릅니다.
- 본문이 이미 충분히 설명한 내용을 표, 플로우차트, 도식으로 한 번 더 복창하지 않습니다. 새 형식은 반드시 `읽기 순서`, `비교 축`, `판단 단계`, `위치 관계` 중 하나를 더 선명하게 만들어야 합니다.

## 형식 선택 기준

### 빠른 판단

| 중심 질문 | 우선 형식 | 이유 |
| --- | --- | --- |
| 무엇이 더 큰가, 더 위험한가, 어디서 갈리는가 | Markdown 표 | 같은 축 위 비교가 핵심이기 때문입니다. |
| 어떤 순서로 읽어야 하는가, 어디서 판단이 뒤집히는가 | 플로우차트(Mermaid) | 단계와 분기 순서가 핵심이기 때문입니다. |
| 값이 어디에 놓이는가, 곡선이 어떻게 변하는가 | 좌표 기반 차트(SVG 등) | 위치와 상대 거리 자체가 설명이기 때문입니다. |
| 어떤 구성요소가 어떻게 연결되는가 | 구조 다이어그램(Mermaid/SVG) | 관계와 연결 구조가 핵심이기 때문입니다. |
| 본문 한두 문장으로 이미 충분한가 | 형식 추가 없음 | 새 형식이 읽기 부담만 늘릴 수 있기 때문입니다. |

### 형식별 역할

#### 표를 먼저 쓰는 경우

- 같은 항목들을 같은 비교 축 위에 나란히 놓아야 할 때
- `덜 나쁜 오독 / 더 위험한 오독 / 더 나은 읽기`처럼 열 구조가 해석을 직접 도울 때
- 숫자, 범주, 장면을 짧게 대조하면 독자가 바로 차이를 붙잡을 수 있을 때

#### 표를 피하는 경우

- 독자가 `1단계 -> 2단계 -> 3단계` 순서로 따라가야 할 때
- `약함 -> 경계 -> 강함`, `입력 -> 중간 조합 -> 최종 판단`처럼 시간적·논리적 진행이 핵심일 때
- 같은 표 안에 `비교 대상`, `절차`, `해석`, `다음 행동`이 한꺼번에 들어가 열 수가 늘어날 때
- 표를 읽기 전에 이미 긴 본문 해설이 필요한데, 표가 그 해설을 더 압축하지 못할 때

#### 플로우차트가 유리한 경우

- 판단 순서가 바뀌면 의미도 바뀌는 설명일 때
- 조건 분기, 경계 통과, 다음 단계 이동처럼 `어디서 갈리는가`가 중요할 때
- 사례 문단의 해석 순서를 짧게 다시 압축해 보여 주고 싶을 때
- 표로 적으면 `행 비교`보다 `절차 추적`이 먼저 필요한 내용일 때

#### 플로우차트를 피하는 경우

- 단순 수치 비교만 하면 충분할 때
- 노드 수가 늘어나 본문보다 도식을 해석하는 비용이 더 커질 때
- 비교 축이 핵심인데도 화살표 흐름으로 바꾸면서 오히려 표보다 덜 직접적이 될 때

#### 좌표 기반 차트가 유리한 경우

- 값의 크기, 거리, 포화, 기울기, 분포, 임계값 위치가 핵심일 때
- 같은 개념이라도 `어디에 위치하는가` 자체가 해설일 때

#### 구조 다이어그램이 유리한 경우

- 층, 모듈, 입력/출력, 관계, 포함 구조를 보여 줄 때
- 시간 순서보다 연결 구조 자체가 더 중요할 때

## 표와 플로우차트의 경계

- `무엇이 다른가`가 중심이면 표를 먼저 검토합니다.
- `어떻게 진행되는가`가 중심이면 플로우차트를 먼저 검토합니다.
- `무엇이 다른가`와 `어떻게 진행되는가`가 모두 필요하면, 한 형식에 억지로 같이 넣지 말고 본문에서 역할을 나눕니다.
- 같은 사례에서 표와 플로우차트를 함께 쓸 수는 있지만, 표는 `비교`, 플로우차트는 `절차 압축` 역할로 분리해야 합니다.
- 사례 바로 아래 표가 이미 `판단 순서`까지 자연스럽게 닫아 준다면 추가 플로우차트를 넣지 않습니다.
- 반대로 표가 있는데도 독자가 `그래서 먼저 무엇을 보고 다음에 무엇을 봐야 하는가`를 놓치면, 짧은 플로우차트가 더 적합할 수 있습니다.

## 읽기 어려워지는 패턴

- 플로우차트가 유리한 절차 설명을 비교 표로 길게 눌러 담는 경우
- 표 한 개에 `상태`, `원인`, `해석`, `다음 행동`, `예외`까지 모두 넣는 경우
- 같은 내용을 본문 문장, 표, 플로우차트에서 거의 같은 표현으로 세 번 반복하는 경우
- 좌표 설명이 필요한 내용을 박스-화살표 다이어그램으로만 처리하는 경우
- 구조 설명이 필요한 내용을 숫자 표로만 눌러 담는 경우
- 비교 표를 여러 개 연달아 둬서 독자가 `행 비교`보다 `표 사이 왕복`을 더 많이 하게 되는 경우

## 본문과의 역할 분담

- 본문 문단은 중심 질문과 핵심 해석을 담당합니다.
- 표는 같은 축 위 비교를 담당합니다.
- 플로우차트는 판단 순서 압축을 담당합니다.
- 좌표 차트는 위치와 변화 양상 설명을 담당합니다.
- 구조 다이어그램은 연결 관계와 구성 설명을 담당합니다.

- 같은 형식을 추가하기 전에 먼저 묻습니다.
  - 이 형식이 본문보다 읽기 순서를 더 선명하게 만드는가
  - 이 형식이 기존 표나 도식보다 새로운 비교 축을 제공하는가
  - 이 형식이 없으면 놓치는 핵심 판단이 실제로 있는가
  - 이 형식이 오히려 본문 해설 없이는 못 읽히는가

위 질문에 분명히 답하지 못하면 새 형식을 넣지 않는 편이 낫습니다.

## 차트 분리 기준

- 한 차트 안에 서로 다른 시각 언어가 섞이면 차트를 나누는 것을 먼저 검토합니다.
- 좌표축, 곡선, 점, 벡터처럼 위치 자체가 의미인 부분과 박스-화살표 흐름처럼 관계가 의미인 부분은 같은 차트에 억지로 넣지 않습니다.
- 위치가 중요한 부분은 SVG, Matplotlib, Vega-Lite 같은 정밀 차트 도구로 만들고, 단순 관계나 반복 흐름은 Mermaid, PlantUML, D2, Graphviz DOT 같은 다이어그램 도구로 분리합니다.
- 예를 들어 경사하강법을 설명할 때 손실 곡선 위의 이동은 SVG가 적합하고, `current parameters -> gradient -> learning rate -> update` 같은 반복 루프는 Mermaid가 적합합니다.
- 한 그림 안에서 `수학 그래프`와 `프로세스 흐름도`가 함께 필요하다면, 본문에서는 그래프를 먼저 보여 주고 이어서 흐름도를 따로 보여 주는 방식을 우선합니다.
- 독자가 한 번에 읽어야 하는 핵심 질문이 두 개 이상이면 차트를 분리합니다. 예를 들어 “곡선에서 어디로 움직이는가”와 “학습 루프가 어떤 단계로 반복되는가”는 서로 다른 질문입니다.

## 파일 형식과 위치

도식은 가능한 한 본문 코드블록을 MkDocs가 직접 렌더링하는 방식을 우선합니다.

현재 이 저장소의 MkDocs 설정에서 코드블록 직접 렌더링을 지원하는 형식은 Mermaid입니다. 도식 도구 목록은 실제로 코드블록 렌더링이 가능한 항목만 기준으로 관리합니다.

사전 렌더링된 SVG/PNG를 별도로 생성해 커밋하는 방식은 기본 원칙으로 삼지 않습니다. 직접 코드블록 렌더링이 불가능하거나, 좌표·수학 그래프·이미지 자산처럼 수동 제어가 필요한 경우에만 예외적으로 사용합니다.

| 도구 | 적합한 경우 | 주의할 점 |
| --- | --- | --- |
| Mermaid | 단순 흐름도, 개념 관계, 단계, 파이프라인, 상태 전이 | 세밀한 좌표, 곡선, 수학 그래프 표현에는 부적합할 수 있음 |

- 단순한 개념 흐름은 Mermaid를 우선 검토합니다.
- 코드블록 렌더링이 가능한 형식으로 표현할 수 있으면 Mermaid를 우선 사용합니다.
- 현재 저장소에서 코드블록 렌더링이 설정되지 않은 형식은 본문 도식의 기본 선택지로 두지 않습니다.
- 수학 개념, 모델 계산, 벡터·행렬, 변화율처럼 좌표와 위치가 중요한 설명은 Mermaid로 표현 가능한지 먼저 검토하고, 어렵다면 수동 SVG를 예외로 사용합니다.
- Mermaid 흐름도는 기본적으로 3열을 넘는 가로 배치를 제한합니다.
- 단계가 4개 이상이면 `LR` 한 줄 배치보다 `TD` 세로 배치, 2행 배치, 또는 ㄹ자 형태의 꺾인 배치를 먼저 검토합니다.
- 모바일과 좁은 본문 폭에서 축소될 가능성이 높은 도식은 `LR`로 긴 박스를 일렬 배치하지 않습니다.
- 머메이드 도식이 너무 세로로 길어질 것 같으면, `subgraph`를 써서 앞 단계를 한 묶음으로 만들고 다음 단계를 옆이나 아래로 꺾는 ㄹ자 배치를 우선 검토합니다.
- 긴 흐름에서 글자를 줄이기 전에 먼저 레이아웃을 바꿉니다. 박스와 화살표가 눌리면 `세로 배치`, `2행 배치`, `ㄹ자 배치`로 구조를 조정합니다.
- 긴 비교 흐름을 억지로 한 개의 Mermaid 안에 넣지 않습니다. 좌우 비교가 길어지면 비교 묶음을 두 개의 짧은 도식으로 분리하고, 분리된 각 도식은 다시 `LR` 짧은 가로 배치가 가능한지 검토합니다.
- `LR`는 짧은 2~3단계 흐름, 작은 비교, 국소적 전환 설명에 우선 사용합니다. `LR`로 만들었을 때 박스 폭이 눈에 띄게 줄거나 본문 폭을 가득 채우면 방향을 바꿉니다.
- Mermaid는 SVG처럼 세밀한 좌표 제어가 어렵기 때문에, 많은 문장을 박스 안에 넣어 레이아웃을 해결하려 하지 않습니다. 먼저 문구를 줄이고, 다음으로 도식을 나누고, 마지막으로 방향을 바꿉니다.
- Mermaid 도식에서 박스 안 글자가 유난히 작아 보이면 대개 박스 수가 너무 많거나 한 줄 폭이 너무 긴 경우입니다. 이 경우 글자 크기를 건드리기보다 노드 수를 줄이거나 2개의 도식으로 나눕니다.
- Markdown 표로 충분한 비교는 차트로 만들지 않습니다.
- 복잡한 그림은 직접 코드블록 렌더링이 어려운 경우에만 `docs/assets/` 아래에 SVG 또는 PNG로 저장합니다.
- 수동 SVG를 예외로 사용할 때는 SVG 자체를 원본으로 봅니다.
- 이미지 파일은 해당 본문 위치에 맞춰 `docs/assets/part-XX/chapter-YY/` 아래에 둡니다.
- Mermaid는 원본 코드블록을 본문에 남깁니다.
- 현재 저장소는 `pymdownx.snippets`와 `pymdownx.superfences`를 함께 써서, Mermaid 외부 원본 파일(`.mmd`, `.mermaid`)을 본문 코드블록 안에 include한 뒤 렌더링할 수 있습니다.
- 따라서 Mermaid도 필요하면 `docs/assets/` 아래의 외부 원본 파일로 분리해 관리할 수 있습니다. 다만 렌더링 결과는 여전히 본문 Markdown의 ` ```mermaid ` 코드블록 안에서 이루어지므로, 본문 참조와 자산 파일 쌍을 함께 관리해야 합니다.
- 공개 본문 자산의 실제 저장소는 `docs/assets/` 하나입니다. 언어별 본문 디렉터리는 자산 저장소가 아니라 자산 참조자입니다.
- Mermaid snippet include는 `mkdocs.yml`의 `pymdownx.snippets.base_path = docs`를 기준으로 해석하므로, 본문에서는 `assets/...` 경로를 공용 자산 루트 참조로 사용합니다.
- 일반 Markdown 이미지 링크, 파일 링크, 예제 링크는 각 본문 파일 위치에서 `../../../assets/...` 같은 상대경로로 연결합니다.
- Mermaid를 언어별 자산처럼 분리 관리할 때는 include 경로, 언어별 파일명, 기준 원본을 함께 맞춥니다. 이때도 새 도식 파일만 두고 본문 참조를 빼먹지 않도록 주의합니다.
- 다국어를 도입하면 도식도 언어별 자산으로 함께 운영합니다.
- 기준 원본은 둘 수 있지만, 배포 원고에 삽입하는 자산은 항상 해당 언어 도식이어야 합니다.
- 도식 내부 텍스트가 있는 SVG, Mermaid, 기타 텍스트 기반 도식은 본문 언어와 같은 언어로 번역해 배치합니다.
- 언어별 도식 파일은 예외가 아니라 기본 운영 단위입니다.
- 언어별 도식 파일을 만들면 파일명, 자산 위치, 기준 원본, 동기화 순서를 일관되게 정하고 관리 메모에 남깁니다.
- 언어별 도식 파일명에는 언어 약어를 반드시 붙입니다. 영문 원본은 `-en`, 한글 파생본은 `-ko`처럼 파일명 끝에 언어 약어를 붙입니다.
- 한글, 영어, 중국어 도식은 같은 의미 구조를 공유하되, 배포 원고에서는 각 언어 자산을 직접 참조합니다.
- 본문에서 어떤 언어 도식을 참조하는지도 명시적으로 관리합니다. 한국어 본문은 `-ko`, 영어 본문은 `-en`, 중국어 본문은 `-zh` 자산을 참조하는 것을 기본으로 합니다.
- 지금처럼 Mermaid를 본문 코드블록으로 렌더링하더라도, 외부 `.mmd` 파일로 분리한 경우에는 `-ko`/`-en`/`-zh` 자산 쌍 또는 세트를 유지할 수 있습니다.
- 배포 안정성을 위해 GitHub Pages 빌드 환경에도 해당 렌더러가 설치되어 있어야 합니다. 새 코드블록 렌더러를 추가하면 `.github/workflows/deploy.yml`의 설치 단계도 함께 확인합니다.
- 본문에 직접 코드블록으로 넣을 수 있는 형식인지 도식 작성 전에 확인하고, 가능하면 코드블록 렌더링을 우선합니다.

## Mermaid 자산 운영

- Mermaid는 "본문 안에 적는 일회성 코드"보다 `docs/assets/` 아래에서 재사용·동기화하는 "텍스트 자산"으로 관리할 수 있습니다.
- 자산으로 관리하는 Mermaid의 최소 단위는 `본문 참조 1개 + 배포 언어별 대응 .mmd 파일 세트 + 자산 폴더 README`입니다.
- 본문 Markdown은 렌더링 진입점이고, 실제 도식 원본은 `docs/assets/part-XX/chapter-YY/` 아래 `.mmd` 파일로 본다고 가정합니다.
- Mermaid를 외부 자산 파일로 분리할 때는 기본적으로 `docs/assets/part-XX/chapter-YY/` 아래에 둡니다.
- 현재 본문에서 `assets/...` 경로를 include하더라도, 그 기준 경로는 `docs/assets/` 원본 저장소로 해석해 관리합니다.
- 파일 확장자는 기본적으로 `.mmd`를 사용합니다. 특별한 이유가 없으면 `.mermaid`와 혼용하지 않습니다.
- 언어별 파일명에는 언어 약어를 반드시 붙입니다. 영문 기준 원본은 `-en.mmd`, 한글 자산은 `-ko.mmd`, 중국어 자산은 `-zh.mmd`를 사용합니다.
- 중국어 간체판처럼 추가 번역 경로가 실제로 본문을 운영하고 있으면, 도식 내부 라벨도 같은 규칙으로 `-zh.mmd`에 번역해 함께 유지합니다.
- 한국어, 영어, 중국어 본문은 각각 대응 언어 `.mmd`를 직접 include하도록 관리합니다.
- 언어별 자산 호환용 symlink는 두지 않습니다. 경로 문제는 `snippet include는 assets/...`, 일반 링크는 상대경로`라는 두 규칙으로 해결합니다.
- 자산 폴더에는 가능하면 짧은 `README.md`를 두고, 어떤 본문이 어떤 파일을 참조하는지와 `영문 원본 우선 수정 -> 한글 파생본 동기화` 원칙을 함께 적습니다.
- 외부 Mermaid 자산을 본문에 넣을 때는 다음 패턴을 기본으로 사용합니다.

```md
```mermaid
--8<-- "assets/part-05/chapter-01/perceptron-flow-ko.mmd"
```
```

- 한국어 본문은 기본적으로 `-ko.mmd`를 include하고, 대응 `-en.mmd`는 향후 번역용 기준 원본으로 같은 폴더에 보관합니다.
- 기준 원본을 먼저 수정한 뒤, 다른 언어 도식도 같은 작업 안에서 같은 의미 구조와 같은 노드 관계를 유지한 채 라벨과 최소 레이아웃을 함께 동기화합니다.
- 아직 번역 본문 경로가 열리지 않은 Section에서는 현재 배포 중인 언어 자산만 먼저 둘 수 있습니다. 이 경우 자산 폴더 `README.md`에 현재 운영 중인 언어 범위를 남기고, 새 언어 본문을 열 때 대응 도식 자산도 함께 추가합니다.
- 같은 Section 안에 Mermaid가 여러 개 있더라도, 각 도식은 파일을 분리해 이름만 보고 역할을 알 수 있게 둡니다. `diagram-1.mmd`, `figure-final.mmd` 같은 임시 이름은 피합니다.
- 다만 기존 원고를 대량 전환하는 정리 단계에서는 도식 역할명을 즉시 안정적으로 짓기 어렵다면 `Section ID + mermaid 순번` 기반 이름을 우선 사용할 수 있습니다. 예를 들어 `p4-2-1-mermaid-01-ko.mmd`처럼 Section 기준으로 추적 가능하게 두고, 이후 구조가 안정되면 더 설명적인 이름으로 바꿉니다.
- 기존 본문의 인라인 Mermaid를 자산 파일로 옮길 때는 먼저 동일한 렌더링 결과가 나오게 분리하고, 그 다음 단계에서만 언어쌍 정리나 레이아웃 보정을 합니다.
- 외부 Mermaid 자산을 추가하거나 바꾸면 다음 네 가지를 함께 확인합니다.
  - 본문 Markdown의 include 경로가 실제 파일과 일치하는가
  - 현재 배포 중인 언어별 `.mmd` 파일 세트가 모두 있는가
  - 각 언어 본문이 자기 언어 자산을 직접 참조하고 있는가
  - 자산 폴더 `README.md`의 파일 목록과 운용 원칙이 최신 상태인가
  - 해당 Section의 릴리즈노트에 관련 자산 경로와 운용 변경 사실이 반영됐는가
- SVG처럼 좌표 기반 자산도 언어별 자산 운영을 기본 원칙으로 합니다. 본문에 삽입하는 SVG는 한국어 본문이면 `-ko.svg`, 영어 본문이면 `-en.svg`, 중국어 본문이면 `-zh.svg`를 사용합니다.
- Mermaid 자산을 SVG/PNG처럼 별도 산출물로 다시 커밋할 필요는 없습니다. 이 저장소에서 Mermaid의 배포 산출은 MkDocs 렌더링 결과이고, 저장소가 관리하는 원본은 `.mmd` 파일입니다.
- 본문 안에 직접 적는 Mermaid 코드블록을 외부 자산 파일로 승격할 때는, 도식 내용만 옮기고 설명 문단의 의미를 함께 바꾸지 않습니다. 먼저 도식 참조 방식만 분리한 뒤, 필요하면 별도 수정으로 라벨 언어와 문장 호흡을 조정합니다.

## 도구 선택 기준

| 목적 | 우선 도구 | 저장 방식 |
| --- | --- | --- |
| 개념 흐름, 모델 구조, 학습 순서 | Mermaid | Markdown 코드 블록 |
| 간단한 수치 비교 | Markdown 표 | Markdown |
| 데이터 기반 정적 차트 | Python 또는 Vega-Lite | 스크립트와 이미지 |
| 복잡한 시스템 구조 | Mermaid 또는 수동 SVG | 원본 코드 또는 SVG |
| 논문 그림 재구성 | 직접 작성한 SVG/PNG | 이미지와 출처 |

이 표는 빠른 선택 기준이다. 실제 적용 판단은 이 문서의 `파일 형식과 위치`, `차트 분리 기준`, `검증` 항목을 함께 본다.

## 도구 대체 판단 메모

- `prior belief -> evidence -> posterior belief`처럼 단계 흐름이 중심이면 Mermaid를 우선한다.
- 모집단, 표본, 데이터셋의 포함 관계나 train/test 분할 흐름처럼 개념 관계가 중심이면 Mermaid로 충분한 경우가 많다.
- `input -> model -> prediction -> loss -> objective` 같은 계산 단계 흐름도 Mermaid를 우선 검토한다.
- 경사하강법처럼 `곡선 위 이동`과 `업데이트 루프`가 함께 필요하면 하나의 그림에 억지로 넣지 않는다. 손실 곡선은 SVG로, `current parameters -> gradient -> learning rate -> update` 반복은 Mermaid로 분리하는 편이 낫다.
- 수학 그래프, 벡터·행렬 변환, 분포 비교, 확률 점수와 threshold 위치처럼 좌표와 상대 위치 자체가 설명인 경우에는 SVG를 유지한다.
- Mermaid로 바꿨을 때 설명력이 떨어지지 않는지 먼저 본다. 유지보수 편의가 설명 정확도보다 앞서면 안 된다.

## SVG 기본 구조

- SVG에는 반드시 `<title>`과 `<desc>`를 넣어 접근성과 검색 가능성을 확보합니다.
- 단일 개념 차트는 기본 `viewBox="0 0 760 430"`을 우선 사용합니다.
- 좌우 비교, 전후 비교, 변환 전후처럼 두 패널이 필요한 차트는 `viewBox="0 0 920 430"`을 사용할 수 있습니다.
- 2x2 패널, 여러 카드, 하단 요약 박스를 함께 사용하는 비교 도식은 기본 높이에 맞추려고 억지로 압축하지 않습니다. 패널 내부 도식이 아래로 밀리면 `viewBox` 높이와 패널 높이를 먼저 늘립니다.
- 흐름 화살표, 반복 루프, 하단 요약 박스가 함께 들어가면 `viewBox` 높이를 늘려 충분한 여백을 둡니다.
- 배경은 단순하게 유지합니다.
- 의미 없는 그라데이션, 불필요한 그림자 효과, 장식용 도형을 넣지 않습니다.

## 수학 차트의 구성 요소

수학 차트에는 가능하면 다음 요소를 일관되게 둡니다.

- 제목 또는 핵심 메시지
- 축(axis) 또는 기준선
- 격자(grid) 또는 눈금(tick)
- 주요 점(point), 선(line), 벡터(vector), 구간(interval)
- 변화량 표시: `Δx`, `Δy`, 방향 화살표 등
- 차트 아래 한 문장 요약

모든 요소가 항상 필요하지는 않습니다. 다만 독자가 차트만 보고도 “무엇을 보라는 것인가”를 파악할 수 있어야 합니다.

## 색상 기준

차트의 색상 의미는 일관되게 사용합니다.

| 역할 | 색상 방향 |
| --- | --- |
| 기본 함수, 주 곡선, 주요 벡터 | 파란색 계열 |
| 변화량, 증가, 비교 강조 | 빨간색 계열 |
| 입력 변화, 기준 이동, 보조 방향 | 초록색 계열 |
| 축, 보조선, 흐름 화살표 | 회색 계열 |
| 반복, 되돌아가기, 업데이트 루프 | 파란색 계열 점선 |

색상만으로 의미를 전달하지 않습니다. 라벨, 선 종류, 위치 설명을 함께 둡니다.

- 그래프의 곡선과 동작 화살표가 한 차트에 함께 있으면 같은 색상 계열을 쓰지 않습니다.
- 그래프 곡선은 값이나 함수의 형태를 보여 주고, 화살표는 이동, 반복, 흐름을 보여 주므로 시각 역할을 분리합니다.
- 이 경우 곡선은 청록색, 짙은 중립색, 보라색 등으로 분리하고, 업데이트나 반복 화살표는 파란색 또는 회색 계열로 유지할 수 있습니다.
- 단일 차트 안에서 같은 색은 같은 의미를 가져야 합니다. 같은 파란색이 곡선과 이동 화살표를 동시에 뜻하게 만들지 않습니다.

## 화살표와 흐름 표시

- 차트의 핵심 흐름은 화살표만 보고도 방향을 알 수 있어야 합니다.
- 주요 흐름 화살표는 배경, 카드, 요약 박스와 겹치지 않게 배치합니다.
- 반복 루프나 되돌아가는 화살표는 일반 흐름 화살표보다 굵게 표시하고, 점선이나 색상으로 구분합니다.
- 반복 루프는 하단 요약 문구와 겹치기 쉽기 때문에 요약 박스를 아래로 분리하거나 루프를 별도 여백에 둡니다.
- 화살표 머리는 모바일에서도 보이도록 충분히 크게 둡니다.
- 화살표 머리는 선 두께와 균형을 맞춥니다. 머리만 과하게 크면 흐름보다 장식처럼 보이므로 마커 크기를 줄이거나 선 두께를 함께 조정합니다.
- 화살표가 선, 카드 테두리, 텍스트와 가까우면 의미가 약해지므로 주변에 여백을 둡니다.
- 화살표 머리는 내용 박스 안쪽으로 파고들지 않게 합니다. 박스를 가리키는 화살표는 끝점을 박스 테두리 바깥이나 테두리 직전으로 두고, 머리가 텍스트 영역을 덮지 않는지 확인합니다.
- 화살표가 카드 사이의 관계를 보여 줄 때는 카드 내부 텍스트보다 카드의 바깥 경계나 빈 여백을 향하게 합니다.
- 흐름을 설명하는 라벨은 화살표 바로 위나 아래에 둘 수 있지만, 선과 겹치면 안 됩니다.
- 화살표 라벨이 선과 가까우면 흰색 또는 배경색 캡슐 박스 안에 넣어 독립된 읽기 영역으로 만듭니다.
- 화살표가 굵어질수록 라벨은 더 멀리 두거나 별도 박스로 분리합니다.
- 되돌아가는 루프는 본문 요약 박스 위를 통과하지 않게 하고, 요약 박스와 최소한 한 줄 높이 이상의 간격을 둡니다.
- 좌우 패널을 연결하는 전환 화살표는 라벨과 따로 떨어뜨려 두지 않습니다. `same data`, `convert`, `then` 같은 전환 라벨은 화살표 위의 캡슐 박스 또는 화살표 시작점 근처의 한 묶음으로 배치해 독자가 라벨을 어느 흐름에 붙여 읽어야 하는지 알 수 있게 합니다.
- 좌우 패널 사이의 중앙 전환 영역은 너무 넓게 비워 두지 않습니다. 패널 간격이 넓으면 전환 라벨, 짧은 화살표, 방향 표시를 중앙 정렬해 두 패널의 관계가 끊겨 보이지 않게 합니다.
- 머메이드 흐름도에서 박스 수가 많아지면 화살표 길이가 길어지고 박스가 축소되기 쉬우므로, 화살표와 박스 비율이 무너지기 전에 레이아웃을 꺾습니다.

## 겹침 방지 기준

- 텍스트는 선, 화살표, 카드 테두리, 아이콘, 데이터 점과 겹치면 안 됩니다.
- 카드 내부 텍스트는 카드 테두리와 충분한 안쪽 여백을 둡니다.
- 패널형 차트에서는 모든 내부 도형, 선, 노드, 라벨이 패널 경계 안에 들어와야 합니다. 내부 요소가 패널 밖으로 삐져나오면 패널 높이를 늘리거나 내부 도식을 위로 재배치합니다.
- 패널형 차트에서는 제목과 설명문이 있는 상단 헤더 영역을 별도로 보호합니다. 노드, 선, 카드, 표 같은 도식 요소는 패널 제목과 설명문 아래에 충분한 간격을 두고 시작해야 합니다.
- 패널 내부 요소는 패널 경계선에 닿기 전에 최소 24px 이상의 안쪽 안전 여백을 남깁니다. 텍스트 길이를 포함한 실제 오른쪽 끝과 아래쪽 끝을 기준으로 확인합니다.
- Mermaid를 사용하는 경우에도 같은 원칙을 적용합니다. 렌더러가 자동 배치하더라도 결과 SVG에서 첫 노드가 상단 헤더를 밀거나 마지막 노드가 하단 문장을 압박하면, 원본 Mermaid 구조를 다시 나눕니다.
- 전체 SVG에서도 모든 텍스트, 카드, 화살표 머리, 데이터 박스는 `viewBox` 안쪽에 완전히 들어와야 합니다. 생성 후 오른쪽과 아래쪽 경계에서 잘리는 요소가 없는지 먼저 확인합니다.
- 같은 줄에 여러 값 박스를 배치할 때는 마지막 박스의 오른쪽 끝을 계산합니다. 박스 묶음이 패널을 넘으면 간격을 줄이기보다 묶음 전체를 왼쪽으로 옮기거나 박스 크기와 문구를 줄입니다.
- 결과 패널(result panel)은 내부 텍스트가 길어지기 쉽습니다. `row 0 + offset`처럼 긴 반복 문구가 경계를 넘으면 `row 0`처럼 짧게 줄이고 본문이나 캡션에서 의미를 설명합니다.
- 행렬, 표, 배열처럼 축(axis) 또는 방향 화살표를 함께 설명하는 도식에서는 축 화살표와 축 라벨까지 패널 내부 요소로 계산합니다. 표 본체만 패널 안에 맞추지 말고, 축 라벨의 실제 하단 위치와 공통 요약 박스 사이에 여백을 확보합니다.
- 축 라벨이 패널 아래쪽에 놓이면 공통 하단 요약 박스와 쉽게 겹칩니다. 이 경우 요약 박스를 아래로 내리거나 `viewBox`와 패널 높이를 늘려 축 라벨을 패널 내부에 완전히 포함시킵니다.
- 축 라벨은 표, 행렬, 강조 셀과 겹치지 않게 배치합니다. 긴 문장형 라벨보다 `axis 0: rows`, `axis 1: columns`처럼 짧은 라벨을 우선하고, 필요하면 배경 캡슐을 둡니다.
- 축이나 전환 화살표의 라벨은 화살표와 시각적으로 붙어 있어야 합니다. 라벨이 화살표에서 떨어져 보이면 캡슐 박스를 화살표 바로 위나 아래에 두고 중앙을 맞춥니다.
- 축 방향 계산 결과의 `result shape` 같은 결과 라벨은 결과 패널 내부에 둡니다. 패널 밖으로 밀려나면 라벨을 억지로 아래에 두지 말고 패널 높이와 `viewBox`를 늘립니다.
- 표, 행렬, 배열의 행·열 라벨과 마지막 행은 하단 요약 박스에 가려지면 안 됩니다. 데이터 본체가 패널 하단에 가까우면 패널과 `viewBox`를 먼저 늘립니다.
- 코드 표현과 설명 문장을 같은 캡슐 안에 넣을 때는 충분한 가로 폭이 확인된 경우에만 같은 줄을 사용합니다. 코드가 길면 코드와 설명을 두 줄로 쌓아 겹침을 방지합니다.
- 슬라이스, 범위, 경계값처럼 아래쪽 주석이 많은 도식은 주석까지 패널 내부 요소로 봅니다. `kept`, `stop before`, `step by` 같은 라벨과 하단 요약 박스 사이에 충분한 간격을 둡니다.
- 패널 안에 `Question: ...` 같은 설명문이 있으면, 원형 노드나 연결선이 해당 문장 위로 올라오지 않게 합니다. 패널 안쪽에서 헤더 영역과 도식 영역을 시각적으로 분리합니다.
- 트리(tree)나 그래프(graph)처럼 노드-엣지 구조가 들어가는 패널은 원형 노드 반지름과 하단 라벨 높이를 포함한 실제 bounding box를 계산해 패널 안쪽 여백을 확보합니다.
- 좌우 비교 차트에서는 양쪽 패널의 내부 도식 중심이 비슷한 높이와 밀도로 보이게 맞춥니다. 한쪽 도식이 지나치게 오른쪽이나 아래쪽으로 치우치면 비교보다 배치 불균형이 먼저 보입니다.
- 2x2 비교 도식에서는 상단 패널과 하단 패널의 시각 밀도를 맞추되, 하단 패널의 도식이 요약 박스와 가까워지면 요약 박스를 아래로 내리거나 `viewBox` 높이를 늘립니다.
- 차트 하단 요약 문구는 도식의 일부가 아니라 해석 문장입니다. 흐름선, 루프, 화살표 머리와 분리합니다.
- 하단 요약 박스는 마지막 패널 또는 마지막 도식 요소와 최소 24px 이상의 수직 간격을 둡니다.
- 하단 요약 문장은 박스 폭 안에 실제로 들어가는 길이로 제한합니다. 문장이 길면 박스를 넓히기보다 핵심 문장으로 줄이고, 세부 설명은 본문으로 보냅니다.
- 전체 차트를 요약하는 문구는 특정 패널 내부에 넣지 말고, 가능하면 패널 밖의 공통 하단 요약 박스로 분리합니다.
- Mermaid 도식 바로 아래에 이어지는 본문 문장이나 목록도 사실상 하단 요약과 같은 충돌 위험을 가집니다. 도식 끝점과 다음 문단 사이가 지나치게 붙어 보이면, 본문을 줄이기보다 도식을 더 단순한 구조로 다시 그립니다.
- 패널 내부에 보조 설명 박스를 둘 때는 같은 패널의 코드 박스, 표, 노드-엣지 도식과 최소 24px 이상의 간격을 둡니다. 간격을 확보하기 어렵다면 보조 설명을 본문이나 전체 하단 요약으로 옮깁니다.
- 패널 내부 보조 설명 박스의 문구는 짧게 유지합니다. 긴 해석 문장은 패널 밖 공통 요약, 이미지 앞뒤 본문, 또는 체크리스트로 이동합니다.
- 노드-엣지 도식에서 엣지 위 숫자 라벨은 선 위에 바로 얹지 말고 배경 박스와 함께 선에서 약간 떨어뜨립니다. 숫자가 노드 테두리나 다른 엣지와 가까우면 라벨 위치를 조정해 숫자와 연결선의 역할을 분리합니다.
- 코드처럼 줄 단위 텍스트가 들어가는 박스는 마지막 줄이 테두리에 닿지 않도록 아래쪽 내부 여백을 둡니다. 닫는 중괄호, 괄호, 마지막 코드 줄이 박스 경계선과 겹쳐 보이면 박스 높이를 늘리거나 텍스트 y 좌표를 조정합니다.
- 강조 박스, 라벨 박스, 요약 박스가 서로 붙어 있으면 독자는 하나의 요소로 오해할 수 있으므로 시각적 간격을 둡니다.
- 텍스트가 선 위에 올라가면 선을 옮기는 것을 우선하고, 어려우면 텍스트에 배경 박스를 둡니다.
- 한 줄 라벨이 길어져 화살표나 도형과 충돌하면 문구를 줄이거나 두 줄로 나눕니다.
- 차트 안에서 가장 중요한 흐름은 가장 먼저 보이도록 하고, 보조 설명은 별도 박스나 본문 설명으로 넘깁니다.

## 글자와 라벨

- SVG 안의 텍스트는 모바일에서도 읽히도록 너무 작게 만들지 않습니다.
- 일반 라벨은 14px 이상, 제목은 18px 이상을 기준으로 합니다.
- 화살표 라벨, 요약 문구, 카드 내부 설명이 서로 겹치지 않도록 세로 여백을 먼저 확보합니다.
- 차트 안 문구가 짧을수록 좋지만, 의미를 잃을 정도로 축약하지는 않습니다. `task`, `decision`, `baseline`처럼 표준 용어는 유지하고, 설명 문장은 본문이나 캡션으로 뺍니다.
- 한 도표 안에서는 텍스트 정렬 규칙을 먼저 정하고 일관되게 적용합니다.
- 패널 제목, 설명 문장, 긴 문구는 좌측 정렬을 기본으로 합니다.
- 작은 카드, 원, 버튼형 박스처럼 짧은 상태값이나 후보명을 담는 요소는 가운데 정렬을 사용할 수 있습니다.
- 가운데 정렬을 사용할 때는 눈대중으로 `x` 좌표를 보정하지 말고, 요소의 중앙 좌표와 `text-anchor="middle"`을 사용합니다.
- 같은 성격의 요소는 같은 정렬 방식을 사용합니다. 예를 들어 후보 카드가 가운데 정렬이면 선택 결과 카드와 거절 카드도 가운데 정렬합니다.
- 좌측 정렬 요소와 가운데 정렬 요소가 한 차트에 함께 있을 수는 있지만, 역할이 달라야 합니다. 설명문은 좌측 정렬, 짧은 라벨은 가운데 정렬처럼 구분합니다.
- 차트 내부의 보이는 문구는 해당 본문 언어로 작성합니다.
- 각 언어 본문은 차트 앞뒤 문장, 이미지 대체 텍스트, `<desc>`, 근거 메모도 해당 언어와 맞춰 관리합니다.
- 다른 언어를 추가하면 같은 원칙을 적용합니다. 도식 안 문구와 본문 해설을 함께 그 언어로 맞춥니다.
- 언어별 도식을 만들 때도 의미 구조와 시각 구조는 최대한 같게 유지하고, 바뀌는 것은 주로 라벨 언어와 그에 따른 최소한의 레이아웃 조정이어야 합니다.
- 기준 원본이 무엇이든, 다른 언어 도식은 같은 작업 안에서 함께 동기화합니다.
- 수학 기호, 함수식, 표준 용어는 영어 또는 기호를 함께 사용합니다.
- 본문에서 이미 설명한 용어라도 차트 안에서는 짧은 라벨을 붙입니다.

## 본문 삽입 기준

- 본문에서 차트를 삽입할 때는 이미지 바로 앞뒤에 차트가 무엇을 보여 주는지 짧게 설명합니다.
- 차트는 본문을 대체하지 않습니다. 본문 설명을 보강하는 역할로 사용합니다.
- 차트가 본문 주장에 근거로 쓰이면 근거 메모에 차트의 목적, 자체 제작 여부, 외부 자료 참조 여부를 남깁니다.
- 시각화 파일을 추가할 때는 가능하면 다음 정보도 함께 남깁니다.
  - 무엇을 설명하는 그림인지
  - 어떤 데이터나 자료를 바탕으로 만들었는지
  - 자동 생성인지 수작업 작성인지
  - 외부 자료를 참고했다면 출처
  - 공용 자산인지, 언어별 자산인지
  - 언어별 자산이라면 기준 원본과 동기화 대상 언어
  - 영문 기준 원본에서 파생되었는지 여부

## 검증

- 새 차트를 추가하더라도 즉시 `mkdocs build`를 반복하지 않고, 차트가 포함된 파트를 포함해 전체 파트 점검이 끝난 뒤 `mkdocs build`로 링크와 렌더링 오류를 함께 확인합니다.
- 모바일 화면에서 라벨이 너무 작거나 잘리지 않는지 확인합니다.
- 수식, 축, 화살표가 본문 설명과 모순되지 않는지 확인합니다.
- SVG를 직접 브라우저에서 열어 화살표, 라벨, 요약 박스가 겹치지 않는지 확인합니다.
- MkDocs 페이지에 삽입된 상태에서도 확인합니다. 단독 SVG와 본문 삽입 상태의 표시 크기가 다를 수 있습니다.
- 차트를 수정한 뒤에는 다음 항목을 눈으로 확인합니다.
  - 화살표 방향이 명확한가
  - 화살표 머리가 보이는가
  - 라벨이 선이나 화살표와 겹치지 않는가
  - 하단 요약 문구가 도식 요소와 분리되어 있는가
  - 모바일 폭에서도 텍스트가 잘리거나 겹치지 않는가
  - Mermaid 박스 안 글자가 다른 차트보다 유난히 작아지지 않았는가
