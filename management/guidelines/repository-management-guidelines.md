# 저장소 관리 가이드라인

이 문서는 `AGENTS.md`에서 분리한 저장소 구조, 관리 문서 역할, 브랜치, 배포, 편집, 검증 기준을 다룬다. AI 에이전트는 `AGENTS.md`로 초기 방향을 잡은 뒤, 저장소 운영 판단이 필요하면 이 문서를 확인한다.

## 문서 위치

- 이 저장소는 MkDocs + Material for MkDocs 기반이다.
- 독자에게 배포할 책 본문은 `docs/` 아래 Markdown 파일로 작성한다.
- 사이트 소개 페이지 `docs/index.md`와 독자용 목차 설명 페이지 `docs/table-of-contents.md`도 배포 본문으로 관리한다.
- 책 본문은 Part 단위로 `docs/parts/part-XX/` 아래에 둔다.
- 각 Part의 개요는 `docs/parts/part-XX/index.md`로 작성하고, 장별 본문은 `docs/parts/part-XX/chapter-YY/section-ZZ.md` 형식으로 작성한다.
- 각 Part에는 시작 페이지와 마무리 페이지가 있어야 한다.
- Part 시작 페이지는 `docs/parts/part-XX/index.md`를 사용한다.
- Part 마무리 페이지는 `docs/parts/part-XX/summary.md`를 사용한다.
- 배포 목차는 `mkdocs.yml`의 `nav`에서 관리한다.
- `docs/index.md`와 `docs/table-of-contents.md`는 Part 본문 밖에 있는 공개 진입 문서이므로, 본문 메타데이터 관리 대상에 포함한다.
- `docs/index.md`는 릴리즈노트 관리 대상에 포함하지만, `docs/table-of-contents.md`는 독자용 목차 갱신이 잦으므로 별도 Section 릴리즈노트를 운영하지 않는다.
- 개념사전 공개 진입 파일은 `docs/reference/concept-glossary.md`이고, 항목 본문은 `docs/reference/concept-glossary-terms/`에서 단어별 원고로 관리한다.
- 개념사전 색인과 다국어 탐색 파일은 `concept-glossary-guidelines.md`를 따른다.
- 집필 기준, 조사 자료, 근거 분석, 작성 원칙은 `management/` 아래에 둔다.
- `management/README.md`는 관리 문서의 역할 분담과 위치를 설명하는 인덱스로 사용한다.
- 릴리즈노트는 `management/release-notes/` 아래에 모아 둔다.
- `mkdocs.yml`의 `nav`에는 배포할 책 본문만 연결하고, 관리자료는 연결하지 않는다.
- `.tmp/`는 외부 자료 원문 확인을 위한 임시 작업공간이며 커밋하지 않는다.
- `site/`는 빌드 산출물이며 명시적 지시 없이 커밋하지 않는다.

## 역할 분담

- `AGENTS.md`는 AI 에이전트가 가장 먼저 확인하는 초기 라우팅 문서다.
- `management/README.md`는 관리 문서 전체의 역할 분담과 위치를 안내한다.
- `management/guidelines/README.md`는 가이드라인 폴더 안 문서의 범위와 포함·제외 기준, 작업 유형별 참조 순서를 맡는다.
- 세부 절차, 예외 규칙, 반복 체크 항목, 유형 분류 기준은 가능한 한 개별 가이드라인 문서에서만 관리한다.
- 같은 규칙을 여러 문서에 반복해서 자세히 적지 않는다.
- 원고 표현, Python 예제, 차트·도식, 번역, 개념사전처럼 세부 판단이 필요한 항목은 해당 가이드 문서 위치를 먼저 안내하는 인덱스 방식으로 운영한다.
- 다음처럼 작업 중 빠뜨리기 쉬운 확인 포인트는 `AGENTS.md`에도 짧게 중첩할 수 있다.
  - 전용 가이드를 먼저 봐야 하는 작업이라는 점
  - Python 기준 소스 유지, 판단 종결 표현 금지, 다음 Part/Section 안내 절제처럼 본문 작성 중 자주 놓치는 표현 기준
  - `main` 푸시가 곧 배포라는 점

## 작업 관리

- 작업 전에는 현재 브랜치와 변경 범위를 확인한다.
- Section 본문 작업은 `Section ID`를 기준으로 추적한다.
- Section 본문을 수정했다면 본문 메타데이터와 릴리즈노트 연결을 함께 확인한다.
- 개념사전은 전용 가이드에 따라 릴리즈노트 연결 대상에서 제외한다.
- 원고 수정, 예제 추가, 도식 추가, 번역, 목차 변경처럼 전용 가이드가 있는 작업은 해당 가이드를 먼저 확인한다.
- 작업 중에는 관련 없는 기존 변경을 되돌리거나 함께 커밋하지 않는다.
- 작업 완료 전에는 변경 파일, 본문 구조, 링크, 메타데이터, 릴리즈노트 정합성을 확인한다.

## 다국어 구조

- 현재 기본 집필 언어는 한국어다.
- 다국어 원고의 대응 관계는 파일명보다 `Section ID`를 기준으로 추적하며, `management/release-notes/sections/`의 릴리즈노트로 확인할 수 있어야 한다.
- 언어별 본문, 공용 자산, 언어별 보조 자산의 경계를 먼저 분리한다.
- 공용 자산은 가능한 한 하나만 유지하고, 언어마다 달라지는 설명은 본문, 캡션, 대체 텍스트, 용어 해설에서 처리한다.
- 다국어 도입 전까지는 기존 `docs/` 구조를 유지하되, 새 파일과 자산 이름은 특정 언어에 과도하게 종속되지 않게 짓는다.
- 다국어 구조를 도입하면 각 언어 사이트의 `nav`는 별도로 관리할 수 있지만, Part/Chapter/Section의 개념 구조와 학습 순서는 가능한 한 서로 대응되게 유지한다.
- 특정 언어에서만 문서를 먼저 작성한 경우, 다른 언어 문서가 아직 없다는 이유로 공용 자산 경로나 본문 식별 체계를 임시 이름으로 어지럽히지 않는다.
- 다국어 배포를 시작하면 링크 정책도 함께 점검한다.
  - 내부 링크는 가능한 한 같은 언어 파일을 우선 가리킨다.
  - 언어 전환이 필요한 경우에만 명시적으로 다른 언어 문서로 이동시킨다.
  - 언어별 개념사전 링크, 다국어 내부 링크, 자산 링크의 실제 경로 형식은 각 번역 가이드와 차트 가이드라인의 운영 규칙을 따른다.
- 다국어 배포를 시작하면 `mkdocs.yml`, 플러그인 설정, `nav`, 검색 설정, 배포 워크플로를 한 번에 검토한다.

## Part 구조

- Part 시작 페이지와 마무리 페이지는 각각 오버뷰와 요약 역할을 맡는다.
- Part 시작/마무리 페이지의 세부 포함 항목과 작성 순서는 `manuscript-writing-workflow.md`를 따른다.
- 새 Part를 만들거나 Part 구조를 바꾸면 `index.md`, `summary.md`, `mkdocs.yml`의 `nav` 반영 여부를 함께 확인한다.

## 브랜치와 배포

- `dev`는 일반 작성과 편집 브랜치다.
- `main`은 배포 브랜치다.
- `main`에 push되면 GitHub Actions Pages 배포가 실행된다.
- 일반적인 원고 작성, 초안 추가, 구조 변경, 커밋, 푸시는 기본적으로 `dev`에만 반영한다.
- `main` 반영은 배포 실행으로 간주한다.
- 사용자가 `main에 반영`, `배포`, `배포 페이지 갱신`, `main으로 푸시`처럼 명시적으로 지시한 경우에만 `main`에 push한다.
- 브랜치가 불명확하거나 배포에 영향을 줄 수 있는 작업 전에는 현재 브랜치를 확인한다.

## 편집과 검증

- 기존 문서의 톤과 목차 구조를 우선 따른다.
- 이해를 늘리지 않는 표현 간소화나 의미 변화 없는 문장 손질처럼, 내용 변화에 영향을 주지 않는 수정은 하지 않는다.
- 불필요한 대규모 리팩터링이나 파일 이동은 피한다.
- 수동 파일 수정은 가능하면 패치 단위로 작게 수행한다.
- 작업 전후에 변경 목록을 확인하고, 관련 없는 변경을 되돌리지 않는다.
- 사용자 요청이나 명시된 검증 단계 없이 임의의 빌드 명령을 실행하지 않는다.
- 임의 빌드는 사용자가 테스트 중인 환경을 다시 빌드해 작업 흐름을 방해할 수 있으므로, 빌드 실행은 필요한 검증 시점에만 제한한다.
- 빌드 검사는 개별 Section이나 작은 패치마다 반복하지 않고, 기본적으로 전체 파트를 순차적으로 확인하고 수정한 작업이 끝난 뒤 수행한다.
- 작업 중간에는 본문 구조, 용어, 링크, 릴리즈노트 정합성을 먼저 점검하고, 빌드 확인은 전체 파트 검토 종료 시점에 모아 실행한다.
- 현재 저장소의 기본 빌드 확인 명령은 다음과 같다.
  - `.venv/bin/python -m mkdocs build`
- MkDocs 빌드와 관련 스크립트 실행 시에는 가능하면 시스템 `python3` 대신 `.venv/bin/python`을 우선 사용한다.
- 빌드 경고가 발생하면 실제 실패인지, git 히스토리 부재로 인한 날짜 플러그인 fallback 같은 허용 가능한 경고인지 구분해서 보고한다.
