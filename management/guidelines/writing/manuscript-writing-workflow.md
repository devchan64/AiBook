# 원고 작성 워크플로우

## 목적

이 문서는 책 원고를 새로 쓰거나 크게 수정할 때 반복해서 확인하는 세부 작성 절차를 정리한다.

이 문서가 다루는 범위는 다음과 같다.

- Part 시작/마무리 페이지 작성 기준
- 본문 작성 흐름
- Python 예제 작성 절차
- 초심자 보강 판단 절차
- 사례 작성 순서
- Section 경계와 생략 회수 규칙

저장소 전체 공통 원칙, 용어 원칙, 출처와 저작권의 최상위 기준은 `AGENTS.md`를 따른다.

## 언제 이 문서를 보는가

- 새 Part의 시작 페이지나 마무리 페이지를 쓸 때
- Section 초안을 처음 쓸 때
- 기존 Section을 크게 재구성할 때
- Python 예제를 넣거나 바꿀 때
- 초심자 보강, 보충학습 분리, 사례 보강을 판단할 때

## Part 작성 기준

### Part 시작 페이지

Part 시작 페이지는 해당 Part의 독서 방향을 잡는 오버뷰다.

다음 내용을 포함한다.

- 이 Part의 목적
- 이 Part가 필요한 이유
- 이 Part에서 다루는 주요 질문
- 이 Part에서 설명할 범위와 설명하지 않을 범위
- 앞선 Part와의 연결
- 이후 Part로 이어지는 연결
- 이 Part를 읽고 나면 생겨야 할 이해

Part 시작 페이지는 상세 개념 설명을 미리 대신하지 않는다. 상세 설명은 각 Chapter와 Section으로 넘긴다.

### Part 마무리 페이지

Part 마무리 페이지는 해당 Part의 요약과 다음 학습으로 넘어가기 위한 정리다.

다음 내용을 포함한다.

- 이 Part에서 다룬 핵심 흐름
- 반드시 기억할 개념
- 오해하기 쉬운 지점
- 다음 Part로 넘어가기 전에 확인할 질문
- 다음 Part와 연결되는 관점

Part 마무리 페이지는 새로운 핵심 개념을 처음 도입하는 장소로 쓰지 않는다. 필요한 새 개념은 다음 Part의 시작 페이지나 해당 Section에서 다룬다.

## 본문 작성 원칙

- 설명은 가능한 한 `왜 필요한가`, `핵심 원리는 무엇인가`, `간단히 어떻게 확인할 수 있는가`의 흐름을 따른다.
- 정의만 나열하지 말고 개념 사이의 연결을 설명한다.
- 초반 도입에서는 집필자의 진행 멘트를 반복하기보다, 문제 상황과 핵심 개념으로 바로 들어가는 문장을 우선한다.
- 질문 문장과 핵심 정의는 가능하면 일반 본문 문단 안에서 자연스럽게 이어지게 쓴다.
- 하나의 문서는 초심자, 재학습자, 경험 있는 비전공자가 모두 따라올 수 있게 쓴다.
- 모든 Part는 초심자를 기준으로 원고를 작성한다.
- 모든 Section에서는 이전 Part에서 다룬 용어라도 핵심 개념이면 짧게 재소개한다.
- 알고리즘 이름, 라이브러리 API, 수식 표기를 먼저 앞세우지 않는다.
- 예시는 가능한 한 작은 표, 짧은 업무 상황, 간단한 도식으로 시작한다.
- `여기서는 다루지 않습니다` 같은 문장은 단독으로 끝내지 않는다. 반드시 후속 Section, 보충학습, 범위 밖 중 하나로 연결한다.
- 설명하지 않는 내용이 뒤에서도 회수되지 않으면 가능한 한 `보충학습`으로 회수한다.
- 일반 문장, 질문 목록, 단계 목록, 체크리스트는 코드블럭으로 감싸지 않는다.
- 별도 학습 절 명칭은 `보충학습`으로 통일한다.

## Python 예제 워크플로우

### 작업 전 확인

- 현재 Section의 중심 질문이 무엇인가
- 예제가 현재 절에서 확인할 개념이 무엇인가
- 출력값이 독자가 바로 읽을 수 있는가

### 작성 규칙

- 코드 앞에 문제 상황, 입력(input), 정답(label) 또는 기대 출력(output), 확인할 개념을 짧게 둔다.
- 가능하면 `print` 또는 이에 준하는 출력 코드를 함께 둔다.
- 코드 블록 아래에는 가능하면 실행 결과 예시도 함께 둔다.
- 우선적으로 보여 줄 값은 샘플 수, `shape`, 분포, 분리 결과, 예측과 실제값 비교처럼 현재 절의 중심 질문과 직접 연결된 값이다.
- 아직 설명하지 않은 고급 지표, 튜닝 로그, 성능 비교는 범위 안에 있을 때만 넣는다.
- 의사 코드보다 실제 실행 가능한 예제를 우선한다.
- 가능하면 실제 라이브러리, 실제 데이터 형식, 실제 전처리 흐름, 실제 모델 입출력 중 적어도 하나와 연결한다.
- 단순화가 필요하면 축약한 부분과 실제 관찰 포인트를 함께 밝힌다.
- 독자가 수치를 바꿔 보며 결과 차이를 다시 확인할 수 있어야 한다.

## 초심자 보강 워크플로우

### 판단 순서

1. 지금 막히는 이유가 현재 개념의 핵심 때문인가, 선행 지식 부재 때문인가
2. 이 설명이 현재 Section의 범위를 흐리지 않고 들어갈 수 있는가
3. 작은 예시 하나로 해결되는가, 별도 학습 흐름이 필요한가
4. 뒤 Chapter에서도 같은 보강이 반복해서 필요할 가능성이 높은가
5. 지금 본문에 넣으면 핵심 설명보다 보조 설명이 더 길어지는가

### 판단 결과

- `핵심 이해에 직접 필요`하면 현재 Section에 추가한다.
- `선행 지식 복구가 목적`이면 `보충학습`으로 분리한다.

### 보강 최소 단위

1. 한 문장 직관
2. 2~5행짜리 작은 표
3. 장난감 데이터 예시
4. 작은 도식
5. 코드와 실행 결과
6. 위 다섯 가지로 해결되지 않을 때만 보충학습

## 사례 작성 워크플로우

사례 문단은 가능하면 다음 순서를 따른다.

1. 문제 장면
2. 사람이 쓰던 기준
3. 그 기준의 한계
4. 모델이나 개념이 바꾸는 점
5. 확인 가능한 결과

사례만으로 입력과 출력이 잡히지 않으면 문장만 늘리지 말고 작은 표나 장난감 데이터 예제를 바로 붙인다.

## Section 경계 워크플로우

- 하나의 Section은 하나의 중심 질문에 답해야 한다.
- 다른 Section의 핵심 설명, 예시, 결론, 체크리스트를 미리 당겨 쓰지 않는다.
- 현재 Section의 논의는 그 범위 안에서만 확장한다.
- 필요한 배경 설명은 허용하되 길어지면 다음 Section으로 넘기거나 관리 메모에 남긴다.
- 현재 Section에서 생략한 내용은 `후속 본편 Section`, `보충학습`, `범위 밖` 중 하나로 드러나야 한다.
- 현재 Section에 바로 넣기 어렵지만 반복적으로 필요한 내용은 `새 본편 Section 후보` 또는 `새 보충학습 후보`로 관리한다.
- 새 Section 후보를 만들 때는 먼저 다음 순서로 판단한다.
  - 현재 Section 안에 짧게 보강할 수 있는가
  - 이미 예정된 후속 본편 Section에서 회수되는가
  - 여러 Chapter에서 반복 참조될 선행 지식이라 `보충학습`으로 분리해야 하는가
  - 이 책의 현재 범위 밖으로 두는 편이 맞는가
- 새 Section을 추가하면 `mkdocs.yml`의 `nav` 반영 여부를 확인한다.
- 가능하면 Section 작성 후 `management/authoring/section-x-y-evidence-analysis.md` 형식의 근거 검토 메모를 남긴다.

## Section 권장 공통 구조

1. 이전 Section과의 연결
2. 이 Section의 범위
3. 목표
4. 핵심 설명
5. 예시 또는 실습
6. 이 절에서 기억할 관점
7. 체크리스트
8. 출처와 참고 자료

이 구조를 기계적으로 맞추기보다 `이론형`, `실습형`, `혼합형`에 따라 비중을 조절한다.
