# 원고 작성 워크플로우

이 문서는 책 원고를 새로 쓰거나 크게 수정할 때 적용하는 본문 작성 기준을 다룬다. `Section ID`, `Version`, 릴리즈노트 연결은 `section-metadata-guidelines.md`, Section별 중심 학습 산출물 추적은 `section-learning-focus-guidelines.md`를 따른다.

## 목적과 범위

이 문서가 다루는 범위는 다음과 같다.

- Part 시작/마무리 페이지의 본문 역할
- Section 본문 작성 흐름
- Section 경계와 생략 항목 처리
- 본문 소제목과 진행 메타 표현
- 초심자 보강 판단
- 사례·예시·연습·예제 배치
- Python 예제와 시각 자료를 본문 흐름에 연결하는 방식

이 문서가 직접 다루지 않는 범위는 다음과 같다.

- `Section ID`, 제목 앞 인덱스, `Version` 같은 본문 메타데이터 형식
- 릴리즈노트 파일 위치, 파일명, 항목 형식
- Section별 중심 학습 산출물의 Part 체크포인트 항목 작성 기준
- Python 예제의 세부 작성 기준
- 차트·그래프·도식 자산의 세부 작성 기준
- 개념사전 항목의 세부 구조

## 원고 작성·수정 작업 순서

1. `AGENTS.md`로 저장소 전역 원칙과 현재 작업의 적용 범위를 확인한다.
2. 수정 대상의 `Section ID`, `Version`, 대응 릴리즈노트 연결은 `section-metadata-guidelines.md`로 확인한다.
3. 현재 Section의 중심 질문을 한 문장으로 확인한다.
4. 중심 질문이나 학습 산출물이 바뀌면 `section-learning-focus-guidelines.md`에 따라 Part 체크포인트 노트를 확인한다.
5. 필요하면 해당 `management/authoring/section-...-evidence-analysis.md`를 열어 근거, 용어, 후속 설명 위치를 확인한다.
6. 본문에서 새로 고정하거나 반복 사용할 핵심 용어가 있으면 `concept-glossary-guidelines.md`를 확인한다.
7. 본문 구조가 크게 바뀌면 이 문서의 Section 경계, 소제목, 사례·연습 기준을 적용한다.
8. 본문을 실제로 수정했다면 메타데이터와 릴리즈노트 연결을 함께 갱신한다.

## Part 페이지 작성 기준

Part 시작 페이지는 해당 Part의 독서 방향을 잡는 오버뷰다.

- 이 Part의 목적
- 이 Part가 필요한 이유
- 이 Part에서 다루는 주요 질문
- 이 Part에서 설명할 범위와 설명하지 않을 범위
- 앞선 Part와의 연결
- 이후 Part로 이어지는 연결
- 이 Part를 읽고 나면 생겨야 할 이해

Part 시작 페이지는 상세 개념 설명을 미리 대신하지 않는다. 상세 설명은 각 Chapter와 Section으로 넘긴다.

Part 마무리 페이지는 해당 Part의 요약과 다음 학습으로 넘어가기 위한 정리다.

- 이 Part에서 다룬 핵심 흐름
- 반드시 기억할 개념
- 오해하기 쉬운 지점
- 다음 Part로 넘어가기 전에 확인할 질문
- 다음 Part와 연결되는 관점

Part 마무리 페이지는 새로운 핵심 개념을 처음 도입하는 장소로 쓰지 않는다.

## 목차 변경 워크플로우

- 배포 기준 목차는 `mkdocs.yml`의 `nav`를 기준으로 본다.
- 독자용 설명 목차는 `docs/table-of-contents.md`에서 관리한다.
- 실제 파일 구조는 `Part > Chapter > Section`이고, `Module`은 여러 Chapter를 읽기 흐름으로 묶는 편집 단위로만 사용한다.
- 새 Part, Chapter, Section을 추가하거나 순서를 바꾸면 `docs/table-of-contents.md`와 `mkdocs.yml`이 현재 구조와 같은 방향을 가리키는지 함께 확인한다.
- 외부 교재나 강의의 목차를 그대로 복제하지 않는다. 반복 주제와 교육적 필요를 현재 책의 흐름에 맞게 재배치한다.
- 새 장을 추가할 때는 `왜 필요한가`, `어느 Part와 연결되는가`, `어떤 근거 문서가 뒷받침하는가`를 먼저 확인한다.

## 본문 작성 원칙

- 설명은 가능한 한 `왜 필요한가`, `핵심 원리는 무엇인가`, `간단히 어떻게 확인할 수 있는가`의 흐름을 따른다.
- 정의만 나열하지 말고 개념 사이의 연결을 설명한다.
- 질문 문장과 핵심 정의는 가능하면 일반 본문 문단 안에서 자연스럽게 이어지게 쓴다.
- 모든 Part는 초심자를 기준으로 원고를 작성한다.
- `초심자`는 선행 지식 가정, 예시 크기, 표와 도식 보강, `보충학습` 분리 여부를 판단하는 설계 기준이다.
- 본문에서는 `초심자 기준에서는`, `초심자를 위해`, `이 절을 이렇게 읽으면 된다` 같은 메타 표지로 전개를 끌고 가지 않는다.
- 알고리즘 이름, 라이브러리 API, 수식 표기를 먼저 앞세우지 않는다.
- 새로운 핵심 개념은 같은 Part 안에서 처음 등장하는 Section에서 한 번 충분히 설명하고 개념사전으로 연결한다.
- 같은 Part 안의 후속 Section에서는 이미 설명한 핵심 개념의 상세 정의나 비교 표를 반복하지 않고, 현재 절 이해에 꼭 필요한 최소 연결만 남기거나 개념사전 링크로 보낸다.
- 일반 문장, 질문 목록, 단계 목록, 체크리스트는 코드블럭으로 감싸지 않는다.
- 별도 학습 절 명칭은 `보충학습`으로 통일한다.

## Section 구성 판단

Section은 하나의 중심 질문에 답해야 한다. 다음 역할은 필요에 따라 배치하되, 고정 소제목처럼 기계적으로 맞추지 않는다.

1. 도입: 이전 흐름 연결, 현재 중심 질문, 다음 질문과의 경계를 한 문단 안에서 처리
2. 핵심 설명
3. 필요한 사례, 예시, 비교표, 도식, 코드, 연습, 예제
4. 체크리스트
5. 출처와 참고 자료

`이론형`, `실습형`, `혼합형`에 따라 포함 여부, 비중, 문단 위치를 조절한다. 사례, 예시, 연습, 예제는 현재 Section의 중심 질문을 이해하게 만드는 보강 역할이므로, 필요하면 개념 설명 중간이나 절차 설명 사이에 바로 붙인다.

## 소제목과 진행 메타

- 소제목은 진행 안내가 아니라 독자가 지금 읽을 구체 개념, 오해, 비교 대상, 판단 기준을 바로 보게 해야 한다.
- `주요 학습내용`, `세부 학습내용`, `세부 학습내용 보충`, `먼저 연결할 개념`, `이 절의 목표`, `이 절의 범위`, `이 절을 읽는 순서`, `사례 및 예시`, `연습 및 예제`처럼 진행 방식이나 보강 수단의 종류만 말하는 제목은 쓰지 않는다.
- 필요하면 `평균이 가리는 차이`, `입력과 라벨이 만드는 학습 신호`, `MCP가 연결 형식을 분리하는 이유`처럼 문단의 내용과 판단 기준이 보이는 제목으로 바꾼다.
- `체크리스트`와 `출처와 참고 자료`는 유지 소제목 구조다.
- Section 말미의 자기 확인 블록 표지는 원칙적으로 `체크리스트`로 통일한다.
- Section 본문에서 `닫힌 판단`, `이 절에서 닫은 것`처럼 요약 확인을 문단으로 따로 말하지 않는다.
- 진행 메타 소제목의 현재 잔여 위치와 변경 제안은 `../authoring/progress-meta-heading-audit.md`와 `../authoring/progress-meta-heading-proposal.md`에서 확인한다.

## Section 경계와 생략 항목 처리

먼저 다음 네 가지를 순서대로 확인한다.

1. 현재 Section의 중심 질문은 하나인가
2. 지금 언급하려는 항목이 그 질문에 답하는 데 필요한가
3. 자세히 설명하지 않는다면 후속 본편 Section, 보충학습, 체크리스트 중 어디에서 다시 설명되는가
4. 어느 위치에서도 다시 설명되지 않는다면 현재 Section에서 언급하지 않을 수 있는가

범위 설명은 기본 항목이 아니다. 뒤 Section에서 본격적으로 소개할 내용을 현재 Section 앞에서 일부 끌어와야만 현재 질문의 경계가 선명해질 때 제한적으로 쓴다.

- 현재 질문과 직접 연결되지 않는 고급 항목은 범위 안내에 열거하지 않는다.
- `다루지 않습니다`, `깊게 다루지 않습니다` 같은 표현은 독자 흐름을 보호할 필요가 있을 때만 쓴다.
- 바로 다음 Section에서 이어질 내용은 `범위 밖`보다 `이번 절은 어디까지, 다음 절은 무엇부터`의 역할 분담 문장으로 쓴다.
- 여러 항목을 한꺼번에 묶지 않고, 항목마다 후속 설명 위치를 따로 확인한다.

현재 Section에 바로 넣기 어렵지만 반복적으로 필요한 내용은 `새 본편 Section 후보` 또는 `새 보충학습 후보`로 관리한다. 새 Section을 추가하면 `mkdocs.yml`의 `nav` 반영 여부를 함께 확인한다.

## 초심자 보강 워크플로우

판단 순서:

1. 지금 막히는 이유가 현재 개념의 핵심 때문인가, 선행 지식 부재 때문인가
2. 이 설명이 현재 Section의 범위를 흐리지 않고 들어갈 수 있는가
3. 최소 예시 하나로 이해할 수 있는가, 아니면 더 충분한 예시나 별도 학습 흐름이 필요한가
4. 뒤 Chapter에서도 같은 보강이 반복해서 필요할 가능성이 높은가
5. 지금 본문에 넣으면 핵심 설명보다 보조 설명이 더 길어지는가

판단 결과:

- `핵심 이해에 직접 필요`하면 현재 Section에 추가한다.
- `선행 지식 복구가 목적`이면 `보충학습`으로 분리한다.
- 보강이 필요하더라도 진행 메타 안내를 늘리기보다 표, 짧은 사례, 직접 비교 문장으로 바로 설명한다.

## 사례·예시·연습·예제 역할 구분

- `사례`: 문제 장면, 사람이 쓰던 기준, 한계, 개념이 바꾸는 점, 확인 가능한 결과를 보여 주는 설명 블록
- `예시`: 충분한 정보를 제공하는 표, 짧은 수치, 짧은 비교처럼 개념을 바로 붙잡게 하는 보조 장면
- `연습`: 독자가 방금 배운 개념이나 판단 기준을 직접 적용해 보는 실습 블록
- `예제`: 코드, 실행 절차, 출력 결과처럼 독자가 조건이나 값을 바꾸며 확인할 수 있는 검증 블록

사례와 예시는 `있다`는 사실만으로 통과시키지 않는다. 독자가 `왜 이 개념이 필요한가`, `어디서 판단이 갈리는가`, `그래서 무엇이 더 잘 보이는가`를 말할 수 있어야 한다.

연습과 예제도 `있다`는 사실만으로 통과시키지 않는다. 독자가 실제로 채우기, 표시하기, 분류하기, 값 바꾸기, 비교하기 중 하나 이상의 행동을 해야 한다.

## Python 예제 연결 규칙

- Python 예제를 넣거나 바꿀 때의 세부 기준은 `python-example-guidelines.md`를 따른다.
- 이 문서는 예제를 현재 Section의 중심 질문과 어떻게 연결할지만 다룬다.
- Python 예제는 기준 소스를 유지하는 것을 기본값으로 둔다. 학습을 쉽게 만든다는 이유로 실행 가능한 기준 소스를 여러 조각으로 쪼개지 않는다.
- 긴 Python 예제가 필요하면 코드를 나누는 대신 설명을 나눈다.
- 사용법 안내가 아닌 Python 예제는 독자가 조작할 값과 관찰할 출력 변화가 있어야 한다.

## 시각 형식 선택 연결 규칙

- 표, 플로우차트, 그래프, 차트, 구조 다이어그램 가운데 무엇이 맞는지는 `chart-guidelines.md`를 따른다.
- 이 문서는 시각 형식을 본문 해설과 어떤 역할로 나눌지만 다룬다.
- 같은 사례를 설명할 때 표는 비교, 플로우차트는 판단 순서 압축, 본문 문장은 해석 마무리 역할로 구분한다.
