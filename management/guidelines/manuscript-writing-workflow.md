# 원고 작성 워크플로우

## 목적

이 문서는 책 원고를 새로 쓰거나 크게 수정할 때 반복해서 확인하는 세부 작성 절차를 정리한다.

이 문서가 다루는 범위는 다음과 같다.

- Part 시작/마무리 페이지 작성 기준
- 본문 작성 흐름
- 초심자 보강 판단 절차
- 사례 작성 순서
- Section 경계와 생략 회수 규칙

이 문서가 직접 다루지 않는 범위는 다음과 같다.

- Section ID, 제목 앞 인덱스, Version 같은 본문 메타데이터 형식
- 릴리즈노트 파일 위치, 파일명, 항목 형식
- Python 예제의 세부 작성 기준
- 차트·그래프·도식 자산의 세부 작성 기준
- 개념사전 항목의 세부 구조

저장소 전체 공통 원칙, 용어 원칙, 출처와 저작권의 최상위 기준은 `AGENTS.md`를 따른다.

`AGENTS.md`가 저장소 전역 원칙과 먼저 볼 문서의 인덱스를 맡는다면, 이 문서는 실제 원고 표현과 구조 판단에 사용하는 세부 기준을 맡는다.

## 언제 이 문서를 보는가

- 새 Part의 시작 페이지나 마무리 페이지를 쓸 때
- Section 초안을 처음 쓸 때
- 기존 Section을 크게 재구성할 때
- 초심자 보강, 보충학습 분리, 사례 보강을 판단할 때
- 목차 구조나 `mkdocs.yml`의 `nav`를 바꿀 때
- 원고 구조 변경 뒤 Section 메타데이터 갱신이 필요한지 확인할 때

## 원고 작성·수정 작업 순서

1. `AGENTS.md`로 저장소 전역 원칙과 현재 작업의 적용 범위를 확인한다.
2. 수정 대상의 `Section ID`, `Version`, 대응 릴리즈노트 연결은 `section-metadata-guidelines.md`로 확인한다.
3. 수정 대상 Section의 중심 질문과 Section 경계를 확인한다.
4. 필요하면 해당 `management/authoring/section-...-evidence-analysis.md`를 열어 근거, 용어, 후속 회수 지점을 확인한다.
5. 문단 재구성이 크면 이 문서의 문단 구조 점검 메모를 함께 적용한다.
6. Part 수준 흐름과 중심 주제를 다시 잡아야 하면 해당 `management/authoring/part-XX-open-checklist.md`를 확인한다.
7. 본문을 실제로 수정했다면 `section-metadata-guidelines.md`에 따라 메타데이터와 릴리즈노트 연결을 함께 갱신한다.

## 목차 변경 워크플로우

- 배포 기준 목차는 `mkdocs.yml`의 `nav`를 기준으로 본다.
- 독자용 설명 목차는 `docs/table-of-contents.md`에서 관리한다.
- 실제 파일 구조는 `Part > Chapter > Section`이고, `Module`은 여러 Chapter를 읽기 흐름으로 묶는 편집 단위로만 사용한다.
- 새 Part, Chapter, Section을 추가하거나 순서를 바꾸면 `docs/table-of-contents.md`와 `mkdocs.yml`이 현재 구조와 같은 방향을 가리키는지 함께 확인한다.
- 외부 교재나 강의의 목차를 그대로 복제하지 않는다. 반복 주제와 교육적 필요를 현재 책의 흐름에 맞게 재배치한다.
- 새 장을 추가할 때는 `왜 필요한가`, `어느 Part와 연결되는가`, `어떤 근거 문서가 뒷받침하는가`를 먼저 확인한다.
- 오래된 목차 초안은 별도 관리 문서로 누적하지 않고, 현재 기준 문서에 흡수한 뒤 폐기한다.

## 작업 후 관리 연결

- 이 문서는 원고 구조와 표현 판단을 다룬다.
- `Section ID`, 제목 앞 인덱스, `Version`, 릴리즈노트 연결은 `section-metadata-guidelines.md`를 따른다.
- 릴리즈노트 파일의 위치와 항목 형식은 `../release-notes/sections/README.md`를 따른다.

## 근거 메모 정리 워크플로우

- `section-...-evidence-analysis.md`는 대응 원고 본문과 `출처와 참고 자료`에 핵심 근거가 실제로 반영된 뒤에만 폐기한다.
- 일괄 삭제하지 않고 `대응 원고`, `핵심 주장`, `핵심 출처`, `현재 구조와의 일치 여부`를 먼저 대조한다.
- 이미 본문에 반영된 판단은 Part 체크포인트 노트나 집필 가이드로 흡수하고, evidence 메모 원문은 계속 누적하지 않는다.
- 파일명 규칙과 현재 원고 구조가 어긋나는 evidence 메모는 자동 폐기하지 않는다. 구조 불일치 보류군으로 따로 남기고, 현재 구조 기준으로 다시 쓸지 폐기할지 별도 판단한다.

## Part 작성 기준

### Part 시작 페이지

Part 시작 페이지는 해당 Part의 독서 방향을 잡는 오버뷰다.

다음 내용을 포함한다.

- 이 Part의 목적
- 이 Part가 필요한 이유
- 이 Part에서 다루는 주요 질문
- 이 Part에서 설명할 범위와 설명하지 않을 범위
- 앞선 Part와의 연결
- 이후 Part로 이어지는 연결
- 이 Part를 읽고 나면 생겨야 할 이해

Part 시작 페이지는 상세 개념 설명을 미리 대신하지 않는다. 상세 설명은 각 Chapter와 Section으로 넘긴다.

### Part 마무리 페이지

Part 마무리 페이지는 해당 Part의 요약과 다음 학습으로 넘어가기 위한 정리다.

다음 내용을 포함한다.

- 이 Part에서 다룬 핵심 흐름
- 반드시 기억할 개념
- 오해하기 쉬운 지점
- 다음 Part로 넘어가기 전에 확인할 질문
- 다음 Part와 연결되는 관점

Part 마무리 페이지는 새로운 핵심 개념을 처음 도입하는 장소로 쓰지 않는다. 필요한 새 개념은 다음 Part의 시작 페이지나 해당 Section에서 다룬다.

## 본문 작성 원칙

- 설명은 가능한 한 `왜 필요한가`, `핵심 원리는 무엇인가`, `간단히 어떻게 확인할 수 있는가`의 흐름을 따른다.
- 정의만 나열하지 말고 개념 사이의 연결을 설명한다.
- 초반 도입에서는 집필자의 진행 멘트를 반복하기보다, 문제 상황과 핵심 개념으로 바로 들어가는 문장을 우선한다.
- 질문 문장과 핵심 정의는 가능하면 일반 본문 문단 안에서 자연스럽게 이어지게 쓴다.
- 하나의 문서는 초심자, 재학습자, 경험 있는 비전공자가 모두 따라올 수 있게 쓴다.
- 모든 Part는 초심자를 기준으로 원고를 작성한다.
- `초심자`는 설계 기준이다. 선행 지식 가정, 예시 크기, 표와 도식 보강, `보충학습` 분리 여부는 이 기준으로 판단한다.
- 본문에서는 `초심자 기준에서는`, `초심자를 위해`, `이 절을 이렇게 읽으면 된다` 같은 메타 표지로 전개를 끌고 가지 않는다. 현재 절의 흐름은 문제 장면, 사례, 비교표, 연결 문장만으로 이해되게 써야 한다.
- 새로운 핵심 개념은 같은 Part 안에서 처음 등장하는 Section에서 한 번 충분히 설명하고 개념사전으로 연결한다.
- 같은 Part 안의 후속 Section에서는 이미 설명한 핵심 개념의 상세 정의나 비교 표를 반복하지 않고, 현재 절 이해에 꼭 필요한 최소 연결만 남기거나 개념사전 링크로 보낸다.
- 개념사전 항목 구조, `중심 Section`·`등장 Section`, 표제어 분리 기준 자체는 `concept-glossary-guidelines.md`를 따른다. 현재 문서는 본문 Section에서 그 개념을 어떻게 처음 설명하고 이후 절에서 얼마나 반복할지만 다룬다.
- 다음 Part에서 같은 개념이 다시 핵심이 되면, 그 Part 안에서 처음 등장하는 Section에서 필요한 범위만 다시 정리한다.
- 알고리즘 이름, 라이브러리 API, 수식 표기를 먼저 앞세우지 않는다.
- 사례, 예시, 연습, 예제는 필수 고정 항목이 아니라 필요할 때 쓰는 보강 수단이다. 어떤 보강 수단을 선택할지는 이 문서의 `초심자 보강 워크플로우`와 `사례·예시·연습·예제 역할 구분`을 따른다.
- 진행 메타를 늘려 학습밀도를 올리지 않는다. 설명, 해설, 사례, 비교표, 입력 파일, 출력 해석, 직접 바꿔 볼 값, 보조자료, 판단 기준을 현재 설명 안에 배치해 밀도를 올린다.
- Section 경계와 자세히 설명하지 않는 항목의 회수는 이 문서의 `Section 경계와 회수 규칙`을 따른다.
- 일반 문장, 질문 목록, 단계 목록, 체크리스트는 코드블럭으로 감싸지 않는다.
- 별도 학습 절 명칭은 `보충학습`으로 통일한다.
- Section 말미의 자기 확인 블록 표지는 원칙적으로 `체크리스트`로 통일한다. 같은 역할의 표지를 `짧은 점검`과 혼용하지 않는다.
- 학술적 배경과 역사 설명은 현재 Section의 중심 질문을 더 잘 이해하게 만들 때만 남긴다. 발상의 전환, 기존 방식의 한계, 현재 개념이 왜 필요한가를 짧게 보여 주는 수준은 허용하지만, 독립된 위치 설명, 계보 설명, 연표 설명으로 길어져 본론보다 앞서면 축약하거나 다른 위치로 분리한다.

## Section 권장 공통 구조

1. 도입: 이전 흐름 연결, 현재 중심 질문, 다음 질문과의 경계를 한 문단 안에서 처리
2. 핵심 설명
3. 사례 및 예시(필요 시)
4. 연습 및 예제(필요 시)
5. 체크리스트
6. 출처와 참고 자료

이 구조를 기계적으로 맞추기보다 `이론형`, `실습형`, `혼합형`에 따라 포함 여부와 비중을 조절한다. 특히 `사례 및 예시`와 `연습 및 예제`는 필수 고정 항목이 아니라, 현재 Section의 중심 질문을 더 잘 닫기 위해 필요할 때 추가하는 보강 블록이다.

이전 Section과의 연결, 현재 Section의 경계, 다루지 않는 내용은 독립 소제목이나 진행 메타 블록으로 만들지 않는다. 필요한 경우 도입 문단이나 연결 문장 안에서 자연스럽게 처리한다. 범위 표는 뒤에서 소개할 내용을 앞에서 일부 끌어와야 현재 질문의 경계가 분명해질 때만 제한적으로 쓰며, 자세히 설명하지 않는 항목은 후속 회수 위치가 확정된 경우에만 담는다.

Section 말미의 자기 확인 블록은 `체크리스트`로 통일한다. `이 절에서 기억할 관점`, `짧은 점검`처럼 같은 역할을 하는 별도 블록은 만들지 않고, 필요한 요약 항목은 체크리스트 안으로 합친다.

## Section 경계와 회수 규칙

먼저 다음 네 가지를 순서대로 확인한다.

1. 현재 Section이 닫을 중심 질문은 하나인가
2. 지금 언급하려는 항목이 그 질문을 닫는 데 필요한가
3. 자세히 설명하지 않는다면 후속 본편 Section, 보충학습, 체크리스트 중 어디에서 회수되는가
4. 어느 위치에서도 회수되지 않는다면 현재 Section에서 언급하지 않을 수 있는가

범위 설명은 기본 항목이 아니다. 뒤 Section에서 본격적으로 소개할 내용을 현재 Section 앞에서 일부 끌어와야만 현재 질문의 경계가 선명해질 때 제한적으로 쓴다. 이때도 범위 안내가 실제 설명보다 길어지면 Section 경계를 다시 검토한다.

`이 절의 범위`, `이 절의 목표`, `이 절을 읽는 순서`, `이 보충학습의 범위`, `이 보충학습의 목표`처럼 진행 방식을 제목으로 세우지 않는다. 보충학습 절도 `무엇을 구분하는가`, `어떤 오해를 바로잡는가`, `어떤 연결을 복구하는가`가 제목에서 바로 보이게 쓴다.

다루지 않는 내용을 언급해야 할 때는 다음 기준을 적용한다.

- 현재 질문과 직접 연결되지 않는 고급 항목은 범위 안내에 열거하지 않는다.
- `다루지 않습니다`, `깊게 다루지 않습니다` 같은 표현은 독자 흐름을 보호할 필요가 있을 때만 쓴다.
- 바로 다음 Section에서 이어질 내용은 `범위 밖`보다 `이번 절은 어디까지, 다음 절은 무엇부터`의 역할 분담 문장으로 쓴다.
- 여러 항목을 한꺼번에 묶지 않고, 항목마다 회수 위치를 따로 확인한다.

현재 Section에 바로 넣기 어렵지만 반복적으로 필요한 내용은 `새 본편 Section 후보` 또는 `새 보충학습 후보`로 관리한다. 새 Section 후보는 `현재 Section 안에서 보강 가능한가`, `예정된 후속 Section에서 회수되는가`, `보충학습으로 분리해야 하는가`, `현재 책 범위 밖인가` 순서로 판단한다. 새 Section을 추가하면 `mkdocs.yml`의 `nav` 반영 여부를 함께 확인한다.

학술적 배경과 역사 설명도 같은 기준을 따른다. 현재 중심 질문을 직접 밀지 못하고 `이 개념이 어디에 놓이는가`만 길게 설명하면 오버뷰에 가까운 문단으로 보고 줄이거나 분리한다.

## 초심자 보강 워크플로우

### 판단 순서

1. 지금 막히는 이유가 현재 개념의 핵심 때문인가, 선행 지식 부재 때문인가
2. 이 설명이 현재 Section의 범위를 흐리지 않고 들어갈 수 있는가
3. 최소 예시 하나로 이해가 닫히는가, 아니면 더 충분한 예시나 별도 학습 흐름이 필요한가
4. 뒤 Chapter에서도 같은 보강이 반복해서 필요할 가능성이 높은가
5. 지금 본문에 넣으면 핵심 설명보다 보조 설명이 더 길어지는가

### 판단 결과

- `핵심 이해에 직접 필요`하면 현재 Section에 추가한다.
- `선행 지식 복구가 목적`이면 `보충학습`으로 분리한다.
- 보강이 필요하더라도 `초심자에게 먼저 필요한 것은 ...` 같은 메타 안내를 늘리기보다, 충분한 정보를 제공하는 표·짧은 사례·직접 비교 문장으로 바로 설명한다.

### 보강 최소 단위

아래 목록은 보강의 하한선이다. 이 순서를 기계적으로 지키라는 뜻이 아니라, 초심자에게 실제로 필요한 이해가 더 크다면 더 충분한 설명과 예시를 바로 제공하는 편이 우선이다.

1. 한 문장 직관과 이를 설명하는 해설
2. 충분한 정보를 제공할 수 있는 표
3. 맥락이 분명한 간단한 데이터 예시
4. Section 이해를 지지할 수 있는 도식
5. 코드와 실행 결과, 그리고 해설
6. 위 다섯 가지로 해결되지 않을 때만 보충학습

## 사례·예시·연습·예제 역할 구분

구조 용어는 다음처럼 구분한다.

- `사례`: 문제 장면, 사람이 쓰던 기준, 한계, 개념이 바꾸는 점, 확인 가능한 결과를 보여 주는 설명 블록
- `예시`: 충분한 정보를 제공하는 표, 짧은 수치, 짧은 비교처럼 개념을 바로 붙잡게 하는 보조 장면
- `연습`: 독자가 방금 배운 개념이나 판단 기준을 직접 적용해 보는 실습 블록
- `예제`: 코드, 실행 절차, 출력 결과처럼 독자가 조건이나 값을 바꾸며 확인할 수 있는 검증 블록

필요해서 본문에 넣을 때는 `사례`와 `예시`를 묶어 `사례 및 예시`로 두고, 실습과 검증은 `연습 및 예제`로 따로 둔다.

두 블록의 기준은 다음처럼 분리한다.

- `사례 및 예시`는 독자가 개념이 왜 필요한지 납득하게 하는 관찰·비교 블록이다. 독자가 직접 답을 쓰기보다, 문제 장면과 판단 차이를 읽고 `무엇이 더 잘 보이는가`를 이해하게 만든다.
- `연습 및 예제`는 독자가 개념을 실제로 적용해 보는 실습·검증 블록이다. 독자가 빈칸을 채우거나, 항목을 분류하거나, 값을 바꾸거나, 출력 차이를 비교한 뒤 바로 해설과 대조하게 만든다.
- 같은 소재를 두 블록에 모두 쓸 수는 있지만 역할을 바꿔야 한다. 사례에서는 장면과 오해를 보여 주고, 연습에서는 독자가 직접 표시·선택·계산·비교하게 한다.

### 사례 및 예시 기준

사례와 예시는 `있다`는 사실만으로 통과시키지 않는다.

- `사례`는 독자가 그 장면만 읽고도 `왜 이 개념이 필요한가`를 납득할 수 있어야 한다.
- `사례`는 가능하면 `문제 장면 -> 사람이 먼저 쓰던 기준 -> 그 기준의 흔들림 또는 한계 -> 개념 적용 후 무엇이 더 선명해지는가 -> 확인 가능한 결과`까지 닫는다.
- `예시`는 사례 본문을 추상적으로 다시 말하는 데 그치지 않고, 판단 차이가 실제로 보이게 해야 한다.
- `예시`의 표·수치·비교는 `무엇이 더 유리한가`, `어느 쪽으로 분류되는가`, `어디서 판단이 갈리는가`처럼 결과 차이를 드러내야 한다.
- 사례만으로 입력과 출력이 잡히지 않으면 문장만 늘리지 말고 표나 맥락이 분명한 간단한 데이터 예제를 붙인다.
- 사례가 Section 이해를 실질적으로 떠받치고 판단 순서가 문장만으로 흐릿하면, 사례 문단 가까이에 짧은 Mermaid 흐름도를 둔다.
- 사례를 읽고도 개념 필요성이 흐리거나, 예시를 보고도 판단 차이가 한눈에 보이지 않으면 미통과로 보고 다시 쓴다.

### 사례 및 예시 빠른 점검

- 사례만 읽어도 독자가 `왜 이 개념이 필요한가`를 한 문장으로 말할 수 있는가
- 사람이 하던 기존 판단 방식과 개념 적용 후 판단 방식의 차이가 드러나는가
- 예시가 `기여`, `영향` 같은 추상어 반복이 아니라 실제 비교 결과를 보여 주는가
- 사례 마지막이 `그래서 무엇이 더 잘 보이는가`를 분명히 닫는가
- 사례 흐름도가 있다면 새로운 이론을 추가하지 않고 사례의 판단 순서만 압축하는가
- 사례와 예시를 빼면 설명이 거의 달라지지 않는 수준이라면, 아직 보강이 부족한 것으로 본다

### 연습 및 예제 기준

연습과 예제도 `있다`는 사실만으로 통과시키지 않는다.

- `연습`은 독자가 방금 배운 개념이나 판단 기준을 스스로 한 번 적용해 보게 해야 한다.
- `예제`는 단순 실행 예시가 아니라, `입력을 바꾸면 무엇이 달라지는가` 또는 `어느 조건에서 결과가 갈리는가`를 확인하게 해야 한다.
- 연습은 설명 문단을 읽는 활동에 머물지 않고, 독자가 실제로 채우기·표시하기·분류하기·값 바꾸기·비교하기 중 하나 이상의 실습 행동을 하게 구성한다.
- 비코드 연습도 가능하면 `실습 대상 -> 독자가 할 작업 -> 확인 해설` 구조를 갖춘다. 예를 들어 문장 두 개를 제시했다면, 독자가 표시할 항목이나 빈칸 표를 먼저 두고 바로 뒤에서 확인 해설로 닫는다.
- 직관 위주의 연습은 반드시 별도 예제를 붙이지 않아도 된다. 관찰값, 판단 질문, 바로 뒤 해설만으로 현재 개념 경계를 충분히 적용하게 만들 수 있으면 연습으로 닫는다.
- 실험 위주의 연습은 예제가 필요하다. 값을 바꾸거나 조건을 조정했을 때 출력, 후보 순서, 경계, 실패 조건이 어떻게 달라지는지를 실제 실행 절차나 출력 결과로 확인하게 한다.
- 한 Section 안에 직관 연습과 실험 예제를 함께 둘 때는 `실행 전 예상 연습 -> 예제 실행 또는 출력 확인 -> 출력 해석 연습`처럼 예제가 답을 대신 말하기보다 독자의 판단을 검증하게 배치한다.
- 연습에서 독자에게 질문을 던졌다면, 그 질문에 대한 답 또는 해설을 반드시 바로 뒤에 둔다. 질문만 나열하고 해설 없이 체크리스트로 넘기지 않는다.
- 답이나 해설은 독자가 자기 판단과 바로 대조할 수 있을 만큼 가까이 둔다.
- 해설은 정답만 적지 말고, 왜 그 답이 현재 Section의 중심 개념이나 판단 기준과 연결되는지 한 문장 이상으로 닫는다.
- 출력값이 하나 나오더라도, 그 값이 현재 절의 중심 질문과 어떻게 연결되는지 해설이 바로 뒤따라야 한다.
- 코드 재출력, 표 재진술, 정의 반복만 있고 독자가 실제로 판단을 수정하거나 값을 바꿔 볼 지점이 없으면 미통과로 본다.

### 연습 및 예제 빠른 점검

- 현재 절에서 새로 설명한 핵심 개념이나 핵심 판단 기준마다 독자가 직접 적용해 볼 연습 지점이 있는가
- 독자가 먼저 스스로 답하거나 판단을 적어 볼 지점이 있는가
- 독자가 실제로 채우기·표시하기·분류하기·값 바꾸기·비교하기 같은 실습 행동을 하게 되어 있는가
- 실습 대상, 독자가 할 작업, 바로 뒤 확인 해설이 한 덩어리로 붙어 있는가
- 질문을 던진 모든 연습 항목에 답 또는 해설이 바로 뒤따르는가
- 답을 비교할 기준이나 해설이 바로 뒤에 있는가
- 해설이 정답 확인에 그치지 않고 현재 Section의 중심 개념으로 이유를 닫는가
- 표 재진술, 코드 재출력, 정의 반복이 아니라 실제 검증 행동이 있는가
- 현재 절의 사례와 표가 이미 말한 내용을 다른 형식으로 복창하는 데 그치지 않는가
- 값을 하나 이상 바꿔 보며 결과 차이를 확인할 수 있는가
- 결과가 바뀌는 이유를 현재 절의 핵심 개념으로 설명해 주는가
- 연습을 해 본 뒤 독자가 `무엇이 경계였는가`, `왜 출력이 달라졌는가`를 한 문장으로 말할 수 있는가

## Python 예제 연결 규칙

- Python 예제를 넣거나 바꿀 때의 세부 기준은 `python-example-guidelines.md`를 따른다.
- 이 문서는 예제를 `현재 Section의 중심 질문과 어떻게 연결할지`, `사례 및 예시`와 `연습 및 예제`를 어떻게 구분할지 같은 본문 구조 판단만 다룬다.
- `연습 및 예제`는 Python 코드만 뜻하지 않는다. 코드가 과한 절이라면 비코드 연습으로 개념 적용을 닫고, 코드가 필요한 절이라면 Python 예제를 추가해 검증 단계를 더한다.
- 설명, 사례, 예제의 핵심이 수식에 의해 값이 단계적으로 바뀌는 과정에 있다면 `수식 기반 변환 추적 원칙`을 검토한다.
- 이 원칙은 최종 출력값보다 `입력값이 중간 계산값, 변환 후 표현, 최종 출력으로 어떻게 바뀌는가`를 보는 일이 학습 포인트일 때 적용한다.
- 적용할 때는 단계별 산출물을 나누고, 각 산출물 아래에는 결과 요약보다 `이 단계에서 값의 의미가 어떻게 달라졌는가`를 짧게 설명한다.
- 최종 결과만 읽어도 충분한 예제에는 적용하지 않는다. 이 원칙은 그래프나 표를 늘리는 규칙이 아니라, 중간 변환을 보이지 않으면 학습 포인트가 약해지는 경우에만 쓴다.

## 시각 형식 선택 연결 규칙

- 표, 플로우차트, 그래프, 차트, 구조 다이어그램 가운데 무엇이 맞는지는 `chart-guidelines.md`를 따른다.
- 현재 문서는 `시각 형식을 넣을지 말지`, `본문 해설과 어떤 역할로 나눌지`만 다룬다.
- 같은 사례를 설명할 때 표는 비교, 플로우차트는 판단 순서 압축, 본문 문장은 해석 마무리 역할로 구분한다.
- 표가 이미 비교를 충분히 닫고 있는데 절차 설명까지 같이 떠안아 읽기 순서를 끊고 있으면, 표를 늘리기보다 짧은 플로우차트나 절차형 문장으로 분리한다.
- 반대로 플로우차트가 있는데 독자가 `어느 쪽이 더 큰가`, `어디서 갈리는가`를 빨리 대조해야 한다면, 긴 화살표 흐름보다 작은 비교 표가 더 적합할 수 있다.

## 문단 구조 점검 메모

- 현재 원고는 이미 `짧은 일반 문단 + 잦은 소제목 + 목록/표/코드 보조 블록` 구조가 강하다.
- 전면 형식 개편보다 문단의 역할이 섞였는지 먼저 점검한다.
- 진행 표지 없이도 현재 질문과 다음 질문의 경계가 읽혀야 한다.
- 메타 제목이 아니라 일반 문장만으로도 절의 역할이 드러나야 한다.
- 문단 수가 지나치게 많은 장문 Section은 `개념 지도`, `세부 설명`, `사례`, `연습`이 뒤섞였을 가능성을 먼저 본다.
- 사례와 Python 예제가 한 덩어리로 섞여 읽히면, 사례는 장면 이해로, 예제는 실습 검증으로 다시 나눈다.
- 이때 구조를 다음 질문 순서로 다시 묶는 편이 좋다.
  - 왜 지금 필요한가
  - 현재 질문과 다음 질문의 경계가 어디서 갈리는가
  - 이번 절을 읽고 어떤 판단을 할 수 있어야 하는가
  - 핵심 개념은 무엇인가
  - 사례로 어떻게 보이는가
  - 직접 확인하려면 무엇을 해보면 되는가
