# 원고 작성 워크플로우

## 목적

이 문서는 책 원고를 새로 쓰거나 크게 수정할 때 반복해서 확인하는 세부 작성 절차를 정리한다.

이 문서가 다루는 범위는 다음과 같다.

- Part 시작/마무리 페이지 작성 기준
- 본문 작성 흐름
- Python 예제 작성 절차
- 초심자 보강 판단 절차
- 사례 작성 순서
- Section 경계와 생략 회수 규칙

저장소 전체 공통 원칙, 용어 원칙, 출처와 저작권의 최상위 기준은 `AGENTS.md`를 따른다.

## 언제 이 문서를 보는가

- 새 Part의 시작 페이지나 마무리 페이지를 쓸 때
- Section 초안을 처음 쓸 때
- 기존 Section을 크게 재구성할 때
- Python 예제를 넣거나 바꿀 때
- 초심자 보강, 보충학습 분리, 사례 보강을 판단할 때
- 목차 구조나 `mkdocs.yml`의 `nav`를 바꿀 때
- Section 버전 코드와 릴리즈노트를 갱신할 때

## 목차 변경 워크플로우

- 배포 기준 목차는 `mkdocs.yml`의 `nav`를 기준으로 본다.
- 독자용 설명 목차는 `docs/book/table-of-contents.md`에서 관리한다.
- 실제 파일 구조는 `Part > Chapter > Section`이고, `Module`은 여러 Chapter를 읽기 흐름으로 묶는 편집 단위로만 사용한다.
- 새 Part, Chapter, Section을 추가하거나 순서를 바꾸면 `docs/book/table-of-contents.md`와 `mkdocs.yml`이 현재 구조와 같은 방향을 가리키는지 함께 확인한다.
- 외부 교재나 강의의 목차를 그대로 복제하지 않는다. 반복 주제와 교육적 필요를 현재 책의 흐름에 맞게 재배치한다.
- 새 장을 추가할 때는 `왜 필요한가`, `어느 Part와 연결되는가`, `어떤 근거 문서가 뒷받침하는가`를 먼저 확인한다.
- 오래된 목차 초안은 별도 관리 문서로 누적하지 않고, 현재 기준 문서에 흡수한 뒤 폐기한다.

## Section 버전·릴리즈노트 워크플로우

- Section을 실제로 수정했다면 본문 수정만 하고 끝내지 않습니다.
- 수정한 Section의 제목 바로 아래에는 다음 두 줄만 둡니다.
  - `Section ID`
  - `Version`
- 버전 코드는 수정일 기준 `vYYYY.MM.DD` 형식을 사용합니다.
- `Section ID`는 목차 인덱스와 같아야 합니다. 예를 들어 `P5-11.1`처럼 본문 번호와 직접 대응해야 합니다.
- Section 제목 앞 인덱스도 `Section ID`와 완전히 같아야 합니다. `3.1`, `11.2`처럼 축약한 번호를 제목에 따로 쓰지 않습니다.
- 날짜성 메타데이터는 `Version` 한 줄만 사용합니다.
- `Last Updated` 같은 별도 수정일 줄은 Section 본문에 두지 않습니다.
- 같은 날 여러 차례 수정한 경우에도 Section 본문 안의 버전 코드는 날짜 기준으로 유지합니다.
- 같은 날의 여러 수정 사항은 릴리즈노트에서 `### vYYYY.MM.DD` 한 항목으로 통합해 기록합니다.
- Section별 릴리즈노트는 `management/release-notes/sections/` 아래에서 관리합니다.
- 본문을 수정했다면 가능한 한 같은 작업에서 릴리즈노트 파일도 함께 갱신합니다.
- 번역본이 생기면 릴리즈노트에 `원문 기준 버전`, `언어별 추가 수정`, `번역 반영 상태`를 구분해서 남깁니다.
- 릴리즈노트 파일은 별도 체인지로그를 두지 않고, 버전 항목을 같은 파일 안에서 이어서 유지합니다. 상단에는 `Section ID`와 본문 경로만 남깁니다.

### 작업 순서

1. 수정 대상 Section의 `Section ID`를 확인합니다.
2. 본문 제목 아래에 `Section ID`와 `Version`이 있는지 확인합니다.
3. 본문을 수정한 뒤 수정일 기준으로 `Version`을 갱신합니다.
4. `management/release-notes/sections/part-XX/` 아래 대응 릴리즈노트 파일을 갱신하거나 새로 만듭니다.
5. 상단에는 `Section ID`와 본문 경로만 두고, 변경 이유와 본문 반영 내용은 최신 버전 항목에만 남깁니다.
6. 같은 작업에서 Part 체크리스트를 함께 쓰는 경우, 남은 후속 작업만 요약해 적고 릴리즈노트 내용을 중복 저장하지 않습니다.

### 번역본 대응 메모

- 번역본이 아직 없어도 `번역 동기화 메모`는 비워 두지 않습니다.
- 최소한 `영향 없음`, `확인 필요`, `향후 번역 반영 필요` 중 하나로 남깁니다.
- 한 언어에서만 문장을 추가 수정했다면, 릴리즈노트에 `원문 기준 버전과 차이`를 따로 적어 이후 동기화 충돌을 막습니다.

## 근거 메모 정리 워크플로우

- `section-...-evidence-analysis.md`는 대응 원고 본문과 `출처와 참고 자료`에 핵심 근거가 실제로 반영된 뒤에만 폐기한다.
- 일괄 삭제하지 않고 `대응 원고`, `핵심 주장`, `핵심 출처`, `현재 구조와의 일치 여부`를 먼저 대조한다.
- 이미 본문에 반영된 판단은 Part 체크리스트나 집필 가이드로 흡수하고, evidence 메모 원문은 계속 누적하지 않는다.
- 파일명 규칙과 현재 원고 구조가 어긋나는 evidence 메모는 자동 폐기하지 않는다. 구조 불일치 보류군으로 따로 남기고, 현재 구조 기준으로 다시 쓸지 폐기할지 별도 판단한다.

## Part 작성 기준

### Part 시작 페이지

Part 시작 페이지는 해당 Part의 독서 방향을 잡는 오버뷰다.

다음 내용을 포함한다.

- 이 Part의 목적
- 이 Part가 필요한 이유
- 이 Part에서 다루는 주요 질문
- 이 Part에서 설명할 범위와 설명하지 않을 범위
- 앞선 Part와의 연결
- 이후 Part로 이어지는 연결
- 이 Part를 읽고 나면 생겨야 할 이해

Part 시작 페이지는 상세 개념 설명을 미리 대신하지 않는다. 상세 설명은 각 Chapter와 Section으로 넘긴다.

### Part 마무리 페이지

Part 마무리 페이지는 해당 Part의 요약과 다음 학습으로 넘어가기 위한 정리다.

다음 내용을 포함한다.

- 이 Part에서 다룬 핵심 흐름
- 반드시 기억할 개념
- 오해하기 쉬운 지점
- 다음 Part로 넘어가기 전에 확인할 질문
- 다음 Part와 연결되는 관점

Part 마무리 페이지는 새로운 핵심 개념을 처음 도입하는 장소로 쓰지 않는다. 필요한 새 개념은 다음 Part의 시작 페이지나 해당 Section에서 다룬다.

## 본문 작성 원칙

- 설명은 가능한 한 `왜 필요한가`, `핵심 원리는 무엇인가`, `간단히 어떻게 확인할 수 있는가`의 흐름을 따른다.
- 정의만 나열하지 말고 개념 사이의 연결을 설명한다.
- 초반 도입에서는 집필자의 진행 멘트를 반복하기보다, 문제 상황과 핵심 개념으로 바로 들어가는 문장을 우선한다.
- 질문 문장과 핵심 정의는 가능하면 일반 본문 문단 안에서 자연스럽게 이어지게 쓴다.
- 하나의 문서는 초심자, 재학습자, 경험 있는 비전공자가 모두 따라올 수 있게 쓴다.
- 모든 Part는 초심자를 기준으로 원고를 작성한다.
- 새로운 핵심 개념은 같은 Part 안에서 처음 등장하는 Section에서 한 번 충분히 설명하고 개념사전으로 연결한다.
- 같은 Part 안의 후속 Section에서는 이미 설명한 핵심 개념의 상세 정의나 비교 표를 반복하지 않고, 현재 절 이해에 꼭 필요한 최소 연결만 남기거나 개념사전 링크로 보낸다.
- 다음 Part에서 같은 개념이 다시 핵심이 되면, 그 Part 안에서 처음 등장하는 Section에서 필요한 범위만 다시 정리한다.
- 알고리즘 이름, 라이브러리 API, 수식 표기를 먼저 앞세우지 않는다.
- 예시는 가능한 한 작은 표, 짧은 업무 상황, 간단한 도식으로 시작한다.
- 다만 이것은 설명의 시작점일 뿐 상한선이 아니다. 초심자 이해에 실제로 필요하면 더 충분한 표, 사례, 예제, 해설로 확장하는 편을 우선한다.
- 이해 중심 Section의 사례는 가능하면 `사람이 먼저 쓰던 기준 -> 그 기준의 한계 -> 개념이 바꾸는 점 -> 확인 가능한 결과`까지 닫아, 정의와 판단 흐름이 분리되지 않게 한다.
- `여기서는 다루지 않습니다` 같은 문장은 단독으로 끝내지 않는다. 반드시 후속 Section, 보충학습, 범위 밖 중 하나로 연결한다.
- 설명하지 않는 내용이 뒤에서도 회수되지 않으면 가능한 한 `보충학습`으로 회수한다.
- `깊게 다루지 않는 항목`을 목록이나 표로 2개 이상 적었다면, 각 항목마다 회수 위치를 개별적으로 확인한다. 한 문장으로 여러 항목을 묶어 넘기지 않는다.
- 회수 위치를 적으려는 항목이 후속 본편 Section에도 없고, `이 책의 범위 밖`으로 두기에도 맞지 않으면, 원고를 닫기 전에 `보충학습` Section 후보를 먼저 만든다.
- `나중에 다룬다`, `후반에서 본다`, `이 절 후반에서 회수한다`처럼 임시 예고만 남기지 않는다. 실제 Section ID가 없으면 `새 본편 Section 후보` 또는 `새 보충학습 후보`로 바로 관리한다.
- 일반 문장, 질문 목록, 단계 목록, 체크리스트는 코드블럭으로 감싸지 않는다.
- 별도 학습 절 명칭은 `보충학습`으로 통일한다.
- Section 말미의 자기 확인 블록 표지는 원칙적으로 `체크리스트`로 통일한다. 같은 역할의 표지를 `짧은 점검`과 혼용하지 않는다.
- 학술적 배경과 역사 설명은 현재 Section의 중심 질문을 더 잘 이해하게 만들 때만 남긴다. 발상의 전환, 기존 방식의 한계, 현재 개념이 왜 필요한가를 짧게 보여 주는 수준은 허용하지만, 독립된 위치 설명, 계보 설명, 연표 설명으로 길어져 본론보다 앞서면 축약하거나 다른 위치로 분리한다.

## Python 예제 워크플로우

### 작업 전 확인

- 현재 Section의 중심 질문이 무엇인가
- 예제가 현재 절에서 확인할 개념이 무엇인가
- 출력값이 독자가 바로 읽을 수 있는가

### 작성 규칙

- 코드 앞에 문제 상황, 입력(input), 정답(label) 또는 기대 출력(output), 확인할 개념을 짧게 둔다.
- 가능하면 `print` 또는 이에 준하는 출력 코드를 함께 둔다.
- 코드 블록 아래에는 가능하면 실행 결과 예시도 함께 둔다.
- 우선적으로 보여 줄 값은 샘플 수, `shape`, 분포, 분리 결과, 예측과 실제값 비교처럼 현재 절의 중심 질문과 직접 연결된 값이다.
- 아직 설명하지 않은 고급 지표, 튜닝 로그, 성능 비교는 범위 안에 있을 때만 넣는다.
- 의사 코드보다 실제 실행 가능한 예제를 우선한다.
- 가능하면 실제 라이브러리, 실제 데이터 형식, 실제 전처리 흐름, 실제 모델 입출력 중 적어도 하나와 연결한다.
- 단순화가 필요하면 축약한 부분과 실제 관찰 포인트를 함께 밝힌다.
- 독자가 수치를 바꿔 보며 결과 차이를 다시 확인할 수 있어야 한다.

## 초심자 보강 워크플로우

### 판단 순서

1. 지금 막히는 이유가 현재 개념의 핵심 때문인가, 선행 지식 부재 때문인가
2. 이 설명이 현재 Section의 범위를 흐리지 않고 들어갈 수 있는가
3. 최소 예시 하나로 이해가 닫히는가, 아니면 더 충분한 예시나 별도 학습 흐름이 필요한가
4. 뒤 Chapter에서도 같은 보강이 반복해서 필요할 가능성이 높은가
5. 지금 본문에 넣으면 핵심 설명보다 보조 설명이 더 길어지는가

### 판단 결과

- `핵심 이해에 직접 필요`하면 현재 Section에 추가한다.
- `선행 지식 복구가 목적`이면 `보충학습`으로 분리한다.

### 보강 최소 단위

아래 목록은 보강의 하한선이다. 이 순서를 기계적으로 지키라는 뜻이 아니라, 초심자에게 실제로 필요한 이해가 더 크다면 더 충분한 설명과 예시를 바로 제공하는 편이 우선이다.

1. 한 문장 직관
2. 2~5행짜리 작은 표
3. 장난감 데이터 예시
4. 작은 도식
5. 코드와 실행 결과
6. 위 다섯 가지로 해결되지 않을 때만 보충학습

## 사례 작성 워크플로우

사례 문단은 가능하면 다음 순서를 따른다.

1. 문제 장면
2. 사람이 쓰던 기준
3. 그 기준의 한계
4. 모델이나 개념이 바꾸는 점
5. 확인 가능한 결과

사례만으로 입력과 출력이 잡히지 않으면 문장만 늘리지 말고 표나 장난감 데이터 예제를 바로 붙인다.
한두 개의 짧은 보강만으로도 여전히 판단 과정이 보이지 않으면, 초심자가 스스로 따라갈 수 있을 만큼 사례 단계, 입력 표, 예제 해설을 더 충분히 제공한다.

사례가 현재 Section 이해를 실질적으로 떠받치면, 가능하면 사례 문단 바로 아래에 짧은 Mermaid 흐름도를 함께 둔다. 이 도식은 새로운 설명을 추가하는 자리가 아니라, 방금 읽은 사례를 `문제 장면 -> 기존 기준 또는 오해 경로 -> 개념이 바꾸는 판단 -> 다음 확인` 순서로 다시 압축해 보여 주는 자리에 가깝다.

사례 흐름도는 다음 기준을 우선한다.

1. 5~8개 노드 수준의 짧은 흐름
2. 사례 문단에 이미 나온 표현 위주로 재사용
3. 같은 절의 표, 체크리스트, Python 예제와 역할 중복 최소화
4. 새로운 이론 확장보다 판단 순서의 재확인 우선
5. 가능하면 사례 제목 아래 1~2문단 안쪽에 배치

## Section 경계 워크플로우

- 하나의 Section은 하나의 중심 질문에 답해야 한다.
- 다른 Section의 핵심 설명, 예시, 결론, 체크리스트를 미리 당겨 쓰지 않는다.
- 현재 Section의 논의는 그 범위 안에서만 확장한다.
- 필요한 배경 설명은 허용하되 길어지면 다음 Section으로 넘기거나 관리 메모에 남긴다.
- 여기서 말하는 `배경 설명`에는 학술적 배경과 역사 설명도 포함한다. 배경이 현재 중심 질문을 직접 밀지 못하고 `이 개념이 어디에 놓이는가`만 길게 설명하기 시작하면, 그 문단은 본문보다 오버뷰에 가까운 것으로 보고 줄이거나 분리한다.
- 현재 Section에서 생략한 내용은 `후속 본편 Section`, `보충학습`, `범위 밖` 중 하나로 드러나야 한다.
- 생략 항목이 여러 개라면, 각 항목이 어디로 가는지 하나씩 대응시킨다. 일부만 회수 위치가 있고 나머지가 비어 있으면 범위 정리가 끝난 것으로 보지 않는다.
- 현재 Section에 바로 넣기 어렵지만 반복적으로 필요한 내용은 `새 본편 Section 후보` 또는 `새 보충학습 후보`로 관리한다.
- 새 Section 후보를 만들 때는 먼저 다음 순서로 판단한다.
  - 현재 Section 안에 충분한 예시와 함께 보강할 수 있는가
  - 이미 예정된 후속 본편 Section에서 회수되는가
  - 여러 Chapter에서 반복 참조될 선행 지식이라 `보충학습`으로 분리해야 하는가
  - 이 책의 현재 범위 밖으로 두는 편이 맞는가
- 위 네 가지 중 어디에도 안정적으로 들어가지 않는 항목은, 기본적으로 `보충학습` 후보를 먼저 검토한다.
- 새 Section을 추가하면 `mkdocs.yml`의 `nav` 반영 여부를 확인한다.
- 가능하면 Section 작성 후 `management/authoring/section-x-y-evidence-analysis.md` 형식의 근거 검토 메모를 남긴다.

## Section 권장 공통 구조

1. 이전 Section과의 연결
2. 이 Section의 범위
3. 목표
4. 핵심 설명
5. 사례 및 예시
6. 연습 및 예제
7. 이 절에서 기억할 관점
8. 체크리스트
9. 출처와 참고 자료

이 구조를 기계적으로 맞추기보다 `이론형`, `실습형`, `혼합형`에 따라 비중을 조절한다.

여기서 자기 확인 블록의 기본 표지는 `체크리스트`다. 기존 원고에 `짧은 점검`이 남아 있더라도 새 작성과 구조 정리의 기준형으로 삼지 않는다.

여기서 구조 용어는 다음처럼 구분한다.

- `사례`: 문제 장면, 사람이 쓰던 기준, 한계, 개념이 바꾸는 점, 확인 가능한 결과를 보여 주는 설명 블록
- `예시`: 작은 표, 짧은 수치, 짧은 비교처럼 개념을 바로 붙잡게 하는 보조 장면
- `예제`: 코드, 실행 절차, 출력 결과처럼 독자가 직접 확인할 수 있는 실습 블록

따라서 Section 구조에서는 `사례`와 `예시`를 묶어 `사례 및 예시`로 두고, 코드와 실습은 `연습 및 예제`로 따로 둔다.

## 문단 구조 점검 메모

- 현재 원고는 이미 `짧은 일반 문단 + 잦은 소제목 + 목록/표/코드 보조 블록` 구조가 강하다.
- 전면 형식 개편보다 다음 항목을 우선 점검한다.
  - `이 절의 범위`가 빠진 초기 섹션
  - `이 절의 목표`가 빠진 초기 섹션
  - 문단 수가 지나치게 많은 장문 섹션
  - 사례와 Python 예제가 한 덩어리로 섞여 읽히는 섹션
- 긴 섹션을 다듬을 때는 `개념 지도`, `세부 설명`, `사례`, `연습`이 뒤섞여 있는지 먼저 본다.
- 이때 구조를 다음 질문 순서로 다시 묶는 편이 좋다.
  - 왜 지금 필요한가
  - 어디까지 다루는가
  - 이번 절을 읽고 무엇을 할 수 있어야 하는가
  - 핵심 개념은 무엇인가
  - 사례로 어떻게 보이는가
  - 직접 확인하려면 무엇을 해보면 되는가
