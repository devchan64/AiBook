# Python 예제 작성 가이드

작성일: 2026-07-19

## 목적

- 이 문서는 책 본문에 Python 예제를 넣거나 수정할 때 반복해서 확인할 기준을 정리한다.
- 목적은 `현재 Section의 중심 질문과 직접 연결되는 예제`, `실행과 출력이 분명한 예제`, `표·사례·체크리스트와 역할이 겹치지 않는 예제`를 유지하는 것이다.
- 이 가이드는 `Python 코드가 꼭 필요한가`, `코드가 필요 없다면 어떤 연습으로 개념 적용을 닫을 것인가`도 함께 판단한다.

## 언제 이 문서를 보는가

- 새 Python 예제를 처음 넣을 때
- 기존 Python 예제를 다른 예제로 교체할 때
- Python 예제가 읽는 CSV 입력 자산을 새로 만들거나 링크할 때
- 코드 블록을 연습·예제 역할로 유지할지, 표나 사례로 바꿀지 판단할 때
- 초심자에게 필요한 예제 해설 수준을 점검할 때

## 작업 전 확인

- 현재 Section의 중심 질문이 무엇인가
- 현재 Section이 새로 설명한 핵심 개념이나 핵심 판단 기준이 무엇인가
- 예제가 현재 절에서 확인할 개념이 무엇인가
- 출력값이 독자가 바로 읽을 수 있는가
- 이 절에 이미 비코드 연습이 있다면 Python 예제가 그 연습을 확장하는지, 아니면 같은 말을 반복하는지
- 코드 연습이 표, 그래프, 사례보다 실제로 더 유리한가
- 이 예제가 `설명형` 또는 `실험형` 중 무엇으로 설계되는가
- 둘 중 하나로 분명히 설명되지 않는다면, Python 예제가 아니라 표, 사례, 체크리스트, 비코드 연습으로 닫을 수 있는가

## 예제 유형 구분

- `설명형`: 코드 사용법, 라이브러리 문법, 실행 순서, 입력 형식처럼 `코드 자체를 어떻게 읽고 쓰는가`를 소개하는 예제입니다.
- `실험형`: 독자가 값, 임계값, 편향, 입력 조합, 하이퍼파라미터 같은 요소를 직접 바꿔 보며 경계 이동, 출력 반전, 민감도 차이, 실패 조건을 탐색하게 하는 예제입니다.
- `검증형`이라는 독립 유형은 유지하지 않습니다. 입력 변화, 비교 기준, 출력 차이가 실제 조작 변수와 관찰 변화로 이어지면 `실험형`으로 재설계하고, 그렇지 않으면 Python 코드가 아니라 비코드 연습이나 설명 표로 전환합니다.

판단 원칙:

- `설명형`은 코드 사용법 자체가 현재 절의 중심 질문일 때만 검토합니다. 같은 역할을 표, 사례, 비코드 연습이 더 잘 수행하면 Python 코드를 넣지 않습니다.
- 직관 위주의 연습은 Python 예제가 없어도 됩니다. 개념 경계, 용어 구분, 후보 해석처럼 손으로 판단할 수 있는 내용은 관찰값과 해설이 붙은 비코드 연습으로 닫습니다.
- 실험 위주의 연습은 Python 예제를 우선 검토합니다. 독자가 값을 바꾸거나 조건을 조정했을 때 출력, 후보 순서, 경계, 실패 조건이 달라지는지를 봐야 한다면 실행 가능한 예제로 확인하게 합니다.
- Python 코드를 유지하려면 `설명형` 또는 `실험형` 중 하나로 명확히 판정되어야 합니다.
- `설명형` 예제를 유지하려면, 독자가 지금 배워야 하는 것이 개념 자체가 아니라 코드 사용 절차나 문법이라는 근거가 있어야 합니다.
- `실험형` 예제를 유지하려면, 독자가 무엇을 바꿔 볼지와 그때 무엇을 관찰해야 하는지가 코드 앞뒤 설명에 분명해야 합니다.
- 코드가 아니면 확인하기 어려운 계산 순서가 있더라도, 독자가 조작할 값이나 관찰 변화가 없다면 Python 예제가 아니라 설명형 보조 코드, 표, 사례 중 무엇이 맞는지 다시 판정합니다.

## Python 예제와 표·그래프 선택 기준

Python 예제는 `코드가 실행된다`는 이유만으로 유지하지 않습니다. 독자가 직접 값을 바꾸거나 여러 입력을 처리했을 때, 손으로 보기 어려운 변화가 출력으로 드러나는 경우에 우선합니다.

판단 순서:

1. 현재 Section의 중심 질문이 계산 절차, 반복 처리, 임계값 변화, 그룹 비교, 누락 탐지, 민감도 확인처럼 실행을 통해 더 잘 드러나는가
2. 독자가 바꿀 수 있는 입력, 기준값, 조건, 데이터 범위가 있는가
3. 값을 바꾸면 출력, 순위, 경계, 실패 여부, 비용, 누락, 대표성 판단 중 하나 이상이 실제로 달라지는가
4. 그 변화가 표나 그래프만으로는 충분히 설명되지 않고, 코드 실행 경험이 학습에 추가 이득을 주는가

선택 기준:

| 형식 | 우선 선택하는 경우 | 피해야 하는 경우 |
|---|---|---|
| Python 예제 | 여러 행·조건·그룹을 처리해야 하거나, 입력값을 바꾸면 결과가 눈에 띄게 달라지는 경우 | 결과 변화폭이 작거나, 고정 답안을 다시 출력하거나, 표·그래프와 같은 결론만 반복하는 경우 |
| 표 | 개념 구분, 용어 비교, 판단 기준, 작은 사례 대응 관계를 한눈에 정리하는 경우 | 행이 많아 손으로 추적하기 어렵거나, 임계값 변경에 따른 판정 변화를 독자가 직접 확인해야 하는 경우 |
| 그래프 | 추세, 분포, 격차, 순위 변화, 경계 이동을 시각적으로 비교해야 하는 경우 | 그래프가 이미 결론을 충분히 보여 주는데 코드가 같은 값을 다시 계산만 하는 경우 |
| 비코드 연습 | 문장 해석, 사례 분류, 질문에 대한 판단처럼 독자의 개념 적용이 중심인 경우 | 계산 절차나 데이터 처리 흐름을 직접 확인해야 하는 경우 |

결과 변화폭이 작아 표나 그래프만으로 충분히 보이는 예제는 Python으로 연산시키지 않습니다. 이때 코드가 추가되면 학습밀도가 올라가기보다 독자가 `왜 코드를 실행해야 하는지`를 다시 추론해야 합니다.

그래프는 코드와 별개의 선택지가 아니라 관찰 형식입니다. 데이터의 패턴, 순위, 분포, 경계 이동을 보는 것이 목적이면 그래프를 우선 검토하고, 그 그래프를 만들기까지의 데이터 처리 과정 자체가 학습 대상일 때만 Python 예제로 유지합니다.

코드를 지웠을 때 같은 Section의 표, 그래프, 사례, 해설만으로 학습 목표가 거의 그대로 달성된다면 그 코드는 제거 후보입니다. 반대로 코드를 지우면 `무엇을 바꾸면 어떤 판단이 바뀌는가`를 독자가 확인할 방법이 사라진다면 Python 예제로 유지할 근거가 있습니다.

## Part 3 이후 실제 모델 사용 판단

Part 1과 Part 2에서는 개념 지도와 Python 기초 자체가 중심이므로, 실제 AI 모델을 성급하게 붙이면 설치, API, 라이브러리 문법이 본문 질문을 가릴 수 있습니다. 하지만 Part 3부터는 데이터셋, 샘플 단위, 라벨, 평가, 모델 선택, 딥러닝, LLM 구조로 이어지므로 실제 모델이나 모델에 가까운 라이브러리를 실행해 보는 예제가 학습 효과를 높일 수 있습니다.

따라서 Part 3 이후의 Python 예제는 실제 모델 사용을 지나치게 보수적으로 배제하지 않습니다. 현재 Section의 중심 질문이 다음 중 하나라면 실제 모델 실행을 우선 검토합니다.

- 같은 데이터라도 샘플 단위, feature, label, split에 따라 모델 입력과 평가가 달라지는 경우
- baseline model, classifier, regressor, clustering, vectorizer, embedding, tokenizer, retrieval model처럼 해당 개념을 모델 출력으로 보는 편이 더 분명한 경우
- threshold, hyperparameter, random seed, train/test split, preprocessing, prompt, decoding setting을 바꾸면 예측, 순위, 오류 유형, 비용, 실패 조건이 달라지는 경우
- 실제 라이브러리의 기본 동작을 봐야 추상 설명이 `장난감 계산`으로만 남지 않는 경우
- 독자가 이후 프로젝트나 서비스 구현으로 넘어가기 전에 최소한의 실행 감각을 가져야 하는 경우

권장 방식:

- Part 3-4에서는 scikit-learn, pandas, NumPy, matplotlib처럼 설치 부담이 낮고 교육적으로 널리 쓰이는 라이브러리를 우선한다.
- Part 5에서는 PyTorch, TensorFlow, NumPy 기반 직접 계산 중 현재 절의 중심 질문을 가장 잘 드러내는 쪽을 고른다. 신경망 구조나 학습 흐름이 중심이면 작은 실제 모델 실행을 적극 검토한다.
- Part 6에서는 tokenizer, vectorizer, embedding, retrieval, local LLM, API 호출 mock, Ollama, ChromaDB(chromadb) 같은 실제 시스템에 가까운 실행을 검토한다. 다만 최신 API, 과금, 계정, 네트워크 의존이 본문 이해보다 커지면 mock이나 로컬 실행으로 축약한다.
- LLM, local LLM, Ollama처럼 모델에 직접 프롬프트를 보내는 Python 예제에서는 모델 입력 프롬프트를 기본적으로 영어로 작성한다. 독자에게 보여 주는 원문 요청은 본문 언어로 둘 수 있지만, 모델 판단용 `prompt`, `model_request`, system instruction은 영어 기준으로 분리해 두는 편이 다국어 번역본에서도 같은 실행 기준을 유지하기 쉽다.
- RAG, 벡터 데이터베이스(vector database), 검색 payload, 메타데이터(metadata) 필터, top-k 후보 반환을 다루는 Section에서는 ChromaDB 같은 로컬 라이브러리형 벡터 데이터베이스를 사용할 수 있다. 이때 중심은 제품 사용법이 아니라 `문서, 임베딩, 메타데이터를 함께 넣고 질문에 맞는 원문과 payload를 다시 받는 경험`이어야 한다.
- ChromaDB를 사용할 때 기본 embedding 함수가 외부 모델 다운로드나 네트워크 의존을 만들면, 본문 예제에서는 TF-IDF, scikit-learn, 작은 로컬 embedding처럼 미리 계산한 embeddings를 직접 넣는 방식을 우선한다. 영속 서버, 대규모 색인 운영, 성능 튜닝, 배포 구성은 본문 Section보다 Part 7 프로젝트나 보충 자료에 더 적합하다.
- 모델을 쓰더라도 `한 번 학습하고 점수 하나 출력`에서 멈추지 말고, 독자가 바꿀 값과 그에 따라 달라지는 출력 또는 실패 조건을 함께 둔다.
- 실제 모델 예제의 출력은 accuracy 같은 단일 점수보다 예측 샘플, 오류 사례, confusion matrix, 후보 순위, decision boundary, residual, retrieved document, generated text 차이처럼 현재 Section의 중심 질문을 직접 보여 주는 값을 우선한다.
- 실행 시간이 길거나 재현성이 흔들리는 모델은 작은 데이터, 고정 seed, 짧은 반복, 일부 결과 발췌를 사용한다. 그래도 핵심 관찰이 불안정하면 본문 예제가 아니라 Part 7 프로젝트나 보충 자료로 넘긴다.
- LLM처럼 실행 결과가 모델 버전, 샘플링 설정, 실행 시점에 따라 달라지는 예제는 `직접 실행 스크립트`와 `저장 로그 스냅샷`을 분리할 수 있다. 직접 실행 스크립트는 Ollama나 SDK로 실제 모델을 호출해 원문 응답을 만들고, 저장 로그 스냅샷은 그 원문 응답을 관찰 열로 줄여 CSV나 JSONL로 남긴 파일이다.
- 저장 로그 스냅샷을 본문 예제의 입력으로 쓰는 방식은 프롬프트 비교, 응답 경로 비교, self-consistency 후보 분포, 평가 로그, 도구 호출 로그처럼 `모델을 매번 다시 호출하면 느리거나 흔들리지만, 관찰 기준은 반복해서 읽어야 하는 Section`에서 효율적이다.
- 저장 로그 스냅샷을 사용할 때는 반드시 `어떤 모델`, `어떤 설정`, `어떤 실행 시점 또는 실행 조건`에서 생성된 기록인지 메타 열이나 본문 설명으로 남긴다. 예를 들어 `log_source`, `model_name`, `temperature`, `run_id`, `prompt_type`, `path_type` 같은 열을 둔다.
- 저장 로그 스냅샷은 정답표가 아니다. 본문에서는 `스냅샷 로그`, `저장 응답 로그`, `관찰 기록`처럼 표현하고, 모델이나 설정이 바뀌면 숫자와 문장이 달라질 수 있음을 안내한다. 코드가 해야 할 일은 정답 대조가 아니라 로그를 읽어 분포, 점검 신호, 누락, 경계 사례를 다시 계산하게 하는 것이다.
- 생성 스크립트는 원문 응답 전체를 그대로 본문에 붙이는 도구가 아니라, 원문 응답에서 현재 Section이 볼 관찰 열을 추출하는 도구로 작성한다. 예를 들어 `final_answer`, `retrieved_doc_id`, `format_ok`, `keyword_hits`, `missing_evidence`, `tool_error`, `rule_warning`, `minority_answer`처럼 Section 중심 질문과 직접 연결되는 열을 남긴다.
- Python 예제의 소스코드 길이에는 고정 제한을 두지 않는다. 코드가 길어도 현재 Section의 중심 질문을 실제 실행 흐름, 입력 변화, 관측 결과, 실패 조건으로 확인하게 만든다면 유지할 수 있다. 다만 길어진 코드의 각 부분이 본문 해설과 연결되어야 하며, 설치·환경 설정·부수 구현이 중심 개념을 가리면 예제를 나누거나 보충 자료로 넘긴다.

피해야 할 오해:

- 실제 모델을 쓰는 것 자체가 좋은 예제를 보장하지 않는다. 모델 실행이 Section의 중심 질문을 더 선명하게 만들 때만 쓴다.
- 초심자에게 어렵다는 이유만으로 실제 모델 사용을 자동 배제하지 않는다. 필요한 경우 코드 앞뒤 설명, 작은 입력 파일, 출력 해석을 보강해 진입 장벽을 낮춘다.
- 모델 성능 경쟁이나 튜닝 로그가 중심이 되면 본문 Section의 범위를 넘어설 수 있다. 이때는 `왜 이 설정을 바꾸면 무엇이 달라지는가`만 남기고 과도한 실험 관리는 프로젝트 파트로 넘긴다.

## 정답 확인형 코드 판단

하드코딩된 정답표를 코드 안에 두고 입력 이름과 대조하는 예제는 학습 효과가 낮습니다. 이런 코드는 독자에게 개념을 적용하게 하기보다, 이미 만든 답을 프로그램이 다시 읽어 주는 역할에 머물기 쉽습니다.

다음 기준으로 처리합니다.

- 지도학습 예제에서 `정답(label)`을 입력 데이터의 한 열로 설명하는 것은 허용한다. 다만 그 label은 모델 학습, 평가, 오류 비교, 경계 변화 관찰에 쓰여야 한다.
- `expected_answer`, `answer_key`, `correct_labels`처럼 사람이 미리 넣은 정답 사전을 만들고 코드가 `맞음/틀림`만 출력한다면 Python 예제가 아니라 정답 확인표에 가깝다.
- 독자가 할 일이 입력을 바꾸거나 판단 기준을 조정하는 것이 아니라, 코드가 출력한 정답과 자기 답을 대조하는 것뿐이라면 비코드 연습과 해설로 전환한다.
- 정답 확인이 필요하면 먼저 독자가 분류, 표시, 순서 선택, 이유 쓰기 같은 판단을 하게 하고, 바로 뒤의 해설에서 기준을 설명한다. Python은 그 판단 기준이 여러 입력에서 어떻게 흔들리는지 보여 줄 때만 붙인다.
- 코드가 정답을 미리 들고 있더라도, 임계값 변경, 특징 제거, 데이터 분할, 오류 유형 비교처럼 조작 변수에 따라 판정이나 해석이 실제로 달라지면 실험형 예제로 유지할 수 있다.
- 유지 여부의 핵심 질문은 `코드가 답을 확인하는가`, 아니면 `코드가 판단 기준이 작동하고 실패하는 조건을 드러내는가`이다.

## 작성 규칙

- 원고에 Python 예제를 반영하기 전에는 가능한 한 같은 환경에서 실제로 실행하고, 출력물이 Section의 중심 질문과 조작 변수를 드러내는지 확인한다. 실행만 성공했더라도 출력이 학습 효과를 만들지 못하면 예제를 다시 설계하거나 표·사례·비코드 연습으로 바꾼다.
- 생성 이미지, 모델 응답, 후보 목록처럼 출력의 해석이 주관적으로 흔들릴 수 있는 예제는 특히 실제 출력물을 확인한다. 단발 출력이 조작 변수의 효과를 분리해 보여 주지 못하면, 그 출력물을 본문 예시나 학습 자산으로 사용하지 않는다.
- 새로운 핵심 개념이나 핵심 판단 기준을 설명한 Section에서는 `예시`와 `연습 또는 예제`가 함께 있어야 한다. Python 코드는 그중 `예제`를 담당할 때만 넣는다.
- 코드가 현재 절의 핵심 개념을 실제 입력 변화, 비교 기준, 출력 차이로 실험하게 하지 못하면 Python 예제를 억지로 넣지 말고 비코드 연습으로 닫는다.
- 코드 앞에 문제 상황, 입력(input), 정답(label) 또는 기대 출력(output), 확인할 개념을 짧게 둔다.
- 가능하면 `print` 또는 이에 준하는 출력 코드를 함께 둔다.
- 코드 블록 아래에는 가능하면 실행 결과 예시도 함께 둔다.
- 우선적으로 보여 줄 값은 샘플 수, `shape`, 분포, 분리 결과, 예측과 실제값 비교처럼 현재 절의 중심 질문과 직접 연결된 값이다.

- 의사 코드보다 실제 실행 가능한 예제를 우선한다.
- 가능하면 실제 라이브러리, 실제 데이터 형식, 실제 전처리 흐름, 실제 모델 입출력 중 적어도 하나와 연결한다.
- Part 3 이후에는 실제 모델이나 모델에 가까운 라이브러리를 사용하는 예제를 적극 검토한다. 단, 모델 사용 자체가 목적이 아니라 Section의 중심 질문을 출력 변화로 확인하게 해야 한다.
- 다만 실제 라이브러리 사용이 현재 Section의 중심 질문보다 설치, API 사용법, 프로젝트 환경 설정을 더 크게 만들면 본문 Section 안에 억지로 넣지 않는다. 그런 실습은 Part 7 프로젝트 목차로 넘기고, 현재 Section에는 핵심 판단을 확인할 수 있는 축약 실험만 둔다.
- 단순화가 필요하면 축약한 부분과 실제 관찰 포인트를 함께 밝힌다.
- 독자가 수치를 바꿔 보며 결과 차이를 다시 확인할 수 있어야 한다.
- 실험형 예제라면 적어도 하나 이상의 `조작할 값`, `관찰할 출력`, `해석할 질문`을 코드 앞뒤에 명시한다.
- 사용법 안내가 아닌 Python 예제는 적어도 하나 이상의 조작 변수를 가져야 하며, 그 값을 바꾸면 출력, 순위, 경계, 실패 여부, 비용, 누락 중 하나 이상이 실제로 달라져야 한다.
- 코드 안의 주석은 주요 함수와 변수가 영어 코드로 작성되어 있을 때, 독자가 도메인 의미를 파악하는 시간을 줄이고 실행 흐름, 조작 변수, 관찰 포인트를 놓치지 않게 돕는 설명으로 쓴다. 다만 주석이 본문 설명, 출력 해석, 개념 정의를 대신하게 하지 않는다.
- 초심자가 모를 수 있는 변수명, 함수명, 전처리 단계, 비교 기준, 임계값, 출력 계산은 필요한 위치에 짧은 주석으로 붙인다.
- 주석은 `무엇을 하는가`만 반복하기보다 `왜 이 줄이 현재 예제의 관찰 포인트와 연결되는가`를 짧게 드러낸다.
- 코드 사용법 자체를 가르치는 설명형 예제에서는 주석으로 읽는 순서를 안내할 수 있지만, 문법 설명이 길어지면 코드 밖 본문으로 분리한다.
- 실험형 예제에서는 조작해 볼 값 근처에 주석을 두어 독자가 어느 값을 바꾸면 되는지 바로 알 수 있게 한다.

- 해설은 출력값을 다시 읽는 수준에 그치지 말고, 왜 그 출력 차이가 현재 Section의 중심 개념이나 판단 기준을 확인해 주는지 닫아야 한다.
- 실험형 예제의 출력은 단순 정답 나열보다 `경계 위/아래`, `가장 민감한 입력`, `출력이 뒤집히는 조건`, `실패하는 경우`처럼 탐색 결과를 읽게 하는 쪽을 우선한다.
- 실제 맥락을 단순화하더라도, 가능하면 실제 신호, 실제 컬럼, 실제 모델 입출력, 실제 전처리 형태 중 적어도 하나는 남겨 장난감 계산으로만 보이지 않게 한다.

## 코드 주석 기준

- 주석은 본문 독자가 영어 함수명·변수명 때문에 도메인 의미를 바로 파악하기 어렵거나, 코드를 처음 읽을 때 실행 흐름에서 막히는 지점에 둔다.
- 주석의 우선순위는 `도메인 의미가 담긴 변수와 함수`, `조작 변수`, `계산 단계의 의도`, `출력에서 관찰할 차이`, `단순화한 가정`이다.
- 한 줄짜리 코드에 같은 뜻을 반복하는 주석은 붙이지 않는다.
- 여러 줄에 걸친 단계라면 첫 줄 앞에 짧은 주석을 두고, 각 줄마다 설명을 반복하지 않는다.
- 예제에서 일부 현실 조건을 생략했다면 주석 또는 코드 앞뒤 설명으로 무엇을 단순화했는지 밝힌다.
- 주석은 독자가 바꿔 볼 수 있는 값과 바꾸면 안 되는 구조를 구분해 주어야 한다.
- 본문에서 이미 충분히 설명한 용어 정의를 코드 안 주석으로 다시 길게 쓰지 않는다.
- 코드만 복사해 실행해도 최소한 `어디를 바꾸고`, `무엇을 출력으로 봐야 하는지`가 주석과 변수명으로 드러나야 한다.

## CSV 입력 자산 기준

- 원시 입력 데이터가 CSV, JSON, 로그 파일처럼 파일 형태를 가질 수 있다면, 가능하면 그 파일을 코드 밖 자산으로 분리하고 본문에서는 `입력 파일 설명`과 `실행 코드`를 구분해 제시한다.
- 입력 파일을 따로 두었다면, Python 코드는 인라인 문자열이나 하드코딩된 배열을 다시 복제하지 말고 실제 파일을 읽는 단계부터 시작한다.
- 본문에 데이터 표를 길게 넣어야 할 정도로 입력이 커지면, Part 7 프로젝트 실습에서 쓰는 방식처럼 CSV 자산을 따로 만들고 본문에는 파일 링크, 한 행의 의미, 핵심 열, 짧은 발췌만 둔다.
- 독자가 CSV 원본을 다운로드하지 않고 먼저 확인할 필요가 있는 입력 자산에는 원본 링크와 함께 `내용 보기` 대상을 표시한다. 기본 표기는 CSV 링크에 `{ .csv-preview }` 클래스를 붙이는 방식으로 한다.
- `내용 보기`는 원본 파일을 대체하지 않는다. 본문에는 원본 CSV 링크를 유지하고, 미리보기는 앞부분 일부 행과 열 구조를 확인하는 보조 장치로만 사용한다.
- 모든 CSV 링크에 자동으로 `내용 보기`를 붙이지 않는다. 실제 파일이 존재하고, 해당 Section의 입력 이해에 도움이 되는 CSV 자산에만 선택적으로 붙인다. 코드 설명 안의 예시 파일명, 가짜 파일명, 아직 만들지 않은 파일명에는 붙이지 않는다.
- `내용 보기`가 있더라도 본문에는 `한 행이 뜻하는 것`, `핵심 열`, `조작 변수가 판정에 영향을 주는 열`, `출력에서 관찰할 차이`를 짧게 설명해야 한다. 미리보기 표가 입력 설명을 대신하게 하지 않는다.
- 데이터 처리 예제는 원시데이터가 충분해야 코드의 동작을 이해할 수 있다. 따라서 필터링, 묶기, 집계, 분할, 누락 처리, 대표성 점검처럼 여러 행의 관계를 읽어야 하는 예제는 본문 안의 작은 하드코딩 배열보다 CSV 입력 자산을 우선한다.
- CSV 입력 자산은 코드가 보여 주려는 판단을 실제로 드러낼 만큼 충분한 행과 조건을 가져야 한다. 최소한 `정상 사례`, `경계 사례`, `부족하거나 실패하는 사례`, `비교 기준을 넘는 사례` 중 현재 Section의 중심 질문에 필요한 대비가 들어 있어야 한다.
- 모델 실행 로그를 CSV 입력 자산으로 둘 때는 원시 입력, 모델 호출 조건, 관찰 결과를 구분할 수 있어야 한다. 본문 예제는 가능하면 저장 로그 CSV를 읽어 집계하고, 별도 생성 스크립트는 같은 CSV를 다시 만들 수 있게 둔다.
- 저장 로그 CSV에는 결과만 두지 말고 결과가 어떤 입력과 실행 조건에서 나왔는지 알 수 있는 열을 함께 둔다. 최소 기준은 `run_id`, 입력 식별자, 조건 식별자, `log_source`, `model_name`, 주요 설정값, 관찰 결과 열이다.
- 저장 로그 CSV를 사용하는 본문에는 `이 로그는 특정 실행 조건에서 얻은 스냅샷`이라는 안내를 둔다. 독자가 직접 생성 스크립트를 다시 실행하면 값이 달라질 수 있으며, 그 차이 자체가 모델 출력의 흔들림과 관찰 기준의 필요성을 보여 줄 수 있다.
- CSV 입력 자산의 기본 하한은 36행 이상으로 본다. 36행보다 작아도 되는 경우는 코드 사용법 자체를 보여 주는 설명형 예제처럼 행 간 관계가 핵심이 아닐 때뿐이며, 이때도 CSV 자산보다 본문 표나 짧은 인라인 예제가 더 적합한지 먼저 판단한다.
- 그룹이나 시계열을 다루는 CSV는 최소 두 개 이상의 그룹을 두고, 적어도 한 그룹은 18행 이상을 가져야 한다. 그래야 반복, 순서, 묶기 전후 차이가 출력에서 드러난다.
- 임계값, 누락, 실패 조건, 대표성 공백을 다루는 CSV는 기준 아래 사례, 기준 근처 사례, 기준 위 사례를 최소 하나씩 포함하는 것을 우선한다. 값 하나를 바꿔도 모든 행의 판정이 그대로라면 입력 데이터가 부족한 것이다.
- 그룹, 시간 순서, 대표성, 분할, 누락, 임계값을 다루는 예제라면 CSV에는 한 그룹만 두지 않는다. 서로 다른 그룹이나 조건이 최소 두 개 이상 있어야 하고, 조작 변수를 바꿨을 때 어느 행·그룹·조건의 판정이 달라지는지 출력에서 확인할 수 있어야 한다.
- CSV가 작더라도 `세 행짜리 장난감 표`처럼 보이면 안 된다. 행 수를 늘리는 목적은 분량이 아니라 관찰 차이를 만들기 위한 것이므로, 각 행은 반복, 편향, 누락, 경계, 비교 대상 중 하나 이상의 역할을 가져야 한다.
- 본문에는 CSV 전체를 길게 복제하지 말고, 파일 링크와 함께 `한 행이 뜻하는 것`, `핵심 열`, `조작 변수가 판정에 영향을 주는 열`, `출력에서 관찰할 차이`를 짧게 설명한다.

## 금지 패턴

- 핵심 개념 설명만 있고 독자가 직접 적용해 볼 연습이 없는 Section을 Python 예제 하나로 형식적으로만 메우지 않는다.
- 앞 절이나 바로 위 표에서 이미 정리한 대응 관계를 코드가 그대로 다시 `print`만 하는 예제는 두지 않는다.
- 코드가 새 판단을 요구하지 않고, 고정된 정답표를 재출력하는 수준이면 연습·예제 역할을 하지 못하는 것으로 본다.
- 하드코딩된 정답 사전이나 라벨 목록을 만든 뒤 입력별 `맞음/틀림`만 출력하는 코드는 Python 예제로 유지하지 않는다.
- 실행 결과가 `무엇이 달라졌는가`, `왜 이 결과가 현재 절의 핵심 질문과 연결되는가`를 보여 주지 못하면 예제를 다시 설계한다.
- 독자에게 던진 해석 질문의 답이나 해설이 없으면, 예제가 아니라 미완성 질문 목록으로 보고 보강한다.
- 입력 변화, 오답 가능성, 비교 기준이 전혀 없으면 학습 검증용 예제로 보지 않는다.
- `scene -> answer`, `name -> label`처럼 선언적 매핑만 출력하는 블록은 가능한 한 표나 체크리스트로 대체하고, 코드 블록으로 유지하지 않는다.
- 같은 절의 표, 사례, 체크리스트가 이미 더 잘 설명하는 내용을 코드가 반복하면 삭제하거나 비코드 연습으로 바꾼다.
- 코드 사용법을 가르치는 절이 아닌데도, 계산 설명을 다시 보여 주기 위해 설명형 코드를 넣지 않는다.
- 입력 이름만 그럴듯하게 바꾸고 실제로는 추상 수식 값을 재출력하는 예제를 `실험형`으로 포장하지 않는다.
- 독자가 조작할 수 있는 값이 없거나, 값을 바꿔도 관찰 포인트가 달라지지 않으면 `실험형` 예제로 보지 않는다.
- 설명을 모두 코드 주석 안에 넣고 코드 앞뒤의 문제 상황, 출력 해석, 현재 Section과의 연결을 비워 두지 않는다.
- `이 줄은 값을 더한다`, `반복문을 실행한다`처럼 코드가 이미 말하는 내용을 반복하는 주석으로 코드 블록을 채우지 않는다.
- 주석이 너무 길어 코드 실행 흐름보다 주석 읽기가 중심이 되면 본문 설명, 표, 단계 목록으로 분리한다.
- 실제 데이터나 모델과의 연결 없이 고정된 세네 개 숫자만 대입해 결과를 다시 출력하는 블록은 기본적으로 장난감 예제 후보로 보고 재검토한다.
- 결과 변화폭이 작아 표나 그래프만으로 충분히 읽히는 내용을 코드로 다시 연산시키지 않는다.
- CSV 자산을 만들었더라도 한두 개 조건만 담겨 있어 출력이 항상 같은 결론으로 닫히면 충분한 입력 데이터로 보지 않는다.
- 조작 변수나 임계값을 소개했는데 CSV 안에 그 기준 위/아래 또는 변경 전/후 판정 차이를 보여 줄 행이 없으면 실험형 예제로 보지 않는다.
- 모든 행이 같은 그룹, 같은 라벨, 같은 조건, 같은 결과만 보여 주면 CSV 파일로 분리했더라도 표를 코드 밖으로 옮긴 것일 뿐이며, 예제로서 다시 설계한다.
- `내용 보기` 미리보기만 믿고 원본 CSV 링크, 핵심 열 설명, 출력 해석을 생략하지 않는다.
- 존재하지 않는 CSV 파일명이나 코드 설명용 가짜 파일명에 `{ .csv-preview }`를 붙이지 않는다.
- 표나 사례가 이미 같은 확인을 충분히 수행하는데 코드가 `맞는지 다시 본다` 수준으로만 남아 있으면, 그 Python 예제는 원고 이해에 기여하지 않는 것으로 보고 제거 후보로 검토한다.
- 검색 결과, 후보 목록, 모델 출력, 도구 호출 결과가 이미 사람이 만든 라벨이나 고정 답안으로 들어 있고 코드는 집계나 출력만 한다면 실험 예제로 보지 않는다.
- 실험을 말하는 예제는 결과를 미리 주입하지 않는다. 코드는 입력 데이터와 조작 변수에서 관찰 결과를 만들어 내야 하며, 실패나 차이는 실행 결과로 드러나야 한다.
- 코드 블록 바로 위에 CSV 본문을 길게 인라인으로 복제해 두어, `입력 파일 설명`과 `실행 코드`의 경계가 흐려지는 구성은 피한다.

## 초심자 점검

- 예제가 없다면, 그 자리를 대신하는 비코드 연습이 현재 절의 핵심 개념을 충분히 붙잡아 주는가
- 코드만 읽어도 예제가 왜 필요한지 드러나는가
- 코드 주석이 초심자의 실행 흐름 이해를 돕되, 본문 해설을 대신하고 있지는 않은가
- 조작할 값과 관찰할 출력이 변수명, 주석, 코드 앞뒤 설명으로 모두 확인되는가
- 출력값을 보고 독자가 현재 절의 개념을 다시 확인할 수 있는가
- CSV 입력 파일만 열어도 한 행의 의미, 비교되는 조건, 부족하거나 경계에 걸리는 사례가 보이는가
- CSV 입력 자산이 본문 이해에 중요하다면 원본 링크와 `내용 보기` 표시가 함께 있는가
- 조작 변수를 바꾸면 CSV 안의 어떤 행·그룹·조건이 다른 판정을 받는지 설명할 수 있는가
- 코드 블록 아래 설명이 `무엇을 봐야 하는가`를 닫아 주는가
- 해석 질문을 던졌다면 바로 뒤에서 답과 이유를 함께 닫아 주는가
- 표나 사례가 더 적합한데 관성적으로 코드 블록을 쓰고 있지는 않은가
- 코드를 지워도 표, 그래프, 사례, 해설만으로 같은 학습 목표가 거의 그대로 달성되지는 않는가
- 실험형이라면 독자가 `무엇을 바꾸고`, `무엇이 바뀌며`, `왜 그렇게 바뀌는가`를 한 문장으로 말할 수 있는가
