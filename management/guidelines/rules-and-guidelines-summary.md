# 집필 규칙·가이드라인 요약

작성일: 2026-07-01

이 문서는 저장소의 집필 규칙을 빠르게 다시 잡기 위한 운영용 요약입니다. 기준 원문은 `AGENTS.md`와 `management/guidelines/` 아래 문서이며, 실제 수정 전에는 필요한 원문을 다시 확인하는 것을 원칙으로 합니다.

## 기준 문서 맵

이 저장소의 문서는 성격이 다릅니다. 먼저 `규칙 원문`, 그다음 `작업형 가이드`, 마지막으로 `분석 메모`를 구분해서 읽는 것이 가장 효율적입니다.

### 1. 규칙 원문

이 문서들은 판단이 충돌할 때 우선권을 가집니다.

| 문서 | 역할 | 먼저 볼 때 |
| --- | --- | --- |
| `AGENTS.md` | 저장소 전체 규칙의 기준 원문 | 모든 작업 시작 전 |

### 2. 작업형 가이드

이 문서들은 특정 작업을 할 때 강하게 참고해야 하는 실행 기준입니다.

| --- | --- | --- |

| `management/guidelines/python-example-guidelines.md` | Python 예제 작성 기준 | Python 예제 추가·수정, 코드 블록 유지 여부 판단 전 |
| `AGENTS.md` | 초심자 설명·예시 보강 기준 | 새 Section 초안, 예시 보강, 보충학습 분리 판단 전 |

이 문서들은 규칙 원문이라기보다, 기존 원고를 정리하거나 후속 판단을 돕는 참고 자료입니다.

| `management/authoring/section-...-evidence-analysis.md` | 특정 Section의 근거 검토 메모 | 기존 절 수정, 근거 확인, 후속 설명 위치 판단 시 |

## 문서별 역할 분담

- `AGENTS.md`: 프로젝트 목적, 독자 기준, 문서 위치, Section 경계, Python 예제 원칙, 용어, 출처, 저작권, 배포, 빌드 검증까지 포함하는 최상위 규칙 문서입니다.
- `AGENTS.md`: 초심자가 막히는 지점을 현재 Section 안에서 풀지, `보충학습`으로 분리할지 판단하는 기준이 포함되어 있습니다.
- `management/guidelines/manuscript-writing-workflow.md`: Part/Section 작성, 초심자 보강, 사례 작성, Section 경계 같은 원고 작성 절차를 다루는 상세 문서입니다.
- `management/guidelines/python-example-guidelines.md`: Python 예제의 입력·출력 제시 방식, 금지 패턴, 초심자 점검 기준을 다루는 상세 문서입니다.
- `management/guidelines/chart-guidelines.md`: 차트의 표현 방식, Mermaid 우선 원칙, SVG 예외 조건, 레이아웃, 겹침 방지, 검증 기준까지 다루는 상세 문서입니다.
- `management/release-notes/sections/README.md`: Section 버전 코드, 수정일 기준 버전 갱신, 제목 앞 인덱스와 `Section ID`의 동일 규칙, Section별 릴리즈노트 파일 관리 방식을 다루는 운영 문서입니다.
- `management/release-notes/sections/README.md`: 앞으로 번역본이 생겼을 때도 `Section ID` 기준으로 대응 버전을 추적하는 운영 문서입니다.
- `management/guidelines/english-translation-guidelines.md`: 영어 번역 시 한국어 원문 대조, 공통 릴리즈노트 기록, `빈 줄 제외 라인 수 5% 미만` 검수 기준을 포함한 번역 운영 문서입니다.
- `management/guidelines/chinese-translation-guidelines.md`: 중국어 간체 번역 시 한국어 원문 대조, 공통 릴리즈노트 기록, `빈 줄 제외 라인 수 5% 미만` 검수 기준을 포함한 번역 운영 문서입니다.
- 원칙 문서와 가이드라인 문서는 별도 리비전노트를 두지 않고 문서 자체를 직접 갱신합니다.
- `author-notes.md`: 본문 규칙 문서가 아니라, 저자 관점 문장을 안전하게 일반화하기 위한 메모입니다. 사실 주장 근거 문서로 사용하지 않습니다.
- `section-...-evidence-analysis.md`: 개별 Section의 근거, 용어, 출처 충돌, 회수 위치를 기록하는 문서입니다. 전역 규칙은 아니지만, 해당 절 수정 시에는 실질적으로 가장 가까운 작업 메모입니다.
- `part-XX-open-checklist.md`: 이미 반영된 설명을 반복 저장하지 않고, 각 Part에서 아직 남은 작업만 추린 체크리스트입니다.

## 작업 유형별 참조 순서

### Section 본문을 새로 쓰거나 크게 고칠 때

1. `AGENTS.md`
2. `management/guidelines/manuscript-writing-workflow.md`
3. 필요하면 해당 `section-...-evidence-analysis.md`
4. 문단 재구성이 크면 `management/guidelines/manuscript-writing-workflow.md`의 문단 구조 점검 메모를 같이 본다.
5. Part 수준 후속 작업이 있으면 해당 `part-XX-open-checklist.md`
6. 실제로 수정한 Section이라면 `management/release-notes/sections/README.md`를 따라 버전 코드와 릴리즈노트도 함께 갱신한다.
7. 번역본이 아직 없더라도 릴리즈노트에 번역 반영 필요 여부를 남긴다.

### Python 예제를 넣거나 고칠 때

1. `AGENTS.md`의 Python 예제 원칙
2. `management/guidelines/python-example-guidelines.md`
3. 현재 Section의 중심 질문과 출력값 점검
4. 필요하면 `AGENTS.md`의 초심자 보강 기준으로 예제 보강 수준 판단

### 차트, Mermaid, SVG를 만들 때

1. `AGENTS.md`의 도식 원칙
2. `chart-guidelines.md`

### 관점 문장, 머리말, 도입 문장을 다듬을 때

1. `AGENTS.md`의 기본 관점과 집필 태도
2. `author-notes.md`
3. 사실 주장이 섞이면 별도 근거 확인

## 노트 정리 원칙

- `section-...-evidence-analysis.md`에는 근거와 용어 판단, 현재 본문에서 아직 중요한 경계만 남깁니다.
- 이미 본문에 반영된 집필 메모나 끝난 작업 목록은 Section 메모에 계속 누적하지 않습니다.
- 후속 작업은 가능한 한 `part-XX-open-checklist.md`로 옮겨 Part 단위로 관리합니다.
- `review`, `plan`, `curriculum-review` 문서의 남은 항목을 Part 체크리스트로 옮겼다면 원본 문서는 삭제해도 됩니다.
- evidence 메모를 폐기할 때는 대응 원고 본문과 참고문헌 반영을 먼저 대조하고, 구조가 어긋나는 메모는 자동 폐기하지 않습니다.

## 가장 중요한 원칙

### 1. 책의 목적과 독자 기준

- 이 저장소는 AI 재학습용 정적 웹 책을 만드는 프로젝트입니다.
- 기본 독자는 비전공 초심자이며, 대학 수준의 수학·프로그래밍·시스템 기초를 모를 수 있다고 가정합니다.
- 설명은 단순 자료 수집이 아니라 `기초 복구 -> 머신러닝 -> 딥러닝 -> LLM/생성형 AI -> 프로젝트`로 이어지는 학습 경로를 만들어야 합니다.

### 2. 집필 태도

- 사용자의 기억, 비유, 직관은 `작업 가설`로 보존합니다.
- 교과서, 논문, 공식 문서와 연결되는 설명은 `표준적 설명`으로 정리합니다.
- 근거가 부족하거나 충돌하는 내용은 `검증 필요`로 분리합니다.
- 설명은 가능하면 `왜 필요한가 -> 핵심 원리는 무엇인가 -> 어떻게 확인할 수 있는가` 흐름을 따릅니다.
- 이해 중심 섹션의 사례는 가능하면 `사람이 먼저 쓰던 기준 -> 그 기준의 한계 -> 개념이 바꾸는 점 -> 확인 가능한 결과`까지 닫습니다.

### 3. 문서 위치와 구조

- 배포 본문은 `docs/` 아래에만 둡니다.
- 본문은 `docs/parts/part-XX/chapter-YY/section-ZZ.md` 구조를 따릅니다.
- 각 Part에는 `index.md`와 `summary.md`가 있어야 합니다.
- 관리 문서는 `management/` 아래에 둡니다.
- 새 Section, 새 Part, 구조 변경 시 `mkdocs.yml`의 `nav` 반영 여부를 확인합니다.

## Section 작성 기준

### Section 경계

- 하나의 Section은 하나의 중심 질문에 답해야 합니다.
- 다른 Section의 핵심 설명, 예시, 결론, 체크리스트를 미리 당겨 쓰지 않습니다.
- 현재 Section에서 생략한 내용은 반드시 다음 중 하나로 연결합니다.
  - 후속 본편 Section
  - 보충학습
  - 책의 범위 밖

### 권장 공통 구조

`AGENTS.md`의 기본 구조는 다음 순서입니다.

1. 이전 Section과의 연결
2. 이 Section의 범위
3. 목표
4. 핵심 설명
5. 사례 및 예시
6. 연습 및 예제
7. 이 절에서 기억할 관점
8. 체크리스트
9. 출처와 참고 자료

문단 재배치 작업에서는 이를 더 실무적으로 다음 골격으로 다시 묶어 사용할 수 있습니다.

1. 학습 배경
2. 학습 목표
3. 주요 학습내용
4. 세부 학습내용
5. 사례 및 예시
6. 연습 및 예제
7. 이 절에서 기억할 관점
8. 체크리스트
9. 출처와 참고 자료

모든 섹션을 기계적으로 같은 분량으로 맞추기보다 `이론형`, `실습형`, `혼합형`에 따라 비중을 조절합니다.
- 다만 새로운 핵심 개념이나 핵심 판단 기준을 실제로 설명하는 본문 Section이라면, 같은 절 안에 최소한 하나 이상의 `예시`와 하나 이상의 `연습 또는 예제`를 두는 쪽을 기본 규칙으로 봅니다.
- 핵심 개념 설명만 길게 두고 예시·연습 없이 넘기는 구성은 학습 밀도를 분산시키는 패턴으로 보고 피합니다.

자기 확인 블록의 기준 표지는 `체크리스트`입니다. 같은 역할의 구조 표지를 `짧은 점검`과 혼용하지 않는 쪽을 기준으로 봅니다.

구조 용어는 다음처럼 구분합니다.

- `사례`: 문제 장면과 판단 흐름을 설명하는 블록
- `예시`: 작은 표, 짧은 수치, 짧은 비교처럼 개념을 바로 붙잡게 하는 보조 블록
- `예제`: 코드, 실행 절차, 출력 결과처럼 독자가 직접 확인하는 실습 블록

따라서 구조 표지에서는 `사례 및 예시`와 `연습 및 예제`를 기본 축으로 사용하고, 같은 절 안에서 `사례로 보기`와 `사례 및 예시`처럼 역할이 같은 표지를 중복으로 두지 않습니다.

사례와 예시는 `있다`는 사실만으로 통과시키지 않습니다.

- `사례`는 독자가 그 장면만 읽고도 `왜 이 개념이 필요한가`를 납득할 수 있어야 합니다.
- `사례`는 가능하면 `사람이 먼저 쓰던 기준 -> 그 기준의 흔들림 또는 한계 -> 개념 적용 후 무엇이 더 선명해지는가 -> 확인 가능한 결과`까지 닫습니다.
- `예시`는 사례 본문을 추상적으로 다시 말하는 데 그치지 않고, 판단 차이가 실제로 보이게 해야 합니다.
- `예시`의 표·수치·비교는 `무엇이 더 유리한가`, `어느 쪽으로 분류되는가`, `어디서 판단이 갈리는가`처럼 결과 차이를 드러내야 합니다.
- 사례를 읽고도 개념 필요성이 흐리거나, 예시를 보고도 판단 차이가 한눈에 보이지 않으면 미통과로 보고 다시 씁니다.

### 사례·예시 빠른 점검

- 사례만 읽어도 독자가 `왜 이 개념이 필요한가`를 한 문장으로 말할 수 있는가
- 사람이 하던 기존 판단 방식과 개념 적용 후 판단 방식의 차이가 드러나는가
- 예시가 `기여`, `영향` 같은 추상어 반복이 아니라 실제 비교 결과를 보여 주는가
- 사례 마지막이 `그래서 무엇이 더 잘 보이는가`를 분명히 닫는가
- 사례와 예시를 빼면 설명이 거의 달라지지 않는 수준이라면, 아직 보강이 부족한 것으로 본다

### `다루지 않는다` 문장 규칙

- `여기서는 다루지 않습니다.`로 끝내지 않습니다.
- 반드시 바로 이어서 다음 중 하나를 밝힙니다.
  - 어느 Chapter/Section에서 다시 다루는지
  - 어느 `보충학습`에서 회수하는지
  - 이 책의 범위 밖인지
- 생략 항목이 여러 개라면, 각 항목마다 회수 위치를 따로 대응시킵니다.
- 후속 본편 Section이 없고 `범위 밖`으로 두기에도 맞지 않으면, `보충학습` Section 후보를 먼저 만듭니다.
- `후반에서 다룬다`처럼 임시 예고만 남기지 않습니다. 실제 Section ID가 없으면 `새 본편 Section 후보` 또는 `새 보충학습 후보`로 관리합니다.

## 초심자 보강 기준

- 초심자 보강은 `수준을 낮추는 일`이 아니라 `공백을 메우는 일`입니다.
- 주로 메우는 공백은 다음 다섯 가지입니다.
  - 선행 개념 공백
  - 용어 공백
  - 실행 환경 공백
  - 예시 해석 공백
  - 왜 필요한지에 대한 맥락 공백

보강 방식은 두 가지 중 하나만 선택합니다.

1. 현재 Section에 짧게 추가
2. `보충학습` Section으로 분리

현재 Section에 추가할 조건:

- 현재 중심 질문에 직접 필요할 때
- 작은 표, 짧은 예시, 간단한 도식 같은 최소 보강으로 시작할 수 있을 때
- 그리고 필요하면 그 최소 보강을 넘어 초심자에게 충분한 예시와 예제로 바로 확장할 수 있을 때
- 지금 막히는 이유가 핵심 개념 이해 부족일 때

`보충학습`으로 분리할 조건:

- 선행 지식 복구가 목적일 때
- 설명이 길어져 현재 Section 범위를 흐릴 때
- 설치, 운영체제, 수학 기초, Python 기초처럼 여러 장에서 재사용될 때

## Python 예제 기준

- 세부 기준 원문은 `management/guidelines/python-example-guidelines.md`를 먼저 본다.
- Python 예제는 `연습 및 예제`를 채우는 여러 방식 중 하나다. 코드가 필요 없는 절이라면 비코드 연습으로 닫고, 코드가 개념 검증에 실제로 도움이 될 때만 Python 예제를 넣는다.
- 코드 앞에 `문제 상황`, `입력(input)`, `기대 출력(output)` 또는 `출력`, `확인할 개념`을 짧게 둡니다.
- 가능하면 `print` 등으로 실행 결과를 바로 확인하게 합니다.
- 코드 블록 아래에는 가능하면 실행 결과 예시를 함께 둡니다.
- 현재 Section의 중심 질문과 직접 연결되는 출력값을 우선 보여 줍니다.
- 아직 설명하지 않은 고급 지표, 튜닝 로그, 성능 비교는 범위 안에 있을 때만 넣습니다.
- 의사 코드보다 실제 실행 가능한 예제를 우선합니다.
- 독자가 값을 바꿔 보며 결과 차이를 다시 확인할 수 있어야 합니다.

연습과 예제도 `있다`는 사실만으로 통과시키지 않습니다.

- `연습`은 독자가 방금 배운 개념이나 판단 기준을 스스로 한 번 적용해 보게 해야 합니다.
- `예제`는 단순 실행 예시가 아니라, `입력을 바꾸면 무엇이 달라지는가` 또는 `어느 조건에서 결과가 갈리는가`를 확인하게 해야 합니다.
- 답이나 해설은 독자가 자기 판단과 바로 대조할 수 있을 만큼 가까이 둡니다.
- 출력값이 하나 나오더라도, 그 값이 현재 절의 중심 질문과 어떻게 연결되는지 해설이 바로 뒤따라야 합니다.
- 코드 재출력, 표 재진술, 정의 반복만 있고 독자가 실제로 판단을 수정하거나 값을 바꿔 볼 지점이 없으면 미통과로 봅니다.

### 연습·예제 빠른 점검

- 독자가 먼저 스스로 예측하거나 판단해 볼 지점이 있는가
- 값을 하나 이상 바꿔 보며 결과 차이를 확인할 수 있는가
- 결과가 바뀌는 이유를 현재 절의 핵심 개념으로 설명해 주는가
- 예제가 사례 본문을 다른 형식으로 다시 말하는 데 그치지 않고, 실제 검증 행동을 추가하는가
- 연습을 해 본 뒤 독자가 `무엇이 경계였는가`, `왜 출력이 달라졌는가`를 한 문장으로 말할 수 있는가

## 사례 작성 기준

초심자용 사례는 추상어를 바꿔 적는 문장이 아니라, 실제 장면이 떠오르게 써야 합니다. 기본 흐름은 다음과 같습니다.

1. 문제 장면
2. 사람이 쓰던 기준
3. 그 기준의 한계
4. 모델이나 개념이 바꾸는 점
5. 확인 가능한 결과

사례만으로 입력과 출력이 잘 안 잡히면 문장만 늘리지 말고 표나 장난감 데이터 예제를 붙입니다.
한두 개의 짧은 보강만으로도 판단 과정이 보이지 않으면, 초심자가 스스로 따라갈 수 있을 만큼 사례 설명과 예제 해설을 더 충분히 제공합니다.

이때 작은 표, 짧은 비교, 짧은 숫자 장면은 `예시`로 보고 `사례 및 예시` 블록 안에서 함께 다룹니다. 코드, 실행 절차, 출력 결과는 `예제`로 보고 `연습 및 예제` 블록으로 분리합니다.

사례가 현재 절 이해를 떠받치면, 사례 바로 아래에 짧은 Mermaid 흐름도를 붙여 장면의 판단 순서를 다시 보여 줍니다. 이 도식은 새로운 이론 확장보다 `문제 장면 -> 기존 기준 또는 오해 경로 -> 개념이 바꾸는 경로 -> 다음 확인`을 압축해 되짚는 역할을 맡깁니다.

여기서 `짧은`은 도식의 역할을 압축용으로 제한한다는 뜻이지, 사례나 예제 자체를 최소 분량으로만 유지하라는 뜻은 아닙니다.

## 차트와 다이어그램 기준

- 차트는 장식이 아니라 설명용이어야 합니다.
- 한 차트에는 하나의 중심 개념만 담습니다.
- 가능하면 Mermaid 코드블록을 우선 사용합니다.
- 복잡한 좌표형 설명이 필요할 때만 예외적으로 SVG를 사용합니다.
- 도식 내부 문구는 기본적으로 영문을 사용합니다.
- 사례 도식은 가능하면 5~8개 노드 수준의 작은 흐름으로 유지하고, 사례 문단에 이미 나온 표현을 재사용합니다.
- Mermaid는 긴 가로 일렬 배치를 피하고, 3열을 넘기지 않도록 우선 검토합니다.
- 표로 충분한 비교는 차트로 만들지 않습니다.
- 외부 도식을 재작성해도 출처를 남깁니다.
- 새 도식 추가 후에도 즉시 임의 빌드를 실행하지 않고, 사용자 요청이나 명시된 검증 시점에 `mkdocs build`와 모바일 가독성을 함께 확인합니다.

## 용어, 출처, 저작권

### 용어

- 처음 나오는 핵심 용어는 `한국어(English)` 형식 병기를 우선합니다.
- 같은 Part 안에서는 새로운 핵심 개념의 상세 설명을 처음 등장하는 Section 한 곳에 두고, 이후 Section에서는 개념사전 링크 중심으로 연결합니다.
- 특히 `추론`, `파라미터`, `모델`, `생성`, `층위`는 문맥별로 구분합니다.
- 번역어 하나가 여러 영어 개념을 덮으면 영어 원어를 기준으로 분해합니다.

### 출처

- AI 생성 문장은 초안일 뿐이며, 사실 주장에는 근거가 필요합니다.
- 출처에는 가능한 한 제목, 저자 또는 기관, URL, 확인 날짜를 포함합니다.
- 외부 URL 링크는 새 창 속성을 붙입니다.
- 원문 확인 자료는 가능하면 `.tmp/`에 내려받아 검토합니다.
- 현재 동향, 기능, 정책, 가격처럼 바뀔 수 있는 정보는 작성 시점에 다시 확인합니다.

### 저작권과 예측성 내용

- 외부 교재, 강의, 번역서, 블로그, 기사, 도표는 대한민국 저작권 기준으로 보수적으로 검토합니다.
- 외부 자료의 목차, 문제, 해설, 긴 문단, 이미지 재사용은 특히 조심합니다.
- 전망, 예측, 시장·사회 영향은 근거 있는 외부 자료 기반으로만 작성합니다.
- 개인 추측이나 AI가 만들어 낸 전망을 사실처럼 쓰지 않습니다.

## 편집·배포·검증 기준

- 기본 작업 브랜치는 `dev`입니다.
- `main` 반영은 배포로 간주하며, 사용자가 명시적으로 요청할 때만 수행합니다.
- 기존 문서 톤과 구조를 우선 따릅니다.
- 불필요한 대규모 리팩터링이나 파일 이동은 피합니다.
- 관련 없는 변경은 되돌리지 않습니다.
- 사용자 요청이나 명시된 검증 단계 없이 임의의 빌드 명령을 실행하지 않습니다.
- 임의 빌드는 사용자가 테스트 중인 환경을 다시 빌드해 흐름을 방해할 수 있으므로, 필요한 검증 시점에만 제한합니다.
- 기본 빌드 확인 명령은 `.venv/bin/python -m mkdocs build`입니다.
- 빌드 검사는 개별 수정마다 반복하지 않고, 기본적으로 전체 파트를 순차적으로 점검하고 본문 보강이 끝난 뒤 한 번에 수행합니다.

## 한 줄 판단 기준

- 규칙 충돌 시: `AGENTS.md` 우선
- 초심자 설명이 부족할 때: 먼저 현재 Section 안에서 최소 보강을 검토하되, 필요하면 충분한 예시와 예제로 바로 확장
- 설명이 길어져 중심 질문이 흐려질 때: `보충학습` 분리 검토
- 차트가 길고 복잡할 때: 문구를 줄이기보다 먼저 도식을 나누거나 세로 배치 검토
- 예제가 추상적일 때: 문장을 더 늘리기보다 입력·출력·표·실행 결과를 붙이고, 그래도 부족하면 예시 수와 해설을 늘림
- `여기서는 다루지 않는다` 문장이 나올 때: 후속 위치, 보충학습, 범위 밖 중 하나를 즉시 명시

## 실제 작업 순서

1. `AGENTS.md`에서 Section 범위, Python 예제, 출처, 배포 규칙을 먼저 확인합니다.
2. 작업이 예시 보강이면 `AGENTS.md`의 초심자 보강 기준을 봅니다.
3. 작업이 문단 재배치면 `manuscript-writing-workflow.md`의 문단 구조 점검 메모를 같이 봅니다.
4. 작업이 차트 수정이면 `chart-guidelines.md`를 기준으로 봅니다.
5. 기존 절을 고칠 때는 해당 `section-...-evidence-analysis.md` 메모가 있는지 확인합니다.
6. 수정 후에는 우선 변경 범위의 구조, 용어, 출처, 후속 연결을 점검하고, 빌드는 개별 패치 직후나 개별 Part 마감 직후가 아니라 전체 파트 검토가 끝난 뒤 실행합니다.
