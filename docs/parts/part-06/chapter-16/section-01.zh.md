LLM 评估不是简单检查回答听起来是否可信。它会按照准确性、帮助性、安全性、依据性、格式符合度等标准检查回答。换句话说，它更接近逐项检查什么地方已经好、什么地方仍然有风险，而不是只问这个回答看起来好不好。

## 分开评估 LLM 回答的轴

核心问题是：

- 为什么 LLM 评估很难？
- 应该评估什么？
- 为什么要区分模型评估和系统评估？

如果评估被压缩成`一个准确率数字`，生成式 AI 输出中的失败就很难拆开。一个句子可以很自然，但事实是错的。它可以引用文档，却得出文档之外的结论。它也可以符合格式要求，却仍然不能用于用户的真实工作。所以这一阶段的核心变化，是从`是否留下记录`转向`应该按哪些质量轴判断这条记录和回答`。

评估会重新读取 harness 留下的记录，并用不同问题判断最终回答、输入请求、依据文档和输出格式。同一条执行记录，会因为读取目的不同而产生不同问题。

| 同一条记录 | P6-15 harness 层的问题 | P6-16 evaluation 层的问题 | P6-17 operations 中再次读取的问题 |
| --- | --- | --- | --- |
| 用户请求和输出候选 | 输入了什么，返回了什么回答？ | 回答是否真的解决了请求任务？ | 哪类请求的质量不稳定？ |
| 检索文档和依据段落 | 系统回答前读了什么？ | 回答中的主张是否符合依据文本？ | 应该在哪里调整搜索范围和文档选择？ |
| 输出格式和约束 | 要求的格式是什么？ | 输出是否遵守了请求格式和必需项？ | 应该在哪里强化服务响应规则？ |

所以，即使是同一个 trace，问题也会变化：在 harness 层问`是否记录了`，在 evaluation 中问`满足了哪些质量轴`，在 operations 中问`哪些请求类型持续摇晃`。

这一阶段首先要留下的记录，是按轴判断哪些轴通过、哪些轴失败，以及显示应先修正什么的 first fix axis。

## 区分自然回答和质量标准

在入门层面，你应该能够解释 LLM evaluation，区分准确性、帮助性、安全性、依据性等评估轴，并区分模型评估和系统评估。你还应该能够区分一个写得自然的回答，以及实际可以检查的质量标准。

首先要拆开的场景是：

| 最先看到的阻塞 | 首先要问的问题 | 为什么这个问题要先问 |
| --- | --- | --- |
| 回答读起来自然，但仍然不可靠 | 核心事实和计算真的正确吗？ | 流畅句子会隐藏准确性问题，所以事实先于语气。 |
| 句子看起来对，但很难马上使用 | 它是否足够帮助用户完成工作？ | 正确陈述和可用回答并不总是同一件事。 |
| 回答说用了来源，但仍然难以信任 | 回答是否真的连到了依据文本？ | 即使存在检索或引用，依据性也可能失败。 |
| 格式礼貌且正确，但发布起来有风险 | 应先阻断哪个轴：安全、格式符合度，还是帮助性？ | 一个回答可能同时在多个轴失败，所以格式通过和安全通过不能视为同一件事。 |

这张表让 evaluation 更容易被读成`判断看起来好的回答先在哪里失败的标准`，而不是`一串评估术语`。

## 为什么 LLM 评估很难

在传统分类问题中，正确标签往往比较清楚。在生成式 AI 中，正确回答可能不止一个，而且我们必须同时看自然性、事实性、格式和依据。

- 可接受的回答可能不止一个。
- 句子可以很自然，但事实是错的。
- 内容可以是对的，但格式不合适。
- 回答可以看起来很好，但依据很弱。

因此，LLM 评估通常不会用一行`对`或`错`结束。

这是它和传统机器学习评估的重要差异。在分类问题中，`是否正确`是中心。在生成式 AI 中，还要问`它是怎样正确的`，以及`哪些地方正确、哪些地方仍然薄弱`。

## 应该评估什么

下面这些评估轴应先分开。

| 评估轴 | 核心问题 |
| --- | --- |
| 准确性 | 事实和计算是否正确？ |
| 帮助性 | 回答是否真的帮助用户完成任务？ |
| 安全性 | 它是否减少有害结果？ |
| 依据性 | 回答是否连接到给定文档或证据？ |
| 格式符合度 | 它是否遵守请求的格式和约束？ |

如果不分开这些轴，很容易把流畅回答误认为准确且安全的回答。

也可以把这张表记成一句话：

- 准确性问`它对吗`。
- 帮助性问`它有用吗`。
- 安全性问`它是否降低风险`。
- 依据性问`它从哪里来`。
- 格式符合度问`它是否遵守了要求的形状`。

## 为什么模型评估和系统评估不同

这个区分必须先建立。这样当回答失败时，我们才能分开判断，是模型没能生成好句子，还是搜索和依据使用等系统路径失败了。

基于 LLM 的系统通常不只是一个模型。例如在 RAG 系统中，需要分别检查：

- 检索是否有效
- 检索到的文档是否被正确读取
- 回答是否充分反映依据

在使用工具的系统中，还要检查：

- 是否选择了合适的工具
- 调用参数是否正确
- 执行结果是否被正确读取

所以：

- 模型评估更接近评估句子生成。
- 系统评估更接近评估包括检索、工具、执行、输出在内的完整流程。

这个区分能帮助我们诊断一个 LLM 服务问题是来自句子生成本身，还是来自检索质量、工具调用、后处理等系统路径。

| 评估对象 | 主要检查内容 |
| --- | --- |
| 模型 | 句子生成、格式、推理结果 |
| 系统 | 检索、工具、执行、完整响应路径 |

## 为什么一个分数不够

眼前的问题是：`能不能只用一个分数概括全部？` 实际上，一个分数会隐藏很多问题。

例如：

- 帮助性可以很高，但事实性很低
- 安全性可以很高，但回答过于保守
- 检索可以很好，但最终摘要是错的

所以 LLM 评估更安全的做法，不是用`一个绝对分数`覆盖全部，而是读取准确性、安全性、依据性、格式符合度中哪个轴不稳定。

## 为什么需要反复比较

评估不只是学术 benchmark。它也用于反复比较同一组问题。

- 这个部署版本是否比上一个版本更好？
- 哪类问题失败更多？
- 是检索质量下降，还是生成质量下降？
- 格式变化是否影响了帮助性或依据性？

换句话说，评估不是用来炫耀模型的数字，而是用同一套标准比较变更前后输出的标准。

拉近到服务运营中，evaluation 更像是反复检查`同一固定问题集上什么改善了、什么退步了`，而不是称赞`一个好回答`。

| 为什么重复同一评估集 | 运营真正想知道什么 |
| --- | --- |
| 比较部署前后的质量 | 这次变更真的改善了系统吗？ |
| 查看同一失败是否回来 | 是否发生了回归？ |
| 查看检索、生成或格式是否不稳定 | 能否把薄弱轴缩小到模型输出或系统组合？ |

因此，评估既是选择看起来好的回答的过程，也是用固定问题集追踪回归的过程。

放进服务结构流程中：

- 设计 prompt、RAG、工具和 AI agent
- 产生实际输出
- evaluation 决定用什么标准保留和比较这些结果

## 案例和例子

这些案例的重点不是`结果看起来好不好`，而是`哪个评估轴先失败`。

### 案例 1. 评估文档摘要

假设会议记录摘要被写成了流畅的句子。第一眼很容易因为它易读、格式整齐，就判断它很好。但如果`部署推迟到8月2日`、`需要法律审查`、`负责人改为 Mina`等关键结论被遗漏，这个摘要就不能直接用于工作。好看的句子和重要信息保留，是不同的评估轴。

例如，即使语气自然，如果报告摘要遗漏了延期原因，它也接近失败。如果这个摘要被上报，读者可能只知道日程变了，却仍然必须重新打开原文才能知道原因。标准会从`句子是否自然易读`变成`核心结论和决定是否保留下来`。所以 evaluation 必须把`关键信息是否仍在`和自然性分开检查。

这个案例重要，是因为摘要`看起来好`和`能用于工作`经常不同。可读性不等于决策所需的信息都保留下来。当句子非常自然时，人们反而可能更晚才发现遗漏。因此 evaluation 不应该只因为流畅就让回答通过，而要检查原文中必须保留的决定和风险项。

| 可见状态 | 容易先下的判断 | Evaluation 必须另行检查的内容 |
| --- | --- | --- |
| 句子自然且简短 | `摘要做得好` | 核心决定和负责人变化是否保留？ |
| 格式干净且编号清楚 | `足够用于报告` | 延期原因和法律审查是否仍在？ |
| 易读且不重复 | `质量高` | 重要信息保留是否通过最低标准？ |

这里要守住的标准，是不要把`好看的句子`和`足够用于工作的摘要`当成同一件事。

### 案例 2. 基于 RAG 的问答

假设一个 RAG 回答非常流畅，但添加了检索文档中没有的数字或条件。如果句子很顺，人们除非逐行对照来源，否则很容易相信它。例如，文档只说`Basic 为14天`，但回答添加`已开封商品也可30天`，句子自然，依据性却失败了。即使有引用链接，如果被引用段落实际上没有说这个条件，依据性仍然失败。

如果这个回答用于客户指引，语气可以很顺，但内容可能违反政策。标准会从`回答是否流畅可信`变成`回答中的每个条件是否真的符合依据文档`。在 RAG 中，比可信感更重要的是附带依据是否真的支撑回答。因此 evaluation 应该把文档-回答匹配和引用准确性，与回答句子本身分开检查。

这个场景有风险，是因为很多用户会觉得只要 RAG 附了来源就更安全。但依据性不会因为存在检索文档而自动成立。如果回答句子稍微走出依据文本，来源链接反而会让用户更相信它。因此 evaluation 要先问每个主张和引用句子是否真的相连。

| 回答状态 | 从外部看起来怎样 | Evaluation 首先检查什么 |
| --- | --- | --- |
| 附了来源链接 | 依据看起来扎实 | 链接段落是否真的说明了数字和条件？ |
| 句子自然礼貌 | 看起来可以给客户 | 是否添加了文档之外的条件？ |
| 引用格式正确 | 看起来有依据 | 引用准确性和文档-回答匹配是否过阈值？ |

这里要越过的误解是：`有来源，就有依据性`。

### 案例 3. 评估格式和帮助性

假设客户指引回答礼貌且语法正确。如果语气好，很容易觉得它通过了。但如果它遗漏了用户下一步必须做什么，工作就没有结束。例如在账号锁定通知中，如果缺少`身份验证`、`密码重置链接`、`问题持续时发送请求编号`，即使句子自然，客户也必须再次询问。

标准会从`语气是否友好`变成`用户能否执行下一步行动`。如果格式正确但下一步行动为空，格式符合度可能通过，帮助性却失败。因此这个案例中要检查的结果不是回答是否礼貌，而是它是否真的包含用户能立即跟随的必需行动和条件。

三个案例可以按评估轴这样归类。

| 情况 | 即使看起来好也容易漏掉的问题 | 需要另行检查的评估轴 |
| --- | --- | --- |
| 文档摘要 | 流畅句子可能遗漏关键决定 | 关键信息保留和遗漏 |
| RAG 问答 | 可以有来源，但添加文档外条件 | 依据性和引用准确性 |
| 客户指引 | 礼貌句子可能遗漏下一步行动 | 格式符合度和帮助性 |

## 先按评估轴分开的场景

初读 evaluation 时最容易漏掉的，是因为`看起来不错`就立刻让回答通过。真正的 evaluation 更接近分开`哪个轴先失败`，而不是相信一个印象。实用检查问题如下。

| 如果你怀疑这个 | 首先要问的问题 |
| --- | --- |
| `读起来不错，所以没问题吧？` | 必需信息和决定真的保留下来了吗？ |
| `附了来源，为什么还是不安？` | 每个主张是否真的匹配被引用句子？ |
| `内容似乎对，但很难马上用。` | 请求格式和必需行动说明是否真的存在？ |
| `语气友好，但照做安全吗？` | 是否需要过滤风险指令或过度自信的主张？ |
| `内容对，但用户不知道下一步做什么。` | 是否包含可执行的下一步行动或检查标准？ |

如果直接转向`哪个轴先失败`，回答可以被更简洁地读取。

| 首先要留下的判断 | 留下这个判断的标准 |
| --- | --- |
| `correctness needs review` | 数字、事实或条件与依据冲突 |
| `groundedness needs review` | 存在来源，但回答主张并不匹配引用句子 |
| `format/helpfulness needs reinforcement` | 内容正确，但请求格式、必需项或下一步行动缺失 |
| `safety needs review` | 友好的回答仍包含风险指令或过度自信主张 |

关键是把`看起来好`和`哪个轴必须先修正`分开。这样才能把同一个回答标记为内容错误、依据不匹配、格式缺失、帮助性不足或安全问题。

首先要学会的标准很简单。Evaluation 不是`选择看起来好的回答`。它是把准确性、帮助性、安全性、依据性、格式符合度分开，再决定哪个轴先修正。执行路径成本、重试、fallback 路径是运营约束，会在 P6-17 处理。

## 练习和例子

这个例子的目标，是看到 LLM evaluation 不是一个项目，而是多个轴，并从结果中读出`哪个候选应被接受`和`什么应先修正`。只看一个回答时，很容易以`对`或`错`结束，所以这里把多个本地 LLM 的输出候选并排放置，检查哪个轴把它们区分开。

例子首先把同一小任务集发送给 `qwen2.5:1.5b`、`llama3.2:1b`、`llama3.2:latest` 等轻量本地 Ollama 模型，然后把输出保存在中文 CSV [p6_16_1_llm_eval_outputs_zh.csv](/AiBook/assets/part-06/chapter-16/p6_16_1_llm_eval_outputs_zh.csv){ .csv-preview }中。一行表示`一个模型对一个任务的回答结果`。`source_excerpt` 是要比较的依据，`required_claim_terms` 是必须从依据带到回答中的核心表达，`unsupported_claim_terms` 是走出依据的表达，`safety_risk_terms` 和 `safety_required_terms` 是安全性判断用的风险表达和必需保护提示，`format_terms` 与 `helpful_terms` 是格式和有用性判断项，`model_output` 是实际模型输出。

输出会显示模型级评估报告、准确性、依据性、安全性、格式符合度、帮助性的汇总值，以及 first fix axis。代码中要看的核心点，是按轴检查不会只看一个对错结果。它会同时应用多个标准：依据性、安全指引、格式符合度和有用性。这个 rubric 是简单的字符串检查，所以不能代替真正的语义评估。它的目的，是说明即使在同一输入和同一依据下，不同模型也可能在不同轴失败，而这些差异可以作为 CSV 行和评估轴留下来。

要一起读取的评估标准是：

| 检查项 | 为什么需要 |
| --- | --- |
| `correctness` | 检查依据中的核心主张是否留在回答中 |
| `groundedness` | 检查回答是否添加依据之外的条件 |
| `safety` | 避免风险表达，并要求安全任务中的保护性指引 |
| `format_compliance` | 检查是否遵守请求格式和结束条件 |
| `helpfulness` | 检查回答是否包含下一步行动或使用信息 |
| `next_fix` | 决定失败候选应先修正哪个轴 |

## 按评估轴分开的修正方向

前面的例子不是用来制作分数表的代码。它是一个小场景，展示`同一个问题的多个输出候选必须按轴不同读取`。重要的不是再添加一个案例，而是学会把 evaluation 读成多个检查轴和批量比较，而不是一个分数。

核心点是：

- 即使输出句子只有一句
- 检查问题也可以有多个
- 所以 evaluation 更接近逐项检查清单，而不是一句判断

用一句话说，LLM evaluation 不是`给一个分数`；它是`决定接受哪个候选、先修正哪个轴的比较标准`。

到了服务阶段，我们必须更直接地区分`哪些标准被满足`，而不只是问`它是否说得好`。因此，evaluation 更适合作为决定接受哪个候选和先修复哪个轴的比较标准，而不是对输出的印象。

这个评估标准重要，是因为它：

- 检查工具连接和执行结构是否真的按质量轴产生好回答
- 让 evaluation 成为修正优先级标准，而不是炫耀模型性能
- 为下一节把同一评估轴分给自动检查和人工审查做准备
- 创建以后验证结果时会使用的标准

## 检查清单

- 你应该能够把 evaluation 说明成`在多个质量轴上区分通过和失败`，而不是`检查一个准确率`。
- 你应该能够说出，区分模型评估和系统评估有助于更准确地缩小同一失败的原因。
- 你不应该把自然回答和可检查的质量标准当成同一件事。
