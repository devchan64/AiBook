# Part 6. 프로젝트

Part 6은 앞에서 정리한 개념을 `작은 산출물로 다시 확인하는 구간`입니다. 여기서는 더 새로운 이론을 길게 늘리기보다, 이미 배운 개념이 실제 프로젝트 문서 안에서 어떻게 다시 등장하는지 확인합니다.

이 Part는 특히 다음 독자에게 중요합니다.

- AI를 읽을 줄은 알지만 아직 직접 작은 결과물을 남겨 본 적이 없는 독자
- 예제 코드를 따라 했지만 `왜 이 순서로 프로젝트를 정리해야 하는지`는 아직 모호한 독자
- LLM, RAG, agent 이야기를 들었지만 실제로는 무엇을 기록하고 검증해야 하는지 정리하고 싶은 독자

## 이 파트의 목적

Part 6의 목적은 거대한 서비스를 완성하는 것이 아닙니다. 오히려 다음처럼 더 작은 목표를 분명히 합니다.

- 질문을 한 문장으로 쓰기
- 데이터나 입력을 명확히 적기
- baseline을 두기
- 코드와 출력 결과를 남기기
- 실패와 한계를 회고 문서로 정리하기
- 필요하면 run record, 평가 메모, 운영 로그까지 산출물로 남기기

즉, `이해한 내용을 다시 실행 가능한 형태로 남기는 것`이 Part 6의 핵심입니다.

여기서 중요한 점은 `프로젝트를 했다`는 말을 코드 파일 하나로 대신하지 않는 것입니다. Part 6에서는 가능한 한 다음 같은 기록 이름이 실제로 남아야 합니다.

- `project_note`, `retrospective_note`
- `project_run`, `comparison_rows`
- `test_records`, `evaluation_records`
- `retrieval_records`, `selected_evidence`
- `execution_records`, `review_summary`
- `incident_records`, `improvement_plan`

즉, Part 6은 `모델을 만들었다`보다 `무슨 기록을 남겼는가`를 더 엄격하게 묻는 파트입니다.

## 앞선 Part와의 연결

앞선 Part들은 개념을 쌓는 구간이었습니다. 하지만 많은 학습자는 이 단계에서 멈추면 다음 문제를 겪습니다.

- 개념을 안다고 느끼지만, 실제 프로젝트 문서를 어떻게 시작해야 할지 모른다.
- 모델 점수는 보지만 baseline이나 실패 기록은 남기지 않는다.
- RAG나 agent를 흥미로운 기능으로는 이해하지만, 평가와 운영 관점은 빠뜨린다.

Part 6은 이 공백을 메웁니다. 작은 프로젝트라도 `문제 정의 -> 구현 -> 결과 -> 회고`까지 남겨야 배움이 다음 작업으로 이어집니다.

Part 5 마지막에서 이미 본 것처럼, 생성형 AI 기능은 `질문 -> 근거 또는 도구 -> 답변 -> 평가 -> 기록` 흐름으로 읽어야 합니다. Part 6은 이 흐름을 실제 프로젝트 산출물로 바꾸는 파트입니다. 즉, 여기서의 핵심은 코드를 더 길게 쓰는 일이 아니라, 무엇을 어떤 형식으로 남겨야 다음 반복이 가능해지는지를 익히는 데 있습니다.

## 이 파트의 목표

- 프로젝트는 어디서부터 시작해야 하는가?
- 작은 데이터 분석도 프로젝트라고 부를 수 있는가?
- baseline과 개선은 어떻게 비교해야 하는가?
- 딥러닝과 텍스트 분류 프로젝트는 무엇을 최소 단위로 확인해야 하는가?
- RAG와 agent 프로젝트에서는 무엇을 품질 기준으로 삼아야 하는가?
- 배포와 운영에서는 어떤 실패 기록이 필요한가?

이 목표들을 프로젝트 문서 관점으로 다시 쓰면 다음과 같습니다.

| 프로젝트 단계 | 최소 산출물 |
| --- | --- |
| 질문 설정 | 한 문장 목표, 확인할 기준 |
| 입력 정리 | 데이터, 문서, 도구, 제약 조건 |
| baseline | 가장 단순한 비교 기준과 그 결과 |
| 실행 | 코드, 출력, 중간 관찰 |
| 평가 | 자동 점검, 사람 검토, 비교 메모 |
| 운영 회고 | 실패 기록, 다음 개선 순서 |

이 최소 산출물을 Part 6의 실제 프로젝트 축으로 다시 쓰면 다음처럼 볼 수 있습니다.

| 프로젝트 축 | 대표 산출물 예시 |
| --- | --- |
| 분석 시작 | `project_note`, `retrospective_note` |
| baseline 비교 | `project_run`, `baseline_error_ids` |
| 이미지/텍스트 분류 | `test_records`, `evaluation_records` |
| RAG | `retrieval_records`, `grounded_answer_record` |
| agent | `planned_steps`, `execution_records`, `final_report` |
| 배포/운영 | `review_summary`, `incident_records`, `improvement_plan` |

## 이 파트에서 설명하는 범위와 설명하지 않을 범위

이 Part는 다음 범위를 다룹니다.

- 작은 프로젝트 목표를 세우는 방법
- 입력과 출력 정의
- baseline과 비교
- 결과와 한계 기록
- RAG, agent, 배포 프로젝트의 기본 문서 구조

이 Part는 다음 내용은 깊게 다루지 않습니다.

- 대규모 학습 인프라 구축
- 복잡한 MLOps 파이프라인 자동화
- 장기 운영 비용 최적화의 심화 분석
- 실제 상용 서비스 수준의 보안 정책 설계 전부

이 생략 항목 가운데 비용, 운영, 권한, 실패 대응의 큰 그림은 본문 안에서도 P6-6.2 권한과 로그 검토, P6-7.1 배포와 모니터링 목표, P6-7.2 실패 기록과 개선 계획에서 다시 회수합니다. 반면 대규모 학습 인프라와 상용 서비스 수준의 전체 보안 설계는 이 책의 현재 프로젝트 입문 범위 밖으로 둡니다.

즉, 이 Part는 `실전의 전체`가 아니라 `실전으로 넘어가기 위한 최소 프로젝트 감각`을 다룹니다.

특히 이 파트에서는 다음 구분을 계속 유지합니다.

- `분석 프로젝트`: 질문, 표, 요약값, 관찰 메모가 중심
- `모델 프로젝트`: baseline, 예측 결과, 오류 사례가 중심
- `RAG/agent 프로젝트`: 근거 문서, 도구 결과, run record, 실패 로그가 중심

이 구분은 단순한 장르 분류가 아니라, 어떤 산출물을 우선 남겨야 하는지를 정하는 기준이기도 합니다.

- 분석 프로젝트에서는 `요약값`보다 `질문과 관찰 메모`가 먼저입니다.
- 모델 프로젝트에서는 `accuracy`보다 `비교 행`과 `오류 샘플`이 먼저입니다.
- RAG 프로젝트에서는 `답변`보다 `검색 근거`와 `answer_status`가 먼저입니다.
- agent 프로젝트에서는 `성공 여부`보다 `permission`, `approved`, `next_action`이 먼저입니다.
- 배포 프로젝트에서는 `배포 완료`보다 `incident_records`와 `next_action`이 먼저입니다.

Part 6에서는 이 예시들을 별도 `보충학습`으로 다시 빼지 않습니다. 분석 프로젝트의 `project_note -> retrospective_note`, 모델 프로젝트의 `baseline -> comparison_rows`, RAG의 `retrieval_records -> answer_status`, agent의 `execution_records -> approval`, 배포의 `incident_records -> improvement_plan`처럼, 각 축의 핵심 예시를 이미 본문 안에서 직접 따라가게 두는 편이 현재 프로젝트 입문 흐름에 더 잘 맞기 때문입니다.

## 이후 Part로의 연결

Part 6이 끝나면 독자는 더 큰 프로젝트를 스스로 설계할 수 있어야 합니다.

- 더 큰 데이터셋으로 실험 반복하기
- 라이브러리와 프레임워크를 붙여 구조 확장하기
- RAG 품질 평가 체계를 더 정교하게 만들기
- agent 로그와 권한 정책을 별도 문서로 분리하기
- 운영 지표와 회고 문서를 팀 단위로 확장하기

즉, 이 Part는 책의 마지막이지만 동시에 다음 학습의 출발점입니다.

## 이 파트에서 끝내지 않는 질문

Part 6은 프로젝트 입문 흐름을 다루는 파트이므로 다음 질문은 이후 실제 프로젝트로 넘깁니다.

- 팀 단위 협업 문서와 실험 추적 체계를 어떻게 설계할 것인가?
- 더 큰 데이터셋과 더 긴 운영 로그를 어떤 기준으로 관리할 것인가?
- 배포 자동화와 권한 검토를 어느 단계까지 문서화할 것인가?

즉, Part 6은 `프로젝트를 시작하고 회고하는 최소 구조`를 닫는 파트이지, 모든 실무 체계를 여기서 끝내는 파트는 아닙니다.

## 이 파트를 읽고 나면 생겨야 할 이해

Part 6을 읽고 나면 독자는 다음 정도의 감각을 가져야 합니다.

- 프로젝트는 구현보다 먼저 질문과 기준점을 정해야 한다.
- 작은 데이터 분석도 유효한 프로젝트 단위가 될 수 있다.
- baseline과 개선 비교가 없는 모델 결과는 해석이 약하다.
- LLM 프로젝트는 답변 예시뿐 아니라 검색 실패, 도구 실패, 권한, 로그까지 함께 기록해야 한다.
- 프로젝트 회고는 실패를 숨기는 문서가 아니라 다음 반복을 준비하는 문서다.

이 다섯 줄을 가장 짧게 묶으면 다음과 같습니다.

`프로젝트는 결과물 하나를 만드는 일이 아니라, 다음 반복에 다시 쓸 수 있는 기록을 남기는 일이다.`

## 프로젝트 문서의 공통 형식

Part 6의 각 프로젝트는 가능한 한 다음 흐름으로 씁니다.

- 문제 정의
- 데이터 또는 입력
- 접근 방법
- 구현
- 결과
- 한계와 개선점
- 출처와 참고 자료

이 형식은 기계적인 템플릿이라기보다, 프로젝트를 다시 실행하고 다시 읽을 수 있게 만드는 최소 공통 구조입니다.

생성형 AI 관련 프로젝트에서는 여기에 다음 항목이 자주 추가됩니다.

- 근거 문서 또는 검색 결과
- 도구 호출 결과 또는 실행 로그
- 자동 평가 결과
- 사람 검토 메모
- 실패 시 run record 또는 fallback 기록

이 공통 형식을 독자가 다시 점검할 때는 다음처럼 읽어도 좋습니다.

| 문서 질문 | 확인할 산출물 |
| --- | --- |
| 무엇을 하려 했는가? | 목표 문장, `planned_steps`, `project_note` |
| 무엇을 넣었는가? | 데이터 표, 문서 조각, 도구 목록 |
| 어떻게 비교했는가? | baseline, `comparison_rows`, `evaluation_records` |
| 무엇이 근거였는가? | `selected_evidence`, `retrieval_candidates` |
| 어디서 멈췄는가? | `blocked`, `insufficient_evidence`, 실패 상태 |
| 다음에 무엇을 바꿀 것인가? | `review_summary`, `improvement_plan` |

## 완료 기준

- 작은 프로젝트를 질문, 입력, 구현, 결과, 회고 흐름으로 정리할 수 있다.
- baseline과 개선 모델의 차이를 문서로 설명할 수 있다.
- RAG와 agent 프로젝트에서 품질과 운영 관점을 함께 적을 수 있다.
- 실패 기록과 다음 개선 계획을 프로젝트 결과 안에 남길 수 있다.

가장 짧게 줄이면 Part 6의 완료 기준은 다음 한 문장으로 묶입니다.

`작은 프로젝트라도 다시 실행할 수 있는 기록과 다음 반복을 위한 회고를 남길 수 있어야 한다.`
