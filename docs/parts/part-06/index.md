# Part 6. LLM과 생성형 AI

Section ID: `P6-index`
Version: `v2026.07.18`

Part 6는 LLM과 생성형 AI를 실제 구조 기준으로 다시 묶는 파트입니다. Part 1~5에서 위치와 기반을 준비했다면, 여기서는 더 이상 설명을 뒤로 미루지 않고 `LLM은 어떤 구조로 동작하는가`, `왜 다음 토큰 예측으로도 긴 답변과 지시 수행이 가능한가`, `왜 검색·도구·에이전트가 붙는가`를 본문 흐름 안에서 직접 설명합니다.

주요 개념의 상세 설명은 처음 한 번만 본문에 두고, 뒤 절에서는 현재 맥락에 필요한 최소 설명만 남기는 편이 안정적입니다. 그래서 `왜 토큰이 필요한가`는 `P6-1.1`, `토큰(token)`의 기본 정의는 `P6-1.2`, `임베딩(embedding)`은 `P6-2.1`, `Transformer를 LLM 관점에서 다시 읽는 기준`은 `P6-3.1`, `RAG`는 `P6-10.1`, `에이전트(agent)`는 `P6-13.1`, `MCP`는 `P6-14.1`, `평가(evaluation)`는 `P6-15.1`을 대표 설명 위치로 먼저 붙잡고, 뒤 절에서는 개념사전과 대표 Section를 다시 연결하는 편이 가장 안전합니다.

Part 6의 핵심 목적은 “생성형 AI 서비스가 왜 지금과 같은 구조를 갖는가”를 설명할 수 있게 만드는 데 있습니다. 챗봇, 문서 요약, 검색 보강, 코드 생성, 에이전트 같은 사용 경험만으로는 토큰(token), Transformer, GPT, 사전학습(pretraining), 지시 튜닝(instruction tuning), RAG(retrieval-augmented generation), 도구 사용(tool use), MCP(Model Context Protocol)가 어떻게 한 줄로 이어지는지 잡기 어렵습니다. Part 6는 그 연결을 실제 본문 설명으로 닫는 자리입니다.

그래서 Part 6는 본류를 먼저 세웁니다. 이 본류는 크게 보면 `모델 내부를 이해하는 전반부`와 `그 모델을 실제 서비스 구조로 연결하는 후반부`로 나뉩니다.

1. 토큰이 왜 필요한지, 토큰이 무엇인지, 토큰화가 무엇인지와 무엇을 바꾸는지
2. 임베딩과 표현
3. Transformer를 LLM 관점에서 다시 읽기
4. GPT 계열과 다음 토큰 예측
5. 사전학습, 파인튜닝, 지시 튜닝, 정렬
6. 프롬프트, RAG, 벡터 검색
7. 도구 사용, 에이전트, MCP, 하네스
8. 평가, 운영, 통합 미니 실습

이 구분을 더 짧게 말하면 다음과 같습니다.

| 큰 구간 | 먼저 닫는 질문 | 현재 묶이는 Chapter |
| --- | --- | --- |
| 전반부 | LLM은 입력을 어떻게 읽고 어떤 구조로 생성하며 어떻게 조정되는가? | Chapter 1-8 |
| 후반부 | 이해한 LLM을 현재 서비스에서 어떤 근거·실행·운영 구조로 써야 하는가? | Chapter 9-17 |

이 과정에서 BERT 계열과 LLM 발전사는 본류를 읽기 위한 `배경 지도`로 다룹니다. 배경 설명은 필요하지만, 중심축은 `생성형 AI의 동작 원리와 서비스 연결`입니다.

각 장을 모두 같은 종류의 설명으로 읽지 않는 편이 더 안정적입니다. 아래 표처럼 읽는 층위를 나눠 두면 흐름이 덜 섞입니다.

| --- | --- | --- |

| 조정과 사용 경험 | 같은 구조가 왜 다른 응답 성격으로 보이는가? | 사전학습, 파인튜닝, 지시 튜닝, 정렬 |
| 서비스 연결 | 모델 밖에서 무엇을 더 붙여야 실제 기능이 되는가? | 프롬프트, RAG, 벡터 검색, tool use, agent, MCP |

현재 Part 6는 Chapter 번호 자체를 크게 다시 섞기보다, `현재 순서를 유지한 채 본류와 배경 축을 더 분명히 읽게 하는 방식`으로 정리합니다. 따라서 독자는 먼저 Chapter 1부터 Chapter 17까지를 본류로 읽고, Chapter 18 `LLM 발전사`, Chapter 19 `BERT 계열`은 뒤에서 다시 붙는 비교·배경 축으로 읽으면 됩니다.

Part 6는 개념 설명에서 멈추지 않고, 다음처럼 `무엇을 먼저 확인하고 어떤 판단으로 이어져야 하는가`를 함께 보게 합니다.

- tokenization -> 입력이 어떻게 잘렸고 문맥 길이에 어떤 영향을 주는가
- RAG -> 어떤 근거를 찾았고 왜 그 근거를 선택했는가
- agent -> 어떤 단계를 거쳐 실행했고 어느 지점에서 검토가 필요한가
- evaluation/operations -> 답변 품질, 실패 사례, 답변 상태, 다음 조치를 어떻게 정리할 것인가

| 지금 먼저 막히는 장면 | 먼저 떠올릴 질문 | 왜 이 질문이 먼저 필요한가 |
| --- | --- | --- |
| 답변은 그럴듯한데 왜 맞거나 틀리는지 구조가 안 보인다 | 지금 막히는 곳은 생성 구조 자체인가? | 토큰, Transformer, GPT 축을 먼저 잡지 않으면 뒤의 서비스 연결도 기능 목록처럼 보이기 쉽기 때문입니다. |
| 프롬프트는 써 봤는데 RAG, tool use, agent가 왜 따로 필요한지 헷갈린다 | 지금 필요한 것이 근거 연결인가, 실제 실행인가, 여러 단계 흐름인가? | 서비스 연결 층을 나누지 않으면 검색, 도구, 에이전트를 같은 말처럼 섞어 읽기 쉽기 때문입니다. |
| 답은 맞아 보여도 서비스로 옮기면 왜 불안한지 모르겠다 | 지금 문제는 품질 판정인가, 운영 한도와 실패 대응인가? | evaluation과 operations를 분리해야 `좋은 답`과 `운영 가능한 서비스`를 다른 질문으로 읽을 수 있기 때문입니다. |
| GPT, BERT, 발전사, 조정 기법이 한꺼번에 섞여 머릿속에 정리가 안 된다 | 지금은 본류를 먼저 다시 읽어야 하는가, 아니면 배경 축을 뒤에서 붙여야 하는가? | 본류와 배경 축의 순서를 잡지 않으면 발전사와 비교 항목이 핵심 구조보다 앞에 서 버리기 때문입니다. |

이 표를 먼저 붙잡고 아래의 본류 묶음과 배경 축을 읽으면, Part 6를 `장 순서 안내`보다 `지금 막힌 경험을 어떤 구조 질문으로 바꿔 읽을 것인가`의 입구로 더 직접 사용할 수 있습니다.

## Part 6의 목적과 범위

Part 6의 책임은 `생성형 AI 서비스가 왜 이런 구조를 갖는가`를 설명하는 데 있습니다. 앞선 Part에서 이름만 먼저 지나갔던 토큰, Transformer, GPT, 사전학습, RAG, 도구 사용, 에이전트, MCP, 평가를 여기서는 실제 본문 설명으로 회수합니다. 이름이 다시 나오는 것만으로는 부족하고, `왜 필요한가`, `무엇을 바꾸는가`, `어떤 판단으로 이어지는가`까지 닫혀야 이 Part의 역할을 다했다고 볼 수 있습니다.

그래서 Part 6는 다음 네 축을 본편 범위로 삼습니다.

- 토큰, 임베딩, Transformer, GPT, next-token prediction의 기본 구조
- 사전학습, 파인튜닝, 지시 튜닝, 정렬의 역할 구분
- 프롬프트, RAG, 벡터 검색, 도구 사용, 에이전트, MCP, 하네스의 연결 구조
- 평가, 운영, 실패 대응, 작은 통합 기능 흐름

Part 6를 다 읽고 나면 아래 정도의 질문에는 답할 수 있어야 합니다.

- LLM은 입력을 어떻게 읽고 다음 출력을 어떻게 고르는가?
- GPT와 BERT는 왜 구조도 다르고 강한 과업도 다른가?
- 프롬프트만으로 되는 일과 RAG·도구가 필요한 일은 무엇이 다른가?
- 에이전트와 MCP는 왜 프롬프트 확장이 아니라 실행 환경 문제로 읽어야 하는가?
- 좋은 답변과 운영 가능한 서비스는 왜 다른가?

이 목표를 Part 6 준비 관점으로 다시 쓰면 다음처럼도 정리할 수 있습니다.

## 읽기 기준

익숙한 서비스 경험과 낯선 구조 용어가 한꺼번에 섞여 나오므로, 모든 구현 세부를 한 번에 잡기보다 먼저 다음 세 질문으로 층위를 구분해야 합니다.

| 먼저 붙잡을 질문 | 이 질문이 필요한 이유 | 여기서 어디까지 잡으면 충분한가 |
| --- | --- | --- |
| 지금 설명하는 것은 `모델 내부 원리`인가, `서비스 연결 방식`인가? | LLM 문맥에서는 토큰, attention, RAG, agent가 한 문서 안에 함께 나와도 같은 층위의 개념이 아닙니다. | Transformer와 next-token prediction은 모델 원리, RAG와 tool use는 서비스 연결 방식이라는 구분을 먼저 잡아야 합니다. |
| 이 시스템은 `무엇을 바로 생성`하고, 무엇은 `밖에서 가져오거나 실행`하는가? | 생성형 AI를 이해하려면 모델이 내부 지식만으로 답하는 경우와 외부 문서·도구가 붙는 경우를 구분해야 합니다. | 프롬프트만으로 되는 일과 RAG·도구가 필요한 일이 다르다는 점을 먼저 구분해야 합니다. |
| 결과를 좋게 만든다는 말이 `모델 성능 향상`인가, `서비스 설계 개선`인가? | 생성 품질 문제는 항상 모델 재학습으로만 해결되지 않습니다. 검색, 프롬프트, 도구 연결, 평가 설계가 함께 작동합니다. | 모델 자체와 서비스 구성요소를 분리해 봐야 합니다. |

가장 짧게는 다음처럼 정리할 수 있습니다. LLM은 다음 토큰을 예측하는 구조이고, 그 구조가 긴 생성과 지시 수행으로 이어집니다. 지식 부족과 실행 한계를 보완하려고 RAG와 도구가 붙고, 실제 서비스에서는 에이전트, MCP, 평가, 운영까지 함께 봐야 합니다.

## 왜 이 구조가 필요한가

생성형 AI를 다시 공부할 때 가장 자주 생기는 혼동은 `모델이 하는 일`과 `서비스가 추가로 붙이는 일`이 뒤섞이는 점입니다. 같은 답변이 좋아졌더라도 그 이유는 더 큰 모델, 더 나은 프롬프트, 외부 근거 연결, 도구 실행, 다단계 흐름 설계 가운데 어디에 있을 수 있습니다. 이 차이를 구분하지 못하면 생성형 AI를 이해하는 대신 기능 목록만 외우게 됩니다.

Part 6는 이 혼동을 줄이는 공통 구조를 만듭니다. 토큰과 Transformer 같은 내부 원리에서 시작해, 왜 RAG와 tool use가 붙고 왜 agent와 MCP가 필요한지까지 같은 축으로 보면, 이후의 제품 문서와 실무 설계도 `입력 설계 문제`, `근거 연결 문제`, `실행 단계 문제`, `운영 판단 문제`로 다시 나누어 읽을 수 있습니다.

따라서 이 index에서 확인해야 할 최종 결과는 Part 6를 `챗봇 기능 모음`이 아니라, 모델 내부 원리와 서비스 연결 구조를 함께 설명하는 본류로 읽을 수 있는가입니다.

## 먼저 가를 구조 질문

`기능 이름은 익숙한데 왜 이 장이 필요한지 모르겠다`는 상태라면, 장을 처음부터 다시 읽기보다 지금 막힌 장면을 어떤 구조 질문으로 바꿔 읽어야 하는지 먼저 가르는 편이 더 안전합니다.

| 지금 익숙한 사용 경험 | 실제로 먼저 바꿔 읽어야 할 질문 | 먼저 들어갈 Chapter 묶음 |
| --- | --- | --- |
| 답변은 그럴듯한데 왜 틀리는지 모르겠다 | 지금 문제는 생성 구조 자체인가, 근거와 최신성 부족인가? | Chapter 3-5, Chapter 9-10 |
| 문서를 붙였는데도 답이 불안하다 | 문서를 붙인 것과 근거를 제대로 선택한 것은 어떻게 다른가? | Chapter 10-11 |

## 완료 기준

- Transformer가 왜 LLM의 핵심 구조인지 설명할 수 있다.
- GPT 계열이 다음 토큰 예측 기반의 생성 모델이라는 점을 설명할 수 있다.
- BERT 계열과 GPT 계열의 차이를 읽기 중심 작업과 생성 중심 작업의 차이로 설명할 수 있다.
- 프롬프트, RAG, 벡터 검색, 도구 사용이 각각 어떤 한계를 보완하는지 설명할 수 있다.
- 에이전트, MCP, 하네스가 프롬프트와 다른 실행 환경의 주제임을 설명할 수 있다.
- 평가와 운영 관점에서 생성형 AI 시스템의 주요 실패 유형을 말할 수 있다.
- 작은 생성형 AI 기능을 어떤 요청 흐름으로 설계하고 회고할지 설명할 수 있다.
