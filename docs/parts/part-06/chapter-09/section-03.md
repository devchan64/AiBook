# P6-9.3 보충학습: Chain-of-thought, self-consistency, automatic prompt optimization을 처음 읽는 법

P6-9.1에서는 프롬프트 엔지니어링(prompt engineering)을 입력 설계의 첫 번째 손잡이로 봤고, P6-9.2에서는 프롬프트만으로 해결되지 않는 한계를 봤습니다. 그런데 실무 문서나 논문을 읽기 시작하면 금방 더 낯선 이름들이 따라붙습니다.

`Chain-of-thought`
`self-consistency`
`automatic prompt optimization`

이 이름들은 프롬프트를 더 복잡하게 만드는 주문 목록이 아니라, `모델에게 중간 단계나 여러 후보를 어떻게 다루게 할 것인가`, `프롬프트 자체를 어떻게 반복 개선할 것인가`와 연결된 전략 이름입니다.

## 이 보충학습의 범위

이 절은 Chain-of-thought(CoT), self-consistency, automatic prompt optimization을 입문 수준에서 구분합니다.

여기서는 다음 질문에 답합니다.

- Chain-of-thought는 무엇을 기대하는 전략인가?
- self-consistency는 왜 한 번의 답 대신 여러 후보를 보게 하는가?
- automatic prompt optimization은 무엇을 자동화하려는가?
- 이런 기법들은 언제 도움이 되고, 언제 과신하면 위험한가?

이 절은 개별 논문의 수식, 벤치마크 전수 비교, 프레임워크별 구현 코드를 깊게 다루지 않습니다. 여기서는 이름을 들었을 때 `어떤 종류의 프롬프트 전략인가`를 읽는 감각만 회수합니다.

지금 읽는 층위는 `프롬프트 전략의 보강 층위`입니다. 앞 절의 프롬프트 엔지니어링이 `입력을 어떻게 설계할까`를 다뤘다면, 여기서는 그 입력 설계를 더 정교하게 만드는 대표 전략 이름들을 보강합니다. 뒤의 RAG, 도구 사용, 평가 절에서는 이런 전략이 어디까지 도움이 되고 어디서부터는 별도 시스템 구조가 필요한지 다시 회수합니다.

이 보충학습은 `출력 경로를 더 잘 유도하는 전략`과 `최신성·근거·실행 보장을 담당하는 구조`를 분리해 보는 손잡이로 읽는 편이 가장 안전합니다.

| 지금 단계의 손잡이 | 바로 다음에 이어질 질문 | 뒤에서 본격적으로 다시 읽는 위치 |
| --- | --- | --- |
| CoT / self-consistency | 답변 경로와 후보 비교를 어떻게 더 안정적으로 유도할 것인가? | P6-9.3 |
| automatic prompt optimization | 프롬프트 실험을 어떤 평가 루프로 반복 개선할 것인가? | P6-9.3, P6-15.1, P6-15.2 |
| 시스템 층의 보장 | 최신 문서, 근거, 도구 실행, 로그는 어떤 별도 구조가 맡는가? | P6-10.1, P6-10.2, P6-12.1, P6-12.2, P6-15.1, P6-16.2 |

이 보충학습의 핵심은 세 전략이 모두 `프롬프트 층의 개선`이지, `시스템 보장 층`의 대체물이 아니라는 점입니다.

## 이 보충학습의 목표

- CoT를 `중간 단계 reasoning을 드러내게 하려는 전략`으로 설명할 수 있습니다.
- self-consistency를 `한 번의 경로보다 여러 후보 경로의 합의를 보는 전략`으로 설명할 수 있습니다.
- automatic prompt optimization을 `프롬프트 자체를 반복 평가하고 개선하려는 접근`으로 설명할 수 있습니다.
- 이 기법들이 최신성, 근거 보장, 도구 실행을 대신하지 않는다는 점을 설명할 수 있습니다.

## 학습 배경

Part 1의 12.2에서는 지시(instruction), 맥락(context), 예시(example)를 나눠 보는 기본 구조를 먼저 잡았습니다. 그 단계에서는 프롬프트를 `입력을 구조화하는 방법`으로 이해하는 것이 더 중요했고, 고급 기법 이름을 바로 늘어놓지 않는 편이 안전했습니다.

하지만 Part 6에서는 사용 경험과 실무 문서를 함께 읽기 시작하므로, 이제 이런 이름들을 더 미루지 않아도 됩니다. 다만 중요한 것은 기법 이름을 외우는 것이 아니라, `이 전략이 어떤 문제를 줄이려는가`를 이해하는 일입니다.

## 먼저 잡을 세 가지

| 질문 | 먼저 붙잡을 기준 |
| --- | --- |
| CoT는 무엇을 바꾸려 하는가? | 답만 내게 하는 대신 중간 단계 reasoning을 더 분명하게 드러내려 합니다. |
| self-consistency는 무엇을 바꾸려 하는가? | 한 번의 답을 믿기보다 여러 후보를 비교해 더 안정된 결론을 얻으려 합니다. |
| automatic prompt optimization은 무엇을 바꾸려 하는가? | 사람이 프롬프트를 수동으로 다듬던 일을 평가 루프로 자동화하려 합니다. |

## Chain-of-thought는 중간 단계를 더 잘 드러내게 하려는 전략이다

가장 널리 알려진 이름은 Chain-of-thought(CoT)입니다. 이 전략의 직관은 간단합니다.

> 답만 바로 말하게 하지 말고, 중간 단계 reasoning을 더 분명하게 거치게 하자.

예를 들어 단순 요청은 다음처럼 보일 수 있습니다.

> 이 문제의 답을 구해줘.

CoT 스타일 요청은 보통 다음처럼 바뀝니다.

> 바로 답만 쓰지 말고,
> 어떤 기준으로 생각했는지 단계별로 정리한 뒤
> 마지막에 결론을 써줘.

이 전략이 기대하는 효과는 `복잡한 과업에서 중간 단계가 더 안정적으로 드러나는가`입니다. 특히 수학 문제, 논리 비교, 조건이 많은 분류, 문서 비교 같은 장면에서 자주 언급됩니다.

다만 여기서 중요한 점이 있습니다.

- CoT는 최신 문서를 자동으로 찾아 주지 않습니다.
- CoT는 계산 정확도를 자동으로 보장하지 않습니다.
- CoT는 외부 도구 실행을 대신하지 않습니다.

즉 CoT는 `생각 과정을 더 잘 펼치게 해 보려는 입력 전략`이지, 시스템 보장을 붙이는 구조는 아닙니다.

## self-consistency는 한 번의 답보다 여러 후보의 합의를 본다

self-consistency는 CoT와 자주 함께 언급됩니다. 직관은 다음과 같습니다.

> 한 번의 reasoning 경로만 믿지 말고,
> 여러 번 생성한 경로 중 더 자주 도달하는 결론을 보자.

입문 단계에서는 이렇게 이해하면 충분합니다.

- CoT: 한 번의 reasoning 경로를 더 길게 펼친다.
- self-consistency: 그런 reasoning 경로를 여러 번 만들어 보고 더 일관된 결론을 본다.

예를 들어 같은 문제를 여러 번 풀게 하고, 마지막 결론이 가장 자주 나온 답을 채택하는 방식으로 설명할 수 있습니다.

이 전략이 기대하는 효과는 `한 번의 우연한 실수나 표현 흔들림을 줄일 수 있는가`입니다. 특히 결론이 하나로 모여야 하는 문제에서 자주 등장합니다.

하지만 이 역시 한계가 있습니다.

- 여러 번 돌렸다고 최신 정보가 생기지는 않습니다.
- 여러 후보가 같은 잘못된 전제를 공유하면 합의도 같이 틀릴 수 있습니다.
- 비용과 지연 시간이 늘어날 수 있습니다.

즉 self-consistency는 `한 번의 답을 그대로 믿지 않는 전략`이지, 진실 보장 장치는 아닙니다.

## automatic prompt optimization은 프롬프트 개선을 자동화하려는 접근이다

세 번째 이름은 automatic prompt optimization입니다. 이 표현은 조금 넓게 쓰입니다. 공통 직관은 다음입니다.

> 사람이 프롬프트를 손으로 조금씩 고치던 일을,
> 점수와 평가 루프를 붙여 더 자동으로 개선해 보자.

예를 들어 다음처럼 생각할 수 있습니다.

1. 프롬프트 초안을 만든다.
2. 여러 입력에서 결과를 평가한다.
3. 어떤 프롬프트가 더 점수가 좋은지 비교한다.
4. 더 나은 표현이나 구조를 다시 제안한다.

이 전략이 중요한 이유는, 프롬프트 엔지니어링이 원래부터 `입력 변화에 따른 출력 변화를 관찰하는 반복 실험`이기 때문입니다. automatic prompt optimization은 그 반복 실험을 더 체계적으로 만들려는 방향입니다.

다만 여기서도 과장이 붙기 쉽습니다.

- 자동 최적화가 곧 정답을 보장하지는 않습니다.
- 평가 기준이 약하면 자동화도 약합니다.
- 특정 데이터셋에만 잘 맞는 프롬프트로 과적합될 수 있습니다.

즉 자동화는 `프롬프트 실험을 더 빨리 돌리는 도구`이지, 평가 품질 자체를 대체하지는 않습니다.

## 세 전략을 한 번에 구분하면

| 전략 | 무엇을 조정하려 하는가 | 먼저 기대하는 효과 | 바로 해결되지 않는 것 |
| --- | --- | --- | --- |
| Chain-of-thought | 한 번의 답 안에서 reasoning 전개 | 중간 단계가 더 분명해짐 | 최신성, 외부 근거, 실행 보장 |
| self-consistency | 여러 reasoning 후보의 비교 | 결론 흔들림 감소 | 공통 전제가 틀릴 때의 오류 |
| automatic prompt optimization | 프롬프트 반복 개선 과정 | 실험 속도와 구조화 향상 | 평가 기준의 약함, 구조 보장 부재 |

이 표에서 핵심은 세 전략이 모두 `프롬프트 층`에서 움직인다는 점입니다. 즉 P6-9.2에서 본 것처럼, 모델 밖의 문서 연결이나 도구 실행 보장은 여전히 다른 구조가 필요합니다.

## 언제 도움이 되고, 언제 과신하면 위험한가

도움이 되는 장면은 대체로 다음과 같습니다.

- 조건이 여러 개인 추론형 질문
- 단계 설명이 중요한 교육용 출력
- 같은 형식을 반복 유지해야 하는 평가 작업
- 프롬프트 후보를 여러 입력에서 비교해야 하는 실험

반대로 과신하면 위험한 장면은 다음과 같습니다.

- 최신 정책이나 가격처럼 외부 최신성이 핵심인 작업
- 실제 계산 도구 확인이 필요한 수치 작업
- 파일 저장, API 호출, 승인 처리처럼 실행 로그가 필요한 작업
- 잘못된 전제가 여러 번 반복돼도 결론이 그럴듯해 보이는 작업

즉 이 전략들은 `입력 설계의 정교화`에는 도움이 되지만, `시스템 보장`을 대신하지는 않습니다.

## 사례로 보기

### 사례 1. 조건이 많은 분류 문제에서 CoT를 붙이는 이유

고객 문의를 `환불`, `배송`, `계정`, `오류` 중 하나로 분류한다고 해 봅시다. 단순 프롬프트는 바로 라벨만 내놓게 할 수 있습니다. 하지만 문의 하나에 여러 조건이 섞이면 모델이 어떤 기준을 먼저 봤는지 알기 어렵습니다.

이때 CoT 스타일 요청은 `어떤 단어와 조건을 먼저 봤는지`, `왜 이 라벨을 골랐는지`를 더 분명하게 드러내게 해 줄 수 있습니다. 사람은 최종 라벨만 보는 대신, 중간 기준이 일관적인지도 함께 검토할 수 있습니다.

여기서 확인해야 할 결과는 라벨 하나만 맞았는가가 아니라, `라벨을 고르는 기준이 더 읽히는가`입니다.

### 사례 2. self-consistency가 있어도 최신 정책 문제는 남는다

최신 환불 정책을 묻는 질문을 여러 번 돌려 보고, 가장 자주 나온 답을 채택한다고 해 봅시다. 결론이 더 안정돼 보일 수는 있습니다. 하지만 모델이 최신 문서를 보지 못했다면, 여러 번 합의한 답도 오래된 정책일 수 있습니다.

즉 self-consistency는 `한 번의 흔들림`을 줄일 수는 있어도, `최신 문서 연결 부재`를 해결하지는 못합니다. 여기서 확인해야 할 결과는 답변 합의가 아니라 `최신 문서 ID가 실제로 붙었는가`입니다.

### 사례 3. automatic prompt optimization이 있어도 평가 기준이 약하면 같이 흔들린다

문서 요약 프롬프트를 자동으로 고치는 루프를 만든다고 해 봅시다. 만약 평가 기준이 `문장이 자연스러운가` 하나뿐이라면, 자동 최적화는 더 그럴듯한 문장을 만드는 쪽으로 수렴할 수 있습니다. 하지만 중요한 근거 문장이 빠지는지, 길이 제한을 지키는지, 독자 수준이 맞는지는 놓칠 수 있습니다.

그래서 automatic prompt optimization에서는 프롬프트 자동 수정 자체보다 `무엇을 좋은 점수로 볼 것인가`가 더 중요합니다. 여기서 확인해야 할 결과는 프롬프트가 바뀌었다는 사실이 아니라, `목적에 맞는 평가 기준으로 실제로 더 나아졌는가`입니다.

## 이 보충학습에서 기억할 관점

- CoT는 중간 단계 reasoning을 더 잘 드러내게 하려는 전략입니다.
- self-consistency는 여러 후보 reasoning의 합의를 보려는 전략입니다.
- automatic prompt optimization은 프롬프트 개선 루프를 더 자동화하려는 접근입니다.
- 세 전략 모두 프롬프트 층의 개선이지, 최신성·근거·도구 실행의 구조 보장은 아닙니다.

- Chain-of-thought를 중간 단계 reasoning 전개 전략으로 설명할 수 있는가?
- self-consistency를 여러 후보 합의 전략으로 설명할 수 있는가?
- automatic prompt optimization을 프롬프트 개선 자동화 접근으로 설명할 수 있는가?
- 이 전략들이 RAG, 도구 사용, 실행 로그를 대신하지 않는다고 설명할 수 있는가?
- 프롬프트 층의 개선과 시스템 층의 보장을 구분할 수 있는가?
