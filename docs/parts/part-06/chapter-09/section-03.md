# P6-9.3 보충학습: Chain-of-thought, self-consistency, automatic prompt optimization은 프롬프트 층에서 무엇을 더하는가

Section ID: `P6-9.3`
Version: `v2026.07.18`

P6-9.1에서는 프롬프트 엔지니어링(prompt engineering)을 입력 설계의 첫 번째 제어 지점으로 봤고, P6-9.2에서는 프롬프트만으로 해결되지 않는 한계를 봤습니다. 그런데 실무 정리나 논문, 제품 설명으로 넘어가면 CoT, self-consistency, automatic prompt optimization 같은 이름이 다시 연속해서 등장합니다. 여기서 더 중요한 것은 이름을 따라가는 일이 아니라, 이 전략들이 프롬프트 층에서 무엇을 더 조정하려는지 먼저 구분하는 기준입니다.

`Chain-of-thought`
`self-consistency`
`automatic prompt optimization`

이 이름들은 프롬프트를 더 복잡하게 만드는 주문 목록이 아니라, `모델에게 중간 단계나 여러 후보를 어떻게 다루게 할 것인가`, `프롬프트 자체를 어떻게 반복 개선할 것인가`와 연결된 전략 이름입니다. 이 절에서는 세 전략이 프롬프트 층에서 실제로 무엇을 더 바꾸고, 무엇은 여전히 못 바꾸는가를 같은 축에서 정리합니다.

## 세 전략이 다루는 문제

이 절은 Chain-of-thought(CoT), self-consistency, automatic prompt optimization을 입문 수준에서 구분합니다.

- Chain-of-thought는 무엇을 기대하는 전략인가?
- self-consistency는 왜 한 번의 답 대신 여러 후보를 보게 하는가?
- automatic prompt optimization은 무엇을 자동화하려는가?
- 이런 기법들은 언제 도움이 되고, 언제 과신하면 위험한가?

여기서는 이름을 들었을 때 `어떤 종류의 프롬프트 전략인가`를 구분하고, 각 전략이 프롬프트 층에서 무엇을 더 바꾸려 하는지 정리합니다. 앞 절의 프롬프트 엔지니어링이 `입력을 어떻게 설계할까`를 다뤘다면, 여기서는 그 입력 설계를 더 정교하게 만드는 대표 전략 이름들이 각각 어떤 막힘에 먼저 대응하는지 보강합니다. 뒤의 RAG, 도구 사용, 평가 절에서는 이런 전략이 어디까지 도움이 되고 어디서부터는 별도 시스템 구조가 필요한지 다시 회수합니다.

## 왜 프롬프트 한계 뒤에도 이 전략들을 따로 구분해야 하는가

P6-9.2를 읽고 나면 두 가지를 쉽게 섞게 됩니다. 하나는 `프롬프트는 한계가 있다`는 말이고, 다른 하나는 `그런데 왜 또 프롬프트 전략 이름을 더 배우는가`라는 의문입니다. 이 둘을 풀지 않으면 CoT나 self-consistency를 `프롬프트 한계를 넘어서는 만능 해결책`처럼 읽거나, 반대로 `어차피 RAG와 도구가 필요하다면 이런 전략은 다 쓸모없다`고 오해하기 쉽습니다.

하지만 Chapter 9의 실제 흐름은 그 사이에 있습니다. P6-9.2는 `프롬프트 층 밖에서 해결해야 할 문제`를 분리한 절이고, P6-9.3은 `그래도 프롬프트 층 안에서 더 정교하게 다룰 수 있는 전략`을 정리하는 절입니다. 즉, 이 절은 한계를 부정하는 보충이 아니라 한계를 인정한 뒤에도 남는 프롬프트 층의 전략 공간을 정리하는 보충입니다.

| 바로 앞 절에서 이미 잡은 것 | 이 보충 절에서 새로 잡는 것 | 바로 뒤 장으로 넘기는 질문 |
| --- | --- | --- |
| 최신성, 근거, 실행은 프롬프트만으로 닫히지 않는다 | reasoning 경로, 여러 후보 비교, 프롬프트 실험 루프는 여전히 프롬프트 층에서 더 다듬을 수 있다 | 어디서부터는 RAG, 도구 사용, 평가 구조를 붙여야 하는가 |
| 입력 조정과 시스템 구조 보장은 다른 층이다 | CoT, self-consistency, automatic prompt optimization은 모두 입력 조정 층의 전략이다 | 각 전략이 실제로 어떤 막힘에서 먼저 떠오르는가 |

즉, 이 절의 닫힘은 `전략 이름을 더 많이 아는 것`이 아니라 `프롬프트 층에서 더 바꾸는 것`과 `시스템 구조를 붙여야 하는 것`을 덜 섞는 데 있습니다.

| 지금 단계의 초점 | 바로 다음에 이어질 질문 | 뒤에서 본격적으로 다시 읽는 위치 |
| --- | --- | --- |
| CoT / self-consistency | 답변 경로와 후보 비교를 어떻게 더 안정적으로 유도할 것인가? | P6-9.3 |
| automatic prompt optimization | 프롬프트 실험을 어떤 평가 루프로 반복 개선할 것인가? | P6-9.3, P6-15.1, P6-15.2 |
| 시스템 층의 보장 | 최신 문서, 근거, 도구 실행, 로그는 어떤 별도 구조가 맡는가? | P6-10.1, P6-10.2, P6-12.1, P6-12.2, P6-15.1, P6-16.2 |

핵심은 세 전략이 모두 `프롬프트 층의 개선`이지, `시스템 보장 층`의 대체물이 아니라는 점입니다.

## 여기서 남겨야 할 구분

- CoT를 `중간 단계 reasoning을 드러내게 하려는 전략`으로 설명할 수 있습니다.
- self-consistency를 `한 번의 경로보다 여러 후보 경로의 합의를 보는 전략`으로 설명할 수 있습니다.
- automatic prompt optimization을 `프롬프트 자체를 반복 평가하고 개선하려는 접근`으로 설명할 수 있습니다.
- 이 기법들이 최신성, 근거 보장, 도구 실행을 대신하지 않는다는 점을 설명할 수 있습니다.

## 학습 배경

Part 1의 12.2에서는 지시(instruction), 맥락(context), 예시(example)를 나눠 보는 기본 구조를 먼저 잡았습니다. 그 단계에서는 프롬프트를 `입력을 구조화하는 방법`으로 이해하는 것이 더 중요했고, 고급 기법 이름을 바로 늘어놓지 않는 편이 안전했습니다.

하지만 Part 6에서는 사용 경험과 실무 구조를 함께 보기 시작하므로, 이제 이런 이름들을 더 미루지 않아도 됩니다. 다만 중요한 것은 기법 이름을 외우는 것이 아니라, `이 전략이 어떤 문제를 줄이려는가`를 이해하는 일입니다.

## Chain-of-thought는 중간 단계를 더 잘 드러내게 하려는 전략이다

가장 널리 알려진 이름은 Chain-of-thought(CoT)입니다. 이 전략의 직관은 간단합니다.

> 답만 바로 말하게 하지 말고, 중간 단계 reasoning을 더 분명하게 거치게 하자.

예를 들어 단순 요청은 다음처럼 보일 수 있습니다.

> 이 문제의 답을 구해줘.

CoT 스타일 요청은 보통 다음처럼 바뀝니다.

> 바로 답만 쓰지 말고,
> 어떤 기준으로 생각했는지 단계별로 정리한 뒤
> 마지막에 결론을 써줘.

이 전략이 기대하는 효과는 `복잡한 과업에서 중간 단계가 더 안정적으로 드러나는가`입니다. 특히 수학 문제, 논리 비교, 조건이 많은 분류, 문서 비교 같은 장면에서 자주 언급됩니다.

다만 여기서 중요한 점이 있습니다.

- CoT는 최신 문서를 자동으로 찾아 주지 않습니다.
- CoT는 계산 정확도를 자동으로 보장하지 않습니다.
- CoT는 외부 도구 실행을 대신하지 않습니다.

즉 CoT는 `생각 과정을 더 잘 펼치게 해 보려는 입력 전략`이지, 시스템 보장을 붙이는 구조는 아닙니다.

## self-consistency는 한 번의 답보다 여러 후보의 합의를 본다

self-consistency는 CoT와 자주 함께 언급됩니다. 직관은 다음과 같습니다.

> 한 번의 reasoning 경로만 믿지 말고,
> 여러 번 생성한 경로 중 더 자주 도달하는 결론을 보자.

이 단계에서는 이렇게 이해할 수 있습니다.

- CoT: 한 번의 reasoning 경로를 더 길게 펼친다.
- self-consistency: 그런 reasoning 경로를 여러 번 만들어 보고 더 일관된 결론을 본다.

예를 들어 같은 문제를 여러 번 풀게 하고, 마지막 결론이 가장 자주 나온 답을 채택하는 방식으로 설명할 수 있습니다.

이 전략이 기대하는 효과는 `한 번의 우연한 실수나 표현 흔들림을 줄일 수 있는가`입니다. 특히 결론이 하나로 모여야 하는 문제에서 자주 등장합니다.

하지만 이 역시 한계가 있습니다.

- 여러 번 돌렸다고 최신 정보가 생기지는 않습니다.
- 여러 후보가 같은 잘못된 전제를 공유하면 합의도 같이 틀릴 수 있습니다.
- 비용과 지연 시간이 늘어날 수 있습니다.

즉 self-consistency는 `한 번의 답을 그대로 믿지 않는 전략`이지, 진실 보장 장치는 아닙니다.

## automatic prompt optimization은 프롬프트 개선을 자동화하려는 접근이다

세 번째 이름은 automatic prompt optimization입니다. 이 표현은 조금 넓게 쓰입니다. 공통 직관은 다음입니다.

> 사람이 프롬프트를 손으로 조금씩 고치던 일을,
> 점수와 평가 루프를 붙여 더 자동으로 개선해 보자.

예를 들어 다음처럼 생각할 수 있습니다.

1. 프롬프트 초안을 만든다.
2. 여러 입력에서 결과를 평가한다.
3. 어떤 프롬프트가 더 점수가 좋은지 비교한다.
4. 더 나은 표현이나 구조를 다시 제안한다.

이 전략이 중요한 이유는, 프롬프트 엔지니어링이 원래부터 `입력 변화에 따른 출력 변화를 관찰하는 반복 실험`이기 때문입니다. automatic prompt optimization은 그 반복 실험을 더 체계적으로 만들려는 방향입니다.

다만 여기서도 과장이 붙기 쉽습니다.

- 자동 최적화가 곧 정답을 보장하지는 않습니다.
- 평가 기준이 약하면 자동화도 약합니다.
- 특정 데이터셋에만 잘 맞는 프롬프트로 과적합될 수 있습니다.

즉 자동화는 `프롬프트 실험을 더 빨리 돌리는 도구`이지, 평가 품질 자체를 대체하지는 않습니다.

## 세 전략을 한 번에 구분하면

| 전략 | 무엇을 조정하려 하는가 | 먼저 기대하는 효과 | 바로 해결되지 않는 것 |
| --- | --- | --- | --- |
| Chain-of-thought | 한 번의 답 안에서 reasoning 전개 | 중간 단계가 더 분명해짐 | 최신성, 외부 근거, 실행 보장 |
| self-consistency | 여러 reasoning 후보의 비교 | 결론 흔들림 감소 | 공통 전제가 틀릴 때의 오류 |
| automatic prompt optimization | 프롬프트 반복 개선 과정 | 실험 속도와 구조화 향상 | 평가 기준의 약함, 구조 보장 부재 |

이 표에서 핵심은 세 전략이 모두 `프롬프트 층`에서 움직인다는 점입니다. 즉 P6-9.2에서 본 것처럼, 모델 밖의 문서 연결이나 도구 실행 보장은 여전히 다른 구조가 필요합니다.

## 언제 도움이 되고, 언제 과신하면 위험한가

도움이 되는 장면은 대체로 다음과 같습니다.

- 조건이 여러 개인 추론형 질문
- 단계 설명이 중요한 교육용 출력
- 같은 형식을 반복 유지해야 하는 평가 작업
- 프롬프트 후보를 여러 입력에서 비교해야 하는 실험

반대로 과신하면 위험한 장면은 다음과 같습니다.

- 최신 정책이나 가격처럼 외부 최신성이 핵심인 작업
- 실제 계산 도구 확인이 필요한 수치 작업
- 파일 저장, API 호출, 승인 처리처럼 실행 로그가 필요한 작업
- 잘못된 전제가 여러 번 반복돼도 결론이 그럴듯해 보이는 작업

즉 이 전략들은 `입력 설계의 정교화`에는 도움이 되지만, `시스템 보장`을 대신하지는 않습니다.

## 사례 및 예시

### 사례 1. 조건이 많은 분류 문제에서 CoT를 붙이는 이유

고객 문의를 `환불`, `배송`, `계정`, `오류` 중 하나로 분류한다고 해 봅시다. 이런 작업을 보면 `정답 라벨만 맞으면 된 것 아닌가`라고 생각하기 쉽습니다. 그래서 모델이 `환불`이라고만 내놓아도 일단 성공처럼 느껴집니다. 하지만 실제 문의에는 `결제는 취소했는데 배송은 이미 시작됐고 환불은 언제 되나요?`처럼 조건이 여러 갈래로 섞이는 경우가 많습니다. 이때 라벨 하나만 보면 모델이 `환불`을 골랐는지, `배송 시작` 조건을 무시했는지, `결제 취소`를 더 크게 봤는지 전혀 읽히지 않습니다.

이때 CoT 스타일 요청은 `어떤 단어와 조건을 먼저 봤는지`, `왜 이 라벨을 골랐는지`, `다른 후보 라벨은 왜 제외했는지`를 더 분명하게 드러내게 해 줄 수 있습니다. 사람은 최종 라벨만 보는 대신, 중간 기준이 실제 업무 기준과 같은 순서로 적용됐는지도 함께 검토할 수 있습니다. 예를 들어 운영 규칙이 `배송 시작 여부를 먼저 보고, 그다음 취소 가능성과 환불 절차를 나눈다`라면, CoT 출력이 그 순서를 따라가는지 확인할 수 있습니다. 여기서 오해는 `라벨만 맞으면 reasoning도 맞았겠지`라는 데 있고, 개념이 바꾸는 점은 `정답 라벨`보다 `라벨을 고르는 기준의 가독성`을 먼저 점검하게 만든다는 데 있습니다. 그래서 이 사례에서 확인해야 할 결과는 라벨 하나만 맞았는가가 아니라, `라벨을 고르는 기준이 더 읽히고 그 순서가 실제 분류 규칙과도 맞는가`입니다.

### 사례 2. self-consistency가 있어도 최신 정책 문제는 남는다

최신 환불 정책을 묻는 질문을 여러 번 돌려 보고, 가장 자주 나온 답을 채택한다고 해 봅시다. 여기서 `여러 번 물어서 같은 답이 반복되면 더 믿을 만하지 않을까`라고 생각하기 쉽습니다. 실제로 결론이 더 안정돼 보이기 때문입니다. 하지만 모델이 최신 문서를 보지 못했다면, 여러 번 합의한 답도 그냥 `오래된 정책의 안정된 반복`일 수 있습니다. 예를 들어 지난달까지는 `사용 후 7일 이내 환불 가능`이었는데 이번 주에 `미개봉 제품만 가능`으로 바뀌었다면, self-consistency는 바뀐 조항을 발견하지 못한 채 예전 규정을 여러 번 확신 있게 반복할 수 있습니다.

즉 self-consistency는 `한 번의 흔들림`을 줄일 수는 있어도, `최신 문서 연결 부재`를 해결하지는 못합니다. 이때 빠지기 쉬운 오해는 `여러 번 합의했으니 사실 확인도 된 것 같다`는 판단입니다. 하지만 여기서 개념이 바꾸는 기준은 `답이 몇 번 반복됐는가`보다 `그 반복이 현재 문서 근거 위에서 일어났는가`를 먼저 보게 만든다는 데 있습니다. 그래서 이 사례에서 확인해야 할 결과는 답변 합의가 아니라 `최신 문서 ID가 실제로 붙었는가`, 그리고 합의된 결론이 정말 현재 조항과 맞는가입니다.

### 사례 3. automatic prompt optimization이 있어도 평가 기준이 약하면 같이 흔들린다

문서 요약 프롬프트를 자동으로 고치는 루프를 만든다고 해 봅시다. `자동 최적화`라는 말을 들으면 프롬프트를 사람보다 더 잘 고쳐 줄 것이라고 기대하기 쉽습니다. 그래서 점수가 조금만 올라가도 `이제 더 좋은 프롬프트를 찾았다`고 생각하기 쉽습니다. 하지만 평가 기준이 `문장이 자연스러운가` 하나뿐이라면, 자동 최적화는 더 그럴듯한 문장을 만드는 쪽으로만 수렴할 수 있습니다. 그렇게 되면 중요한 근거 문장이 빠지는지, 길이 제한을 지키는지, 독자 수준이 맞는지, 금지 표현을 피하는지 같은 핵심 조건은 놓친 채 `말은 매끄럽지만 중요한 정보는 비는` 프롬프트가 선택될 수 있습니다.

그래서 automatic prompt optimization에서는 프롬프트 자동 수정 자체보다 `무엇을 좋은 점수로 볼 것인가`가 더 중요합니다. 여기서 넘어가야 할 지점은 `자동화가 있으니 평가도 같이 해결된다`는 기대입니다. 실제로는 자동화가 빠르게 증폭하는 것은 프롬프트 자체가 아니라, 우리가 정한 평가 기준입니다. 그래서 이 사례에서 확인해야 할 결과는 프롬프트가 바뀌었다는 사실이 아니라, `목적에 맞는 평가 기준으로 실제로 더 나아졌는가`, 그리고 그 점수 상승이 단순 유창성 향상이 아니라 핵심 조건 보존까지 포함하는가입니다.

세 사례를 실무 검토 메모처럼 다시 줄이면 다음과 같습니다.

| 먼저 좋아 보이는 것 | 그대로 믿으면 생기는 오판 | 더 안전한 다음 판단 |
| --- | --- | --- |
| CoT를 붙였더니 설명이 길고 그럴듯해 보임 | 중간 단계가 길다고 최신 근거나 계산 정확도까지 확보된 것으로 오해함 | reasoning 경로 개선과 근거 확보를 따로 점검 |
| self-consistency로 답이 자주 같게 나옴 | 여러 번 합의했으니 맞는 답이라고 과신함 | 공통 전제가 최신 문서와 맞는지 다시 확인 |
| 자동 최적화로 점수가 올랐음 | 평가 세트에만 맞춘 프롬프트를 일반적으로 더 좋아졌다고 오해함 | 평가 기준과 검증 세트가 충분한지 다시 점검 |

## 바로 적용해 보면

이 보충학습을 읽고 바로 실무 문서를 다시 보면, 세 전략 이름을 `무조건 더 강한 방법`처럼 읽는 오해부터 줄이는 편이 좋습니다. 먼저 `지금 부족한 것이 중간 판단 경로인지`, `여러 후보 비교인지`, `프롬프트 실험 루프인지`를 짧게 적어 보면 혼선이 많이 줄어듭니다.

| 지금 막히는 지점 | 먼저 떠올릴 전략 | 아직 이 전략으로 닫히지 않는 것 |
| --- | --- | --- |
| 답은 나오는데 왜 그 답을 골랐는지 안 읽힌다 | CoT | 최신 근거, 실제 실행, 계산 보장 |
| 한 번씩 결론이 흔들려서 어느 답을 믿어야 할지 모르겠다 | self-consistency | 공통 전제가 틀린 경우, 최신 문서 부재 |
| 프롬프트 후보가 너무 많아 손으로 비교가 안 된다 | automatic prompt optimization | 평가 기준의 약함, 특정 세트 과적합 |

여기서 중요한 점은 세 전략 모두 `모델이 답을 만들어 가는 경로`를 더 잘 다루게 하려는 장치라는 것입니다. 반대로 현재 문서 회수, 계산 로그, 저장 성공 기록처럼 모델 바깥의 확인 근거가 비어 있다면, 전략 이름을 바꾸는 것보다 먼저 시스템 구조를 붙여야 합니다.

이 짧은 구분이 잡히면 다음 장들을 읽을 때도 덜 흔들립니다. P6-10 이후의 RAG, P6-12의 tool use, P6-15의 evaluation을 볼 때 `이 장은 프롬프트 전략 보강인가, 아니면 시스템 보장 구조인가`를 바로 가를 수 있기 때문입니다.

## 연습 및 예제

이 절에서 필요한 연습은 논문 세부를 외우는 일이 아니라, 세 전략을 같은 자리에서 비교해도 섞어 쓰지 않는 감각을 만드는 일입니다. 특히 `프롬프트 전략의 문제`와 `시스템 구조의 문제`를 헷갈리지 않는지가 핵심입니다.

### 연습 1. 같은 작업에 어떤 전략을 먼저 붙일까

다음 세 작업을 생각해 보겠습니다.

- 조건이 여러 개인 문의 분류
- 최신 환불 정책 요약
- 반복되는 요약 프롬프트 개선

이때 먼저 붙일 전략은 다음 정도로 구분하는 편이 안전합니다.

| 작업 | 먼저 떠올릴 전략 | 이유 | 이 전략만으로 닫히지 않는 것 |
| --- | --- | --- | --- |
| 조건이 여러 개인 문의 분류 | CoT | 어떤 기준으로 라벨을 골랐는지 중간 단계를 더 또렷하게 드러내기 위해 | 최신 근거, 실행 보장 |
| 최신 환불 정책 요약 | CoT나 self-consistency보다 RAG를 먼저 떠올림 | 여러 번 생각하게 해도 최신 문서를 보지 못하면 오래된 답이 반복될 수 있기 때문 | 최신성, 근거 연결 |
| 반복되는 요약 프롬프트 개선 | automatic prompt optimization | 여러 프롬프트 후보를 같은 평가 기준으로 반복 비교해야 하기 때문 | 평가 기준 품질, 과적합 방지 |

이 표의 핵심은 `전략 이름이 멋져 보여서 먼저 붙이는 것`이 아니라, `지금 부족한 것이 reasoning 경로인가, 최신 근거인가, 평가 자동화인가`를 먼저 가르는 데 있습니다.

바로 위 표를 실무 triage 메모처럼 다시 적으면 다음과 같습니다.

| 장면 | 먼저 분리할 질문 | 먼저 손봐야 할 층위 |
| --- | --- | --- |
| 답은 나오지만 중간 기준이 안 읽힘 | reasoning 경로가 문제인가 | CoT 같은 프롬프트 전략 |
| 답이 여러 번 비슷하게 나오지만 최신성이 의심됨 | 최신 근거 연결이 문제인가 | RAG, 검색, 문서 회수 구조 |
| 프롬프트 후보가 너무 많아 손으로 비교가 안 됨 | 반복 실험 자체가 문제인가 | automatic prompt optimization + 평가 harness |

### 연습 2. 세 전략을 같은 질문에 얹으면 무엇이 달라질까

같은 수치 비교 질문이 있다고 해 보겠습니다. 외부 근거는 이미 충분히 주어졌고, 지금 바꾸고 싶은 것은 답변 경로뿐입니다.

| 붙이는 방식 | 먼저 관찰할 변화 | 같이 늘어나는 비용 또는 주의점 |
| --- | --- | --- |
| CoT | 중간 판단 단계가 더 또렷하게 드러나는가 | 출력 길이 증가, 불필요한 장문 reasoning |
| self-consistency | 한 번의 흔들린 결론보다 더 일관된 결론으로 모이는가 | 여러 번 생성해야 하므로 비용과 지연 증가 |
| automatic prompt optimization | 같은 평가 세트에서 더 안정된 프롬프트 후보가 남는가 | 평가 기준이 약하면 잘못된 방향으로 자동 최적화 |

Chain-of-thought와 self-consistency 관련 대표 논문들도 주로 `복잡한 reasoning 과업에서 중간 경로를 드러내거나 여러 경로의 합의를 보는 방법`으로 설명합니다. 반대로 최신 문서 확보나 실제 도구 실행은 이 전략 자체의 목표가 아닙니다. 그래서 이 절의 실습은 언제나 `프롬프트 전략`과 `시스템 구조`를 따로 구분하는 쪽으로 닫혀야 합니다.

### 연습 3. 언제 프롬프트 전략보다 시스템 구조를 먼저 떠올릴까

다음 장면에서는 CoT, self-consistency, automatic prompt optimization보다 다른 구조를 먼저 떠올리는 편이 더 안전합니다.

| 장면 | 먼저 떠올릴 것 | 왜 프롬프트 전략보다 이쪽이 먼저인가 |
| --- | --- | --- |
| `이번 주 환율 기준으로 정산 금액을 계산해 줘` | 최신 데이터 소스와 계산 도구 | reasoning을 길게 써도 최신 값과 실제 계산이 없으면 답이 닫히지 않기 때문 |
| `현재 재고가 0인 상품만 골라 주문 제한 메일을 보내 줘` | 상태 조회와 실행 도구, 승인 로그 | 합의된 답변보다 실제 상태 조회와 실행 기록이 먼저 필요하기 때문 |
| `사내 규정 PDF에서 최신 조항을 근거로 답해 줘` | 문서 검색과 근거 연결 | 설명 경로보다 최신 문서 회수가 먼저 실패할 가능성이 크기 때문 |

이 연습의 핵심은 전략 이름을 많이 아는 것이 아니라, `지금 문제는 프롬프트 층에서 풀 수 있는가`, `아니면 최신성·근거·실행 구조가 먼저 필요한가`를 분리하는 데 있습니다.

## 체크리스트

- CoT는 중간 단계 reasoning을 더 잘 드러내게 하려는 전략이라는 점을 설명할 수 있는가?
- self-consistency는 여러 후보 reasoning의 합의를 보려는 전략이라는 점을 설명할 수 있는가?
- automatic prompt optimization은 프롬프트 개선 루프를 더 자동화하려는 접근이라는 점을 설명할 수 있는가?
- 세 전략 모두 프롬프트 층의 개선이지, 최신성·근거·도구 실행의 구조 보장은 아니라는 점을 설명할 수 있는가?
