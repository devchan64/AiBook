# Part 6 마무리. LLM과 생성형 AI 정리

Part 6는 생성형 AI를 `대단한 답변기`처럼 소비하는 단계에서 한 걸음 더 나아가, LLM(large language model)이 어떤 입력 단위를 읽고, 어떤 구조 위에서 학습되며, 어떤 서비스 구조 안에서 실제로 동작하는지 실제 설명으로 묶는 구간이었습니다.

이 Part의 핵심은 LLM을 단지 `말을 잘하는 모델`로 보는 데서 멈추지 않는 것입니다. 토큰(token), 임베딩(embedding), Transformer, 사전학습(pretraining), 파인튜닝(fine-tuning), RAG, 도구 사용(tool use), 에이전트(agent), 평가(evaluation), 운영 제약(constraints)까지 이어지는 흐름을 함께 볼 때 비로소 생성형 AI의 실제 구조가 보입니다.

즉, Part 6는 Part 1~4에서 `후속에서 설명한다`고 남겨 둔 GPT, next-token prediction, instruction tuning, RAG, tool use, agent를 실제로 설명해야 하는 파트였습니다.

이 Part를 다시 펼칠 때는 지금 읽는 설명이 어느 층위인지 먼저 구분하는 편이 가장 안전합니다.

| 다시 잡을 층위 | 여기서 확인할 질문 | 대표 주제 |
| --- | --- | --- |
| 모델 내부 원리 | 모델은 입력을 어떻게 읽고 다음 출력을 고르는가? | 토큰, 임베딩, Transformer, GPT |
| 조정과 사용 경험 | 같은 구조가 왜 지시 수행과 대화 품질 차이로 이어지는가? | 사전학습, 파인튜닝, 지시 튜닝, 정렬 |
| 서비스 연결 | 모델 밖에서 무엇을 붙여야 실제 기능이 되는가? | 프롬프트, RAG, 벡터 검색, tool use, agent, MCP |
| 운영 판단 | 답변 품질과 서비스 품질을 어떻게 나눠 보는가? | 평가, 비용, 지연 시간, 실패 대응 |
| 배경 축 | 본류를 어떤 계보와 비교 위에서 다시 읽는가? | LLM 발전사, BERT 계열 |

## 이 파트에서 다룬 핵심 흐름

Part 6의 흐름은 다음처럼 정리할 수 있습니다.

| 흐름 단계 | 이 단계에서 붙잡아야 할 질문 |
| --- | --- |
| 토큰(token)과 토큰화(tokenization) | 모델은 문장을 어떤 입력 단위로 읽는가? |
| 임베딩(embedding)과 의미 공간 | 기호를 어떻게 비교 가능한 표현으로 바꾸는가? |
| Transformer와 GPT 계열, 다음 토큰 예측 | 왜 다음 토큰 예측이 긴 생성과 지시 수행으로 이어지는가? |
| 사전학습, 파인튜닝, 지시 튜닝, 정렬 | 같은 구조가 어떻게 다른 사용 경험으로 조정되는가? |
| 프롬프트(prompt), RAG, 벡터 데이터베이스 | 모델 내부 기억만으로 부족할 때 무엇을 밖에서 붙이는가? |
| 도구 사용(tool use), 함수 호출(function calling), 에이전트(agent) | 답변을 넘어서 조회와 실행까지 어떻게 이어지는가? |
| MCP(Model Context Protocol), 하네스(harness) | 도구 연결과 실행 기록 환경을 어떤 관점으로 정리하는가? |
| 평가, 자동 평가, 사람 평가 | 무엇을 자동으로 점검하고 무엇을 사람 판단으로 남겨야 하는가? |
| 서비스 제약, 실패 대응, 운영 관점 | 좋은 답과 운영 가능한 서비스는 왜 다른가? |
| 작은 생성형 AI 기능 흐름으로 다시 묶기 | 질문 하나가 검색, 답변, 평가, 기록으로 어떻게 닫히는가? |
| 발전사와 BERT 계열을 배경 축으로 다시 정리하기 | 직접 계보와 비교 배경을 어떻게 분리해서 읽어야 하는가? |

이 흐름에서 확인해야 할 결과는 `모델 자체`와 `모델을 둘러싼 시스템`을 분리해 읽을 수 있게 되는 것입니다. Part 6를 읽고 나면 프롬프트를 잘 쓰는 일과, 검색을 붙이는 일과, 도구를 호출하는 일과, 운영 중 실패를 기록하는 일이 서로 다른 층위(level)의 문제라는 점이 분명해져야 합니다. 특히 `모델 내부 원리 -> 조정층 -> 서비스 연결 -> 운영 판단`의 순서를 놓치지 않는 것이 중요합니다.

현재 목차 기준으로 보면 이 파트는 `입력과 표현 -> LLM 핵심 구조 -> 학습과 조정 -> 프롬프트와 근거 연결 -> 실행 구조 -> 평가·운영·통합 실습 -> 배경 축` 순서로 읽히는 편이 더 자연스럽습니다. 즉, Chapter 1~17을 먼저 본류로 읽고, Chapter 18 `LLM 발전사`, Chapter 19 `BERT 계열`은 뒤에서 붙는 배경 축으로 읽는 현재 구조를 유지하는 편이 가장 안정적입니다.

처음 복습할 때는 아래 세 줄을 먼저 다시 붙잡으면 됩니다.

| 지금 먼저 붙잡을 손잡이 | 여기서 바로 확인할 것 |
| --- | --- |
| Chapter 1~17 본류 | 입력, 생성, 검색/실행, 평가/운영이 한 요청 흐름으로 어떻게 닫히는가 |
| Chapter 18~19 배경 축 | 그 본류가 어떤 발전사와 비교 기준 위에 서 있는가 |
| Part 6 산출물 전환 | 이 구조를 어떤 run record와 회고 문서로 다시 써야 하는가 |

같은 흐름을 요청 단위로 다시 압축하면 다음 한 줄로도 묶을 수 있습니다.

`질문을 토큰으로 읽고 -> 필요하면 문서나 도구를 붙이고 -> 답을 생성하고 -> 평가와 기록으로 다시 확인한다.`

이 본류와 배경 축을 다시 나누면 다음처럼 읽는 편이 가장 안정적입니다.

| 먼저 읽는 본류 | 여기서 확인할 것 |
| --- | --- |
| 토큰, 임베딩 | 입력 단위와 표현 |
| Transformer, GPT, next-token prediction | 생성 구조의 핵심 |
| 사전학습, 파인튜닝, 지시 튜닝, 정렬 | 사용 경험을 바꾸는 조정층 |
| 프롬프트, RAG, 벡터 검색, tool use, agent | 모델 밖의 검색·실행 연결 |
| 평가, 운영, 통합 미니 실습 | 품질 판단과 기록 구조 |

| 나중에 붙는 배경 축 | 여기서 다시 읽는 것 |
| --- | --- |
| LLM 발전사 | 현재 본류가 어떤 계보 위에 서 있는가 |
| BERT 계열 비교 | 생성 중심 GPT 계열과 읽기 중심 계열을 어떻게 구분하는가 |

즉, Part 6는 먼저 `어떻게 동작하는가`를 읽고, 그다음 `어디서 왔고 무엇과 다른가`를 붙이는 순서로 보는 편이 안전합니다.

이 본류를 서비스 요청 하나의 흐름으로 가장 짧게 다시 읽으면 아래 네 단계로 압축할 수 있습니다.

| 한 요청의 본류 흐름 | 여기서 먼저 확인할 것 |
| --- | --- |
| 입력을 읽는다 | 토큰, 임베딩, 문맥 표현 |
| 답을 만들거나 조정한다 | Transformer, GPT, 사전학습, 지시 튜닝 |
| 부족하면 밖에서 보완한다 | RAG, tool use, agent, MCP |
| 결과를 점검하고 남긴다 | 평가, 운영, 기록, 다음 조치 |

처음 복습할 때는 다음 두 줄을 다시 확인하면 본류와 배경 축이 빠르게 정리됩니다.

## 반드시 기억할 개념

Part 6에서 특히 오래 남겨야 할 개념은 다음과 같습니다.

| 구분 | 기억할 관점 |
| --- | --- |
| 토큰 | 모델은 사람이 보는 문장 전체가 아니라 토큰 단위로 입력과 출력을 읽습니다. |
| 임베딩 | 임베딩은 기호(symbol)를 의미 비교가 가능한 벡터(vector)로 바꾸는 표현입니다. |
| Transformer | 현재 LLM의 중심 구조는 self-attention과 병렬 계산 위에 서 있습니다. |
| 사전학습 | LLM은 대규모 데이터에서 다음 토큰 예측을 통해 언어 패턴을 먼저 익힙니다. |
| 파인튜닝과 정렬 | 모델을 특정 과업(task)이나 지시(instruction)에 더 맞게 조정하는 단계가 따로 있습니다. |
| 프롬프트 | 프롬프트는 입력을 잘 구성하는 방법이지, 모델 자체의 지식을 새로 학습시키는 과정은 아닙니다. |
| RAG | RAG는 모델 내부 기억을 늘리는 것이 아니라, 외부 근거를 검색해 입력 문맥으로 연결하는 구조입니다. |
| 벡터 검색 | 의미적으로 가까운 문서를 찾는 방식이지만, 검색 품질은 임베딩 품질과 인덱스 구조에 함께 좌우됩니다. |
| 에이전트 | 에이전트는 목표를 여러 단계의 계획, 행동, 관찰 흐름으로 연결하는 실행 구조입니다. |
| MCP와 하네스 | MCP는 도구 연결 인터페이스를, 하네스는 실행·평가·기록 환경을 정리하는 관점입니다. |
| 평가와 운영 | 좋은 답변 예시와 좋은 서비스 운영은 같은 말이 아닙니다. 품질, 비용, 지연 시간, 실패 대응을 함께 봐야 합니다. |

이 표를 다 읽고 나면 마지막으로 다음 구분이 남아야 합니다.

- `모델 구조`: 토큰, 임베딩, Transformer, 사전학습
- `서비스 연결`: 프롬프트, RAG, 벡터 검색, tool use, agent
- `운영 판단`: 평가, 자동/사람 검토, 비용, 지연 시간, 실패 대응

이 구분은 Part 6에서 무엇을 먼저 기록해야 하는지 정하는 기준이기도 합니다.

- 모델 구조를 설명했다면 다음에는 `입력과 출력 기록`이 남아야 합니다.
- 서비스 연결을 설명했다면 다음에는 `근거와 도구 결과 기록`이 남아야 합니다.
- 운영 판단을 설명했다면 다음에는 `평가 상태와 실패 기록`이 남아야 합니다.

## 오해하기 쉬운 지점

Part 6에서는 특히 다음 오해를 조심해야 합니다.

- LLM을 곧 AI 전체라고 보면 안 됩니다.
- 프롬프트(prompt)와 파인튜닝(fine-tuning)을 같은 것으로 읽으면 안 됩니다.
- RAG를 `모델이 외부 사실을 완전히 이해한 상태`로 오해하면 안 됩니다.
- 도구 사용(tool use)이 붙었다고 해서 자동으로 에이전트(agent)가 되는 것은 아닙니다.
- MCP를 하나의 제품 이름이나 특정 벤더 전용 기능처럼 읽으면 안 됩니다.
- 하네스(harness)를 단일 도구 이름으로 고정하면 안 됩니다.
- 자동 평가 점수 하나만 높다고 실제 사용자 경험이 바로 좋아지는 것은 아닙니다.
- 생성 품질이 좋아 보여도 비용(cost), 지연 시간(latency), 권한(permission), 실패 처리(failure handling)가 준비되지 않으면 서비스 완성이라고 보기 어렵습니다.
- 검색, 도구 사용, 평가를 각각 이해했다고 해서 곧바로 한 요청 흐름으로 구현할 수 있는 것은 아닙니다.
- 발전사에서 유명한 모든 딥러닝 사건을 곧바로 LLM의 직접 계보로 읽으면 안 됩니다.

특히 Part 6 뒤쪽에서 다시 확인해야 하는 오해는 다음과 같습니다.

| 헷갈리기 쉬운 장면 | 더 정확한 구분 |
| --- | --- |
| 출처 링크가 있으니 곧바로 groundedness도 충분하다 | 링크 존재와 실제 해석 정확성은 다릅니다. |
| 자동 평가를 통과했으니 바로 서비스 품질도 충분하다 | 자동 점검과 사람 검토는 서로 다른 실패를 잡습니다. |
| 더 큰 모델이면 곧바로 더 좋은 서비스다 | 품질, 지연 시간, 비용, 처리량은 함께 봐야 합니다. |
| timeout과 hallucination은 둘 다 그냥 실패다 | 시스템 실패와 모델 실패는 대응 경로가 다릅니다. |

## 이 파트에서 끝내지 않는 질문

Part 6는 생성형 AI의 구조와 서비스 연결을 설명하는 데 집중했습니다. 따라서 다음 질문은 의도적으로 Part 7의 프로젝트 문맥으로 넘깁니다.

- 실제 데이터와 로그를 가지고 어떤 최소 기능을 먼저 만들 것인가?
- baseline, 개선 실험, 실패 기록을 어떤 문서와 산출물로 남길 것인가?
- 배포와 운영 검토를 어떤 순서로 프로젝트 문서에 반영할 것인가?

즉, Part 6는 `왜 이런 구조가 필요한가`를 설명하는 파트이고, Part 7은 그 구조를 실제 프로젝트 산출물로 확인하는 파트입니다.

이때 넘겨지는 가장 중요한 전환은 다음과 같습니다.

- Part 6에서는 `개념 이름`을 이해합니다.
- Part 7에서는 그 이름이 `어떤 기록 항목`으로 남아야 하는지 확인합니다.

예를 들어:

- tokenization은 입력 길이와 문맥 사용량 기록으로 남아야 합니다.
- RAG는 선택한 근거와 답변 연결 메모로 남아야 합니다.
- agent는 실행 단계와 승인 여부 기록으로 남아야 합니다.
- 운영 실패는 실패 원인과 다음 조치 기록으로 남아야 합니다.

여기서 특히 넘겨지는 실천 질문은 다음과 같습니다.

- 어떤 질문은 prompt만으로 닫히고 어떤 질문은 retrieval이나 tool이 필요한가?
- 검색 실패, 근거 부족, 실행 실패를 어떤 run record로 남길 것인가?
- 자동 평가와 사람 검토를 실제 프로젝트 문서 안에서 어떤 순서로 둘 것인가?

## 다음 파트와 연결되는 관점

Part 7에서는 지금까지 배운 내용을 작은 프로젝트로 다시 확인합니다. 따라서 Part 6의 마지막에서 가장 중요한 연결은 `개념 설명을 실제 산출물로 옮기는 기준`입니다.
