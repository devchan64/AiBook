# P6-1.2 토큰(token)은 무엇인가

Section ID: `P6-1.2`
Version: `v2026.07.12`

P6-1.1에서는 왜 LLM이 글자 수나 문장 수만으로는 다루기 어려운 문제를 만나고, 왜 다른 계산 단위가 필요한지 보았습니다. 이제 그 단위가 실제로 무엇인지 잡아야 합니다. 토큰(token)은 모델이 입력을 읽고 출력을 고를 때 세는 기본 계산 단위입니다.

이 절에서 붙잡아야 할 핵심은 세 가지입니다. 토큰은 단어와 항상 같지 않고, 모델은 토큰을 ID와 벡터로 바꿔 계산하며, 엔지니어링 관점에서는 바로 이 토큰 문자열, 토큰 수, 토큰 ID가 입력 해석의 첫 관찰값이 됩니다.

## 토큰은 무엇을 세는 단위인가

사람은 보통 글자 수, 단어 수, 문장 수로 입력을 봅니다. 하지만 모델은 이 단위들을 그대로 계산에 쓰지 않습니다. 먼저 입력을 더 작은 계산 조각으로 바꾸고, 그 조각들을 순서대로 읽습니다. 그 조각이 토큰입니다.

토큰은 모델이 입력과 출력을 다룰 때 세는 기본 계산 단위입니다.

## 토큰은 단어와 왜 다른가

토큰은 경우에 따라 다음처럼 보일 수 있습니다.

- 한 단어
- 단어 일부
- 공백을 포함한 짧은 조각
- 숫자와 기호가 섞인 조각
- 구두점까지 붙은 조각

즉, 토큰은 사람이 직관적으로 느끼는 `단어`와 항상 같지 않습니다. 같은 한 단어처럼 보여도 여러 토큰으로 쪼개질 수 있고, 반대로 짧은 조각 몇 개가 하나의 토큰처럼 처리될 수도 있습니다.

다음 표처럼 보면 차이가 더 분명합니다.

| 사람이 보는 단위 | 모델이 다시 묻는 질문 |
| --- | --- |
| 단어 하나인가 | 계산 조각이 몇 개인가 |
| 문장 한 줄인가 | 토큰 시퀀스로 어떻게 바뀌는가 |
| 같은 표현인가 | 계산 입력으로도 같은 조각인가 |

## 모델 안에서는 어떻게 쓰이나

토큰은 그대로 계산되지 않습니다. 모델은 보통 다음 흐름으로 입력을 다룹니다.

```mermaid
--8<-- "assets/part-06/chapter-01/p6-c01-s01-diagram-01-ko.mmd"
```

이 흐름에서 중요한 점은 두 가지입니다.

- 모델은 문장을 바로 이해하는 것이 아니라 먼저 토큰 시퀀스로 바꿉니다.
- 토큰은 이후 `ID -> 벡터` 변환을 거쳐야 실제 계산에 들어갑니다.

즉, 토큰은 그 자체로 완성된 의미 단위라기보다, 모델 계산이 시작되는 입구에 가깝습니다.

엔지니어링 관점에서 이 흐름이 중요한 이유는, 사람이 실제로 확인할 수 있는 값도 이 흐름을 따라 바뀌기 때문입니다.

| 사람이 실제로 확인하는 값 | 이 값이 뜻하는 것 |
| --- | --- |
| 토큰 문자열(token pieces) | 모델이 원문을 어떤 계산 조각으로 잘랐는가 |
| 토큰 수(token count) | 길이, 비용, 한도 판단의 기초값 |
| 토큰 ID(token ids) | 각 조각이 모델 내부 사전에서 어떤 번호로 다뤄지는가 |

즉, `토큰이 무엇인가`를 안다는 것은 용어 정의 하나를 외우는 일이 아니라, 나중에 tokenizer 출력이나 로그를 볼 때 무엇을 읽고 있는지 구분할 수 있다는 뜻입니다.

## 왜 이 구분이 실제로 중요한가

토큰을 `단어 비슷한 것` 정도로만 받아들이면, 뒤 절에서 반복해서 생기는 오해를 설명하기 어렵습니다.

- 왜 짧아 보이는 문장이 예상보다 길게 계산되는가
- 왜 같은 한 단어처럼 보여도 여러 조각으로 읽히는가
- 왜 모델은 문장을 바로 이해하는 것이 아니라 `ID -> 벡터` 변환을 먼저 거치는가

즉, 이 절의 목적은 토큰을 외우는 데 있지 않고, `모델은 무엇을 계산 입력으로 받는가`를 분명히 잡는 데 있습니다.

## 왜 이 정의가 엔지니어링 관점에서 중요한가

토큰을 `단어 비슷한 것`으로만 알면 뒤 절에서 비용과 길이를 읽을 때 자꾸 사람 기준으로 되돌아갑니다. 반대로 아래 세 층위를 구분해 두면, tokenizer 출력과 서비스 로그를 볼 때도 같은 기준으로 읽기 시작할 수 있습니다.

- 원문 문자열: 사람이 입력한 문장
- 토큰 문자열: 모델이 실제로 자른 계산 조각
- 토큰 수와 ID: 모델이 길이와 계산 준비에 쓰는 값

그래서 이 절은 정의 절이지만, 동시에 뒤의 엔지니어링 판단을 위한 입구이기도 합니다.

이 절에서 아직 하지 않아도 되는 일도 분명합니다.

- 특정 토크나이저를 구현할 필요는 없습니다.
- BPE, WordPiece, SentencePiece 차이를 외울 필요도 없습니다.
- 문장을 보고 정확한 토큰 수를 손으로 계산할 필요도 없습니다.

지금 필요한 수준은 다음 정도면 충분합니다.

- 토큰은 모델의 계산 단위다.
- 토큰은 단어와 항상 같지 않다.
- 모델은 토큰을 숫자와 벡터로 바꿔 계산한다.

이 세 가지가 잡혀야 다음 절에서 `토큰을 어떻게 읽고 사용해야 하는가`, 그다음 절에서 `토큰화가 무엇을 바꾸는가`를 자연스럽게 읽을 수 있습니다.

## 사례 및 예시

### 사례 1. 사람이 보는 단어와 토큰이 다를 때

사람은 `환불정책`이나 `Authorization` 같은 표현을 보통 한 단어처럼 읽습니다. 하지만 모델은 이런 표현을 항상 한 덩어리로 읽는다고 보장할 수 없습니다. 경우에 따라 더 작은 계산 조각으로 나눌 수도 있고, 반대로 자주 함께 나타나는 조각은 하나로 읽을 수도 있습니다.

이 사례에서 먼저 닫아야 할 문장은 이것입니다.

`토큰은 사람이 느끼는 단어와 항상 같지 않다.`

즉, 토큰은 국어 문법의 단어 정의가 아니라 모델이 실제 계산에 쓰는 조각입니다. 이 사례에서 엔지니어링 관점으로 정말 확인해야 할 값은 `사람이 단어라고 느끼는가`가 아니라 `tokenizer가 실제로 몇 조각으로 나누는가`입니다.

### 사례 2. 문장 하나가 토큰 시퀀스로 바뀔 때

`회의는 내일 10:00 AM입니다`를 사람은 일정 안내 한 문장으로 읽습니다. 하지만 모델은 이 문장을 그대로 계산하지 않습니다. 먼저 여러 조각의 순서열로 바꾸고, 그 순서열을 입력으로 받습니다.

입문 감각으로는 아래처럼 보면 충분합니다.

| 사람이 읽는 문장 | 모델 쪽에서 먼저 보는 것 |
| --- | --- |
| `회의는 내일 10:00 AM입니다` | `회의` / `는` / `내일` / `10:00` / `AM` / `입니다` 같은 토큰 시퀀스 |

여기서 중요한 것은 정확한 개수를 외우는 일이 아니라, 모델이 먼저 `문장 전체`가 아니라 `조각의 순서`를 입력으로 받는다는 점입니다.

이 사례에서 엔지니어링 관점으로 정말 확인해야 할 값은 `문장 의미를 사람이 어떻게 읽는가`가 아니라 `토큰 시퀀스가 어떤 순서로 만들어졌는가`입니다.

### 사례 3. 토큰은 바로 계산되는 것이 아닐 때

토큰은 계산의 출발점이지만, 토큰 문자열 자체가 그대로 계산되지는 않습니다. 모델은 먼저 토큰을 ID로 바꾸고, 그 ID를 다시 벡터로 바꾼 뒤 계산에 넣습니다.

같은 흐름을 가장 짧게 줄이면 다음과 같습니다.

| 단계 | 여기서 일어나는 일 |
| --- | --- |
| 문장 | 사람이 읽는 원문 문자열 |
| 토큰 시퀀스 | 모델이 읽을 계산 조각의 순서 |
| 토큰 ID | 각 조각에 붙은 숫자 |
| 벡터 | 실제 계산에 들어가는 표현 |

이 사례에서 초심자가 넘어가야 할 오해는 `모델이 문장을 통째로 읽는다`는 상상입니다. 실제로는 `문장 -> 토큰 시퀀스 -> ID -> 벡터` 흐름을 거쳐야 계산이 시작됩니다.

이 사례에서 엔지니어링 관점으로 정말 확인해야 할 값은 `토큰 문자열 자체`보다 `토큰 수`, `토큰 ID`, `벡터 변환 이전 단계가 어디까지인가`입니다.

같은 장면을 한 번 더 비교표로 줄이면 다음과 같습니다.

| 사람이 먼저 보는 것 | 이 절에서 다시 붙잡아야 하는 것 |
| --- | --- |
| 단어 하나다 | 모델 쪽에서는 여러 계산 조각일 수 있다 |
| 문장 한 줄이다 | 토큰 시퀀스로 바뀐 뒤 계산에 들어간다 |
| 문장을 바로 읽는다 | 토큰은 ID와 벡터를 거쳐 계산된다 |

## 바로 적용해 보면

이 절을 읽은 뒤에는 실제 tokenizer를 아직 돌리지 못하더라도, 아래처럼 `사람이 먼저 하는 말`을 `모델 기준 확인 질문`으로 바꿔 보는 연습을 할 수 있습니다.

| 지금 보는 장면 | 사람이 먼저 하기 쉬운 말 | 토큰 기준으로 먼저 바꿔 물을 말 |
| --- | --- | --- |
| 영어 단어 하나가 보인다 | 단어 하나니까 계산 조각도 하나일 것 같다 | tokenizer는 이 표현을 실제로 몇 조각으로 나누는가 |
| 일정 안내 한 문장이 있다 | 한 문장이니까 길이도 짧을 것 같다 | 토큰 수는 얼마나 되고, 숫자·기호·영문이 어디서 갈리는가 |
| tokenizer 출력에 숫자 목록이 보인다 | 복잡한 내부 값 같아서 그냥 넘어가고 싶다 | 이 숫자들은 어떤 토큰 조각 순서를 가리키는가 |

이 표에서 중요한 것은 정확한 값을 미리 맞히는 일이 아닙니다. 먼저 필요한 것은 `지금 내가 보는 것이 단어 뜻풀이인가, 계산 조각인가, 조각 개수인가, 번호화된 입력인가`를 구분하는 일입니다.

초심자가 여기서 자주 섞는 것도 바로 이 층위들입니다.

- 원문 문자열을 보고도 이미 모델 계산이 시작됐다고 느끼기 쉽습니다.
- 토큰 문자열을 보면 단어 뜻풀이처럼 받아들이기 쉽습니다.
- 토큰 ID를 보면 너무 내부 값 같아서 의미 없이 지나치기 쉽습니다.

하지만 뒤 절에서 길이, 비용, 청크 문제를 읽으려면 이 셋을 먼저 구분할 수 있어야 합니다.

## 연습 및 예제

이 절에서는 토큰화 종류를 비교하기 전에, `토큰 그 자체를 읽는 법`부터 직접 확인하는 편이 좋습니다. 같은 문자열을 tokenizer에 넣고 아래 세 값을 보는 것이 가장 기본적인 연습입니다.

- 토큰 문자열(token pieces)
- 토큰 수(token count)
- 토큰 ID(token ids)

예를 들어 `gpt2` 토크나이저 하나만 써도 충분합니다.

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("gpt2")

text = "회의는 내일 10:00 AM입니다."
pieces = tokenizer.tokenize(text)
ids = tokenizer.convert_tokens_to_ids(pieces)

print("TEXT:", text)
print("TOKENS:", pieces)
print("TOKEN COUNT:", len(pieces))
print("TOKEN IDS:", ids)
```

로컬에서 실제로 실행하면 `gpt2` 기준 이 문장은 31개 토큰으로 나뉘었고, `['Ġ10', ':', '00', 'ĠAM']`처럼 숫자와 영문 약어가 따로 보였습니다. 여기서 독자가 바로 읽어야 할 결과는 다음입니다.

| 출력에서 먼저 볼 것 | 여기서 이해해야 하는 뜻 |
| --- | --- |
| `TOKEN COUNT: 31` | 사람 눈에 한 문장이어도 모델 쪽에서는 더 긴 계산 입력일 수 있다 |
| `['Ġ10', ':', '00', 'ĠAM']` | 시간 표기 하나도 여러 계산 조각으로 갈릴 수 있다 |
| 긴 `TOKEN IDS` 목록 | 모델은 문자열 자체가 아니라 번호화된 조각 순서를 계산 준비에 쓴다 |

같은 연습을 영어 단어 하나에도 해 볼 수 있습니다.

```python
text = "tokenization"
pieces = tokenizer.tokenize(text)
ids = tokenizer.convert_tokens_to_ids(pieces)

print("TEXT:", text)
print("TOKENS:", pieces)
print("TOKEN COUNT:", len(pieces))
print("TOKEN IDS:", ids)
```

실행 결과에서는 `token`, `ization`처럼 나뉘는 모습을 볼 수 있습니다. 이때 확인해야 할 점은 `영어 단어 하나`라는 사람 감각과 `계산 조각 둘`이라는 모델 감각이 다를 수 있다는 사실입니다.

이 연습의 목표는 정확한 숫자를 외우는 데 있지 않습니다. 먼저 필요한 것은 tokenizer 출력에서 `지금 내가 보고 있는 것이 단어 뜻풀이가 아니라 계산 조각, 개수, 번호`라는 점을 분명히 구분하는 일입니다.

같은 내용을 마지막으로 한 번 더 줄이면 다음 세 질문에 바로 답할 수 있으면 충분합니다.

| 장면 | 먼저 답해야 하는 질문 |
| --- | --- |
| 토큰 문자열이 보인다 | 모델이 원문을 어떤 계산 조각으로 잘랐는가 |
| 토큰 수가 보인다 | 길이, 비용, 한도 판단에 어떤 영향을 줄 것인가 |
| 토큰 ID가 보인다 | 이 조각들이 모델 내부에서 어떤 번호 순서로 다뤄지는가 |

즉, 이 절의 닫힘은 `토큰이 무엇인가`를 사전식으로 외우는 데 있지 않고, tokenizer 출력에서 `조각`, `개수`, `번호`를 각각 무엇으로 읽는지 구분할 수 있게 되는 데 있습니다.

## 체크리스트

- 토큰을 `모델이 입력과 출력을 다룰 때 세는 기본 계산 단위`로 설명할 수 있는가?
- 토큰은 단어와 항상 같지 않다는 점을 말할 수 있는가?
- 모델이 토큰을 `ID -> 벡터`로 바꿔 계산한다는 점을 설명할 수 있는가?
- 토큰의 정확한 구현보다 `계산 단위`라는 역할을 먼저 붙잡아야 한다는 점을 이해했는가?
