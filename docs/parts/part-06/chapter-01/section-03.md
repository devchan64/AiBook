# P6-1.3 토큰은 어떻게 사용하나

Section ID: `P6-1.3`
Version: `v2026.07.18`

토큰을 계산 단위로 안다고 해서 바로 충분한 것은 아닙니다. 실제로는 이 단위를 어디에 써야 하는지가 더 중요합니다. 토큰 수는 LLM 서비스를 볼 때 `한도 안에 들어가는가`, `비용이 얼마나 드는가`, `무엇을 같은 문맥 안에 남길 것인가`를 판단하는 공통 눈금입니다.

이 절의 중심 질문은 하나입니다.

`토큰 수가 보이면 어떤 판단값을 먼저 바꿔야 하는가?`

앞으로 길이와 비용 이야기를 읽을 때는 자동으로 `지금 판단이 토큰 기준인가`를 먼저 떠올려야 합니다.

## 입력 길이 판단의 눈금

LLM에서는 보통 `문장을 몇 개 넣었는가`보다 `토큰을 몇 개 넣었는가`가 더 중요합니다. 파일이 하나여도 토큰 수가 많으면 중간이나 뒤가 잘릴 수 있고, 문장이 짧아 보여도 숫자·기호·영문 표기가 많으면 예상보다 긴 입력이 될 수 있습니다.

| 사람이 먼저 보는 것 | 토큰 관점에서 다시 보는 것 |
| --- | --- |
| 문장이 짧은가 | 실제 입력 토큰 수가 작은가 |
| 파일이 한 개인가 | 전체 토큰 길이가 한도 안에 들어오는가 |
| 문단이 보기 좋은가 | 필요한 문맥이 같은 토큰 묶음 안에 남는가 |

## context window는 남길 것과 나눌 것을 가르는 예산

context window는 모델이 한 번에 유지할 수 있는 입력과 출력의 총량을 토큰 기준으로 설명합니다. 그래서 긴 문서를 넣을 때는 `몇 페이지인가`보다 `끝까지 남길 토큰 예산이 있는가`를 먼저 봐야 합니다. 이 예산이 부족하면 문서를 나누거나, 덜 중요한 내용을 줄이거나, 출력 길이를 제한해야 합니다.

예를 들어 다음처럼 판단이 달라집니다.

| 장면 | 사람 기준 첫판단 | 토큰 기준 판단 |
| --- | --- | --- |
| 회의록 30쪽 한 파일 | 파일 하나니까 한 번에 넣을 수 있을 것 같음 | 전체 토큰 길이가 한도 안에 들어오는가 |
| 긴 대화 기록 뒤에 새 질문 추가 | 질문은 한 줄뿐이니 괜찮을 것 같음 | 앞 대화가 이미 예산 대부분을 쓰고 있지 않은가 |
| 규정 문서 여러 개를 같이 넣음 | 파일 수가 적으니 가능할 것 같음 | 각 문서의 토큰 길이를 합치면 얼마나 되는가 |

## 비용은 입력과 출력 토큰 수로 읽는다

많은 서비스가 입력과 출력 비용을 토큰 기준으로 설명합니다. 그래서 같은 한 줄 문장처럼 보여도 실제 토큰 수 차이가 나면 비용도 달라집니다.

가장 자주 쓰는 감각은 다음 정도입니다.

- 입력이 길어질수록 비용이 늘 수 있다.
- 출력 형식이 길어질수록 비용이 늘 수 있다.
- 짧아 보이는 문장도 표기 방식에 따라 더 비쌀 수 있다.

즉, 비용 문제는 `화면에서 몇 줄인가`보다 `실제로 몇 토큰인가`를 먼저 봐야 합니다.

## 문서 분할은 문맥 예산 배분 문제다

토큰 관점은 RAG나 검색용 청크를 나눌 때도 중요합니다. 사람은 문단 둘, 셋이면 적당하다고 느끼기 쉽지만, 실제로는 토큰 길이가 너무 길거나 핵심 조건이 서로 다른 조각으로 찢어질 수 있습니다. 이때 토큰 수는 `얼마나 많이 넣을 수 있는가`만이 아니라 `무엇을 함께 남길 것인가`를 정하는 기준이 됩니다.

그래서 청크를 볼 때는 보통 다음 두 질문이 먼저 붙습니다.

- 한 조각이 토큰 예산을 너무 빨리 먹지 않는가
- 원칙과 예외, 질문과 조건이 같은 조각 안에 남는가

## 출력 길이도 같은 예산을 쓴다

답변 형식을 길게 만들수록 출력 토큰도 늘어납니다. 표, 목록, 코드 블록, 부가 설명이 늘어나면 마지막 핵심 문장이 잘릴 가능성도 함께 커집니다.

예를 들어 배송 지연 안내에서 핵심은 `환불 조건`인데, 앞부분 설명을 너무 길게 쓰면 마지막 조건 문장이 출력 한도에서 잘릴 수 있습니다. 그래서 `무엇이 보기 좋은가`보다 `무엇을 끝까지 남겨야 하는가`를 먼저 봐야 합니다.

## 사례 및 예시

### 사례 1. 파일 하나인데 중간부터 답이 흔들릴 때

회의록 한 파일을 통째로 넣으면 사람은 `파일이 하나니까 괜찮다`고 느끼기 쉽습니다. 하지만 tokenizer나 서비스 로그에서 입력이 7,600 토큰으로 잡히고, 모델의 context window가 8,192 토큰이라고 해 봅시다. 답변에 800 토큰 정도가 더 필요하다면 전체 예산은 이미 부족합니다.

이 사례에서 확인해야 할 결과는 파일 수가 아니라 `전체 입력 토큰 길이 + 남겨야 할 출력 토큰 예산`을 먼저 봐야 한다는 점입니다. 그래야 문서를 나눌지, 앞부분을 줄일지, 출력 길이를 제한할지 판단할 수 있습니다.

### 사례 2. 짧은 문의인데 예상보다 비쌀 때

`회의는 내일 10:00 AM입니다`처럼 짧아 보이는 문장도 숫자와 영문 표기가 섞이면 실제 토큰 수는 사람의 한 줄 감각과 다를 수 있습니다. 더 중요한 것은 출력입니다. 짧은 문의라도 답변 형식이 표, 주의사항, 예시 문구를 계속 붙이면 출력 토큰이 입력보다 훨씬 커질 수 있습니다.

이 사례에서 확인해야 할 결과는 비용을 `화면에서 몇 줄인가`가 아니라 `입력 토큰 수 + 예상 출력 토큰 수`로 읽어야 한다는 점입니다. 비용이 빗나가면 먼저 출력 형식과 최대 출력 길이를 같이 봐야 합니다.

### 사례 3. 검색용 청크는 예쁜데 답이 자꾸 핵심 예외를 놓칠 때

문단 둘, 셋으로 자른 청크가 사람이 보기엔 깔끔해도, 질문과 조건, 원칙과 예외가 다른 토큰 묶음으로 찢어지면 검색 결과는 원칙만 가져오고 중요한 예외를 놓칠 수 있습니다. 예를 들어 청크 크기를 500 토큰으로 잡았는데 원칙 설명이 430 토큰, 예외 설명이 160 토큰이라면 둘은 쉽게 갈라집니다.

이 사례에서 확인해야 할 결과는 문단 모양보다 `같은 토큰 묶음 안에 함께 남겨야 할 문맥`을 먼저 봐야 한다는 점입니다. 이 값이 보이면 chunk size나 overlap을 조정할 이유가 생깁니다.

같은 장면을 운영 메모처럼 다시 줄이면 다음과 같습니다.

| 먼저 보이는 현상 | 토큰 기준으로 다시 묻는 질문 | 바로 조정할 값 |
| --- | --- | --- |
| 파일 하나니까 한 번에 넣어도 될 것 같음 | 입력과 출력 토큰을 합쳐도 context window 안에 남는가 | 입력 분할 기준, 출력 예산 |
| 짧은 문장이니 비용도 작을 것 같음 | 입력보다 출력 토큰이 더 크게 늘고 있지 않은가 | 비용 추정식, 답변 형식 |
| 문단이 깔끔하니 청크도 괜찮을 것 같음 | 핵심 문맥이 같은 토큰 묶음 안에 남는가 | chunk size, overlap |

## 바로 적용해 보면

아래 세 장면에서 먼저 고를 질문을 바꿔 보면, 토큰이 실제로 어디에 쓰이는지 더 빨리 잡힙니다.

| 장면 | 먼저 버릴 질문 | 대신 먼저 붙잡을 질문 |
| --- | --- | --- |
| 긴 문서를 넣는다 | 파일이 몇 개인가 | 끝까지 남길 토큰 예산이 실제로 충분한가 |
| 비용이 자주 튄다 | 화면에서 몇 줄인가 | 입력과 출력 토큰 수가 각각 얼마나 되는가 |
| 검색 답이 예외를 놓친다 | 문단 모양이 깔끔한가 | 질문과 조건, 원칙과 예외가 같은 청크 안에 남는가 |

이 절에서 필요한 적용 수준은 복잡한 계산식이 아니라, 장면마다 `먼저 물어야 할 질문`을 토큰 기준으로 바꾸는 일입니다.

## 여기서 닫을 판단 기준

토큰은 단순 개념어가 아니라 길이, 비용, 문맥, 청크, 출력 제한을 읽는 실무 기준입니다. 지금 닫아야 할 질문은 `토큰화가 어떤 규칙으로 일어나는가`가 아니라, 이미 주어진 토큰 수를 어디에 쓰는가입니다.

다음 절에서는 한 걸음 더 나아가, 텍스트를 어떤 절차로 토큰 시퀀스로 바꾸는지 봅니다.

## 연습 및 예제

아래 세 장면을 보고, 먼저 조정할 판단값을 직접 고릅니다.

| 관찰한 값 | 먼저 조정할 판단값 | 이유 |
| --- | --- | --- |
| 입력 7,600 토큰, 예상 출력 800 토큰, context window 8,192 토큰 | 입력 분할 또는 출력 예산 | 합계가 한 번에 유지할 수 있는 예산을 넘기 때문입니다. |
| 입력 120 토큰, 예상 출력 1,200 토큰 | 답변 형식과 최대 출력 길이 | 비용과 길이는 입력만이 아니라 출력 토큰에서도 커지기 때문입니다. |
| 원칙 430 토큰, 예외 160 토큰, chunk size 500 토큰 | chunk size와 overlap | 원칙과 예외가 같은 문맥 안에 남지 못할 수 있기 때문입니다. |

이 연습의 목표는 토큰화 규칙을 맞히는 것이 아닙니다. 토큰 수가 관찰값으로 주어졌을 때 길이, 비용, 문맥 보존 중 어떤 판단값을 먼저 바꿔야 하는지 고르는 것입니다.

## 체크리스트

- 길이 제한 문제를 문장 수가 아니라 토큰 수 문제로 읽을 수 있는가?
- 비용 문제를 글자 수가 아니라 입력·출력 토큰 수 문제로 읽을 수 있는가?
- 긴 문서 입력에서 파일 수보다 전체 토큰 길이를 먼저 봐야 한다는 점을 설명할 수 있는가?
- 청크 설계에서 보기 좋은 문단보다 토큰 길이와 문맥 보존을 함께 봐야 한다는 점을 설명할 수 있는가?
