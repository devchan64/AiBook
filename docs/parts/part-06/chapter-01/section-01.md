# P6-1.1 왜 토큰이 필요한가

Section ID: `P6-1.1`
Version: `v2026.07.18`

LLM(large language model)을 실제로 쓰기 시작하면 곧바로 다른 질문이 생깁니다. 왜 어떤 입력은 예상보다 비싸고, 왜 긴 문서는 중간에 잘리며, 왜 같은 한 줄 문장도 표기 방식에 따라 길이 감각이 달라지는가 하는 질문입니다.

모델은 글자 수나 문장 수가 아니라 토큰 수를 기준으로 입력을 다룹니다.

즉, 토큰은 먼저 `정의`로 들어오는 개념이 아니라, 길이 제한, 비용, 잘림, 입력 분할 문제를 설명하기 위해 필요한 계산 단위로 들어옵니다.

## 왜 글자 수나 문장 수로는 부족한가

사람은 입력을 보통 다음처럼 읽습니다.

- 문장이 짧은가
- 파일이 몇 개인가
- 문단이 몇 개인가
- 화면에서 얼마나 길어 보이는가

하지만 모델은 이런 단위를 그대로 계산에 쓰지 않습니다. 그래서 사람 기준으로는 비슷한 입력도, 모델 쪽에서는 전혀 다른 길이와 다른 비용으로 읽힐 수 있습니다.

예를 들면 다음과 같습니다.

| 사람 기준 질문 | 실제로 다시 봐야 하는 질문 |
| --- | --- |
| 문장이 짧은가 | 실제 입력 토큰 수가 작은가 |
| 파일이 한 개인가 | 전체 입력이 토큰 한도 안에 들어오는가 |
| 문단이 보기 좋은가 | 필요한 문맥이 같은 조각 안에 남는가 |

여기서 핵심은 `사람이 먼저 세는 단위`와 `모델이 실제로 계산하는 단위`가 다를 수 있다는 점입니다.

## 어떤 문제들이 여기서 생기나

토큰 관점이 필요한 문제는 보통 다음 장면에서 먼저 드러납니다.

### 1. 입력 길이 제한

긴 문서를 넣으면 사람은 `파일 하나니까 한 번에 읽겠지`라고 생각하기 쉽습니다. 하지만 모델은 파일 개수가 아니라 전체 입력 길이를 계산 단위 기준으로 읽기 때문에, 뒤쪽 결론이나 예외 조항이 잘릴 수 있습니다.

### 2. 비용

짧아 보이는 문장도 숫자, 기호, 영문 표기, URL이 섞이면 실제 입력 비용은 더 빨리 커질 수 있습니다. 그래서 `짧은 공지니까 싸겠지`라는 직관이 자주 빗나갑니다.

### 3. 문맥 보존

RAG나 검색용 청크를 자를 때 사람은 문단 수를 먼저 보지만, 실제로는 질문과 조건, 원칙과 예외가 같은 입력 묶음 안에 남는지가 더 중요합니다. 이 문제도 결국 계산 단위를 무엇으로 보느냐와 연결됩니다.

같은 장면을 실무 판단처럼 다시 묶으면 다음과 같습니다.

| 상황 | 사람이 먼저 세는 것 | 모델 쪽에서 먼저 보는 것 | 바로 달라지는 판단 |
| --- | --- | --- | --- |
| 짧은 한 줄 질문 | 문장 수, 글자 수 | 실제 토큰 수 | 예상 비용과 입력 길이 |
| 긴 문서 한 파일 | 파일 수, 페이지 수 | 전체 토큰 길이 | 통째 입력 가능 여부 |
| 검색용 문단 분할 | 문단 수, 보기 좋은 길이 | 같은 조각 안의 문맥 보존 | 청크 설계와 회수 품질 |

## 사례 및 예시

### 사례 1. 같은 한 줄인데 비용 감각이 달라질 때

`오늘 날씨가 좋다`와 `오늘 날씨가 정말 좋다 :)`는 사람 눈에는 둘 다 짧은 한 줄입니다. 하지만 모델 쪽에서는 `정말`, 이모지, 기호 같은 조각이 추가되면서 실제 계산 길이가 달라질 수 있습니다.

이 장면에서 넘어가야 할 오해는 `한 줄이면 다 비슷한 길이`라는 감각입니다. 여기서 정말 확인해야 할 점은 `사람 눈에 짧은가`가 아니라 `모델이 몇 개의 계산 조각으로 읽는가`입니다.

| 입력 장면 | 사람 기준 첫인상 | 토큰 관점에서 다시 봐야 하는 것 |
| --- | --- | --- |
| `오늘 날씨가 좋다` | 짧은 한 줄 | 계산 조각 수의 기준선 |
| `오늘 날씨가 정말 좋다 :)` | 여전히 짧은 한 줄 | 강조 표현과 기호가 토큰 수를 늘리는가 |
| `회의는 내일 10:00 AM입니다` | 짧은 일정 안내 | 숫자와 영문 표기가 얼마나 더 잘게 갈리는가 |

### 사례 2. 파일 하나인데 끝까지 안 읽힐 때

회의록 30쪽을 통째로 넣으면 사람은 `파일 하나니까 한 번에 읽겠지`라고 생각하기 쉽습니다. 하지만 모델은 파일 개수가 아니라 그 안의 긴 토큰 시퀀스를 읽습니다. 표, 숫자 목록, 부록이 많으면 사람이 느끼는 분량보다 토큰 수가 더 빨리 늘 수 있고, 뒤쪽 결론이 잘릴 수도 있습니다.

여기서 바뀌는 기준은 `문서 개수`에서 `끝까지 남길 토큰 예산`으로 옮겨갑니다. 정말 확인해야 할 점도 `파일이 몇 개인가`가 아니라 `끝까지 남길 토큰 예산이 실제로 충분한가`입니다.

| 문서 장면 | 사람 기준 첫판단 | 토큰 관점에서 바뀌는 판단 |
| --- | --- | --- |
| 회의록 30쪽 한 파일 | 파일 하나니까 한 번에 읽힐 것 같음 | 전체 토큰 길이가 한도 안에 들어오는가 |
| 표와 부록이 많은 보고서 | 페이지 수는 비슷해 보임 | 표기 요소가 토큰을 더 빨리 늘리는가 |
| 결론이 마지막에 몰린 문서 | 끝까지 넣었으니 결론도 읽었을 것 같음 | 뒤쪽 핵심 결론이 잘리지 않았는가 |

### 사례 3. 보기 좋은 문단인데 검색이 틀릴 때

RAG용 청크를 나눌 때도 사람은 `문단 둘이면 적당하다`고 느끼기 쉽습니다. 하지만 `원칙` 문단과 `예외` 문단이 서로 다른 토큰 묶음으로 갈라지면 검색은 원칙만 가져오고 중요한 예외를 놓칠 수 있습니다.

그래서 이 장면에서는 `문단이 예쁜가`보다 `질문과 조건, 원칙과 예외가 같은 입력 묶음 안에 남는가`를 먼저 봐야 합니다. 정말 확인해야 할 점도 `문단 모양이 자연스러운가`가 아니라 `필요한 문맥이 같은 계산 조각 안에 남는가`입니다.

## 바로 적용해 보면

아직 실제 토큰 수를 세지 못하더라도, 아래처럼 `사람 기준 질문`을 `모델 기준 질문`으로 바로 바꿔 보는 연습은 할 수 있습니다.

| 지금 보는 입력 | 사람 기준으로 먼저 하기 쉬운 말 | 토큰 관점에서 먼저 바꿔 물을 말 |
| --- | --- | --- |
| 공지 한 줄 | 짧으니 비용도 작겠다 | 숫자, 기호, 영문이 섞여 실제 토큰 수가 늘지 않는가 |
| 회의록 한 파일 | 파일 하나니까 통째로 읽히겠다 | 전체 토큰 길이가 한도 안에 들어오는가 |
| 규정 문단 두 개 | 문단이 깔끔하니 청크도 괜찮겠다 | 원칙과 예외가 같은 토큰 묶음 안에 남는가 |

이 표에서 중요한 것은 정답 숫자를 맞히는 일이 아니라, `무엇을 먼저 세야 하는가`를 바꾸는 일입니다.

같은 기준을 더 짧게 연습하면 다음처럼 읽을 수 있습니다.

| 지금 보이는 문제 | 먼저 떠올려야 할 토큰 관점 |
| --- | --- |
| 답변이 갑자기 비싸게 느껴진다 | `겉보기 길이`가 아니라 `실제 토큰 수`를 먼저 본다 |
| 긴 문서 끝부분이 자꾸 빠진다 | `파일 수`가 아니라 `전체 토큰 길이`를 먼저 본다 |
| 검색 답이 예외를 자꾸 놓친다 | `문단 모양`이 아니라 `같은 토큰 묶음 안의 문맥 보존`을 먼저 본다 |

초심자 기준에서는 이 세 줄을 바로 말할 수 있으면 충분합니다. 아직 정확한 토큰 수를 셀 수 없어도, 적어도 `지금 길이 문제인가`, `비용 문제인가`, `문맥 보존 문제인가`, 그리고 그 셋을 모두 결국 토큰 기준으로 다시 읽어야 하는가`를 구분하기 시작한 것입니다.

같은 작업이라도 토큰 수가 달라지면 무엇이 먼저 달라지는지 더 짧게 붙잡으면 다음처럼 볼 수 있습니다.

| 같은 작업 장면 | 토큰 수가 비교적 작을 때 | 토큰 수가 더 커질 때 먼저 의심할 것 |
| --- | --- | --- |
| 짧은 공지 한 줄 보내기 | 비용과 지연이 크게 문제 되지 않을 수 있음 | 숫자, 기호, 영문 표기 때문에 예상보다 비용이 먼저 늘지 않는가 |
| 긴 회의록 전체 넣기 | 핵심 결론까지 한 번에 남길 여지가 있음 | 뒤쪽 결론이 잘리거나 요약 전에 분할이 필요한가 |
| 규정 검색용 청크 만들기 | 원칙과 예외를 같은 묶음에 둘 여지가 있음 | 예외 문단이 다른 청크로 밀려 검색 답이 흔들리지 않는가 |

이 표의 목적은 정확한 임계값을 외우게 하는 데 있지 않습니다. 초심자가 `토큰 수가 달라지면 가장 먼저 어떤 실패가 바뀌는가`를 장면별로 떠올리게 만드는 데 있습니다.

## 그래서 토큰이 등장한다

이 지점에서 필요한 것이 토큰(token)입니다. 토큰은 모델이 입력과 출력을 다룰 때 세는 계산 단위입니다.

앞의 세 사례가 모두 말하고 싶은 것도 사실은 하나입니다.

- 짧은 문장 비용 문제에서는 `몇 글자인가` 대신 `몇 토큰인가`를 세야 합니다.
- 긴 문서 잘림 문제에서는 `파일이 몇 개인가` 대신 `전체 토큰 길이`를 봐야 합니다.
- 검색 청크 문제에서는 `문단이 예쁜가` 대신 `같은 토큰 묶음 안에 무엇이 남는가`를 봐야 합니다.

즉, 토큰은 새 용어를 하나 더 배우기 위해 등장하는 것이 아닙니다. 사람이 먼저 보던 길이 감각으로는 설명이 안 되는 문제들을, 모델 기준 계산 단위로 다시 읽기 위해 등장합니다.

- 사람 기준 길이 감각만으로는 LLM 입력 문제를 설명하기 어렵다.
- 그래서 모델 기준 계산 단위가 필요하다.
- 그 단위가 토큰이다.

토큰 자체가 정확히 무엇이고, 단어와 어떻게 다르며, 모델 안에서 어떻게 계산되는지는 다음 절 P6-1.2에서 이어집니다. 지금 단계에서는 `사람이 보던 길이 감각`이 아니라 `모델이 세는 계산 단위`를 먼저 떠올릴 수 있으면 충분합니다.

같은 내용을 마지막으로 한 번 더 줄이면, 이 절에서 독자가 바로 답할 수 있어야 하는 질문은 다음 정도입니다.

| 장면 | 먼저 답해야 하는 질문 |
| --- | --- |
| 짧아 보이는 문장이 예상보다 비싸다 | 사람 기준 짧음이 아니라 실제 토큰 수를 보고 있는가 |
| 파일 하나인데 끝까지 안 읽힌다 | 파일 개수보다 전체 토큰 길이를 보고 있는가 |
| 보기 좋은 청크인데 검색 답이 흔들린다 | 문단 모양보다 같은 토큰 묶음 안의 문맥 보존을 보고 있는가 |

즉, 이 절의 닫힘은 `토큰`이라는 이름을 아는 데 있지 않고, 길이·비용·잘림·청크 문제를 볼 때 `사람 기준 길이` 대신 `모델 기준 계산 단위`를 먼저 떠올릴 수 있게 되는 데 있습니다.

## 체크리스트

- 왜 글자 수나 문장 수만으로는 LLM 입력 문제를 설명하기 어려운지 말할 수 있는가?
- 길이 제한, 비용, 문맥 보존 문제가 모두 다른 계산 단위를 요구한다는 점을 이해했는가?
- 토큰이 먼저 `문제 해결을 위한 계산 단위`로 등장한다는 점을 설명할 수 있는가?
