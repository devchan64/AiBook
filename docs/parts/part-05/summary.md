# Part 5 마무리. LLM과 생성형 AI 정리

Part 5는 생성형 AI를 `대단한 답변기`처럼 소비하는 단계에서 한 걸음 더 나아가, LLM(large language model)이 어떤 입력 단위를 읽고, 어떤 구조 위에서 학습되며, 어떤 서비스 구조 안에서 실제로 동작하는지 다시 묶는 구간이었습니다.

이 Part의 핵심은 LLM을 단지 `말을 잘하는 모델`로 보는 데서 멈추지 않는 것입니다. 토큰(token), 임베딩(embedding), Transformer, 사전학습(pretraining), 파인튜닝(fine-tuning), RAG, 도구 사용(tool use), 에이전트(agent), 평가(evaluation), 운영 제약(constraints)까지 이어지는 흐름을 함께 볼 때 비로소 생성형 AI의 실제 구조가 보입니다.

## 이 Part에서 다룬 핵심 흐름

Part 5의 흐름은 다음처럼 정리할 수 있습니다.

> 토큰(token)과 토큰화(tokenization)
> -> 임베딩(embedding)과 의미 공간
> -> LLM의 발전사와 Transformer 구조
> -> 사전학습, 다음 토큰 예측, 파인튜닝, 정렬
> -> 프롬프트(prompt), RAG, 벡터 데이터베이스
> -> 도구 사용(tool use), 함수 호출(function calling), 에이전트(agent)
> -> MCP(Model Context Protocol), 하네스(harness)
> -> 평가, 자동 평가, 사람 평가
> -> 서비스 제약, 실패 대응, 운영 관점

이 흐름은 `모델 자체`와 `모델을 둘러싼 시스템`을 분리해서 읽게 해 줍니다. Part 5를 읽고 나면 프롬프트를 잘 쓰는 일과, 검색을 붙이는 일과, 도구를 호출하는 일과, 운영 중 실패를 기록하는 일이 서로 다른 층위(level)의 문제라는 점이 분명해져야 합니다.

## 반드시 기억할 개념

Part 5에서 특히 오래 남겨야 할 개념은 다음과 같습니다.

| 구분 | 기억할 관점 |
| --- | --- |
| 토큰 | 모델은 사람이 보는 문장 전체가 아니라 토큰 단위로 입력과 출력을 읽습니다. |
| 임베딩 | 임베딩은 기호(symbol)를 의미 비교가 가능한 벡터(vector)로 바꾸는 표현입니다. |
| Transformer | 현재 LLM의 중심 구조는 self-attention과 병렬 계산 위에 서 있습니다. |
| 사전학습 | LLM은 대규모 데이터에서 다음 토큰 예측을 통해 언어 패턴을 먼저 익힙니다. |
| 파인튜닝과 정렬 | 모델을 특정 과업(task)이나 지시(instruction)에 더 맞게 조정하는 단계가 따로 있습니다. |
| 프롬프트 | 프롬프트는 입력을 잘 구성하는 방법이지, 모델 자체의 지식을 새로 학습시키는 과정은 아닙니다. |
| RAG | RAG는 모델 내부 기억을 늘리는 것이 아니라, 외부 근거를 검색해 입력 문맥으로 연결하는 구조입니다. |
| 벡터 검색 | 의미적으로 가까운 문서를 찾는 방식이지만, 검색 품질은 임베딩 품질과 인덱스 구조에 함께 좌우됩니다. |
| 에이전트 | 에이전트는 목표를 여러 단계의 계획, 행동, 관찰 흐름으로 연결하는 실행 구조입니다. |
| MCP와 하네스 | MCP는 도구 연결 인터페이스를, 하네스는 실행·평가·기록 환경을 정리하는 관점입니다. |
| 평가와 운영 | 좋은 답변 예시와 좋은 서비스 운영은 같은 말이 아닙니다. 품질, 비용, 지연 시간, 실패 대응을 함께 봐야 합니다. |

## 오해하기 쉬운 지점

Part 5에서는 특히 다음 오해를 조심해야 합니다.

- LLM을 곧 AI 전체라고 보면 안 됩니다.
- 프롬프트(prompt)와 파인튜닝(fine-tuning)을 같은 것으로 읽으면 안 됩니다.
- RAG를 `모델이 외부 사실을 완전히 이해한 상태`로 오해하면 안 됩니다.
- 도구 사용(tool use)이 붙었다고 해서 자동으로 에이전트(agent)가 되는 것은 아닙니다.
- MCP를 하나의 제품 이름이나 특정 벤더 전용 기능처럼 읽으면 안 됩니다.
- 하네스(harness)를 단일 도구 이름으로 고정하면 안 됩니다.
- 자동 평가 점수 하나만 높다고 실제 사용자 경험이 바로 좋아지는 것은 아닙니다.
- 생성 품질이 좋아 보여도 비용(cost), 지연 시간(latency), 권한(permission), 실패 처리(failure handling)가 준비되지 않으면 서비스 완성이라고 보기 어렵습니다.

- MCP와 하네스를 `실행 환경 정리` 관점으로 설명할 수 있는가?
- 모델 품질과 서비스 품질이 항상 같은 말이 아니라는 점을 설명할 수 있는가?

## Part 5를 마치며

Part 5를 마쳤다면 이제 생성형 AI 설명을 들을 때 무엇이 모델 내부 구조의 문제이고, 무엇이 서비스 설계의 문제이며, 무엇이 운영과 평가의 문제인지 구분할 수 있어야 합니다.
