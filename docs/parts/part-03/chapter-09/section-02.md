# P3-9.2 어떤 문제는 왜 끝까지 비교 리포트로 남겨야 하는가

> Section ID: `P3-9.2`
> Version: `v2026.09.20`

“지금 유량이 기준과 얼마나 다른가?”에 답하려면 관측값과 비교 근거가 필요합니다. 반드시 미래 고장 예측까지 붙여야 하는 것은 아닙니다. [비교 리포트](../../../reference/concept-glossary-parts/05-mieum.md#output-structure)는 관측 차이와 그 한계를 전달하는 산출물입니다. 이 질문을 충족했다면 예측으로 바꾸지 않아도 완성된 결과이며, 목적이 유지되는 동안 계속 사용할 수 있습니다.

## 리포트 한 행에서 확인할 수 있는 것

[P3-8.4](../chapter-08/section-04.md)의 가상 A행을 다시 사용합니다. 한 행은 최근 완료 동작 20건을 묶은 비교 구간입니다. 필요한 측정값이 있고 기준선과 최근의 유형·운전 조건·단위·구간 정의가 같으며, 별도 허용 한계 위반이 없다는 당시의 적용 가정도 유지합니다.

| 항목 | A행의 값 | 뜻 |
| --- | --- | --- |
| window_id | A | 비교 구간 식별자 |
| diff | −0.35 L/min | 최근 동작별 후반 평균의 평균−기준선의 같은 평균 |
| event_count | 20 | 최근의 서로 다른 완료 동작 수 |
| decline_count | 14 | 후반 평균−초반 평균 ≤ −0.30 L/min인 동작 수 |
| decline_ratio | 14/20=0.70 | 해당 하강 조건을 충족한 비율 |
| cause_label | 미확인 | 확정 원인 기록을 아직 확보하지 못함 |

하강 조건은 경계값을 포함하며 동작당 한 번만 셉니다. 기준선과의 차이 −0.35와 동작 내부 하강 판정 −0.30은 비교 대상이 다릅니다. `cause_label`이 미확인이라는 것은 원인이 없거나 정상이라는 뜻이 아닙니다.

리포트의 관측 문장은 “최근 20건의 후반 평균은 기준보다 0.35 L/min 낮고, 동작 내부 하강 조건은 14/20건이 충족했다”입니다. 여기에 “발생 순서와 원인은 미확인”이라는 한계를 붙일 수 있습니다. 70%를 고장 확률로 바꾸거나 14회 연속 하강이라고 쓰지는 않습니다.

## 운영 판단을 붙일 때는 사용한 정책도 적기

같은 행에 `review-v1`을 적용하면 `−0.35 ≤ −0.30`이고 `0.70 ≥ 0.60`이므로 R1입니다. 따라서 `warning_level=caution`, `review_needed=1`, `priority_band=first`를 기록합니다. 이 값은 P3-8.4의 가상 검토 배정 규칙에서 나온 것으로, 원인 라벨이나 고장 확률을 계산한 결과가 아닙니다.

| 리포트에 남길 부분 | A에서 쓸 내용 |
| --- | --- |
| 관측 근거 | diff=−0.35 L/min, 하강 조건 충족 14/20건 |
| 해석 한계 | 시간 순서와 원인 미확인 |
| 정책 적용 | review-v1의 R1에 따라 우선 검토 배정 |
| 다음 확인 | 해당 20건의 시간순 원기록과 동작별 설정 이력 대조 |

리포트는 이렇게 현재 차이를 설명하고 구체적인 확인 행동을 뒷받침할 수 있습니다. 반면 정책이 없는 상태에서 “차이가 크니 검토 우선순위가 높다”고 자동으로 덧붙이면 관측과 배정 판단을 섞게 됩니다. 순서가 있는 검토 큐는 리포트에 담은 근거를 사용할 수 있지만 별도의 정책 산출물입니다.

## 원인을 모르는 것과 미래 결과를 모르는 것은 다르다

`cause_label`이 없으면 이 자료만으로 **확정 원인 분류를 학습**하기는 어렵습니다. 그러나 모든 예측 질문이 막히는 것은 아닙니다. 과거 동작마다 종료 시점에 이용 가능했던 입력과 그 뒤 7일의 고장 여부가 일관되게 연결되어 있다면, 원인 이름 없이도 “7일 안에 고장이 발생하는가?”라는 지도학습 질문을 별도로 검토할 수 있습니다.

여기서 라벨을 요구하는 설명은 **지도학습 예측**에 관한 것입니다. 모든 분석이나 모든 머신러닝 방식에 확정 결과 라벨이 반드시 필요하다는 뜻은 아닙니다. 또한 `review_needed`는 운영 정책의 결과이므로, 그것을 고장 여부의 정답으로 바꾸면 무엇을 학습하는지 달라집니다.

| 구분 | 현재 비교 리포트 | 7일 고장 여부의 지도학습 예측 |
| --- | --- | --- |
| 질문 | 이미 관측한 최근 구간이 기준과 얼마나 다른가 | 동작 종료 시점에 이후 7일 결과를 추정할 수 있는가 |
| 한 사례의 단위 | 여러 동작을 묶은 비교 구간 A | 결과 라벨이 연결되는 개별 동작 |
| 필요한 기록 | 측정 정의·기준선·최근 집계와 적용 정책 | 동작 ID·종료 시점 입력·결과 기간·확정 결과·관측 완료 여부 |
| 확인할 품질 | 계산·비교 조건·설명과 정책 적용의 정합성 | 목표 정의·라벨 범위와 신뢰성·학습에 쓰지 않은 사례의 평가 |

현재 A행에는 개별 동작과 연결된 7일 결과가 없습니다. 구간의 `decline_ratio=0.70`을 복사해 각 동작의 미래 고장 라벨로 만들 수는 없습니다. 필요한 개별 기록을 확보했는지 별도로 확인해야 합니다. 결과 기간의 시작·끝 포함 규칙과 추적 누락도 정의하고, 미완료 관측을 비고장 0으로 채우지 않습니다.

미래 예측이 목적이라면 리포트가 대신 그 질문에 답했다고 하지는 않습니다. 반대로 이미 충족한 비교 질문을 라벨 부족 때문에 실패한 예측 과제로 부를 필요도 없습니다. 비교 리포트를 유지하면서 필요한 결과 기록을 모아 별도의 예측 문제를 준비할 수 있습니다.

## 두 요청을 나누어 답하기

A행을 보고 ① “최근 변화와 오늘 확인할 일을 정리해 달라”, ② “A에 속한 각 동작이 이후 7일 안에 고장 나는지 예측해 달라”라는 요청을 받았습니다. 현재 자료로 쓸 수 있는 답과 추가로 필요한 기록을 구분해 보세요.

해설: ①에는 −0.35 L/min, 14/20건, 원인 미확인을 적고 review-v1의 R1과 원기록·설정 이력 확인을 연결할 수 있습니다. ②에는 현재 구간 요약만으로는 부족합니다. 개별 동작 ID, 예측 시점 입력, 일관된 7일 결과와 관측 완료 상태, 학습과 분리된 평가 자료를 확인해야 합니다. 원인 이름이 없다는 사실만으로 ②가 불가능하다고 결론 내리지는 않습니다.

## 체크리스트
