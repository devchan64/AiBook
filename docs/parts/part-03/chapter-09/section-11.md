# P3-9.11 타깃 후보와 변하는 기준

> Section ID: `P3-9.11`
> Version: `v2026.09.20`

같은 샘플에 검토 필요 여부, 점검 후 상태, 처리 우선순위가 함께 기록될 수 있습니다. 이 열들은 서로 다른 질문에 답합니다. 이번에 무엇을 [타깃](../../../reference/concept-glossary-parts/12-tieut.md#target)으로 학습할지 선택하는 일과, 그 타깃을 어떤 기준으로 판정했는지 기록하는 일을 나누어 보겠습니다.

## 같은 행에 있어도 같은 정답은 아니다

아래는 이 절의 가상 완료 동작 A·B·C입니다. `review_needed`는 정해진 검토 기준에 따른 필요 여부이고, `final_status`는 점검 범위 안에서 확인한 최종 상태입니다. 최종 상태의 정의는 `inspection-status-v1`이며 점검 완료 후 이상이 확인되면 `abnormal`, 확인되지 않으면 `normal`로 기록합니다. `normal`은 이후 고장까지 없다는 뜻이 아닙니다.

| event_id | `review_needed` | `final_status` | `label_status` |
| --- | ---: | --- | --- |
| A | 1 | ? | pending |
| B | 1 | normal | confirmed |
| C | 0 | normal | confirmed |

이 교육용 표는 세 동작 모두 점검 대상에 포함되었다고 가정합니다. 검토 필요 0인 C도 별도 점검을 완료했기 때문에 `normal`이 있습니다. 검토 필요 0을 그대로 정상으로 복사한 것이 아닙니다. A의 `pending`은 결과가 아니라 확인 상태이므로 `normal`·`abnormal`과 나란한 최종 결과 범주로 학습시키지 않습니다.

검토 기준의 판단을 재현하려면 A와 B의 `review_needed=1`이 같은 답입니다. 반면 동작 완료 시점의 정보로 이후 점검 상태를 예측하려면 `final_status`가 타깃이며 A의 정답은 아직 없습니다. B와 C의 `normal` 두 건만으로 학습 자료가 충분하다고 결론 내릴 수도 없습니다. 입력은 점검 전 시점의 정보로 제한하고, 점검 결과를 입력에 넣지 않습니다.

이 절에서는 “점검 후 상태를 예측한다”를 대표 질문으로 선택하므로 `target_name=final_status`, `target_definition_version=inspection-status-v1`을 적습니다. 검토 여부와 처리 순위는 별도 열로 보존합니다. 대표 타깃은 이번 학습·평가에서 답할 질문을 정한 것입니다. 다른 질문이나 여러 결과를 함께 예측하는 설계도 가능하며, 그때는 각 결과의 정의·관측 조건·평가를 따로 명시해야 합니다.

## 같은 관측에 기준 두 개를 적용하면

이번에는 검토 필요 기준만 바뀌는 별도 사례 X를 보겠습니다. 입력 `recent_diff`는 같은 조건의 최근 평균 유량에서 기준선 평균 유량을 뺀 값이며 단위는 L/min입니다. 원자료·집계 구간·기준선·계산 버전을 고정한 X의 값은 `-0.25`입니다. 아래 규칙은 교육용이며 실제 안전 기준이 아닙니다.

| 검토 정의 버전 | 적용 시작 시각(KST) | `review_needed`를 만드는 규칙 | 같은 X=-0.25의 결과 |
| --- | --- | --- | ---: |
| `review-rule-v1` | 2026-09-01 00:00 | `recent_diff <= -0.30`이면 1, 아니면 0 | 0 |
| `review-rule-v2` | 2026-09-15 00:00 | `recent_diff <= -0.20`이면 1, 아니면 0 | 1 |

두 기준 모두 경계값을 포함합니다. X는 `-0.25 <= -0.30`을 만족하지 않지만 `-0.25 <= -0.20`은 만족합니다. 따라서 0에서 1로 달라진 이유는 관측이 악화되어서가 아니라 **정의가 바뀌었기 때문**입니다. 이 판정은 규칙으로 직접 계산할 수 있으므로 이를 재현하기 위해 반드시 모델이 필요한 것도 아닙니다.

[P3-9.8](section-08.md)의 모델 점수 임계값 변경은 고정된 결과 정의 아래에서 배정 정책을 바꾼 예였습니다. 여기서는 `review_needed` 자체를 만드는 기준을 바꾸었습니다. 이 열을 학습 정답으로 사용한다면 정답 정의가 바뀐 것입니다. `final_status`의 점검 정의까지 함께 바뀐 것은 아닙니다.

## 적용일과 과거 자료의 재판정을 분리한다

이 사례에서는 기준이 시행된 이후의 새 판정에 해당 버전을 적용한다고 정합니다. 9월 10일에 판정한 X의 원기록은 `review-rule-v1`, 결과 0으로 보존합니다. 9월 16일에 옛 X를 새 기준으로 다시 판정한다면 `review-rule-v2`, 결과 1이라는 새 기록을 원기록에 연결합니다. 과거 관측 시점이나 원판정 값을 덮어쓰지 않습니다.

| 재판정 전에 확인할 것 | 이번 사례에서 남길 내용 |
| --- | --- |
| 원판정 기준과 시각 | X의 원기록 ID, 9월 10일 판정, `review-rule-v1`, 값 0 |
| 새 기준의 적용 범위 | `review-rule-v2`, 9월 15일 00시 이후 새 판정에 적용. 과거 자료 재판정은 별도 기록 |
| 재판정 가능한 근거 | 같은 원자료·단위·집계·기준선으로 `recent_diff=-0.25`를 확인할 수 있는가 |
| 재판정 결과와 담당자 | 9월 16일, `review-rule-v2`, 값 1, 담당자와 변경 이유를 실제 기록에 기입 |
| 함께 학습할 때의 선택 | 같은 정의로 재판정한 자료를 쓰거나 버전별로 분리. 재판정 불가능한 기록의 범위와 이유를 명시 |

옛 라벨 0만 있고 원래 `recent_diff`나 계산 근거가 없다면 새 라벨을 확정할 수 없습니다. 옛 기준에서 0인 값에는 새 기준에서 1이 되는 -0.25도, 여전히 0인 -0.10도 포함됩니다. 기준 버전 이름만 바꾸어 통일한 것처럼 처리하지 않습니다. 같은 관측의 두 판정은 별개의 독립 샘플 두 건으로 늘리지도 않습니다.

각 결과의 정의와 확인 상태를 정한 뒤 버전 차이를 확인합니다. 기준이 달라졌다면 무엇이 바뀌었는지와 같은 근거로 재판정할 수 있는지를 먼저 확인해야 합니다. 이 메모가 있어야 월별 1의 비율이 변했을 때 관측 변화와 정의 변경을 구분해 살펴볼 수 있습니다.

연습: ① `recent_diff=-0.30`과 `-0.20`은 각 버전에서 어떤 라벨인가요? ② X의 옛 결과 0만 보관되어 있다면 v2 결과를 1로 바꿀 수 있나요? ③ A의 최종 상태가 미확정이라는 이유로 `review_needed=1`을 최종 상태 정답으로 대신 써도 되나요?

해설: ① -0.30은 v1·v2 모두 1이고, -0.20은 v1에서 0·v2에서 1입니다. ② 원래 관측값과 근거가 없으면 확정할 수 없습니다. 이 절의 X=-0.25를 확인할 수 있는 경우에만 새 규칙 결과 1을 계산합니다. ③ 두 열의 질문이 다르므로 대신 쓰지 않습니다. A는 `final_status=?`, `label_status=pending`으로 남깁니다. 미확정 처리의 근거는 [P3-9.10](section-10.md)과 같습니다.
