# P3-8.2 变化信号能说到哪里，原因又该停在哪里

> Section ID: `P3-8.2`
> Version: `v2026.07.25`

一旦有了[基线（baseline）](/AiBook/zh/reference/concept-glossary-pinyin/b/#glossary-baseline)，就可以读取最近区间和平时状态之间的差异。但即便如此，若把它理解成`既然看到了差异，原因也应该马上知道`，仍然非常危险。变化信号可见，和原因被确认，是完全不同的两个阶段。调节了解读强度之后，接下来还必须更明确地规定[解释边界](/AiBook/zh/reference/concept-glossary-pinyin/j/#glossary-interpretation-boundary)。

本章还需要一起回收的另一个视角是`可视化解读（visual interpretation）`。把比较表作为数字来读时会出现过度解读，而在线图、柱状图、分布图这类更容易抓住视线的图里，这种风险会更大。线条看起来分开了、柱子的高度看起来不一样，这些确实有助于更快地捕捉变化信号，但它们本身并不等于原因已经确认，也不等于可以立即得出强结论。因此这里首先要抓住的边界，是不要把`看见了差异`和`原因已经确认`放进同一句话里。

例如，假设最近 20 次运行里，后段下降率比平时更大。这当然可能是一个重要的变化信号。但它的原因究竟是传感器问题、输入条件变化、控制设定变化，还是暂时性的环境因素，单靠这张比较表仍然无法确定。比较表所展示的，是`存在一个不同于平时的结构`，而不是关于`为什么会这样`的完整诊断。

同样的判断，在读图时也一样适用。比如最近区间的折线看起来比基线更低，或者箱线图（box plot）里最近区间的范围看起来更宽。这样的图能帮助你快速抓住`哪里看起来不一样`，但单靠图本身，无法立刻确定这种差异究竟是样本量不足、少数极端值，还是持续性的结构变化造成的。

| 图上先看到的现象 | 只靠图就立刻说出时会有风险的句子 | 更安全的解读 |
| --- | --- | --- |
| 最近的线低于基线 | 状态已经明显恶化了 | 最近区间看起来低于基线，因此需要进一步确认 |
| 最近的柱子更高 | 原因已经很明确了 | 比较值出现差异，因此在不确认原因的前提下进入复核 |
| 箱线图范围变宽 | 系统变得不稳定了 | 最近的离散程度看起来更大，因此需要把重复性和样本量一起看 |

| 表述 | 含义 | 现在这个阶段能说吗 |
| --- | --- | --- |
| 变化信号 | 观测到了不同于平时的结构 | 可以 |
| 告警候选 | 值得由人工先查看 | 可以 |
| 需要复核 | 需要追加确认 | 可以 |
| 原因确认 | 已经判定了为什么会这样 | 通常还不行 |

从这张表能看出，比较结构通常直接支持到的层级，大多是`变化信号`、`告警候选`、`需要复核`。而`原因确认`则需要更多证据。可能要重新检查原始日志、补充运营上下文、追加传感器、结合后续结果，甚至还要引入人的判断。

因此，说[比较表](/AiBook/zh/reference/concept-glossary-pinyin/c/#glossary-comparison-table)是强有力的工具，不等于说它单独就能说明一切。它擅长快速揭示`哪里看起来和平时不同`，但并不是一个可以独立判定`为什么不同`的工具。只有把这条边界守住，才不会把告警和诊断、[复核候选队列](/AiBook/zh/reference/concept-glossary-pinyin/f/#glossary-review-queue)和自动分类混在一起。

统计上的保守性，正是在这里需要出现。如果样本量小，或者重复性弱，那么即便差异已经可见，表达强度也应该降低。因此，在这里最基本的姿态就是`变化被观测到了，但原因尚未确认`。

这不是因为 AI 不够强，而是因为问题结构本来就是这样。比较表很擅长显示`哪里变了`，但往往没有足够根据去单独解释`为什么变了`。所以在数据建模阶段，把[输出结构](/AiBook/zh/reference/concept-glossary-pinyin/s/#glossary-output-structure)设计成`告警候选`、`需要复核`、`比较报告`，往往会比直接做成`自动诊断`更诚实。

这个边界在阅读相关性（correlation）时尤其重要。即使两个值一起变化，也不能马上说一方就是另一方的原因。比如某个输入条件经常和后段下降一起出现，也仍然可能夹杂着隐藏的运行条件、季节性，或者测量方式变化。因此在 Part 3 里，首先要养成的习惯，就是不要把`一起动了`和`就是原因`放进同一句话。

在金融建模（financial modeling）这类误读成本很高的场景中，这一点会更加敏感。价格变化、交易量、风险分数、违约概率等数值，看上去可能高度相关，但如果直接把它们连到实际行动上，就可能带来损失或不公平判断。所以在 Part 3 这个阶段，更安全的做法是把`预测分数`和`实际决策`分开，只有在获得更强证据时，才去谈原因确认或自动行动。

可视化在这里尤其是一把双刃剑。做得好的图，比单个平均值能展示更多结构；但同时，醒目的图形模式也可能让人把信号感受得比实际更强。因此，图形是`寻找是否存在差异`的强工具，但不能直接被当成`判断原因是否已经确认`的工具。

比如，比较下面两句话。

| 表述 | 为什么更安全或更危险 |
| --- | --- |
| 最近区间相对基线，后段下降更大 | 它陈述的是比较结果 |
| 最近区间因为传感器异常而后段下降更大 | 它已经把原因提前定死了 |

运营句子通常按下面的顺序来写。

1. 先说明比较结果。
2. 按照样本量和重复性调节表达强度。
3. 附上人工下一步该做的动作。
4. 只有在有独立证据时，才提原因确认。

例如，`最近区间相对基线，后段下降更大，而最近样本数只有 6，因此在不确认原因的前提下提高复核优先级`，这样的句子同时反映了比较结构和解读边界。相反，`发生了传感器异常`这样的句子，则是在提前使用还不存在的证据。这里的告警，应该保持为帮助人先缩小查看范围的信号，而不是自动诊断结果。

这张图展示的是：比较结果不会直接通向原因确认。要先说变化信号，然后最多推进到需要复核这一层；只有在出现独立因果证据时，才可以进入下一阶段。这里讨论的重点不是计算本身，而是`该说到哪里、该停在哪里`这一解读边界。

这一节也不是在说`运营句子要写得保守一点`这种风格偏好，而是在区分`观测（observation）`、`复核（review）`和`因果主张（causal claim）`这几个层级。可视化解读也放在同一个框架里。图形可以让`被观测到的信号`更快地显现出来，但它本身并不能让你直接跳到`原因主张`这一层。

比较表可以很好地支撑观测和复核阶段，但不会自动把因果主张也替你完成。

如果把同样的边界再压缩一点，可以整理成下面这样。

| 现在正在说的句子 | 更接近的层级 |
| --- | --- |
| 看到了和平时不同的结构 | 变化信号 |
| 值得由人工先看一眼 | 复核候选 |
| 原因是传感器异常 | 原因确认 |

这张表的关键，是不要把比较结构直接支撑的层级，和还需要额外证据的层级混在一起。
