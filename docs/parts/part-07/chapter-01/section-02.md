# P7-1.2 결과와 회고

> Section ID: `P7-1.2`
> Version: `v2026.07.18`

P7-1.1에서는 운영 로그를 읽고 평균, 최대값, 비율을 계산해 기본 관찰을 만들었습니다. 이제는 프로젝트 문서에서 결과를 어떻게 기록하고, 무엇을 아직 모른다고 남길 것인지가 더 중요해집니다. 이 절은 바로 그 질문을 정리합니다. 결과와 회고는 숫자를 다시 적는 절이 아니라, 무엇을 확인했고 무엇은 아직 가설인지 구분해 남기는 단계입니다.

## 이 절의 범위

- 데이터 분석 프로젝트 결과는 어떤 형식으로 정리하면 좋은가?
- 계산 결과와 해석을 어떻게 구분해 적어야 하는가?
- 회고(retrospective)는 실패가 있을 때만 쓰는 문서가 아니라는 점을 어떻게 이해하면 좋은가?

이 절에서는 `사실, 해석, 다음 질문`을 남기는 최소 회고 구조만 다룹니다. 즉, 여기서는 `계산 기록을 어떻게 다음 반복의 의사결정 기록으로 바꿀 것인가`를 먼저 닫습니다. 이후 프로젝트에서 같은 회고 습관은 P7-5.2 검색 품질과 답변 검증, P7-7.2 실패 기록과 개선 계획으로 다시 이어집니다.

Part 7의 공통 회고 형식은 이 절에서 처음 고정됩니다. 이후 프로젝트의 실패 기록과 개선 계획도 모두 여기서 세운 `사실, 해석, 다음 질문` 구조를 다시 사용합니다.

Part 7에서 `회고(retrospective)`와 `검토(review)`의 구분이 다시 흔들리면, 먼저 `회고는 다음 반복을 준비하는 정리`, `검토는 아직 확정하지 않은 항목을 다시 보는 확인`으로 읽고 이 절과 [개념사전](../../../reference/concept-glossary.md)으로 돌아오면 됩니다.

## 이 절의 목표

- 프로젝트 문서에서 `사실`, `해석`, `다음 질문`을 구분해 적을 수 있습니다.
- 검토 기준을 바꾸면 어떤 항목이 회고 문서에 올라오는지 설명할 수 있습니다.
- 결과 요약만으로 끝나지 않고 한계와 보완점을 함께 남길 수 있습니다.
- 프로젝트에서도 회고 문서가 왜 필요한지 설명할 수 있습니다.

## 왜 회고가 필요한가

프로젝트를 끝내면 종종 다음 두 문장으로 끝내려 합니다.

- `평균 방문자 수는 150.7명이었다.`
- `2026-06-05가 가장 좋았다.`

하지만 프로젝트 문서는 계산 결과를 옮겨 적는 곳이 아니라, `지금 무엇을 알게 되었고, 아직 무엇을 모르는지`를 남기는 곳입니다.

회고 문서가 계산 기록과 어떻게 달라지는지 판단 기준을 표로 고정하면 다음과 같습니다.

| 질문 | 짧은 답 |
| --- | --- |
| 왜 회고를 남기는가? | 결과를 다음 반복으로 연결하기 위해 |
| 무엇을 구분해야 하는가? | 사실, 해석, 다음 질문 |
| 그래서 프로젝트 문서가 달라지는 점은 무엇인가? | 계산 기록에서 의사결정 기록으로 바뀐다 |

특히 데이터 분석 프로젝트는 다음 단계로 이어지는 질문이 더 중요합니다.

예를 들어 `오류가 가장 많았던 날`을 찾는 것만으로는 충분하지 않습니다. 실제로는 다음이 더 중요합니다.

- 그 오류가 배포와 연결되었는가?
- 오류 증가가 가입 감소와 함께 나타났는가?
- 다음 실험이나 로그 추가가 필요한가?

## 결과 문서의 기본 구조

프로젝트 회고도 다음 세 칸으로 나누면 훨씬 읽기 쉬워집니다.

| 구분 | 적을 내용 |
| --- | --- |
| 사실 | 코드로 직접 확인한 값 |
| 해석 | 그 값이 시사하는 가능성 |
| 다음 질문 | 바로 이어서 확인해야 할 것 |

이 구분이 중요한 이유는, 숫자는 비교적 단단하지만 해석은 언제나 가설 수준일 수 있기 때문입니다.

이 구조는 Part 7 전체에서 반복해서 쓰이는 공통 형식입니다. 이후 예측 모델, 딥러닝, RAG 프로젝트에서도 같은 세 칸을 다시 쓰게 됩니다.

여기에 한 가지를 더 붙이면 이 절이 Part 7 전체 회고 구조의 진짜 출발점이 됩니다. `사실`, `해석`, `다음 질문` 세 칸을 단순 문장 형식으로만 보지 말고, `추가 검토가 필요한 항목`, `아직 확정되지 않은 해석`, `다음 반복에서 바로 확인할 질문`을 함께 적는 공통 구조로 읽는 것입니다.

| 같이 남길 기록 | 왜 필요한가 |
| --- | --- |
| 사실 | 코드로 직접 확인한 값을 고정하기 위해서입니다. |
| 해석 | 가능한 해석을 사실과 분리해 남기기 위해서입니다. |
| 추가 검토 필요 항목 | 아직 확정할 수 없는 항목을 표시하기 위해서입니다. |
| 다음 질문 | 다음 프로젝트나 다음 반복의 시작 질문을 고정하기 위해서입니다. |

방금 앞 절에서 만든 프로젝트 메모를 다시 읽으면, 이 세 칸이 어디에서 나오는지도 자연스럽게 보입니다.

- 프로젝트 메모의 요약 칸에 들어간 값은 `사실(fact)` 후보입니다.
- 프로젝트 메모의 관찰 칸에 적힌 문장은 `해석(interpretation)` 후보입니다.
- 프로젝트 메모의 다음 질문 칸에 적힌 문장은 그대로 `다음 질문(next question)` 후보입니다.

즉, P7-1.1의 출력은 여기서 회고 문서로 바로 다시 정리되어야 합니다.

## 앞 절 결과를 예시로 다시 정리하기

P7-1.1의 결과를 이 구조에 맞추면 다음처럼 적을 수 있습니다.

| 사실 | 해석 | 다음 질문 |
| --- | --- | --- |
| 평균 전환율은 약 10.5%였다. | 기본 전환 흐름을 잡는 기준점으로 쓸 수 있다. | 이전 주와 비교하면 유지되는 수준인가? |
| 2026-06-05의 가입 수가 가장 높았다. | 특정 메시지, 이벤트, 유입 품질 변화가 있었을 수 있다. | 그날의 유입 채널과 화면 변경 이력이 있는가? |
| 2026-06-06의 오류 수가 가장 높았다. | 시스템 문제가 가입 하락과 연결되었을 가능성이 있다. | 오류 유형과 배포 이력을 함께 확인해야 하는가? |

이 표에서 중요한 점은 `가능성`과 `사실`을 섞지 않는 것입니다. 기준선과 비교한 차이가 보여도, 여기서는 먼저 `추가 확인이 필요한가`를 적는 수준에 머무르는 편이 안전합니다.

`오류 때문에 가입이 떨어졌다`고 단정하는 것은 아직 이릅니다. 지금 단계에서 안전한 표현은 다음과 같습니다.

`오류 증가와 가입 감소가 함께 보였으므로, 관련 가능성을 추가로 확인할 필요가 있다.`

이 문장 차이를 꼭 익혀 두는 편이 좋습니다.

- 위험한 문장: `오류 때문에 가입이 떨어졌다.`
- 안전한 문장: `오류와 가입 감소가 함께 보여 추가 확인이 필요하다.`

## 검토 기준을 바꾸면 회고도 달라진다

실제 프로젝트에서는 회고 문장을 예쁘게 쓰는 일보다 `무엇을 검토 대상으로 올릴 것인가`가 먼저입니다. 같은 데이터라도 기준을 엄격하게 잡으면 한두 건만 회고에 올라오고, 탐색적으로 잡으면 더 많은 후보가 올라옵니다.

앞 절의 운영 로그를 그대로 이어 받되, 이번에는 `어떤 날짜와 채널을 회고 후보로 올릴 것인가`를 기준에 따라 나눠 보겠습니다.

- 문제 상황:
  - 최근 7일 로그를 다시 읽으며 어떤 항목을 `즉시 검토`, `추가 관찰`로 남길지 정해야 한다.
  - 하지만 전환율 하락과 오류율 상승을 어느 수준부터 심각 신호로 볼지는 팀이나 단계마다 다를 수 있다.
- 입력:
  - [`p7-1-traffic-log.csv`](../../../assets/part-07/chapter-01/p7-1-traffic-log.csv)
  - 두 가지 검토 기준: `엄격 모드`, `탐색 모드`
- 기대 출력:
  - 기준별 검토 후보 목록
  - 어떤 날짜가 두 기준 모두에서 올라오는지
  - 회고 문서에 바로 옮길 `사실`, `해석`, `다음 질문`
- 확인할 개념:
  - 회고는 계산 결과를 옮겨 적는 문서가 아니라 검토 우선순위를 고정하는 문서다
  - 기준을 바꾸면 회고 후보도 달라진다
  - 그래도 두 기준에서 공통으로 올라오는 항목은 더 강한 검토 신호로 읽을 수 있다

## Python 예제

```python
import csv
from collections import defaultdict
from datetime import datetime
from pathlib import Path

review_rules = [
    {
        "name": "엄격 모드",
        "conversion_drop_max": -0.035,
        "error_rise_min": 0.011,
    },
    {
        "name": "탐색 모드",
        "conversion_drop_max": -0.025,
        "error_rise_min": 0.009,
    },
]

def conversion_rate(row):
    return row["signups"] / row["visitors"]

def error_rate(row):
    return row["errors"] / row["visitors"]

data_path = Path("docs/assets/part-07/chapter-01/p7-1-traffic-log.csv")
rows = list(csv.DictReader(data_path.open(encoding="utf-8")))
for row in rows:
    row["date"] = datetime.strptime(row["date"], "%Y-%m-%d").date()
    row["visitors"] = int(row["visitors"])
    row["signups"] = int(row["signups"])
    row["errors"] = int(row["errors"])

cutoff = datetime.strptime("2026-06-08", "%Y-%m-%d").date()
baseline_rows = [row for row in rows if row["date"] < cutoff]
recent_rows = [row for row in rows if row["date"] >= cutoff]

baseline_by_channel = defaultdict(lambda: {"visitors": 0, "signups": 0, "errors": 0})
for row in baseline_rows:
    baseline_by_channel[row["channel"]]["visitors"] += row["visitors"]
    baseline_by_channel[row["channel"]]["signups"] += row["signups"]
    baseline_by_channel[row["channel"]]["errors"] += row["errors"]

for channel, totals in baseline_by_channel.items():
    totals["conversion_rate"] = totals["signups"] / totals["visitors"]
    totals["error_rate"] = totals["errors"] / totals["visitors"]

candidate_rows = []
for row in recent_rows:
    baseline = baseline_by_channel[row["channel"]]
    current_conversion = conversion_rate(row)
    current_error = error_rate(row)
    candidate_rows.append({
        "date": row["date"],
        "channel": row["channel"],
        "conversion_rate": round(current_conversion, 4),
        "error_rate": round(current_error, 4),
        "conversion_delta": round(current_conversion - baseline["conversion_rate"], 4),
        "error_delta": round(current_error - baseline["error_rate"], 4),
    })

review_results = {}
for rule in review_rules:
    selected = []
    for row in candidate_rows:
        if (
            row["conversion_delta"] <= rule["conversion_drop_max"]
            and row["error_delta"] >= rule["error_rise_min"]
        ):
            selected.append({
                "date": row["date"],
                "channel": row["channel"],
                "conversion_delta": row["conversion_delta"],
                "error_delta": row["error_delta"],
            })
    review_results[rule["name"]] = selected

strict_keys = {
    (row["date"], row["channel"]) for row in review_results["엄격 모드"]
}
explore_keys = {
    (row["date"], row["channel"]) for row in review_results["탐색 모드"]
}
common_keys = sorted(strict_keys & explore_keys)

회고_메모 = [
    {
        "사실": f"엄격 모드에서는 {len(review_results['엄격 모드'])}건, 탐색 모드에서는 {len(review_results['탐색 모드'])}건이 검토 후보로 올라왔다.",
        "해석": "검토 기준을 조금만 바꿔도 회고 문서에 올라오는 후보 수가 달라진다.",
        "다음 질문": "현재 팀은 즉시 대응 기준과 탐색 관찰 기준을 따로 둘 필요가 있는가?",
    },
    {
        "사실": f"두 기준 모두에서 공통으로 올라온 항목은 {common_keys}였다.",
        "해석": "ads 채널의 특정 날짜들은 기준을 엄격하게 잡아도 계속 남는 강한 이상 신호다.",
        "다음 질문": "이 날짜 전후의 ads landing page, 추적 스크립트, 캠페인 설정을 먼저 확인해야 하는가?",
    },
]

print("기준별 검토 후보 =")
print("읽은 파일 =", str(data_path))
for rule_name, rows in review_results.items():
    print(rule_name, rows)
print("[회고 메모]")
for item in 회고_메모:
    print(item)
```

## 결과를 어떻게 읽는가

이 예제에서 확인해야 할 결과는 `문장을 잘 썼는가`가 아니라, `검토 기준을 바꾸었을 때도 계속 남는 신호가 무엇인가`입니다. 그래야 회고 문서가 단순 감상문이 아니라 다음 행동의 우선순위 표가 됩니다.

## 이 결과를 어떻게 회고로 옮길까

위 출력은 회고 문서 안에서 다음처럼 바로 읽을 수 있습니다.

| 사실 | 해석 | 다음 질문 |
| --- | --- | --- |
| 엄격 모드에서는 4건, 탐색 모드에서는 6건이 검토 후보로 올라왔다. | 검토 기준에 따라 회고 범위가 달라진다. | 즉시 대응 기준과 관찰 기준을 분리할 것인가? |
| 두 기준 모두에서 `ads`의 2026-06-10, 06-11, 06-12, 06-14가 반복 등장했다. | 이 구간은 우연보다 구조적 문제 가능성이 더 크다. | ads landing page, 추적 스크립트, 캠페인 설정을 먼저 볼 것인가? |
| organic과 search는 같은 기준에서 검토 후보로 올라오지 않았다. | 전체 하락처럼 보여도 실제 운영 이상은 특정 채널에 집중됐을 수 있다. | 채널 단위를 더 잘게 쪼개 브라우저, 캠페인, 디바이스 기준도 확인할 것인가? |

이 표에서 중요한 점은 `후보가 많다`보다 `어떤 후보가 기준을 바꿔도 살아남는가`입니다. 실제 프로젝트에서는 바로 그 항목이 먼저 회고 문서의 앞줄로 올라옵니다.

## 회고는 실패 기록만이 아니다

회고(retrospective)라는 말을 들으면 많은 독자가 `잘못한 점을 적는 문서`로만 이해합니다. 하지만 프로젝트 회고는 더 넓습니다.

데이터 분석 프로젝트의 회고에는 보통 다음이 들어갑니다.

- 무엇이 잘 보였는가
- 무엇이 아직 불분명한가
- 어떤 데이터가 더 필요했는가
- 어떤 비교를 못 했는가
- 다음 프로젝트에서 무엇을 먼저 보완할 것인가

즉, 회고는 프로젝트의 패배 선언이 아니라 `다음 반복(iteration)을 준비하는 기록`입니다.

이 점 때문에 회고는 프로젝트의 맨 뒤 부록이 아니라, 다음 프로젝트의 첫 입력으로도 읽을 수 있어야 합니다.

## 프로젝트 회고 예시

이번 프로젝트라면 다음 정도의 회고가 적절합니다.

### 잘 보인 점

- 전체 합계와 채널별 비교를 분리하니 `서비스 전체 하락`과 `ads 채널 이상`을 구분할 수 있었다.
- 검토 기준을 두 가지로 나눠 보니 공통으로 남는 날짜를 우선순위 1 후보로 고정할 수 있었다.

### 아직 모르는 점

- ads 채널 하락이 landing page 오류인지, 추적 스크립트 문제인지, 캠페인 품질 저하인지는 아직 확정할 수 없다.
- 엄격 모드에서 빠지고 탐색 모드에서만 잡힌 날짜를 실제 문제로 볼지 관찰 신호로만 둘지는 더 정해야 한다.

### 다음 반복에서 보완할 점

- `campaign`, `release_version`, `error_type`, `browser` 열을 추가한다.
- 채널 단위뿐 아니라 캠페인 단위 비교도 같이 본다.
- 검토 기준을 `즉시 대응`, `탐색 관찰` 두 층으로 분리해 운영 문서에 남긴다.

## 바로 쓰는 회고 템플릿

이 절을 읽은 뒤 바로 문서에 붙여 넣어 쓸 수 있는 최소 템플릿은 다음처럼 정리할 수 있습니다.

```text
### 사실
- 확인한 값:
- 비교 기준:

### 해석
- 이 값이 시사하는 가능성:
- 아직 단정할 수 없는 점:

### 다음 질문
- 다음에 추가로 확인할 데이터:
- 다음 반복에서 바꿀 점:
```

이 템플릿에서 중요한 점은 문장을 길게 잘 쓰는 일이 아닙니다. 먼저 `확인한 값`, `가능성`, `다음 확인 항목`이 각각 따로 적혀 있는지가 더 중요합니다.

예를 들어 이번 절의 예시를 이 빈칸에 바로 넣으면 다음처럼 됩니다.

```text
### 사실
- 확인한 값: 엄격 모드와 탐색 모드 모두에서 ads 채널의 2026-06-10, 06-11, 06-12, 06-14가 검토 후보로 남았다.
- 비교 기준: 채널별 기준선 전환율과 오류율 대비 최근 7일 변화를 비교했다.

### 해석
- 이 값이 시사하는 가능성: ads 채널에는 기준을 엄격하게 잡아도 사라지지 않는 구조적 이상 신호가 있을 수 있다.
- 아직 단정할 수 없는 점: landing page 오류인지, 추적 스크립트 문제인지, 캠페인 품질 변화인지는 아직 모른다.

### 다음 질문
- 다음에 추가로 확인할 데이터: campaign, release_version, error_type, browser
- 다음 반복에서 바꿀 점: 즉시 대응 기준과 탐색 관찰 기준을 분리해 운영 문서에 남긴다.
```

## 직접 바꿔 보며 확인할 것

이 절은 `기준을 어떻게 쓰는가`에 따라 회고 문장이 달라지는 구조이므로, 실행 뒤에는 검토 기준을 직접 흔들어 보는 편이 좋습니다.

1. 엄격 모드 기준을 조금 더 높이거나 낮춰 봅니다.
   관찰할 점: 공통으로 살아남는 날짜는 그대로인가, 아니면 회고 앞줄에 올라올 후보가 달라지는가?

2. `organic`이나 `search`에 ads와 비슷한 하락 행을 CSV에 한두 건 추가해 봅니다.
   관찰할 점: 회고 문장이 `특정 채널 이상`에서 `여러 채널 동시 이상`으로 바뀌는가?

이 절에서 직접 확인해야 하는 것은 `문장을 예쁘게 쓰는가`보다 `검토 기준을 바꾸면 회고 우선순위가 어떻게 달라지는가`입니다.

## 나쁜 회고와 좋은 회고

회고를 쓸 때는 `결과 요약`과 `해석`을 한 줄에 섞기 쉽습니다. 아래처럼 대비해서 보면 차이가 더 분명합니다.

| 구분 | 예시 |
| --- | --- |
| 나쁜 회고 | `오류가 많아서 가입이 떨어졌다. 다음에는 더 잘하자.` |
| 좋은 회고 | `ads 채널의 2026-06-10, 06-11, 06-12, 06-14는 검토 기준을 바꿔도 반복해서 남았다. 따라서 이 구간은 구조적 이상 신호 후보로 보고, 다음 반복에서는 campaign, release_version, error_type을 함께 기록한다.` |

나쁜 회고는 감상은 남지만 다음 행동이 남지 않습니다. 좋은 회고는 `무엇을 봤는가`, `무엇을 아직 모르는가`, `무엇을 더 넣을 것인가`가 같이 남습니다. 즉, 회고의 경고 문장도 자동 진단이 아니라 검토 필요 항목을 남기는 기록으로 읽혀야 합니다.

## 실무에서 왜 이 방식이 중요한가

실무에서는 분석 결과보다 `분석 결과를 조직이 어떻게 다시 쓸 수 있느냐`가 더 중요합니다.

예를 들어:

- 운영 팀은 오류가 많은 날짜를 보고 장애 기록과 연결합니다.
- 제품 팀은 가입이 높은 날을 보고 UI 변경과 연결합니다.
- 데이터 팀은 다음 주 실험 설계에 필요한 로그 열을 추가합니다.

즉, 프로젝트 문서가 좋다는 뜻은 `계산이 복잡하다`가 아니라 `다른 사람이 다음 행동을 결정할 수 있다`는 뜻에 더 가깝습니다.

## 체크리스트

| 상황 | 먼저 떠올릴 관점 | 왜 중요한가 |
| --- | --- | --- |
| 계산 결과를 숫자만 적고 끝내고 싶어질 때 | 사실, 해석, 다음 질문을 분리해야 한다는 점 | 같은 수치도 무엇이 확인된 사실이고 무엇이 아직 가설인지 나눠 적어야 다음 반복이 흔들리지 않습니다. |
| 회고를 실패가 났을 때만 쓰는 문서로 보게 될 때 | 다음 반복을 준비하는 공통 기록이라는 점 | 잘된 점, 불확실한 점, 추가 검토 필요 항목을 함께 남겨야 뒤 프로젝트가 바로 이어집니다. |
| 다음 장의 기준점(baseline) 비교 프로젝트가 왜 자연스럽게 이어지는지 감이 오지 않을 때 | 회고가 곧 다음 프로젝트의 입력이라는 점 | P7-2 이후 프로젝트들은 모두 이 절의 회고 메모를 바탕으로 비교, 개선, 실패 기록을 확장합니다. |

- 결과 문서는 숫자만 적는 곳이 아니라는 점을 설명할 수 있는가?
- 사실, 해석, 다음 질문을 구분해 적어야 한다는 점을 말할 수 있는가?
- 회고는 실패 기록만이 아니라 다음 반복을 준비하는 문서라는 점을 설명할 수 있는가?
- 프로젝트에서도 한계와 보완점을 남겨야 뒤의 모델 프로젝트가 흔들리지 않는다는 점을 말할 수 있는가?
- 회고를 `실패 보고서`가 아니라 `사실, 해석, 다음 질문을 분리해 남기는 공통 기록 구조`로 설명할 수 있는가?
- 계산 결과와 해석을 분리해 적어야 뒤의 기준점(baseline) 비교와 개선 계획이 더 정확해진다는 점을 말할 수 있는가?
- 다음 프로젝트는 이 절과 다른 방식으로 기록하는 것이 아니라, 여기서 만든 회고 구조에 기준점(baseline) 비교와 모델 개선 판단을 더 얹는 단계라는 점을 잡고 있는가?
- 계산 결과와 해석을 분리해 적을 수 있는가?
- 관찰에서 바로 단정으로 넘어가지 않고 `가능성`으로 표현할 수 있는가?
- 다음 반복에서 추가할 데이터나 비교 항목을 적을 수 있는가?
- 프로젝트 문서가 다른 사람의 다음 행동을 도울 수 있는 형태인가?
