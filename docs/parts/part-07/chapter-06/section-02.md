# P7-6.2 권한과 로그 검토

> Section ID: `P7-6.2`
> Version: `v2026.07.18`

P7-6.1에서는 에이전트를 목표, 도구, 관찰의 흐름으로 설명했습니다. 하지만 실제 에이전트 프로젝트는 여기서 바로 멈추면 위험합니다.

도구를 호출할 수 있다는 말은 곧 다음 질문을 뜻하기 때문입니다.

- 누구 권한으로 실행하는가?
- 실패하면 어디에 남는가?
- 같은 작업을 다시 추적할 수 있는가?

이 절은 에이전트 프로젝트의 `권한(permission)`과 `로그(log)`를 다룹니다. 목적은 에이전트가 무엇을 할 수 있는가보다, 무엇을 해도 되는가와 무엇을 남겨야 하는가를 프로젝트 문서에 적는 데 있습니다.

## 이 절의 범위

- 에이전트 프로젝트에서 권한을 왜 먼저 적어야 하는가?
- 로그는 단순 디버그 출력이 아니라 무엇을 위한 기록인가?
- 승인 여부, 상태, 범위는 어떻게 프로젝트 문서에 남길 수 있는가?

이 절에서는 권한 범위와 로그 기록을 프로젝트 문서에 남기는 최소 기준만 다룹니다. 즉, 여기서는 `실행 가능하다`와 `실행해도 된다`를 어떻게 구분해 기록할지까지를 먼저 닫습니다. 배포 이후 실패 추적과 운영 회고는 P7-7.1, P7-7.2에서 다시 이어집니다.

실행 기록을 운영 문서로 바꾸는 최소 기준은 이 절에서 권한과 로그 중심으로 정리합니다. 에이전트 프로젝트가 `실행 가능하다`와 `실행해도 된다`를 구분해 남겨야 한다는 기준을 여기서 세웁니다.

Part 7에서 `권한(permission)`과 `로그(log)`를 단순 부가 정보처럼 읽게 되면, 이 절과 [개념사전](../../../reference/concept-glossary.md)으로 돌아와 운영 기록의 뜻을 다시 확인하면 됩니다.

## 이 절의 목표

- 에이전트 실행에서 권한과 로그가 왜 중심 요소인지 설명할 수 있습니다.
- 단순 실행 성공 여부보다 `무슨 도구를 어떤 범위에서 썼는가`를 기록하는 법을 알 수 있습니다.
- 실패 대응 문서를 에이전트 실행 기록과 연결할 수 있습니다.

## 왜 권한이 먼저인가

도구를 쓰는 에이전트는 단순 텍스트 생성보다 훨씬 강한 행동력을 가질 수 있습니다.

예를 들어:

- 파일 읽기
- 파일 수정
- 빌드 실행
- 서비스 재시작
- 외부 API 호출

이 행동들은 모두 같은 위험도를 갖지 않습니다. 그래서 프로젝트 문서에는 최소 다음을 구분하는 편이 좋습니다.

권한과 실행 기록을 읽을 때 바로 필요한 판단 기준을 표로 고정하면 다음과 같습니다.

| 질문 | 짧은 답 |
| --- | --- |
| 왜 권한을 먼저 적는가? | 도구마다 위험도가 다르기 때문 |
| 로그는 왜 필요한가? | 어떤 실행이 일어났는지 다시 보기 위해 |
| 최소 산출물은 무엇인가? | 권한, 승인 여부, 결과가 들어간 실행 기록 |

| 항목 | 질문 |
| --- | --- |
| 권한 | 이 도구를 그냥 실행해도 되는가? |
| 승인 | 사람 승인이 필요한가? |
| 허용 범위 | 어느 서비스, 어느 파일, 어느 시스템까지 허용되는가? |
| 기록 위치 | 실행 결과와 실패 원인은 어디에 남는가? |

## 왜 로그가 중요한가

로그는 단순 출력 저장이 아닙니다. 에이전트 프로젝트에서는 다음 목적을 가집니다.

- 어떤 도구를 호출했는지 추적
- 어느 단계에서 실패했는지 확인
- 승인 여부 기록
- 나중에 회고할 근거 확보

즉, 에이전트 로그는 `관찰의 이력`입니다. 결과 한 줄만 남기면 에이전트 프로젝트는 재현과 회고가 거의 불가능해집니다.

## 운영 변경 시나리오 예제

이번 절에서는 P7-6.1에서 본 `결제 API 5xx 오류 급증` 티켓을 이어 받습니다. 이번에는 조회로 끝내지 않고, `롤백 실행`이라는 변경 단계 후보를 하나 더 붙입니다. Python 예제에서 쓸 권한·승인 기록은 [`p7-6-permission-log.csv`](../../../assets/part-07/chapter-06/p7-6-permission-log.csv)로 따로 분리해, 본문 코드가 권한 판단과 보류 해석에 집중하도록 구성합니다.

중요한 점은 다음입니다.

- `메트릭 조회`, `배포 이력 조회`는 읽기 중심 도구다.
- `롤백 실행`은 서비스 상태를 실제로 바꾸는 변경 도구다.
- 따라서 같은 에이전트 루프 안에서도 승인 규칙과 로그 요구 수준이 달라져야 한다.

## Python 예제

이번 예제의 목적은 권한 판단과 실행 결과를 같은 기록으로 묶는 것입니다. 이번에는 단순 성공/실패 대신 필요한 권한, 승인 여부, 보류 상태, 다음 행동을 함께 남겨서 운영 문서가 어떻게 생기는지 보이게 하겠습니다. 원시 단계 데이터는 CSV에 두고, 본문 코드는 `기록 읽기 -> 승인 상태 집계 -> 보류 해석` 흐름에만 집중합니다.

- 문제 상황: 같은 계획이라도 어떤 단계는 승인 없이 실행할 수 없음을 기록한다.
- 입력: 단계별 도구 목록, 권한 범위, 승인 여부
- 기대 출력: 실행 기록, 승인 필요 도구 목록, 보류 단계 수
- 확인할 개념:
  - 실행 성공 여부만으로는 에이전트 운영 상태를 설명할 수 없다
  - 권한과 범위가 있어야 보류 이유를 다시 읽을 수 있다
  - 승인 필요한 변경 도구는 별도 추적 대상으로 남겨야 한다

## 입력 파일

- 파일 경로: [`p7-6-permission-log.csv`](../../../assets/part-07/chapter-06/p7-6-permission-log.csv)
- 한 행의 의미: `도구 한 단계의 권한·승인 기록`
- 핵심 열: `step`, `tool`, `permission`, `scope`, `approved`, `result_status`, `observation`, `next_action`

이 파일에서 특히 먼저 봐야 하는 것은 `permission`, `scope`, `approved` 세 열입니다. 같은 계획 안에서도 조회 도구와 변경 도구가 어떻게 다르게 취급되는지, 그리고 왜 `보류`가 단순 실패가 아닌지 이 세 열이 먼저 설명해 줍니다.

```python
import csv
from pathlib import Path

data_path = Path("docs/assets/part-07/chapter-06/p7-6-permission-log.csv")
rows = list(csv.DictReader(data_path.open(encoding="utf-8")))

계획_단계 = [
    {
        "단계": int(row["step"]),
        "도구": row["tool"],
        "필요한 권한": row["permission"],
        "범위": row["scope"],
        "이유": row["reason"],
    }
    for row in rows
]

실행_기록 = [
    {
        "단계": int(row["step"]),
        "도구": row["tool"],
        "필요한 권한": row["permission"],
        "범위": row["scope"],
        "승인 여부": row["approved"],
        "결과 상태": row["result_status"],
        "관찰 메모": row["observation"],
        "다음 행동": row["next_action"],
    }
    for row in rows
]

검토_요약 = {
    "단계 수": len(실행_기록),
    "승인된 단계 수": sum(entry["승인 여부"] == "예" for entry in 실행_기록),
    "보류 단계 수": sum(entry["결과 상태"] == "보류" for entry in 실행_기록),
    "추가 승인 필요 도구": [
        entry["도구"] for entry in 실행_기록 if entry["승인 여부"] == "아니오"
    ],
    "검토 대상 범위": [
        entry["범위"] for entry in 실행_기록 if entry["결과 상태"] == "보류"
    ],
}

print("읽은 파일 =", data_path)
print("계획 단계 =", 계획_단계)
print("실행 기록 =")
for entry in 실행_기록:
    print(entry)
print("검토 요약 =", 검토_요약)
```

## 결과를 어떻게 읽는가

이 출력에서 중요한 것은 세 번째 단계입니다.

| 단계 | 이번 기록에서 읽어야 할 점 | 해석 |
| --- | --- | --- |
| 메트릭 조회 | 읽기 권한으로 현재 상태를 확인했다 | 조회 단계는 자동화 범위에 넣기 쉽다 |
| 배포 이력 조회 | 최근 변경이 있었음을 확인했다 | 원인 후보를 좁히는 근거가 된다 |
| 롤백 실행 | 기능적으로는 가능하지만 승인 없이는 보류된다 | `할 수 있다`와 `해도 된다`는 다르다 |
| 상태 보고 작성 | 변경 전에도 현재 상태를 문서화할 수 있다 | 보류 상태도 운영 기록으로 남겨야 한다 |

즉, 좋은 에이전트 프로젝트는 `할 수 있는가`만이 아니라 `해도 되는가`를 함께 다룹니다.

이 결과는 다음 세 줄로 요약할 수 있습니다.

- 계획이 있어도 승인 없이는 멈출 수 있다.
- 권한, 범위, 다음 행동이 함께 있어야 보류 상태를 운영적으로 해석할 수 있다.
- 보류는 단순 실패와 다른 상태다.

여기서 한 걸음 더 나가면 에이전트 실행 기록도 `비교 가능한 기록 묶음`으로 읽을 수 있습니다.

| 기록 묶음 | 지금 남기는 이유 |
| --- | --- |
| 권한과 범위 | 어떤 범위까지 자동 실행했는지 비교하기 위해 |
| 승인 여부와 보류 상태 | 기능 실패와 운영 보류를 구분하기 위해 |
| 관찰과 다음 행동 | 같은 문제가 다시 생겼을 때 다음 행동을 바로 정하기 위해 |
| 검토 대상 단계 | 승인 정책이나 도구 설계를 다시 볼 단계를 고정하기 위해 |

## 권한·로그 기록의 최소 구조

에이전트 프로젝트의 권한·로그 기록도 아래와 같은 최소 구조로 시작할 수 있습니다.

```text
### 계획 단계
| 단계 | 도구 | 필요한 권한 | 범위 | 이유 |
| --- | --- | --- | --- | --- |
| 1 |  |  |  |  |

### 실행 기록
| 단계 | 도구 | 승인 여부 | 결과 상태 | 다음 행동 | 관찰 메모 |
| --- | --- | --- | --- | --- | --- |
| 1 |  | 예 / 아니오 | 완료 / 보류 / 실패 |  |  |

### 검토 요약
- 승인된 단계 수:
- 보류 단계 수:
- 추가 승인 필요 도구:
```

이 템플릿에서 중요한 점은 실행 성공 여부만 적는 것이 아니라, `어떤 권한이 필요했는지`, `승인이 있었는지`, `막히면 다음 행동이 무엇인지`까지 함께 적는 것입니다.

가능하면 여기에 `추가 검토 필요` 열도 같이 두는 편이 좋습니다. 어떤 단계는 완료였더라도 권한 범위가 넓거나, 다음 반복에서 정책 재검토가 필요할 수 있기 때문입니다.

## 나쁜 실행 기록과 좋은 실행 기록

에이전트 로그도 자주 `성공했다`, `막혔다` 정도로만 남아 다음 반복에 도움이 되지 않습니다. 아래처럼 대비해 보면 기준이 더 분명해집니다.

| 구분 | 예시 |
| --- | --- |
| 나쁜 기록 | `롤백 단계에서 막혔다. 권한 문제인 듯하다.` |
| 좋은 기록 | `3단계 롤백 실행은 프로덕션 변경 권한이 필요했고 승인 여부는 아니오였다. 결과 상태는 보류로 남기고, 다음 행동은 온콜 리드 승인 요청으로 기록한다. 따라서 이 상태는 기능 오류보다 현재 승인 절차 미완료 신호로 먼저 해석한다.` |

나쁜 기록은 막혔다는 사실만 남고, 왜 멈췄는지와 다음 행동이 분명하지 않습니다. 좋은 기록은 `어느 단계였는가`, `어떤 권한이 필요했는가`, `실패가 아니라 운영 보류인지`, `다음 행동이 무엇인지`를 함께 남깁니다.

## 왜 권한과 로그가 운영 문제인가

이 권한과 로그 구조는 결국 운영 문제와 직결됩니다.

- 잘못된 변경 권한은 사고로 이어질 수 있습니다.
- 로그가 없으면 실패 원인을 설명하기 어렵습니다.
- 승인 정책이 없으면 에이전트 행동 범위가 불명확해집니다.

따라서 에이전트 프로젝트 회고 문서에는 다음을 함께 남길 수 있습니다.

- 어떤 도구는 자동 실행 허용
- 어떤 도구는 사람 승인 필요
- 어떤 실패는 재시도 가능
- 어떤 실패는 즉시 중단해야 함

## 직접 바꿔 보며 확인할 것

이 절은 `보류` 상태를 읽는 절이므로, 실행 뒤에는 승인 여부와 범위를 직접 바꿔 보는 편이 좋습니다.

1. `롤백 실행`의 `approved` 값을 `예`로 바꿔 봅니다.
   관찰할 점: 같은 계획이라도 `보류`가 사라지면 검토 요약과 다음 행동이 어떻게 달라지는가?

2. `상태 보고 작성`의 범위를 더 넓은 운영 문서나 외부 공지처럼 바꿔 봅니다.
   관찰할 점: 실행은 완료여도 회고 문장에서 `권한 범위 재검토`가 더 앞에 올라오는가?

이 절에서 직접 확인해야 하는 핵심은 `성공/실패`보다 `승인 여부와 범위가 운영 해석을 어떻게 바꾸는가`입니다.

이 절은 Part 7 전체 흐름에서 `실행 가능한 프로젝트는 권한과 로그 없이는 운영 관점이 빠진 상태`라는 점을 고정합니다.

## 체크리스트

다음처럼 에이전트 실행 흐름은 보이지만 운영 안전장치 기록이 아직 비어 있다면 이 절의 관점을 먼저 떠올리는 편이 좋습니다.

- 도구를 실제로 쓸 수는 있는데 어떤 권한 범위에서 허용되는지 적지 않은 경우
- 막힌 단계가 있었지만 기능 실패인지 승인 대기인지 구분하지 않은 경우
- 실행 로그는 남겼지만 다음 행동과 검토 대상 단계가 연결되지 않은 경우

이때는 자동화를 더 늘리기 전에 `권한 범위`, `승인 필요 여부`, `허용 범위`, `다음 행동`을 먼저 문서에 남겨야 합니다.

- 에이전트 프로젝트는 권한과 로그 없이 완성되지 않는다는 점을 설명할 수 있는가?
- 승인은 기능 부족이 아니라 운영 안전장치라는 점을 말할 수 있는가?
- 로그는 관찰의 이력이며, 회고의 근거라는 점을 설명할 수 있는가?
- 보류는 현재 권한 정책 아래의 운영 상태이며, 항상 기능 실패와 같지는 않다는 점을 말할 수 있는가?
