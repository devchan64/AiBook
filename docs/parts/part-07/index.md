# Part 7. 프로젝트

> Section ID: `P7-index`
> Version: `v2026.07.12`

Part 7은 앞에서 정리한 개념을 `작은 프로젝트 문서로 다시 확인하는 구간`입니다. 여기서는 더 새로운 이론을 길게 늘리기보다, 이미 배운 개념이 실제 프로젝트 정리 안에서 어떻게 다시 등장하는지 확인합니다.

이 Part는 특히 다음 독자에게 중요합니다.

- AI를 읽을 줄은 알지만 아직 직접 작은 결과물을 남겨 본 적이 없는 독자
- 예제 코드를 따라 했지만 `왜 이 순서로 프로젝트를 정리해야 하는지`는 아직 모호한 독자
- LLM, RAG, 에이전트 이야기를 들었지만 실제로는 무엇을 기록하고 검증해야 하는지 정리하고 싶은 독자

## 이 파트의 목적

Part 7의 목적은 거대한 서비스를 완성하는 것이 아닙니다. 오히려 다음처럼 더 작은 목표를 분명히 합니다.

- 질문을 한 문장으로 쓰기
- 데이터나 입력을 명확히 적기
- 기준점(baseline)을 두기
- 코드와 출력 결과를 남기기
- 실패와 한계를 회고 문서로 정리하기
- 필요하면 실행 기록, 평가 메모, 운영 로그까지 함께 정리하기

즉, `이해한 내용을 다시 실행 가능한 형태로 남기는 것`이 Part 7의 핵심입니다.

여기서 중요한 점은 `프로젝트를 했다`는 말을 코드 파일 하나로 대신하지 않는 것입니다. Part 7에서는 가능한 한 다음 같은 기록이 실제 프로젝트 문서 안에 함께 정리되어야 합니다.

| 기록 종류 | 왜 필요한가 |
| --- | --- |
| 프로젝트 메모와 회고 메모 | 무엇을 확인하려 했고 무엇이 아직 불안정한지 남기기 위해 필요합니다. |
| 실행 결과와 비교 표 | 기준점(baseline)과 개선 결과를 같은 눈금으로 비교하기 위해 필요합니다. |
| 테스트 기록과 평가 기록 | 샘플별 오류와 평가 근거를 다시 읽기 위해 필요합니다. |
| 검색 근거와 선택 근거 | 답변보다 먼저 어떤 근거를 썼는지 검증하기 위해 필요합니다. |
| 실행 기록과 검토 요약 | agent가 어떤 순서로 움직였고 어디서 멈췄는지 추적하기 위해 필요합니다. |
| 장애 기록과 개선 계획 | 배포 뒤 실패와 다음 조치를 분리해 남기기 위해 필요합니다. |

즉, Part 7은 `모델을 만들었다`보다 `무엇을 어떻게 기록해 다음 반복으로 넘길 것인가`를 더 엄격하게 묻는 파트입니다.

## 이 파트의 목표

- 프로젝트는 어디서부터 시작해야 하는가?
- 작은 데이터 분석도 프로젝트라고 부를 수 있는가?
- 기준점(baseline)과 개선은 어떻게 비교해야 하는가?
- 딥러닝과 텍스트 분류 프로젝트는 무엇을 최소 단위로 확인해야 하는가?
- RAG와 에이전트 프로젝트에서는 무엇을 품질 기준으로 삼아야 하는가?
- 배포와 운영에서는 어떤 실패 기록이 필요한가?

이 목표를 실제 프로젝트 문서 기준으로 옮기면 다음과 같습니다.

| 프로젝트 단계 | 최소 문서 요소 |
| --- | --- |
| 질문 설정 | 한 문장 목표, 확인할 기준 |
| 입력 정리 | 데이터, 문서, 도구, 제약 조건 |
| 기준점(baseline) | 가장 단순한 비교 기준과 그 결과 |
| 실행 | 코드, 출력, 중간 관찰 |
| 평가 | 자동 점검, 사람 검토, 비교 메모 |
| 운영 회고 | 실패 기록, 다음 개선 순서 |

이 최소 문서 요소를 Part 7의 실제 프로젝트 축으로 다시 쓰면 다음처럼 볼 수 있습니다.

| 프로젝트 축 | 대표 산출물 예시 | 이 이름을 처음 볼 때 잡아야 할 뜻 |
| --- | --- | --- |
| 분석 시작 | 프로젝트 메모, 회고 메모 | 프로젝트를 시작한 이유와 끝난 뒤 남긴 회고 메모입니다. |
| 기준점(baseline) 비교 | 실행 결과, 기준점 오류 사례 목록 | 한 번의 실행 결과와 기준점이 자주 틀린 사례 목록입니다. |
| 이미지/텍스트 분류 | 테스트 기록, 평가 판단 근거 | 샘플별 테스트 기록과 평가 판단 근거입니다. |
| RAG | 검색 기록, 근거 답변 기록 | 어떤 문서를 찾았고 어떤 근거로 답했는지 남긴 기록입니다. |
| 에이전트 | 계획한 단계, 실행 기록, 최종 정리 문서 | 계획한 순서, 실제 실행 로그, 최종 정리 문서입니다. |
| 배포/운영 | 검토 요약, 장애 기록, 개선 계획 | 검토 요약, 장애 기록, 다음 개선 순서를 적는 문서입니다. |

처음 프로젝트를 쓸 때는 각 축마다 아래 한 줄만 먼저 남겨도 흐름이 많이 또렷해집니다.

| 프로젝트 축 | 제일 먼저 남길 최소 기록 | 이 한 줄이 필요한 이유 |
| --- | --- | --- |
| 분석 시작 | `무엇을 확인하려는가` 한 문장 | 질문 없는 요약은 다음 반복으로 이어지지 않기 때문입니다. |
| 기준점(baseline) 비교 | `가장 단순한 기준 결과` 한 줄 | 좋아졌다는 말을 해석할 바닥선이 필요하기 때문입니다. |
| 이미지/텍스트 분류 | `가장 많이 틀린 샘플` 몇 개 | 점수표만으로는 오류 구조가 보이지 않기 때문입니다. |
| RAG | `어떤 문서를 근거로 썼는가` | 답변보다 근거가 먼저 남아야 다시 검증할 수 있기 때문입니다. |
| 에이전트 | `무슨 도구를 어떤 순서로 썼는가` | 성공/실패보다 실행 경로가 먼저 보여야 하기 때문입니다. |
| 배포/운영 | `무슨 실패가 났고 다음에 무엇을 바꿀 것인가` | 운영 기록은 완료 보고보다 다음 조치가 더 중요하기 때문입니다. |

## 이 파트에서 설명하는 범위와 설명하지 않을 범위

이 Part는 다음 범위를 다룹니다.

- 작은 프로젝트 목표를 세우는 방법
- 입력과 출력 정의
- 기준점(baseline)과 비교
- 결과와 한계 기록
- RAG, 에이전트, 배포 프로젝트의 기본 문서 구조

이 Part는 `실전의 전체`가 아니라 `실전으로 넘어가기 위한 최소 프로젝트 감각`을 다룹니다. 따라서 이 Part 시작 페이지에서는 `작은 질문 설정`, `기준점과 비교`, `오류 사례와 검토`, `RAG와 에이전트 실행 기록`, `배포와 실패 회고`라는 본편의 회수 축을 먼저 보여 줍니다. 권한, 운영, 실패 대응의 큰 그림은 본문 안에서도 P7-6.2 권한과 로그 검토, P7-7.1 배포와 모니터링 목표, P7-7.2 실패 기록과 개선 계획에서 다시 회수합니다.

특히 이 파트에서는 다음 구분을 계속 유지합니다.

- `분석 프로젝트`: 질문, 표, 요약값, 관찰 메모가 중심
- `모델 프로젝트`: 기준점(baseline), 예측 결과, 오류 사례가 중심
- `RAG/에이전트 프로젝트`: 근거 문서, 도구 결과, 실행 기록, 실패 로그가 중심

이 구분은 단순한 장르 분류가 아니라, 어떤 기록을 먼저 정리해야 하는지를 정하는 기준이기도 합니다.

- 분석 프로젝트에서는 `요약값`보다 `질문과 관찰 메모`가 먼저입니다.
- 모델 프로젝트에서는 `정확도(accuracy)`보다 `비교 행`과 `오류 샘플`이 먼저입니다.
- RAG 프로젝트에서는 `답변`보다 `검색 근거`와 `답변 상태`가 먼저입니다.
- 에이전트 프로젝트에서는 `성공 여부`보다 `승인 상태`와 `다음 조치`가 먼저입니다.
- 배포 프로젝트에서는 `배포 완료`보다 `장애 기록`과 `다음 조치`가 먼저입니다.

Part 7에서는 이 예시들을 별도 `보충학습`으로 다시 빼지 않습니다. 각 축의 핵심 예시를 본문 안에서 직접 따라가게 두는 편이 현재 프로젝트 입문 흐름에 더 잘 맞기 때문입니다.

## 이 파트에서 끝내지 않는 질문

Part 7은 프로젝트 입문 흐름을 다루는 파트이므로 다음 질문은 이후 실제 프로젝트로 넘깁니다.

- 팀 단위 협업 문서와 실험 추적 체계를 어떻게 설계할 것인가?
- 더 큰 데이터셋과 더 긴 운영 로그를 어떤 기준으로 관리할 것인가?
- 배포 자동화와 권한 검토를 어느 단계까지 문서화할 것인가?

즉, Part 7은 `프로젝트를 시작하고 회고하는 최소 구조`를 닫는 파트이지, 모든 실무 체계를 여기서 끝내는 파트는 아닙니다.

## 이 파트를 읽고 나면 생겨야 할 이해

Part 7을 읽고 나면 독자는 다음 정도의 감각을 가져야 합니다.

- 프로젝트는 구현보다 먼저 질문과 기준점을 정해야 한다.
- 작은 데이터 분석도 유효한 프로젝트 단위가 될 수 있다.
- 기준점(baseline)과 개선 비교가 없는 모델 결과는 해석이 약하다.
- LLM 프로젝트는 답변 예시뿐 아니라 검색 실패, 도구 실패, 권한, 로그까지 함께 기록해야 한다.
- 프로젝트 회고는 실패를 숨기는 문서가 아니라 다음 반복을 준비하는 문서다.

이 다섯 줄을 가장 짧게 묶으면 다음과 같습니다.

`프로젝트는 결과물 하나를 만드는 일이 아니라, 다음 반복에 다시 쓸 수 있는 기록을 남기는 일이다.`

## 프로젝트 문서의 공통 형식

Part 7의 각 프로젝트는 가능한 한 다음 흐름으로 씁니다.

- 문제 정의
- 데이터 또는 입력
- 접근 방법
- 구현
- 결과
- 한계와 개선점
- 출처와 참고 자료

이 형식은 기계적인 템플릿이라기보다, 프로젝트를 다시 실행하고 다시 읽을 수 있게 만드는 최소 공통 구조입니다.

생성형 AI 관련 프로젝트에서는 여기에 다음 항목이 자주 추가됩니다.

- 근거 문서 또는 검색 결과
- 도구 호출 결과 또는 실행 로그
- 자동 평가 결과
- 사람 검토 메모
- 실패 시 실행 기록 또는 대체 조치 기록

이 공통 형식을 독자가 다시 점검할 때는 다음처럼 읽어도 좋습니다.

| 문서 질문 | 확인할 기록 | 이 기록을 보는 이유 |
| --- | --- | --- |
| 무엇을 하려 했는가? | 목표 문장, 계획 단계, 프로젝트 메모 | 질문과 계획이 없으면 실행 로그만 남고 목적이 사라지기 때문입니다. |
| 무엇을 넣었는가? | 데이터 표, 문서 조각, 도구 목록 | 입력이 빠지면 같은 프로젝트를 다시 실행할 수 없기 때문입니다. |
| 어떻게 비교했는가? | 기준점(baseline), 비교 표, 평가 기록 | 좋아졌다는 말을 같은 기준으로 해석해야 하기 때문입니다. |
| 무엇이 근거였는가? | 선택 근거, 검색 후보 | RAG와 에이전트 결과를 나중에 다시 검증해야 하기 때문입니다. |
| 어디서 멈췄는가? | 막힌 상태, 근거 부족 상태, 실패 상태 | 실패 지점을 남겨야 다음 반복의 출발점이 생기기 때문입니다. |
| 다음에 무엇을 바꿀 것인가? | 검토 요약, 개선 계획 | 회고가 감상문이 아니라 다음 조치로 이어져야 하기 때문입니다. |

이 질문들을 더 실전적으로 줄이면 다음처럼도 점검할 수 있습니다.

| 프로젝트 축 | 나쁜 기록에서 빠지기 쉬운 것 | 좋은 기록이 먼저 남기는 것 |
| --- | --- | --- |
| 분석 | 결과 숫자만 적음 | 질문, 관찰, 다음 질문 |
| 모델 | 정확도만 적음 | 기준점(baseline), 오류 샘플, 비교 이유 |
| RAG | 답변만 적음 | 근거 문서, 답변 상태, 부족 근거 |
| 에이전트 | 성공 여부만 적음 | 도구 순서, 승인 상태, 막힌 지점 |
| 배포 | 장애가 있었다고만 적음 | 장애 범주, 우선순위, 다음 조치 |

## 완료 기준

- 작은 프로젝트를 질문, 입력, 구현, 결과, 회고 흐름으로 정리할 수 있다.
- 기준점(baseline)과 개선 모델의 차이를 문서로 설명할 수 있다.
- RAG와 에이전트 프로젝트에서 품질과 운영 관점을 함께 적을 수 있다.
- 실패 기록과 다음 개선 계획을 프로젝트 결과 안에 남길 수 있다.

가장 짧게 줄이면 Part 7의 완료 기준은 다음 한 문장으로 묶입니다.

`작은 프로젝트라도 다시 실행할 수 있는 기록과 다음 반복을 위한 회고를 남길 수 있어야 한다.`

## 언제 Part 7을 다시 펼쳐야 하는가

다음처럼 개념은 읽었지만 프로젝트 산출물 형태로 다시 묶는 감각이 흐려질 때 Part 7을 다시 펼치는 편이 좋습니다.

- 결과 숫자는 남기는데 기준점(baseline), 오류 사례, 회고 메모가 빠지는 경우
- RAG나 agent를 설명하면서도 근거 기록, 실행 기록, 권한 기록이 함께 남지 않는 경우
- 배포 이후 무엇을 확인하고 무엇을 실패 기록으로 남겨야 하는지 기준이 흔들리는 경우

이때는 새 기능을 더 붙이기 전에 Part 7의 대표 Section를 따라 `질문 -> 실행 -> 평가 -> 회고` 구조를 다시 고정하는 편이 맞습니다.

## 체크리스트

- 프로젝트 목표를 한 문장으로 다시 적을 수 있는가?
- 기준점(baseline), 평가 기록, 실패 기록 중 무엇이 빠졌는지 바로 말할 수 있는가?
- RAG와 agent에서 근거/도구/권한 기록을 분리해 남길 수 있는가?
- 다음 반복을 위한 회고 문장을 각 프로젝트 축마다 남길 수 있는가?
