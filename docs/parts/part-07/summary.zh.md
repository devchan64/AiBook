# Part 7 收尾：项目整理

> Section ID: `P7-summary`
> Version: `v2026.07.12`

Part 7 是一个把前面六个 Part 里恢复并整理过的概念，重新放进 `小型产出物` 里再确认的区段。这个 Part 的核心，不是完成大型服务，而是亲手走一遍问题定义、数据准备、实现、评估、回顾这条共同流程。

这个项目 Part 尤其会同时确认两件事。

- 能不能解释这个概念？
- 能不能用小代码和小结果把这个概念再确认一次？

也就是说，这个 Part 是把 `我知道了` 变成 `我试过了，也留下了记录` 的区段。

## 这一 Part 的目的

Part 7 的目的，是把整本书里学到的概念重新绑进小型项目文档与执行结果里，让下一轮学习变成读者自己也能反复进行的形式。

重新打开 Part 7 时，最快的方式是直接抓住代表 Section 作为把手。分析起点是 `P7-1.1`，`事实 -> 解释 -> 下一问题` 的回顾结构是 `P7-1.2`，基准点比较是 `P7-2.2`，文本评估记录是 `P7-4.2`，RAG 验证是 `P7-5.2`，agent 权限与日志是 `P7-6.2`，部署失败回顾是 `P7-7.2`。

## 这一 Part 的目标

完成这个 Part 之后，你应该能解释：怎样把问题定义、基准点、结果、失败记录、下一步改进计划，留成一组小产出物。

## 这一 Part 走过的核心流程

Part 7 的整体流程可以整理成下面这样。

1. 读取小数据，并概括问题与探索结果。
2. 比较基准模型（baseline）与改进模型。
3. 把深度学习与文本分类流程缩成小例子。
4. 把 RAG 与 agent 结构连到小型服务项目。
5. 留下部署、日志、失败应对与回顾文档。

如果按 `产出物` 的角度重新绑这条流程，就会变成下面这样。

| 项目轴 | 必须留下来的核心记录 | 为什么需要这个记录 |
| --- | --- | --- |
| 分析起点 | 项目笔记、回顾笔记 | 只有把当时想看什么、下次还要回来看什么留下来，下一轮探索才接得上。 |
| 基准点比较 | 执行摘要、逐样本比较表、错误案例列表 | 只有把执行结果和错误案例一起留下，改进才解释得起来。 |
| 图像/文本分类 | 测试记录、评估记录、错误样本 ID | 因为必须重新读样本级判断依据，而不是只看分数表。 |
| RAG | 检索记录、选择依据、依据回答记录 | 因为必须先检查检索依据与连接方式，再去看答案本身。 |
| agent | 计划列表、执行记录、回顾摘要 | 只有把计划和真实执行路径分开看，卡住点才追得出来。 |
| 部署与运营 | 失败记录、改进计划 | 只有把失败留下并把下一步动作分开，运营回顾才会累积。 |

如果再把这张表压到最短，各轴最先不能丢掉的记录就是下面这些。

| 项目轴 | 最先不能丢掉的记录 |
| --- | --- |
| 分析起点 | 一句问题与观察笔记 |
| 基准点比较 | 最简单的基准结果 |
| 图像/文本分类 | 代表性错误样本与评估记录 |
| RAG | 依据文档与回答状态 |
| agent | 工具顺序与审批状态 |
| 部署与运营 | 失败类别与下一步动作 |

虽然每个项目主题不同，但必须留下来的问题其实是一样的。

1. 想解决什么？
2. 输入与输出是什么？
3. 数据是怎样准备的？
4. 基准点是什么？
5. 结果是怎样确认的？
6. 失败与局限是什么？
7. 下一步改进应该从哪里开始？

## 必须记住的概念

Part 7 里一定要带走的视角如下。

| 区分 | 要记住的视角 |
| --- | --- |
| 问题定义 | 项目应当先把问题说清，再谈实现。 |
| 基准点 | 没有基准点，就连“变好了”这句话也会变弱。 |
| 数据 | 就算是玩具数据，输入、输出、切分标准也必须明确。 |
| 评估 | 项目结果必须同时通过数字与案例来读。 |
| 回顾 | 把失败、遗漏、模糊处留下来，本身就是项目文档的核心。 |
| 可复现性 | 必须留下输入、代码、输出记录，项目才能再次运行。 |
| 服务视角 | 在 LLM 项目里，不只是回答质量，检索失败、权限、延迟、日志也要一起看。 |

如果把这个视角再往实务方向推一步，会看到很多时候 `留下了什么记录` 比 `最后结果数字是多少` 更重要。

- 在基准点比较项目里，不只是 `accuracy`，还必须留下 `哪些样本错了`。也就是说，像错误案例列表这样的记录必须存在，下一轮比较才活得起来。
- 在文本项目里，不只是 `对/错`，token 列表、token coverage、词表外 token 也必须留下。你必须看见什么输入被切开了、什么词没进来，才能把预处理问题再找回来。
- 在 RAG 项目里，不只是 `回答`，还必须留下检索候选、回答状态、被选中的依据文档。因为质量复核的起点不是答案本身，而是依据选择过程。
- 在 agent 项目里，不只是 `成功/失败`，还必须留下权限、审批状态、下一步动作。只有知道出现过什么审批与阻断，执行路径才能被重新设计。
- 在部署项目里，不只是 `部署完成`，还必须留下失败记录、优先级、下一步动作。因为运营记录里，下一步动作顺序比完成声明更重要。

由于这些例子轴已经在 Part 7 里分散但充分地回收，所以当前版本不再需要额外的项目 `补充学习`。相反，更重要的是让各节正文示例直接 보여出 `问题 -> 记录 -> 回顾` 这条流。

## 容易误解的地方

这个 Part 里尤其要小心下面这些误解。

- 很容易以为项目只需要留下 `成功案例`。
- 很容易误以为一个结果数字高了，项目就算做得好。
- 做出一个小例子，并不等于立刻理解了生产型服务结构。
- 代码执行过了，与问题定义本身合理，不是同一回事。
- 在 LLM 项目里，一两次回答看起来不错，并不代表评估已经结束。
- 如果不记录运营失败，下一轮改进会很困难。

也就是说，项目文档不应该只证明 `它曾经成功一次`，而应该证明 `下一轮是可能继续的`。

## 这一 Part 解释什么，不解释什么

Part 7 把重点放在解释项目入门结构上。因此，小目标设定、实现、评估、回顾、运营记录会处理，但不会在这里把大规模基础设施与长期运营体系全部讲完。

## 这一 Part 不在这里结束的问题

Part 7 会把下面这些问题交给读者之后的真实项目。

- 下一个真实项目要扩展什么主题？
- 评估与失败记录要怎样长成团队级文档？
- 运营与部署要自动化到什么程度，人工复核又放在哪里？

也就是说，Part 7 与其说是这本书的终点，不如说是后续自主项目的起点。

而且这些问题其实已经在 Part 7 里以很小的形式被预告过了。

- 基准点比较可以长成更大的实验追踪系统。
- token coverage 与 OOV 记录可以连到更精细的 tokenizer 实验。
- RAG 中的依据不足状态记录，可以长成更严格的评估流水线。
- agent 里的运营保留与需要审批的工具记录，可以扩成真实运营策略文档。
- 部署失败记录，会成为团队级事故回顾文档的种子。

## 进入下一阶段学习前要确认的问题

- 能不能用一句话解释每个项目的问题定义与输出标准？
- 有没有把基准点与改进项分开记录？
- 数据准备与切分过程能不能再次执行？
- 结果有没有同时通过数字与案例来读？
- 有没有留下失败案例与改进计划？
- 如果是 LLM 项目，有没有同时检查检索、工具调用、权限、日志、失败应对？

真正重新打开项目文档时，下面这些产出物检查也应当一起确认。

- 有没有执行摘要或回顾摘要？
- 有没有比较表、测试记录、评估记录这类逐样本记录？
- 有没有选择依据、检索候选这类依据记录？
- 有没有执行记录与失败记录这类运营流程记录？

如果把这个检查再压短一点，就会变成下面这样。

| 先检查什么 | 为什么重要 |
| --- | --- |
| 问题还在不在 | 为了重新找回项目当时想验证什么 |
| 基准点还在不在 | 为了重新找回解释改进时的地板线 |
| 错误或失败还在不在 | 为了给下一轮建立出发点 |
| 依据与执行路径还在不在 | 为了重新验证 RAG / agent 的结果 |
| 下一步动作还在不在 | 为了避免回顾只停成一条备忘 |

## Part 7 收尾

项目 Part 的目的，不是做出一个很大的产出物。相反，它更重要的作用，是通过一个小产出物把 `我已经理解了什么、什么地方还不稳定` 显露出来。

完成这个 Part 之后，读者应该能够自己设计下一步。

- 扩展到更大的数据集
- 接上更合适的评估指标
- 对 RAG 质量做比较实验
- 更精细地整理 agent 权限与日志策略
- 把运营成本与失败应对拆成独立文档

也就是说，Part 7 不是结束，而是通向 `从现在开始自己做项目、再通过项目重新学习` 的起点。

最短地说，Part 7 的结论可以收成下面这一句。

`好的项目文档，先留下能再次阅读、再次执行的记录，然后才是模型或代码本身。`

## 什么时候应该重新打开 Part 7 总结

当一个项目做完之后，你想再压缩一次看看究竟该留下什么时，就很适合重新打开这个总结页。例如：

- 做了实现，但不确定问题、基准点、失败记录是否一起留下
- 想重新捆一遍 RAG、agent、部署项目之间共同的记录要素
- 想在进入下一个真实项目之前，先整理应该留下什么样的回顾句子

这时，与其先重新散回各个细节节，不如先回到这个总结页，先确认 `解决了什么`、`留下了什么记录`、`下一步要改什么`。

## 检查清单

- 能不能把各个项目轴最先应该留下的记录，再各自写成一句？
- 能不能解释为什么基准点与失败记录是 Part 7 全体工作的共同标准？
- 能不能重新说清为什么 RAG、agent、部署工作都需要运营视角记录？
- 能不能整理出会立刻带进下一个真实项目的回顾格式？
