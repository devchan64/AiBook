# Part 7. 项目

> Section ID: `P7-index`
> Version: `v2026.07.12`

Part 7 是一个把前面整理过的概念，重新放进 `小型项目文档` 里再确认一次的区段。在这里，与其继续拉长新的理论，不如去确认已经学过的概念，怎样会在真实的项目整理里再次出现。

这个 Part 尤其适合下面这些读者。

- 已经能读 AI 说明，但还没有亲手留下过小成果的读者
- 跟过示例代码，却仍然不清楚 `为什么项目要按这个顺序整理` 的读者
- 听过 LLM、RAG、agent，但想把到底要记录什么、验证什么整理清楚的读者

## 这一 Part 的目的

Part 7 的目的，不是完成一个庞大的服务。相反，它更明确地把目标缩小成下面这些事。

- 用一句话写清问题
- 把数据或输入写清楚
- 设一个基准点（baseline）
- 留下代码与输出结果
- 把失败与局限整理进回顾文档
- 如果需要，也把执行记录、评估笔记、运营日志一起整理

也就是说，Part 7 的核心是 `把已经理解的内容重新留成可执行的形式`。

这里重要的一点是，不要让一句 `我做过项目了` 被单个代码文件取代。在 Part 7 里，尽可能要把下面这些记录真实地一起整理进项目文档。

| 记录类型 | 为什么需要 |
| --- | --- |
| 项目笔记与回顾笔记 | 为了留下当时想确认什么、哪些地方还不稳定。 |
| 执行结果与比较表 | 为了把基准点（baseline）与改进结果放在同一刻度上比较。 |
| 测试记录与评估记录 | 为了重新阅读样本级错误与评估依据。 |
| 检索依据与选择依据 | 为了先验证回答之前到底用了什么依据。 |
| 执行记录与复核摘要 | 为了追踪 agent 按什么顺序行动、又在哪一步停下。 |
| 失败记录与改进计划 | 为了把部署后的失败与下一步动作分开留下。 |

换句话说，Part 7 更严格追问的不是 `你是不是做出了模型`，而是 `你打算把什么记录下来并交给下一轮`。

## 这一 Part 的目标

- 项目应该从哪里开始？
- 小型数据分析也能叫项目吗？
- 基准点与改进应该怎样比较？
- 在深度学习与文本分类项目里，什么是最小确认单位？
- 在 RAG 与 agent 项目里，什么应当被当成质量标准？
- 在部署与运营里，需要留下什么样的失败记录？

如果把这些目标换成真实项目文档的标准，就会变成下面这样。

| 项目阶段 | 最小文档元素 |
| --- | --- |
| 问题设置 | 一句话目标、要确认的标准 |
| 输入整理 | 数据、文档、工具、约束条件 |
| 基准点 | 最简单的比较标准及其结果 |
| 执行 | 代码、输出、中间观察 |
| 评估 | 自动检查、人工复核、比较笔记 |
| 运营回顾 | 失败记录、下一步改进顺序 |

如果再把这些最小文档元素改写成 Part 7 的真实项目轴，也可以读成下面这样。

| 项目轴 | 代表产出物示例 | 第一次看到这个名字时要抓住的意思 |
| --- | --- | --- |
| 分析起点 | 项目笔记、回顾笔记 | 说明项目为何开始，以及结束后留下的回顾笔记 |
| 基准点比较 | 执行结果、基准点错误案例列表 | 一次运行的结果，以及基准点经常出错的案例列表 |
| 图像/文本分类 | 测试记录、评估依据 | 样本级测试记录与评估判断依据 |
| RAG | 检索记录、依据回答记录 | 留下找到了什么文档、又根据什么依据作答的记录 |
| agent | 计划步骤、执行记录、最终整理文档 | 计划顺序、实际执行日志、最终整理文档 |
| 部署/运营 | 复核摘要、失败记录、改进计划 | 复核摘要、失败记录、下一步改进顺序 |

刚开始写项目时，即使每个轴先只留下面这一句，整体流程也会清楚很多。

| 项目轴 | 最先要留下的最小记录 | 为什么需要这一句 |
| --- | --- | --- |
| 分析起点 | 一句 `想确认什么` | 因为没有问题的总结，无法连到下一轮。 |
| 基准点比较 | 一句 `最简单基准结果` | 因为要解释“变好了”，就必须先有地板线。 |
| 图像/文本分类 | 几个 `最常出错的样本` | 因为光看分数表看不出错误结构。 |
| RAG | `用了哪份文档作为依据` | 因为要能之后重新验证，必须先留下依据而不是只留答案。 |
| agent | `按什么顺序用了哪些工具` | 因为在解释成败之前，先要看见执行路径。 |
| 部署/运营 | `发生了什么失败、下一步改什么` | 因为在运营里，下一步动作比完成报告更重要。 |

## 这一 Part 解释什么，不解释什么

这个 Part 会处理下面这些范围。

- 怎样设定一个小项目目标
- 输入与输出定义
- 基准点与比较
- 结果与局限记录
- RAG、agent、部署项目的基本文档结构

这个 Part 不会深入处理下面这些内容。

- 大规模训练基础设施搭建
- 复杂 MLOps 流水线自动化
- 长期运营成本优化的深度分析
- 生产级安全策略设计的全部内容

在这些被省略的项目中，成本、运营、权限、失败应对的大图景，仍会通过正文里的 `P7-6.2` 权限与日志、`P7-7.1` 部署与监控目标、`P7-7.2` 失败记录与改进计划再被回收。相对地，大规模训练基础设施与生产级服务的完整安全设计，则被放在这本书当前的入门项目范围之外。

也就是说，这个 Part 处理的不是 `实战的全部`，而是 `跨进实战前必须先有的最小项目感觉`。

特别是，这个 Part 会一直维持下面这些区分。

- `分析项目`：问题、表、摘要值、观察笔记是中心
- `模型项目`：基准点、预测结果、错误案例是中心
- `RAG / agent 项目`：依据文档、工具结果、执行记录、失败日志是中心

这个区分不只是类型分类，也是决定应该先整理什么记录的标准。

- 在分析项目里，`问题与观察笔记` 先于摘要值。
- 在模型项目里，`比较行` 与 `错误样本` 先于单独的 accuracy。
- 在 RAG 项目里，`检索依据` 与 `回答状态` 先于回答本身。
- 在 agent 项目里，`审批状态` 与 `下一步动作` 先于成功/失败。
- 在部署项目里，`失败记录` 与 `下一步动作` 先于部署完成。

Part 7 不会再把这些例子重新抽成单独的 `补充学习`。就当前项目入门流程来说，让每个轴的核心例子直接在正文里被跟着走完，会更合适。

## 这一 Part 不在这里结束的问题

由于 Part 7 处理的是项目入门流程，下面这些问题会交给读者之后的真实项目去继续。

- 团队级协作文档与实验追踪系统应该怎样设计？
- 更大的数据集与更长的运营日志，应该按什么标准管理？
- 部署自动化与权限复核应当记录到什么程度？

换句话说，Part 7 是闭合 `如何开始与回顾一个项目的最小结构` 的 Part，而不是在这里把所有实务系统都讲完的 Part。

## 读完这一 Part 后会形成的理解

读完 Part 7 之后，读者应该形成大致下面这些感觉。

- 项目应该在实现之前先定好问题与基准点。
- 即使是小型数据分析，也可以是有效的项目单位。
- 没有基准点比较与改进比较的模型结果，很难被解释得扎实。
- 在 LLM 项目里，不只是回答示例，检索失败、工具失败、权限、日志也都要一起记录。
- 项目回顾不是隐藏失败的文档，而是为下一轮准备的文档。

如果把这五行压成最短形式，就会变成下面这一句。

`项目不是做出一个结果，而是留下下一轮还能再次使用的记录。`

## 项目文档的共同格式

Part 7 里的各个项目，尽可能都按下面这条流程来写。

- 问题定义
- 数据或输入
- 方法
- 实现
- 结果
- 局限与改进点
- 来源与参考资料

这个格式不是机械模板，而是让项目可以被再次执行、再次阅读的最小共同结构。

在生成式 AI 相关项目里，下面这些项目也会经常额外出现。

- 依据文档或检索结果
- 工具调用结果或执行日志
- 自动评估结果
- 人工复核笔记
- 失败时的执行记录或替代措施记录

当读者重新检查这个共同格式时，也可以用下面这些问题来读。

| 文档问题 | 要看的记录 | 为什么要看这个记录 |
| --- | --- | --- |
| 想做什么？ | 目标句、计划步骤、项目笔记 | 因为如果没有问题与计划，就只会剩下执行日志，目的会消失。 |
| 放进去了什么？ | 数据表、文档片段、工具列表 | 如果输入缺失，就无法重新执行同一个项目。 |
| 怎样比较的？ | 基准点、比较表、评估记录 | 因为“变好了”的说法必须通过同一标准来解释。 |
| 依据是什么？ | 选择依据、检索候选 | 因为 RAG 与 agent 的结果之后还要能重新验证。 |
| 停在了哪里？ | 卡住状态、依据不足状态、失败状态 | 因为只有留下失败点，下一轮才有出发点。 |
| 下次要改什么？ | 回顾摘要、改进计划 | 因为回顾不能停成备忘，而要通向下一步动作。 |

这些问题如果再更实务地压缩，也可以变成下面这样。

| 项目轴 | 薄弱记录最容易漏掉的东西 | 好记录会先留下什么 |
| --- | --- | --- |
| 分析 | 只有结果数字 | 问题、观察、下一问题 |
| 模型 | 只有 accuracy | 基准点、错误样本、比较理由 |
| RAG | 只有答案 | 依据文档、回答状态、缺失依据 |
| agent | 只有成功/失败 | 工具顺序、审批状态、卡住点 |
| 部署 | 只有发生过故障 | 失败类别、优先级、下一步动作 |

## 完成标准

- 能把一个小项目整理成问题、输入、实现、结果、回顾的流程。
- 能用文档形式说明基准点与改进模型的差别。
- 能在 RAG 与 agent 项目里把质量视角和运营视角一起写下来。
- 能把失败记录与下一步改进计划留在项目结果里。

如果压到最短，Part 7 的完成标准可以收成下面这一句。

`即使是一个小项目，也要能留下让它再次执行的记录，以及为下一轮准备的回顾。`

## 什么时候应该重新打开 Part 7

当概念已经读过，但把它重新绑成项目产出物的感觉开始变模糊时，就适合再打开 Part 7。例如：

- 虽然留下了结果数字，但已经不确定基准点、错误案例、回顾笔记是否一起留下
- 在说明 RAG 或 agent 时，依据记录、执行记录、权限记录没有一起被留下
- 部署之后该看什么、哪些该作为失败记录留下，这个标准开始发虚

这时候，与其先继续往上贴更多新功能，不如先沿着 Part 7 的代表 Section，把 `问题 -> 执行 -> 评估 -> 回顾` 的结构重新固定回来。
