# P1-4.3 特征、表征与参数

> Section ID: `P1-4.3`
> Version: `v2026.07.08`

4.2 整理了 `input`、`output` 和 `data`。这一节往模型内部再走一步，问的是：当真正开始计算时，输入在模型里到底会变成什么样子？

核心问题是：模型看到的是不是原始输入本身，还是会先把它变成更容易计算的值？

这一节用入门层级介绍 `feature`、`representation` 和 `parameter`。重点不是教人从零搭模型，而是让读者能看懂这些词在模型里的位置。

## 这一节的范围

这里不讲如何从头构建模型，也不讲完整的学习流程。算法选择、模型结构和更细的训练过程，会在 Part 4 和 Part 5 再回收。

这一节只回答一个更小的问题：当我们看一个已经定义好的模型时，输入会变成什么值，模型内部又有哪些值会参与输出计算？

## 这一节的目标

- 把 `feature` 理解成模型实际用来计算的输入值。
- 把 `representation` 理解成把原始数据变成更易计算形式后的结果。
- 把 `parameter` 理解成模型内部、参与输出计算的已调整数值。
- 区分原始输入、特征、表征与参数并不是同一个东西。
- 为 4.4 里“问题定义如何影响模型”做准备。

## 三个基准

| 基准 | 为什么重要 | 这一节需要达到的理解程度 |
| --- | --- | --- |
| `feature` 是计算时真正使用的输入值 | 这样能看见人读的原句和模型使用的计算值并不总是同一个东西。 | 区分原始句子与计算用线索。 |
| `representation` 是把数据变成更易计算形式后的结果 | 这会成为后面理解深度学习和 embedding 的基础。 | 理解同一数据可以被改写成不同内部形式。 |
| `parameter` 是模型内部被调整过的值 | 这会直接连到后面的 training 和 inference。 | 区分输入值与模型内部会被调好的值。 |

## 原始输入通常不能直接拿来算

回到客服消息的例子。

> 如果明天还收不到配送，我就取消。

人会同时看到很多线索。

| 人能直接看到的线索 | 可能代表的含义 |
| --- | --- |
| 配送 | 与配送相关 |
| 明天之前 | 时间条件 |
| 还收不到 | 可能有延迟 |
| 我就取消 | 取消意图或施压语气 |

但模型不会像人那样直接理解整句。为了计算，它得先把输入变成某种值。这时就会出现 `feature` 和 `representation`。

> original input -> feature or representation -> model computation -> output

这里最重要的区分是：`原始文本` 和 `模型真正拿来计算的值`，并不一定一样。

## feature 是模型会直接使用的输入值

在机器学习里，`feature` 可以先理解成：模型读进去并参与计算的输入变量。

在客服消息例子里，非常简单的特征可以长这样。

| 原始输入 | 特征例子 |
| --- | --- |
| “我想退款。” | 是否出现 `退款` |
| “配送什么时候到？” | 是否出现 `配送` |
| “商品寄来时是坏的。” | 是否出现损坏相关表达 |
| “我想修改地址。” | 是否出现地址修改相关表达 |

这些特征可以由人预先设计。

| 消息句子 | `退款` 线索 | `配送` 线索 | `损坏` 线索 | label |
| --- | ---: | ---: | ---: | --- |
| “我想退款。” | 1 | 0 | 0 | 退款 |
| “配送什么时候到？” | 0 | 1 | 0 | 配送 |
| “商品寄来时是坏的。” | 0 | 0 | 1 | 换货 |

在这一阶段，只要把 `feature` 理解成“模型实际使用的输入值”就够了。

## feature 不是原始输入本身

这一点很重要。

| 区分 | 例子 |
| --- | --- |
| 原始输入 | “我昨天收到的商品坏了，想换一个新的。” |
| 人设计的特征 | 有损坏线索，有换货线索 |
| 输出标签 | 换货或补发 |

原始输入是一句自然语言；特征则是为了让模型能算，先从句子里抽出来的值。

如果不分清这个层次，就很容易以为“把数据喂给模型，它就会自己懂”。但真正重要的问题是：我们抽了什么值、留下了什么线索、又以什么形式把输入送到模型里。

## representation 是把数据变得更容易计算的结果

`representation` 可以先更宽泛地理解成：把原始数据改写成模型更容易处理的形式之后得到的结果。

同一条客服消息，可以被改写成不同表征。

| 表征方式 | 例子 | 优势 | 限制 |
| --- | --- | --- | --- |
| 关键词特征 | `配送` 出现、`取消` 出现 | 简单、易解释 | 容易漏掉上下文 |
| 数值特征 | 句子长度、感叹号数量 | 易和表格数据结合 | 难以保留足够语义 |
| 类别特征 | 消息渠道：App / 邮件 / 电话 | 易和业务字段连接 | 本身不包含句子意义 |
| 学到的表征 | 把句子转成内部向量 | 更能处理相似性与上下文 | 不容易直接阅读 |

这里的重点是：输入被怎样表示，决定了模型能“看到”怎样的世界。

## 好的表征会显露出真正重要的差别

看这两句话：

> 我想取消付款。  
> 如果物流还不到，我就取消。

它们都包含 `取消`，但前一句更接近付款取消或退款，后一句更接近配送延迟下的条件性取消。

| 表征 | 容易区分这两句吗？ | 为什么 |
| --- | --- | --- |
| 只看是否出现 `取消` | 不容易 | 两句都含有相同的词 |
| 同时看 `配送` 和 `取消` 线索 | 稍微好一些 | 第二句的配送语境开始显现 |
| 用整句级别的更广表征 | 可能好很多 | 条件、意图和上下文都能一起进入 |

好的表征，会帮助模型看见任务真正关心的差异。

## parameter 是模型内部被调整过的值

如果说特征与表征更接近“进入模型时的值形状”，那么 `parameter` 就是模型内部被调整过的值。

在入门层级上，可以把它理解成：

> parameter = 模型把输入变成输出时所依赖的可调内部值

这里最常见的一个词是 `weight`。它是参数的一种，表示某个输入值或内部值对输出的影响有多强。

把客服消息分类问题极度简化后，可以把参数直观地想成下面这样。

| 特征 | 对退款输出影响多强？ | 对配送输出影响多强？ |
| --- | ---: | ---: |
| `退款` 线索 | 强 | 弱 |
| `配送` 线索 | 弱 | 强 |
| `取消` 线索 | 中 | 中 |

这并不是一张真实参数表，只是帮助直观理解参数在做什么。

## 参数、超参数和生成设置不是一回事

初学者很容易混淆，因为像 `temperature`、`top-p`、`max tokens` 之类的值有时也会被叫作参数。

但它们和模型参数不是同一层东西。

| 区分 | 例子 | 谁来定？ | 什么时候使用？ | 含义 |
| --- | --- | --- | --- | --- |
| model parameter | weight, bias | 训练过程中学出来 | 模型内部计算 | 通过学习得到并存放在模型里的值 |
| hyperparameter | learning rate, batch size | 人或调参过程 | 训练设置 | 决定学习过程条件的值 |
| generation setting | temperature, top-p, max tokens | 用户或服务配置 | inference / generation | 改变训练后模型如何选输出的设置 |

所以，当这一节说“学习会改变参数”时，说的是第一类 `model parameters`。

## 这一节要记住的内容

最安全的第一层区分是：

> feature = 参与计算的线索值  
> representation = 数据被改写后的内部形式  
> parameter = 用来计算输出的内部已调整值

只要这个区分稳定下来，4.4 里更大的问题就更容易理解：我们如何定义问题，才会决定需要什么样的模型。
