# P1-4.4 问题定义如何决定模型

> Section ID: `P1-4.4`
> Version: `v2026.07.07`

4.1 把 `model` 看成是为了某个目的而缩减出来的可计算表示；4.2 整理了 `input`、`output` 和 `data`；4.3 则说明输入会被转成 `features` 和 `representations`，再和内部 `parameters` 一起参与计算。

这一节把前面的脉络收束成一个问题：怎样把现实目标定义成一个 AI 任务？

`problem definition` 看起来像是在建模之前做的规划工作，但实际上，它会一起决定模型类型、所需数据、评价标准，以及输出怎样接到真实工作里去。

## 这一节的范围

这里不讲准确率、精确率、召回率、损失函数这些评价指标的详细公式；它们会在 Part 4 再展开。

这里也不讲完整的 AI 服务架构。路由、权限检查、人工复核、工具调用和上线后的监控，会在 P1-14 和 Part 7 再说。

这一节只讲前面那一步：把现实目标变成某种输入-输出任务，并决定“怎样才算做得好”。

## 这一节的目标

- 区分 `real-world goal` 和 `modeling task`。
- 理解：同一个现实目标，可以被拆成不同的 AI 任务。
- 看到：一旦输出定义改变，数据、模型和评价标准也会一起改变。
- 理解模型表现和业务表现并不总是一回事。
- 总结“把问题变成模型”到底意味着什么。

## 三个基准

| 基准 | 为什么重要 | 这一节需要达到的理解程度 |
| --- | --- | --- |
| `real-world goal` 和 `modeling task` 不是同一个东西 | 这样才不会夸大 AI 解决问题的范围。 | 区分“提升客户满意度”和“给客服消息分类”。 |
| 同一个目标可以被改写成不同输出定义 | 这样能看清分类、分数预测和生成为什么会分岔。 | 固定“必须先决定模型输出什么”。 |
| 输出定义会连带改变数据与评价标准 | 这说明在选模型之前，问题设计本身已经很关键。 | 理解只要输出变了，所需案例和“成功”的含义也会跟着变。 |

## 现实目标还不是建模任务

`我们想更好地处理客户支持消息` 是一个现实目标。但光有这句话，还不足以告诉模型该做什么。

要成为建模任务，它必须被改写成更具体的形式。

| 现实目标 | 改写后的建模任务表达 |
| --- | --- |
| 我们想更好地处理客户支持消息 | 根据支持消息文本分类消息类型 |
| 我们想减少配送问题 | 根据订单信息预测配送延迟的可能性 |
| 我们想减少重复客服工作 | 根据消息和政策生成回复草稿 |
| 我们想减少风险交易 | 根据交易信息输出风险分数 |

所以，问题定义做的事就是：

> real-world goal -> modeling task -> input / output / data / evaluation

## 同一个目标可以变成很多不同任务

即使目标同样是“帮助处理客户支持消息”，只要我们要求模型产出的东西不同，它就会变成不同问题。

| 交给模型的任务 | 输出 | 任务性质 |
| --- | --- | --- |
| 选出消息类型 | `退款`、`配送`、`换货`、`其他` | classification |
| 预测紧急程度 | 1 到 5 的分数 | regression 或分数预测 |
| 推荐负责团队 | 物流、支付、客服 | classification 或 recommendation |
| 写回复草稿 | 自然语言句子 | generation |
| 判断是否需要人工复核 | 是 / 否 | binary classification |

假设同一句输入是：

> 我昨天刚下单，但现在还查不到物流。

| 输出定义 | 可能输出 | 所需数据 |
| --- | --- | --- |
| 消息类型分类 | 配送 | 消息文本加消息类型标签 |
| 紧急程度预测 | 2 | 消息文本加紧急程度分数 |
| 回复草稿生成 | “物流信息同步可能需要一些时间……” | 消息、订单状态、政策和好回复样例 |
| 是否要人工复核 | 否 | 消息加“自动处理是否安全”的标签 |

所以，在问“该用什么模型”之前，得先问“它到底要输出什么”。

## 输出定义会改变评价方式

一旦输出被确定，接下来就得决定什么算做得好。

在客服消息例子里，评价标准会随着输出定义一起变化。

| 输出定义 | 可能关注的评价标准 |
| --- | --- |
| 消息类型分类 | 准确率、精确率、召回率、混淆矩阵 |
| 紧急程度分数 | 真实紧急程度与预测分数的差距 |
| 回复草稿生成 | 事实性、政策合规、语气、安全性、人工审查结果 |
| 人工复核判断 | 模型能否抓住那些“绝不能漏掉”的案例 |

选择指标，其实也等于在选择：哪一类错误更危险。

| 错误 | 业务影响 |
| --- | --- |
| 把高风险消息自动处理了 | 可能导致客户损害、政策违规或安全风险 |
| 把安全消息都送去人工复核 | 成本增加、响应变慢 |

所以，问题定义不只包括输出本身，还包括“不同错误的代价”。

## 问题定义也会决定需要收集什么数据

问题定义还会直接影响数据收集。数据再多，如果和模型要解决的任务不匹配，也可能并不有用。

把“减少配送问题”这个大目标拆成三种任务试试看。

| 任务 | 需要的输入数据 | 需要的输出数据 |
| --- | --- | --- |
| 配送延迟预测 | 下单时间、发货时间、地区、商品、物流状态 | 是否延迟或预计到达时间 |
| 配送消息分类 | 客户支持消息文本 | 消息类型标签 |
| 配送回复生成 | 消息文本、订单状态、配送政策 | 好回复样例或回复规则 |

同样都是“配送问题”，只要任务不同，数据形状就完全不同。

## 模型选择发生在问题定义之后

这一阶段，人很容易先被模型名字吸引，比如线性模型、树模型、神经网络或 LLM。但如果先有模型名字，人就容易反过来把问题硬塞进模型里。

更安全的顺序是：

1. 先定义现实目标
2. 再定义建模任务
3. 再定义输入和输出
4. 再定义数据和标注标准
5. 再定义评价标准
6. 最后再挑模型候选
7. 再确认输出会怎样被实际使用

例如，客服消息分类并不天然要求用 LLM。如果消息类型很清楚、数据也整理得好，一个更简单的分类器，甚至规则和模型混合的方案，可能就足够。相反，如果任务是生成自然语言回复草稿，那才更可能需要生成式模型或 LLM。

模型选择很重要，但它代替不了问题定义。

## 模型表现和业务表现可能不同

即使模型指标变好了，也不代表现实工作一定变好了。因为模型只是更大系统中的一个部件。

| 模型可能做得不错，但…… | 业务流程里仍可能出问题 |
| --- | --- |
| 它把消息类型分得很准 | 路由规则仍可能把消息送错团队 |
| 它能很好判断是否能自动化处理 | 政策更新没同步，导致错误指导 |
| 它生成的回复草稿很流畅 | 草稿仍可能因缺乏依据而被人工打回 |
| 它能准确预测延迟风险 | 预警发送太晚，客户体验仍未改善 |

所以，必须把模型评价和业务评价分开。

| 区分 | 问题 |
| --- | --- |
| 模型评价 | 模型输出和目标或标准有多接近？ |
| 业务评价 | 把模型接入后，真实工作有没有变好？ |
| 安全评价 | 错误输出会不会给用户或组织带来风险？ |

## 问题定义文档里至少该写什么

即使只是一个很小的建模任务，如果把下面这些项写下来，混乱也会少很多。

| 项目 | 要问的问题 | 客服消息例子 |
| --- | --- | --- |
| 现实目标 | 为什么需要这个模型？ | 缩短消息处理时间 |
| 建模任务 | 模型要解决什么问题？ | 消息类型分类 |
| 输入 | 模型真正看到什么？ | 消息文本 |
| 输出 | 模型必须产出什么？ | `退款`、`配送`、`换货`、`其他` |
| 数据 | 过去案例是什么？ | 消息文本和人工标签 |
| 标注标准 | 不同人能按同样标准标注吗？ | 退款、配送、换货、其他的定义 |
| 评价标准 | 怎样才算做得好？ | 准确率、召回率、人工复核结果 |
| 错误代价 | 哪类错误更危险？ | 把高风险消息自动处理掉 |
| 使用位置 | 输出会被用在什么地方？ | 路由、自动回复支持、人工复核 |
| 排除范围 | 模型不负责什么？ | 最终退款审批和政策责任 |

这并不是什么宏大的规划文档，而是界定模型世界的最小地图。

## 这一节要记住的内容

`problem definition` 不是在模型之前的附属准备工作，而是决定模型看什么、输出什么，以及如何判断它是否成功的核心阶段。

Chapter 4 的脉络可以压成这样：

1. 现实问题为了某个目的被缩减后，才变成 model
2. model 接收 input，产出 output
3. input 会被转成 features 和 representations 来参与计算
4. problem definition 决定这些选择的标准

所以，在选模型之前，最好能先把这句话补完整：

> 我们想用 [什么输入] 产出 [什么输出]，  
> 并且要用 [什么指标和复核标准] 去检查，  
> 这个输出是否真的帮助了 [哪个业务目标]。

如果这句话还补不完整，那问题往往还不是“该选哪个模型”，而是“现实目标还没有被整理清楚”。
